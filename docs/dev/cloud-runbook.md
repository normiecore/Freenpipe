# Cloud runbook: WORKER and MERGER sessions

This file is the operating manual for Claude Code **cloud sessions** that build Freenpipe. It is
self-contained: a session that starts with no other context follows it top to bottom for its role.
The owner's PC is usually off, so nothing here may depend on it.

- **Owner setup** (done once): [cloud-environment.md](cloud-environment.md).
- **Coordinator mode** (one session plays every role with Workflow batches): [cloud-coordinator.md](cloud-coordinator.md).
- **Routine prompts and schedules**: [cloud-routines.md](cloud-routines.md).
- **Reviewer briefs**: [cloud-reviewers.md](cloud-reviewers.md).
- **CI**: [ci.md](ci.md). The "Freenpipe CI" workflow (`.github/workflows/freenpipe-ci.yml`, jobs
  `windows`, `linux`, `gates`) plus Secret Scan and the Windows CLI Integration Test form the **merge
  gate**: every check run on the PR head has completed with success, skipped or neutral, and those five
  checks are among them. "CI green" below always means this gate (`fp.py ci` applies it).

## 0. Orientation

Freenpipe is a fork of screenpipe's last MIT commit (`892199f`), extended clean-room to parity with
screenpipe v2.7.104. The work is cut into **154 work packages (WPs)** in waves 0 to 8:

| File | What it is |
|---|---|
| `docs/clean-room/PLAN.md` | The plan. Each WP has a `#### <WP-ID> <title>` section: items, dependencies, spec references, description, owner paths and acceptance checks. Sections 2 (ground rules), 4 (acceptance harness), 5 (integration seams) and 6 (shared hotspot files) apply to every WP. Generated from `tools/plan/`; never edit it by hand. |
| `docs/clean-room/DECISIONS.md` | Owner decisions. They bind every WP and win over PLAN.md. |
| `docs/clean-room/specs/*.md` | The specifications the WPs implement. The reverse-engineering phase is over; these are the only evidence. |
| `docs/clean-room/STATUS.md` | Progress board, regenerated by the merger. `python3 tools/plan/status.py` shows the live state. |
| `docs/clean-room/OPEN-QUESTIONS.md` | Spec ambiguities that workers decided. Create it with a `# Open questions` heading if it does not exist yet. |
| `docs/dev/windows-smoke-checklist.md` | Runtime and hardware checks the owner runs on Windows. |

**Roles.** Every routine fire starts a fresh VM and a fresh session that knows nothing except this
repository. Only git and GitHub carry state between sessions.

- **WORKER** (`worker-1`, `worker-2`, `worker-3`): takes one unit of work (a WP, an open PR that
  needs attention, or a fix for a red `main`), implements it on its own branch, gets it reviewed and
  green, and marks it approved.
- **MERGER**: merges approved green PRs in plan order, resolves merge conflicts, keeps STATUS.md
  current and runs the wave integration checklist.

**Tools** (all run on the VM with `python3`/`bash`; read their headers for every option):

| Tool | Use |
|---|---|
| `tools/cloud/bootstrap.sh` | Per-session setup: toolchain, sidecars, `bun install`, build env, dev isolation, disk check. Writes `~/.freenpipe-env.sh`. |
| `tools/plan/status.py` | Status of every WP from git and the GitHub REST API. `--next` (worker queue), `--merge-queue` (merger queue), `--json`. |
| `tools/cloud/fp.py` | Workflow commands: `pick`, `claim`, `push`, `template`, `open-pr`, `ci`, `log`, `rerun`, `approve`, `block`, `merge`, `checkout`, `sync-main`, `publish-status`. |
| `tools/clean-room/verbatim_gate.py` | Clean-room n-gram gate (see [tools/clean-room/README.md](../../tools/clean-room/README.md)). |
| `scripts/ci/verbatim-diff.sh` | The same gate over the lines a branch adds (what CI runs). |

## 1. Rules for every session

### 1.1 Git

- **Branches.** A worker writes only to its own `wp/<WP-ID>` branch (or `fix/main-<sha7>` when it fixes
  a red main). Only the merger updates `main`, and only through REST merges of approved PRs and
  `status:` commits made by `fp.py publish-status`. The merger also pushes conflict-resolution merges
  (`fp.py sync-main`) to `wp/*` and `fix/*` branches.
- **Ignore the default `claude/...` branch** the cloud harness suggests. This workflow never uses it.
- **Never force-push, never delete a branch, never push tags.** (The GitHub proxy refuses deletions
  and tags anyway.)
- **Every commit message ends with a blank line and** `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
  Commit with `git commit -F <file>` or a heredoc so the trailer is exact. A `Claude-Session:` trailer
  the harness adds is fine.
- **Push with `python3 tools/cloud/fp.py push`.** It detects when another session has taken over your
  branch (then you stop and pick other work) and absorbs the merger's sync merges.
- **PRs, comments, CI and merges go through the REST API** (`fp.py`, or `gh api repos/normiecore/Freenpipe/...`).
  `gh pr` and `gh issue` use GraphQL, which the proxy blocks.
- In your VM checkout you may switch branches freely; CLAUDE.md's ban on `git reset --hard`,
  `git clean`, `git checkout -- .` and `git stash` still applies to work you did not write.

### 1.2 Clean room (summary; CLAUDE.md and docs/clean-room/README.md are binding)

- Work only from `docs/clean-room/specs/`, PLAN.md, DECISIONS.md and the MIT base code in this
  repository. **Never consult post-relicense upstream material**: no screenpipe source, commits, PRs,
  issues, docs or changelogs dated after 2026-06-10, no `main` branch of screenpipe/screenpipe or
  mediar-ai/screenpipe, nothing from upstream's `ee/`. Do not clone, fetch or web-browse them. The REA
  toolkit is not available in the cloud and is not needed: the evidence already lives in the specs.
- **Write original code and prose.** Never paste decompiled code, extracted frontend JavaScript, UI
  copy or LLM prompts. Built-in pipes, skills and prompts are written fresh.
- **Interop identifiers match exactly**: HTTP routes, JSON fields, SQL names and DDL, CLI flags,
  settings keys, environment variables, event names, file and directory names.
- **No phoning home**: no vendor host, PostHog key, Sentry DSN or vendor OAuth client id in code that
  builds requests. New network features are user-configured (BYO) or third-party and user-initiated.
- **New source files** start with the two-line Freenpipe header from CLAUDE.md (`#` for Python and
  shell). Leave upstream headers on files you edit.
- **Run the verbatim gate** before review. Over everything your branch adds (what CI runs):
  `bash scripts/ci/verbatim-diff.sh origin/main HEAD`. Over whole files:
  `python3 -I tools/clean-room/verbatim_gate.py <file or dir> ...` (exit 1 on hits). Each hit is an
  8-word prose run shared with the shipped binary. Rewrite it unless it is an interop identifier or
  moved MIT base code, and justify every remaining hit in the PR description.

### 1.3 Platform

- Windows (`x86_64-pc-windows-msvc`) is the primary target, and the VM cannot build it. Write
  `cfg(windows)` code (WASAPI, UIA, WGC, DirectML, Windows OCR, Win32 overlay, WER and so on) in the VM
  anyway. The CI `windows` job compile-checks and tests it. Keep pure logic (parsing, state machines,
  mapping tables) outside the `cfg(windows)` modules so Linux unit tests cover it.
- Keep the macOS and Linux `cfg` paths compiling.
- Anything that needs real Windows hardware or a desktop (screen capture, audio devices, UIA trees,
  DirectML, tray, installer, deep links, UI smoke) goes into `docs/dev/windows-smoke-checklist.md` as an
  entry with the WP id, steps and expected result (format in that file). Never tick those boxes
  yourself; the owner does.

### 1.4 Dev isolation (still applies in the VM)

- Never use `~/.screenpipe` or ports 3030/11435 in code you run or in tests. Use a temporary data dir
  and port 3035. `bootstrap.sh` exports `FP_DD`/`SCREENPIPE_DATA_DIR` (a temp dir), `FP_PORT`/
  `SCREENPIPE_PORT=3035`, `SCREENPIPE_FOCUS_PORT=11436` and `SCREENPIPE_API_KEY=fp-dev-key`.
- Tests create their own temp dirs and synthetic fixtures; never real recordings or databases.

### 1.5 Shell habits in the VM

- Each Bash tool call is a fresh shell. Start build and test commands with `. ~/.freenpipe-env.sh &&`.
- A foreground command waits 2 minutes by default and up to 10 with a `timeout` (more if the owner
  raised `BASH_MAX_TIMEOUT_MS`). Run long builds with `run_in_background` and poll their output file.
  A background command is stopped after about 30 more minutes, so split very long work into steps.
- The VM can be reclaimed when idle. Push before anything long, and push at least every 30 to 45
  minutes (section 3.3).

## 2. Session start (both roles)

```bash
bash tools/cloud/bootstrap.sh            # worker: full setup; give the Bash call a 600000 ms timeout
bash tools/cloud/bootstrap.sh --light    # merger: env, git settings and disk check only
. ~/.freenpipe-env.sh && python3 tools/plan/status.py
```

`bootstrap.sh` is idempotent: if it timed out, run it again and it continues where it stopped. Read
its warnings. Typical ones and what they mean:

- *bun install failed*: Bun has known problems with the cloud proxy. Frontend build and tests then run
  only in CI. Rust work is unaffected.
- *cdn.pyke.io unreachable*: bootstrap fell back to the ONNX Runtime GitHub release (dynamic link;
  `LD_LIBRARY_PATH` is in the env file). Builds still work.
- *apt packages missing*: the environment setup script did not complete. Bootstrap installs them,
  which takes a few minutes.

Your worker id comes from the routine prompt (for example `worker-2`). Pass it as `--worker`.

## 3. WORKER

### 3.1 Pick work

```bash
. ~/.freenpipe-env.sh && python3 tools/plan/status.py --next --worker worker-N   # optional preview
. ~/.freenpipe-env.sh && python3 tools/cloud/fp.py pick --worker worker-N
```

`pick` walks the `--next` list in order and claims the first item it can get. Lost races are normal:
when someone else pushed the branch first, the push is rejected and `pick` moves to the next item. It
prints one line, `picked <kind> <id> <branch> <title>`, and leaves you on that branch. Exit code 2
means there is nothing to do: report that and end the session.

| Kind | Meaning | Go to |
|---|---|---|
| `fix-main` | CI on `main` is red after one re-run and nobody is fixing it | 3.10 |
| `resume` | your own claim from an earlier session that died (no commit for 90 minutes) | 3.2 (read your branch's commits first) |
| `continue-pr` | an open PR that needs work: red CI, or green CI waiting for reviews and approval | 3.9 |
| `takeover` | another worker's claim with no commit for 6 hours | 3.2 (build on what is there) |
| `ready` | an unclaimed WP whose dependencies are all merged, in plan order (wave, then id) | 3.2 |

To claim a specific item instead: `fp.py claim <WP-ID> --worker worker-N` (exit 2 means it is not
available to you; pick another). A claim is an empty commit `claim: <WP-ID> by worker-N` pushed as
`wp/<WP-ID>` from `origin/main`.

### 3.2 Understand the WP

1. Read the WP section: `grep -n "^#### <WP-ID> " docs/clean-room/PLAN.md`, then read from that line to
   the next `#### `. Note the items, depends_on, specs, owner paths and acceptance checks.
2. Read `docs/clean-room/DECISIONS.md` (short, binding) and PLAN.md sections 2, 5 and 6.
3. Read every spec section the WP references and every delta item it lists
   (`grep -n "<item-id>" docs/clean-room/specs/*.md`).
4. Read the code at the owner paths. For a `resume` or `takeover`, read
   `git log --stat origin/main..HEAD` first and continue from there.
5. If the WP's PR already exists (it can, after a takeover), read its description:
   `gh api repos/normiecore/Freenpipe/pulls?head=normiecore:wp/<WP-ID>`.

### 3.3 Implement and checkpoint

- Edit only the WP's owner paths and regions (PLAN.md section 6 lists shared hotspot files). Settings
  keys come from W1-02; later WPs do not add migrations (PLAN.md section 5).
- Regenerate generated files instead of hand-merging them: `bun run bindings:generate` for
  `apps/screenpipe-app-tauri/lib/utils/tauri.ts` (Tauri commands need both `#[tauri::command]` and
  `#[specta::specta]`), `cargo update -w` for `Cargo.lock`, `bun install` for `bun.lock`.
- **Checkpoint at least every 30 to 45 minutes**, and before any long build:

  ```bash
  git add <your files> && git commit -F - <<'EOF'
  wip(<WP-ID>): <what this step did>

  Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
  EOF
  . ~/.freenpipe-env.sh && python3 tools/cloud/fp.py push
  ```

  The push is also your heartbeat. Without a push for 90 minutes, a later session of your worker id
  treats the claim as abandoned and resumes it; after 6 hours any worker may take it over. If
  `fp.py push` says STOP, another session owns the branch now: leave it and pick other work.
- Record every spec ambiguity you resolve: decide, note it for the PR description, and append it to
  `docs/clean-room/OPEN-QUESTIONS.md` under a `## <WP-ID>` heading (question, decision, reason).

### 3.4 Check in the VM

The full Windows and Linux builds run in CI. In the VM, run what is fast and targeted:

```bash
. ~/.freenpipe-env.sh && cargo check -p <crate> --tests                 # each crate you touched
. ~/.freenpipe-env.sh && cargo test -p <crate> [--test <name>] [<filter>]
. ~/.freenpipe-env.sh && cargo check --manifest-path apps/screenpipe-app-tauri/src-tauri/Cargo.toml   # app crate, if touched
. ~/.freenpipe-env.sh && cd apps/screenpipe-app-tauri && bun test <path>   # frontend, if bun install worked
. ~/.freenpipe-env.sh && bun test scripts/ci/vendor-guard.test.ts
. ~/.freenpipe-env.sh && bash scripts/ci/verbatim-diff.sh origin/main HEAD
```

- The first build in a fresh VM compiles the whole dependency tree (whisper.cpp, ONNX Runtime and
  more) and can take 20 minutes or longer. Start it in the background early, for example
  `cargo check -p screenpipe-engine --tests > "$FP_STATE/check.log" 2>&1` with `run_in_background`,
  while you read specs.
- Use the dev profile (bootstrap disables debug info). The `release-dev` profile and the MSVC CRT
  notes in PLAN.md section 3 are for Windows.
- Run every acceptance check that can run on Linux. For the rest, record where it runs instead:
  the CI `windows`/`linux` job, or a Windows smoke checklist entry you add (section 1.3).
- Free disk under 8 GB: run `fp_disk_check` (defined in the env file); it clears old build output.

### 3.5 Review: two independent subagents, up to two fix rounds

When the implementation is complete and pushed, start **two reviewer subagents in parallel** with the
Agent tool, using the briefs in [cloud-reviewers.md](cloud-reviewers.md):

- **Verification reviewer**: re-runs the checks, probes edge cases, checks every acceptance item.
- **Compliance reviewer**: clean room, de-cloud, scope, security, headers, licences.

Give each one the WP id, the branch head sha (`git rev-parse HEAD`) and the brief. Neither sees the
other's report. Each answers `VERDICT: APPROVE` or `VERDICT: CHANGES` with findings.

- On `CHANGES`: fix the findings (or rebut a wrong one with evidence), commit, push, and run that
  reviewer again on the new head. If the fix was large, run both again. At most **two fix rounds**.
- Still `CHANGES` after round two: open the PR anyway (3.6) with the open findings in the description,
  then `fp.py block <PR> --reason "<one line>"`, so the merger skips it and the owner sees it. Move on.
- Save the final reports as `$FP_STATE/review-verification.md` and `$FP_STATE/review-compliance.md`.

### 3.6 Open the PR

```bash
. ~/.freenpipe-env.sh && python3 tools/cloud/fp.py template <WP-ID> --worker worker-N > "$FP_STATE/pr-<WP-ID>.md"
# fill in every section of the file, then:
. ~/.freenpipe-env.sh && python3 tools/cloud/fp.py push
. ~/.freenpipe-env.sh && python3 tools/cloud/fp.py open-pr <WP-ID> --body-file "$FP_STATE/pr-<WP-ID>.md"
```

The template has these sections. Fill all of them; write "none" where nothing applies:

1. WP id and title, plan reference, worker id, items.
2. What changed (3 to 8 bullets).
3. Acceptance checks: one line per plan check, `[x]` only when it passed, and where it ran (VM,
   CI windows job, CI linux job, smoke checklist entry id) or why it cannot run yet.
4. Tests run (commands).
5. Verbatim gate: hit count, and a justification per remaining hit.
6. Windows hardware smoke items you added to `docs/dev/windows-smoke-checklist.md` (ids).
7. Review: each reviewer's verdict and summary, with the head sha it reviewed, written as
   ``(head `<sha>`)``.
8. Spec decisions and open questions.
9. Follow-ups for later WPs.

Opening the PR starts CI (`pull_request` event). Pushing a `wp/*` branch alone does not.

### 3.7 Wait for CI and fix red CI

```bash
. ~/.freenpipe-env.sh && python3 tools/cloud/fp.py ci <PR> --wait 9        # Bash timeout 600000; repeat
. ~/.freenpipe-env.sh && python3 tools/cloud/fp.py ci <PR> --why           # failed jobs, steps, annotations
. ~/.freenpipe-env.sh && python3 tools/cloud/fp.py log <job-id> --tail 300 --grep 'error|panicked|FAILED'
```

- A cold Windows build can take well over an hour. Poll for up to about an hour. If CI is still
  running, end the session cleanly (3.11): a later session continues the PR (`continue-pr`).
- **Flake** (network timeout, runner crash, a test that passes locally and fails once): re-run once
  with `fp.py rerun <PR>`. A second failure is real.
- **Real failure**: fix it on the same branch, commit, `fp.py push`. CI restarts by itself. Windows-only
  compile errors cannot be reproduced in the VM: read the log, fix by reasoning, keep the change
  minimal, and push.
- Every push after the review creates a new head that the reviewers have not seen. Before approving,
  run both reviewers again on the new commits only (`git diff <reviewed-sha>..HEAD`), and save the
  new reports.

### 3.8 Mark the PR ready (approval)

Approve only when **CI is green on the PR head (the merge gate) and both reviewers approved that same head**:

```bash
# reviews in the PR description still match the head:
. ~/.freenpipe-env.sh && python3 tools/cloud/fp.py approve <PR>
# reviews were re-run after later commits:
. ~/.freenpipe-env.sh && python3 tools/cloud/fp.py approve <PR> \
    --verification-file "$FP_STATE/review-verification.md" --compliance-file "$FP_STATE/review-compliance.md"
```

This posts a PR comment that starts with `fp-review: approved verification+compliance`, names the head
sha and carries both summaries. It counts only for that head; any later push makes it stale. The
merger merges from there. If the session still has plenty of context left (less than about half
used), go back to 3.1. Otherwise end the session (3.11).

### 3.9 Continue an open PR (`continue-pr`)

`pick` has put you on the PR branch at its remote head. Find the PR and its state:

```bash
. ~/.freenpipe-env.sh && python3 tools/plan/status.py --json | python3 -c "import json,sys; d=json.load(sys.stdin); print(json.dumps([r for r in d['wps'] if r['id']=='<WP-ID>'][0], indent=1))"
```

- CI red: 3.7. CI green but review pending or stale: run both reviewers on the PR head (on the
  commits since the last approved or reviewed head if the PR description names one), then 3.8.
- No claim commit is made for an open PR, because it would restart CI and void approvals.

### 3.10 Fix a red main (`fix-main`)

`pick` created `fix/main-<sha7>` from `origin/main`. CI on main failed twice for that commit.

1. `fp.py ci --main --why` and `fp.py log <job-id>` to find the failing step and the cause.
2. Usually two WPs merged cleanly but do not fit together. Find the culprit with
   `git log --first-parent --oneline -10 origin/main`.
3. Fix it with the smallest correct change, check in the VM, run both reviewers, then:
   `fp.py template fix/main-<sha7> > "$FP_STATE/pr-fix.md"`, fill it in,
   `fp.py open-pr fix/main-<sha7> --title "<what broke and the fix>" --body-file "$FP_STATE/pr-fix.md"`.
4. CI green and both reviewers approved: `fp.py approve <PR>` (3.8). The merger merges fix PRs first.

### 3.11 End of session

- Never leave uncommitted work. Commit what you have as `wip(<WP-ID>): ...` and `fp.py push`, even if
  it does not build. Say so in the commit body.
- End with a short report: what you picked, what you did, the PR number and state, and anything
  the owner must know (blocked PRs, new smoke checklist entries, open questions).

## 4. MERGER

### 4.1 The queue

```bash
bash tools/cloud/bootstrap.sh --light
. ~/.freenpipe-env.sh && python3 tools/plan/status.py --merge-queue
```

Each line is `<action> <id> <#PR> <head-sha> <title>` (for `integrate`, the wave). Fix PRs come first,
then WPs in plan order. Work through every line, then publish the status (4.6).

### 4.2 `merge`

```bash
. ~/.freenpipe-env.sh && python3 tools/cloud/fp.py merge <PR>
```

`fp.py merge` re-checks every gate before merging: the PR targets `main` from a branch of this
repository, the merge gate is green on the head, a trusted `fp-review: approved` comment names that
head, every dependency is merged and GitHub reports no conflict. It merges with merge method `merge`
and the commit title `Merge <WP-ID>: <title>` (`Merge fix/main-<sha7>: <PR title>` for fixes), which is
how `status.py` recognises merged WPs. Exit 2: a gate is not met, so leave the PR for now. Exit 4:
conflict, so continue with 4.3.

### 4.3 `conflict`

```bash
. ~/.freenpipe-env.sh && python3 tools/cloud/fp.py sync-main <WP-ID>      # merges origin/main into the branch
```

On exit 4, resolve every conflicted file **keeping both sides' intent**. Read the WP's PLAN.md section
and the commits on each side. If the resolution needs `cargo` or `bun`, run the full
`bash tools/cloud/bootstrap.sh` first (the merger normally runs `--light`). Generated files are never
hand-merged:

- `Cargo.lock`: `git checkout --theirs Cargo.lock` (main's), then
  `cargo metadata --format-version 1 > /dev/null` to add back what the branch needs. Do the same for
  `apps/screenpipe-app-tauri/src-tauri/Cargo.lock`, using `--manifest-path`.
- `bun.lock`: main's version, then `bun install` in `apps/screenpipe-app-tauri`. If bun cannot install
  in the VM, keep main's version and say so in a PR comment. CI's frozen install then tells the worker.
- `apps/screenpipe-app-tauri/lib/utils/tauri.ts`: main's version, then `bun run bindings:generate` if the
  session has time for an app-crate build. Otherwise keep main's version and comment on the PR. CI's
  bindings check then sends it back to the worker.
- Append-only docs (`OPEN-QUESTIONS.md`, `windows-smoke-checklist.md`): keep both sides' entries.

Then `git add` the files, `git commit --no-edit` (the message already has the trailer), and
`fp.py push`. CI re-runs. The approval was for the old head, so the PR shows up as `reapprove` once CI
is green.

### 4.4 `reapprove`

The PR head is your own sync merge, CI is green, and the old approval is stale. Review the
resolution only:

```bash
. ~/.freenpipe-env.sh && python3 tools/cloud/fp.py checkout <WP-ID>
git show --remerge-diff HEAD > "$FP_STATE/resolution.diff"    # what the resolution changed vs a plain merge
```

Run both reviewer subagents (cloud-reviewers.md, "Merge resolution" variant) on that diff. If both
approve:

```bash
. ~/.freenpipe-env.sh && python3 tools/cloud/fp.py approve <PR> --note "Re-approval after sync-main; only the conflict resolution was reviewed." \
    --verification-file "$FP_STATE/review-verification.md" --compliance-file "$FP_STATE/review-compliance.md"
```

If a reviewer finds a real problem in the resolution, fix it on the branch and push (CI re-runs).
If it is beyond a resolution fix, `fp.py block <PR> --reason "..."` and report it.

### 4.5 CI on main

```bash
. ~/.freenpipe-env.sh && python3 tools/cloud/fp.py ci --main
```

On `failure` at attempt 1: `fp.py rerun --main` (once). A second failure makes `status.py --next` offer
`fix-main` to the workers. Do not fix main yourself.

### 4.6 Publish the status

After the queue (even when nothing merged):

```bash
. ~/.freenpipe-env.sh && python3 tools/cloud/fp.py publish-status
```

It regenerates `docs/clean-room/STATUS.md` and `status.json` on top of `origin/main` in a throwaway
worktree and pushes one commit `status: <counts> [skip ci]` to `main`, or nothing when nothing
changed. Stale claims (no commit for 6 hours, no PR) show there as released, and workers take them
over.

### 4.7 Wave integration (`integrate wave-N`)

When every WP of a wave is merged:

1. `fp.py ci --main` must be `success` on the latest code commit. If it is pending, leave the item for
   the next run. If it failed, follow 4.5 and stop here.
2. On an up-to-date `main` (`git switch --detach origin/main`), run every acceptance check of the
   wave's WPs that can run on Linux (greps, `cargo test -p ...`, `bun test ...`, Linux harness checks
   on port 3035 with `$FP_DD`). Use background runs for long builds. Note each check as pass, fail,
   or not run with the reason (Windows-only, smoke checklist, too long).
3. Summarise the wave's entries in `docs/dev/windows-smoke-checklist.md` (wave 0) and `docs/dev/smoke/<WP>.md` (wave 1 on): count them, and count those
   the owner has already ticked.
4. Write the notes to `$FP_STATE/wave-N.md` (Markdown: CI result with run links, the checks table,
   the smoke summary, any follow-ups) and record it:

   ```bash
   . ~/.freenpipe-env.sh && python3 tools/cloud/fp.py publish-status --record-wave N --result pass|partial|fail --notes-file "$FP_STATE/wave-N.md"
   ```

   `partial` means everything that ran passed but some Linux checks could not run. `fail` means a
   check failed: name it in the notes so the owner sees it in STATUS.md.

A wave integration can be long. If the session must stop first, record nothing. The next merger run
starts it again.

### 4.8 End of session

Report what you merged, which PRs you synced, re-approved or skipped (and why), blocked PRs (with
reasons), main CI state, and any wave integration recorded.

## 5. Failure modes

| Situation | What happens | What to do |
|---|---|---|
| Plan usage limit reached | Routine runs are rejected until the window resets | Nothing. The next fire resumes from git; pushed claims and PRs carry the state. |
| VM reclaimed mid-work | Unpushed work and background jobs are lost | The next session of the same worker resumes the pushed branch after 90 minutes (`resume`). Push often. |
| Lost claim race | `fp.py claim` exits 2, `pick` moves on | Nothing; normal. |
| `fp.py push` says STOP | Someone took the branch over | Leave it. Pick other work. Never force-push. |
| CI flake | One failed job | `fp.py rerun <PR>` once. A second failure is real. |
| CI cancelled by a newer push | The newer run is the one that counts | Wait for the newer run. |
| Windows-only build error | Cannot reproduce in the VM | Fix from the log and annotations, push, let CI judge. |
| Spec ambiguity | The spec does not settle a detail | Decide, document it in the PR, append it to `docs/clean-room/OPEN-QUESTIONS.md`. |
| Spec gap or schema gap | The WP cannot be done as specified (for example a needed migration, which later WPs must not add) | Open the PR with what is done, `fp.py block <PR> --reason "..."`, report it, and move on. |
| WP blocked by another WP | A dependency is merged but incomplete | Comment on the PR (`gh api repos/normiecore/Freenpipe/issues/<PR>/comments -f body=...`), block it, move on. |
| Merge conflict | GitHub reports `mergeable: false` | The merger runs `fp.py sync-main` (4.3). |
| Main red after merges | Two PRs passed alone but not together | Merger re-runs once (4.5), then a worker takes `fix-main` (3.10). |
| `bun install` fails in the VM | Bun and the cloud proxy disagree | Frontend build and tests run only in CI. |
| Network host blocked (403 `host_not_allowed`) | The environment allowlist lacks a host | Note the host in your report. The owner adds it (cloud-environment.md). |
| Disk full | Build fails with ENOSPC | `fp_disk_check`; as a last resort `rm -rf "$CARGO_TARGET_DIR"`. |
| GitHub API error | `fp.py` prints `GitHub API error` | Retry once. If it persists, report it and end the session. |

## 6. Reference

### `fp.py` exit codes

`0` done, `1` error, `2` not available, lost race or still pending, `3` already merged, `4` merge conflict.

### Markers (PR comments, trusted authors only)

| Comment starts with | Meaning |
|---|---|
| `fp-review: approved verification+compliance` + line `head: <sha>` | Both reviewers approved this head, and CI was green on it |
| `fp-blocked: <reason>` | The merger skips this PR until a later `fp-unblocked` comment |
| `fp-unblocked` | Clears a block |

Only comments by the repository owner, members and collaborators count. Routines act as the owner's
GitHub account.

### Commit subjects the tools read

| Subject | Written by | Read as |
|---|---|---|
| `claim: <WP-ID> by <worker>[ (resume)| (takeover from <worker>)]` | `fp.py claim` | claim owner |
| `merge: origin/main into <branch>` | `fp.py sync-main` | merger sync (triggers `reapprove`) |
| `Merge <WP-ID>: <title>` | `fp.py merge` (REST) | WP merged |
| `status: ... [skip ci]` | `fp.py publish-status` | status only, ignored for CI and merge detection |

### Self-test of the tools

`python3 tools/cloud/test_cloud_tools.py` runs claims, races, takeovers and status publishing
against a throwaway local repository, without network access.
