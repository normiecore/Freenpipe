# W3-06 Windows smoke checks

Entries follow the format in [../windows-smoke-checklist.md](../windows-smoke-checklist.md). Run
them on a W3-06 (or later) build in the isolated dev setup: `FP_DD`, port 3035,
`SCREENPIPE_API_KEY`. `api` and `sqlq` are the helpers from PLAN.md section 4. The unit and
in-process tests (`cargo test -p screenpipe-core --lib pipes::`, `cargo test -p screenpipe-engine
--lib pipe_store`, `cargo test -p screenpipe-engine --lib retranscribe`) already cover the claim,
outcome and finalizer logic with fakes; these entries check it with a real Pi agent, real audio and
a real restart. Every summary uses your own default AI preset (a local Ollama model or your own API
key) and must send nothing to any screenpipe or Freenpipe host.

### W3-06 Event-trigger idempotency, run outcome verification, meeting-summary finalizer

- [ ] **SMK-W3-06-1** (Runtime) Harness: meeting retranscribe reports the transcript update and asks for a summary refresh
  - Setup: release-dev engine on `$FP_PORT` with a fresh `FP_DD`, audio capture on and a local transcription engine selected; the Meeting Summary pipe enabled with your own preset.
  - Steps: 1. `api /meetings/start -X POST -H 'Content-Type: application/json' -d '{"app":"smoke"}'`, note the `id`, and play speech for two minutes. 2. `api /meetings/stop -X POST -H 'Content-Type: application/json' -d '{"id":<id>}'` and wait for the first summary run to finish (`api /meetings/<id>/summary-status`). 3. `api /meetings/<id>/retranscribe -X POST -H 'Content-Type: application/json' -d '{}'`. 4. Wait for the summary status to read `ready` again. 5. `sqlq "select id, status, trigger_type, trigger_event, trigger_key, error_type from pipe_executions where pipe_name='meeting-summary' order by id"`. 6. Start and stop a second meeting with no audio playing, then `api /meetings/<second id>/retranscribe -X POST -H 'Content-Type: application/json' -d '{}'`.
  - Expected: step 3's response has `transcript_updated_at` (an RFC 3339 time) and `"summary_refresh_event_emitted": true`; step 5 shows the first run with `trigger_event` `meeting_ended` and `trigger_key` equal to the meeting id, and a second run keyed `<id>:summary-refresh-<ms>`, both `completed`; step 6's response has `"transcript_updated_at": null` and `"summary_refresh_event_emitted": false`.
  - Result:
- [ ] **SMK-W3-06-2** (Runtime) A rejoined meeting is summarised once
  - Setup: release-dev engine with audio capture and UI-scan meeting detection on; the Meeting Summary pipe enabled; a real call in Teams, Zoom or Meet you can leave and rejoin.
  - Steps: 1. Join the call, talk for three minutes and leave. 2. Within 60 seconds of leaving, rejoin the same call, talk for another minute and leave again. 3. Wait for the summary run to finish. 4. `sqlq "select id, meeting_end from meetings order by id desc limit 2"`. 5. `sqlq "select id, status, trigger_key from pipe_executions where pipe_name='meeting-summary' order by id desc limit 3"` and `sqlq "select * from pipe_event_runs where pipe_name='meeting-summary'"`. 6. `grep -E "already handled|duplicate skipped" "$FP_DD/engine.log"`.
  - Expected: step 4 shows one meeting row for the call (the rejoin reopened it); step 5 shows one execution and one claim with that meeting id as the key; step 6 shows the second `meeting_ended` was skipped as a duplicate (or, if the first run was still running when the meeting ended again, a debug "already running" line instead and still one execution).
  - Result:
- [ ] **SMK-W3-06-3** (Runtime) A summary run cut off by a restart is asked for again once
  - Setup: release-dev engine with the Meeting Summary pipe enabled and a slow-ish preset (a local model) so a run lasts long enough to interrupt.
  - Steps: 1. Start a meeting with `api /meetings/start`, play speech for two minutes, stop it. 2. As soon as `api /meetings/<id>/summary-status` reads `running`, kill the engine process (Task Manager or `taskkill /F /PID <pid>`). 3. Start the engine again on the same `FP_DD`. 4. Wait for the summary status to read `ready`. 5. `sqlq "select id, status, error_type, trigger_key from pipe_executions where pipe_name='meeting-summary' order by id"`. 6. `grep -E "asking again|interrupted by a restart" "$FP_DD/engine.log"`.
  - Expected: the first run is `failed` with `error_type` `interrupted`; a second run keyed `<id>:summary-recovery-1` started after the restart (once the Pi agent was ready) and `completed`; the meeting note has one `## Summary` section; restarting the engine a third time does not start another run for this meeting.
  - Result:
- [ ] **SMK-W3-06-4** (Runtime) Trivial meetings start no pipes; silent meetings are reported as nothing to summarize
  - Setup: release-dev engine with the Meeting Summary pipe enabled; nothing playing.
  - Steps: 1. `api /meetings/start -X POST -H 'Content-Type: application/json' -d '{"app":"smoke"}'` and stop it 20 seconds later. 2. `grep "starts no pipes" "$FP_DD/engine.log"` and `api /meetings/<id>/summary-status`. 3. Start another meeting, stay silent for three minutes, stop it, and wait for its summary run to end. 4. `api /meetings/<second id>/summary-status`.
  - Expected: step 2 shows a log line naming the first meeting as trivial (0 transcript segments in about 20s) and the status reads `idle` with no execution; step 4 reads `failed` with `error_type` `nothing_to_summarize`, and the meeting note gains no `## Summary` placeholder.
  - Result:
- [ ] **SMK-W3-06-5** (Runtime) Stopping a summary run gives its meeting back
  - Setup: release-dev engine with the Meeting Summary pipe enabled and a slow-ish preset.
  - Steps: 1. Start a meeting, play speech for two minutes and stop it. 2. While the summary status reads `pending` or `running`, `api /pipes/meeting-summary/stop -X POST`. 3. `sqlq "select status, error_type from pipe_executions where pipe_name='meeting-summary' order by id desc limit 1"` and `sqlq "select count(*) from pipe_event_runs where pipe_name='meeting-summary' and event_key='<id>'"`. 4. Wait 30 seconds and run step 3 again.
  - Expected: the run is `cancelled` and stays `cancelled` (it does not turn into `completed` or `failed` when the agent exits); the claim count is 0, so a later `meeting_ended` or refresh for this meeting can run the pipe again.
  - Result:
- [ ] **SMK-W3-06-6** (Runtime) Ordinary pipe runs still read as completed with the real Pi agent
  - Setup: release-dev engine with the Pi agent installed and your own default preset; two pipes you normally use (for example a digest pipe and a manual test pipe that writes one file).
  - Steps: 1. Run each pipe from the Pipes page or `api /pipes/<name>/run -X POST`. 2. When they finish, `sqlq "select pipe_name, status, error_type, error_message from pipe_executions order by id desc limit 2"`. 3. Edit the test pipe's prompt to "Call the bash tool to run `exit 0` and then stop without writing any reply." and run it again.
  - Expected: step 2 shows both runs `completed` with no `error_type`; step 3 either completes (if the model still wrote a closing reply) or is `failed` with `error_type` `no_final_result` and a message saying no answer followed. No run that wrote a normal final answer is marked failed.
