# W2-10 Windows smoke checks

Entries follow the format in [../windows-smoke-checklist.md](../windows-smoke-checklist.md). Run
them on a W2-10 (or later) build in the isolated dev setup: `FP_DD`, port 3035,
`SCREENPIPE_API_KEY`. `api` and `sqlq` are the helpers from PLAN.md section 4.

### W2-10 Frame media routes: thumbnail, preview samples, preview media, typed errors, auth

- [ ] **SMK-W2-10-1** (Runtime) Thumbnails of a fresh snapshot frame carry size headers, an ETag and revalidate with 304
  - Setup: release-dev engine build; `source scripts/dev/dev-env.sh smoke` with a new `FP_DD`; engine recording on `$FP_PORT` for two minutes with any app in front.
  - Steps: 1. `ID=$(sqlq "select id from frames where snapshot_path is not null order by id desc limit 1" | tr -dc 0-9)`. 2. `api "/frames/$ID/thumbnail?width=320" -i -o /dev/null`. 3. Repeat step 2. 4. `api "/frames/$ID/thumbnail?width=320" -i -o /dev/null -H "If-None-Match: <etag from step 2>"`.
  - Expected: step 2 is `200` with `content-type: image/jpeg`, `cache-control: private, no-cache`, `x-screenpipe-thumbnail-width: 320`, a matching `x-screenpipe-thumbnail-height`, `x-screenpipe-thumbnail-cache: miss` and `etag: "frame-thumbnail-<ID>-320-75-…"`; step 3 says `hit` with the same ETag; step 4 is `304`.
  - Result:
- [ ] **SMK-W2-10-2** (Runtime) A compacted frame's thumbnail and preview media come from its MP4
  - Setup: as SMK-W2-10-1, but a data dir whose snapshot compaction has run (leave the engine recording for an hour, or reuse an older isolated `FP_DD`); bundled ffmpeg and ffprobe present.
  - Steps: 1. `sqlq "select f.id, f.video_chunk_id, f.app_name, f.timestamp from frames f join video_chunks v on v.id = f.video_chunk_id where f.snapshot_path is null and v.file_path like '%.mp4' order by f.id desc limit 1"`. 2. `api "/frames/<id>/thumbnail?width=320&fallback=false" -i -o thumb.jpg` and open `thumb.jpg`. 3. `api "/frames/preview-media/<video_chunk_id>" -H "Range: bytes=0-99" -i -o /dev/null`. 4. `api "/frames/preview-media/<video_chunk_id>" -H "Range: bytes=999999999999-" -i -o /dev/null`. 5. `api "/frames/preview-samples?app_name=<app>&start_time=<timestamp minus 1 h>&end_time=<timestamp plus 1 h>&limit=6"`. 6. The same with `end_time` 25 h after `start_time`.
  - Expected: step 2 is `200` and the picture shows that moment of the screen, 320 px wide; no console window flashes and no file appears in `%TEMP%` or `C:\tmp`; step 3 is `206` with `content-range: bytes 0-99/<size>`; step 4 is `416` with `content-range: bytes */<size>`; step 5 lists up to 6 frames, compacted ones with `"source":"video"`, a `video_chunk_id` and a `video_offset_seconds`; step 6 is `400`.
  - Result:
- [ ] **SMK-W2-10-3** (Runtime) Frame routes need the API key; /health does not
  - Setup: as SMK-W2-10-1 (API auth is on in the isolated setup).
  - Steps: 1. `curl -s -o /dev/null -w "%{http_code}\n" "http://127.0.0.1:$FP_PORT/frames/$ID"`. 2. Same for `/frames/$ID/thumbnail` and `/frames/preview-media/1`. 3. `curl -s -o /dev/null -w "%{http_code}\n" "http://127.0.0.1:$FP_PORT/health"`. 4. `api "/frames/$ID" -o /dev/null -w "%{http_code}\n"`.
  - Expected: steps 1 and 2 print `403`; step 3 prints `200`; step 4 prints `200`.
  - Result:
