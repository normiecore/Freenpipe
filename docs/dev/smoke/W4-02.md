# W4-02 Windows smoke checks

Entries follow the format in [../windows-smoke-checklist.md](../windows-smoke-checklist.md). Run
them on a W4-02 (or later) build in the isolated dev setup: `FP_DD`, port 3035,
`SCREENPIPE_API_KEY`. `api` and `sqlq` are the helpers from PLAN.md section 4. The in-process
tests (`cargo test -p screenpipe-core --lib pipes::`) already cover the backlog, coalescing, preset
chains, trigger context files, trajectories and the archive sweep with a scripted agent on Linux;
these entries check them with a real Pi agent, real Windows file handling and a real engine. Every
run uses your own AI presets (a local Ollama model or your own API key) and must send nothing to
any screenpipe or Freenpipe host.

### W4-02 Pipe scheduler v2: defer/coalesce, topics, preset '*', trajectories, log archive

- [ ] **SMK-W4-02-1** (Runtime) Two meetings that end while the summary runs are each summarised once
  - Setup: release-dev engine on `$FP_PORT` with a fresh `FP_DD`, audio capture on, a local transcription engine; the Meeting Summary pipe enabled with a slow-ish local preset (so one run lasts a minute or more).
  - Steps: 1. `api /meetings/start -X POST -H 'Content-Type: application/json' -d '{"app":"smoke-a"}'`, play speech for two minutes, then stop it with `api /meetings/stop -X POST -H 'Content-Type: application/json' -d '{"id":<a>}'`. 2. While `api /meetings/<a>/summary-status` reads `running`, start and stop two more meetings (`smoke-b`, `smoke-c`) with a minute of speech each, and stop meeting b a second time (`api /meetings/stop ... {"id":<b>}`). 3. Wait until all three summary statuses read `ready` or `failed`. 4. `sqlq "select id, status, trigger_key, error_type from pipe_executions where pipe_name='meeting-summary' order by id"`. 5. `grep -E "deferred|folded|scheduler backlog" "$FP_DD/engine.log"`.
  - Expected: step 4 shows exactly one run per meeting id, in the order the meetings ended, all `completed`; no row has `error_type` `deferred_backlog_full` or `deferred_expired`; step 5 shows the later meetings were deferred while the first ran (debug level may need `RUST_LOG=screenpipe_core=debug`).
  - Result:
- [ ] **SMK-W4-02-2** (Runtime) A pipe whose named preset is missing fails with `ai_preset_unavailable` and calls no provider
  - Setup: release-dev engine with your normal presets in the scratch `store.bin` (copy your AI settings or create one preset in the dev app); a pipe folder `$FP_DD/pipes/preset-smoke/pipe.md` with `schedule: manual`, `enabled: true`, `preset: deleted-preset` and a one-line prompt.
  - Steps: 1. Start the engine. 2. `api /pipes/preset-smoke/run -X POST`. 3. `api /pipes/preset-smoke/executions`. 4. Change the pipe to `preset: [deleted-preset, "*"]`, run it again and repeat step 3. 5. Watch Resource Monitor's network tab (or `netstat -b`) during step 2.
  - Expected: step 2 returns an error naming `deleted-preset` and listing your available presets; step 3 shows a `failed` row with `error_type` `ai_preset_unavailable` and the same message; no connection is opened during step 2; after step 4 the run uses your default preset and completes.
  - Result:
- [ ] **SMK-W4-02-3** (Runtime) With `SCREENPIPE_TRAJECTORIES_DIR` set, each pipe run writes one JSONL trajectory
  - Setup: `set SCREENPIPE_TRAJECTORIES_DIR=%FP_DD%\traj` and `set SCREENPIPE_TRAJECTORIES_MAX_RUNS=3` (Git Bash: `export ...`) before starting the release-dev engine; any manual pipe that makes a tool call (for example the Day Recap template).
  - Steps: 1. Run the pipe four times with `api /pipes/<name>/run -X POST`, waiting for each to finish. 2. List `$FP_DD/traj`. 3. Open the newest file. 4. Restart the engine without the variable and run the pipe once more.
  - Expected: step 2 shows three files named like `2026-10-27T09-30-00.123Z.jsonl` (the oldest run pruned); step 3 starts with a `run_start` record, has `agent_event` records with the Pi events and ends with `run_end`; no API key or bearer token appears in the file; step 4 writes no new file.
  - Result:
- [ ] **SMK-W4-02-4** (Runtime) The log archive sweep moves old run logs into month archives and skips running pipes
  - Setup: a scratch `FP_DD` with a pipe folder `pipes/archive-smoke/` holding 60 files `logs/YYYYMMDD_HHMMSS.json` dated 30 to 90 days ago (copy one real run log and rename it; set old modified times with PowerShell `(Get-Item $f).LastWriteTime = (Get-Date).AddDays(-40)`); open one of the old files in Notepad++ or another editor that keeps it open.
  - Steps: 1. Start the release-dev engine. 2. Wait six minutes. 3. `grep "pipe log archive" "$FP_DD/engine.log"`. 4. List `pipes/archive-smoke/logs` and `pipes/archive-smoke/logs/archive`. 5. Run the pipe, and while it runs nothing in its logs folder changes.
  - Expected: step 3 shows one line with `scanned=60 archived=10` (or `archived=9 ... failed=1` when Windows refused to delete the file held open, which then stays in place); step 4 shows the newest 50 logs in place and one or more `YYYY-MM.jsonl.gz` files that 7-Zip opens as JSON lines; the engine log has no error from the sweep and the scheduler kept running pipes meanwhile.
  - Result:
- [ ] **SMK-W4-02-5** (Runtime) An event-triggered run writes `.trigger-context.json` inside the pipe folder, and a manual run removes it
  - Setup: release-dev engine with the Meeting Summary pipe enabled.
  - Steps: 1. Start and stop a meeting with speech (as in SMK-W4-02-1). 2. While or after the summary runs, open `$FP_DD/pipes/meeting-summary/.trigger-context.json`. 3. Check the file's owner and permissions in Explorer (Properties > Security). 4. Run the pipe manually from the Pipes settings page. 5. Look for the file again.
  - Expected: step 2 shows `event` `meeting_ended`, `key` equal to the meeting id, `trigger_type` `event`, a `triggered_at` time and the event payload with no tokens or keys; step 3 shows only your user, SYSTEM and Administrators (inherited from the profile folder); after step 4 the file is gone.
  - Result:
- [ ] **SMK-W4-02-6** (UI smoke) Skipped and preset-failure runs read clearly in the pipe history
  - Setup: dev app (`scripts/dev/app-dev.sh`) with SMK-W4-02-2's pipe still on `preset: deleted-preset`, plus a pipe with `schedule: at <an RFC 3339 time three hours ago>` and `enabled: true` written straight into its `pipe.md`.
  - Steps: 1. Start the app and wait one minute. 2. Open Settings > Pipes and expand both pipes' run history. 3. Run the preset pipe from the UI.
  - Expected: the one-off pipe shows as off with one `skipped` run whose error type is `stale_one_off` (the badge may print it as `stale one_off`) and whose message says it was skipped instead of running late; the preset pipe's run shows `failed` with error type `ai_preset_unavailable` and the message naming the missing preset; step 3 shows an error and the pipe does not hang in a running state.
