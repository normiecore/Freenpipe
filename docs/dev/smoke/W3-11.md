# W3-11 Windows smoke checks

Entries follow the format in [../windows-smoke-checklist.md](../windows-smoke-checklist.md). Run
them on a W3-11 (or later) build in the isolated dev setup: `FP_DD`, port 3035,
`SCREENPIPE_API_KEY`, the engine started with
`target/release-dev/screenpipe.exe record --port $FP_PORT --data-dir "$FP_DD" > "$FP_DD/engine.log" 2>&1 &`.
`api` and `sqlq` are the helpers from PLAN.md section 4. The corrupt-frame lines quoted below are
logged at `debug`; start the engine with `RUST_LOG=screenpipe_engine=debug` for SMK-W3-11-2 and -3.

### W3-11 Capture loop hardening A: stages and wedge watchdog, probe timeouts, fail-closed exclusions, corrupt frames

- [ ] **SMK-W3-11-1** (Runtime) `/health` names the capture loop stage while recording
  - Setup: engine recording as above, at least one monitor, normal desktop use.
  - Steps: 1. Use the PC for a minute (switch windows, type). 2. `api /health | python -m json.tool | grep -E '"loop_stage|frames_corrupt'`. 3. Repeat step 2 three times a few seconds apart.
  - Expected: `loop_stage` is one of `heartbeat`, `focus-gate`, `warm-wait`, `cold-wait`, `pause-gate`, `release-stream`, `invalidate-streams`, `exclusion-probe`, `visual-probe`, `trigger-wait`, `capture`, `hot-cache-push`, `trigger-drain` (usually `trigger-wait`, `cold-wait` or `warm-wait`); `loop_stage_age_secs` is a whole number, below 10 while you use the monitor (a `cold-wait` on an unfocused monitor may be older); `pipeline.frames_corrupt_black` and `pipeline.frames_corrupt_green` are present and 0.
  - Result:
- [ ] **SMK-W3-11-2** (Manual) Dark screens are stored, not rejected as black
  - Setup: engine recording with `RUST_LOG=screenpipe_engine=debug`; Windows Terminal (or `cmd`) with a pure black background; a dark-mode app (VS Code or Explorer in dark mode).
  - Steps: 1. Maximise the black terminal on one monitor, clear it (`cls`) so only the prompt shows, wait 10 s, then type a command. 2. Switch to the dark-mode app, click around for 20 s. 3. `grep -c "is corrupt" "$FP_DD/engine.log"`. 4. `sqlq "SELECT app_name, snapshot_path FROM frames ORDER BY id DESC LIMIT 10"` and open two of the newest JPEGs.
  - Expected: step 3 prints 0; the newest frames include the terminal and the dark-mode app with non-empty `snapshot_path`, and the JPEGs show the prompt and the dark UI; `api /health` still reports `pipeline.frames_corrupt_black` 0.
  - Result:
- [ ] **SMK-W3-11-3** (Hardware) A GPU reset leaves no black or green frames in the timeline
  - Setup: engine recording with `RUST_LOG=screenpipe_engine=debug`; Graphics Tools installed for `dxcap` (Settings > System > Optional features > "Graphics Tools"); an elevated prompt.
  - Steps: 1. Note the time and the `pipeline.frames_corrupt_*` values from `api /health`. 2. Run `dxcap -forcetdr` (the screen goes black for one to three seconds). 3. Keep using the desktop for 3 minutes. 4. `grep -nE "is corrupt|corrupt frames in a row|vision capture watchdog" "$FP_DD/engine.log"`. 5. Look through the frames of those 3 minutes in the timeline (or open the JPEGs from `sqlq "SELECT snapshot_path FROM frames ORDER BY id DESC LIMIT 40"`).
  - Expected: no stored frame is all black or carries a green band; any frame the reset garbled appears as `captured frame on monitor N is corrupt (Black|Green); not storing it` and raises the matching counter; usually one `monitor N: 3 corrupt frames in a row ...; releasing the capture stream so the next capture opens a fresh one` line per monitor (a further `33 corrupt frames in a row` line only if the session stayed broken; any such line is followed by frames with real content); frames with real content resume within a few seconds of the reset; no `vision capture watchdog` restart line (the reset is shorter than the 2 minute wedge threshold).
  - Result:
- [ ] **SMK-W3-11-4** (Runtime) Deliberate pauses never trigger a watchdog restart
  - Setup: engine recording; two monitors if available; the app (or `curl`) able to call `/vision/device/stop`.
  - Steps: 1. Pause one monitor: `api /vision/device/stop -X POST -H "Content-Type: application/json" -d '{"monitor_id": <id>}'` (ids from `api /vision/device/status`). 2. Lock the screen (Win+L) for 5 minutes, then unlock. 3. Put the PC to sleep for 2 minutes, wake it and log in. 4. Leave the paused monitor paused and use the other one for 5 more minutes. 5. Resume the paused monitor with `/vision/device/start`. 6. `grep -n "vision capture watchdog" "$FP_DD/engine.log"`.
  - Expected: step 6 prints nothing; the paused monitor stays paused through the lock and sleep (`api /vision/device/status` shows `user_disabled: true` until step 5) and records again after step 5.
  - Result:
- [ ] **SMK-W3-11-5** (Runtime) A day of recording: restarts are rare, bounded and recover capture
  - Setup: engine recording for a full working day of normal use (the longer the better), with monitor changes, sleep and lock as they come.
  - Steps: 1. At the end, `grep -nE "vision capture watchdog|change probe on monitor|window exclusion list" "$FP_DD/engine.log"`. 2. For each `restarting the VisionManager` line, look at the next 20 lines and the timeline around that time.
  - Expected: no `window exclusion list` lines (Windows has no per-window exclusion list); `change probe ... gave no screenshot` lines, if any, are each followed by `change probe on monitor N answers again`; every `...; restarting the VisionManager` line is followed by `vision capture watchdog: VisionManager restarted after a ... on monitor N` and frames resume on that monitor within a minute; never more than 3 restart lines in any hour. If a restart line appears, attach it with the 20 lines before it to the result: it names the stage the loop froze in.
  - Result:
- [ ] **SMK-W3-11-6** (Manual) A screen the OS blanks on purpose is not stored and does not read as a stall
  - Setup: engine recording with `RUST_LOG=screenpipe_engine=debug`; any program that asks for elevation (for example `regedit`), with UAC at its default level so the prompt uses the dimmed secure desktop.
  - Steps: 1. Start `regedit` and leave the UAC prompt open for 2 minutes without answering. 2. While it is open, from another device or after closing it, read `api /health` and note `frame_status` and `unhealthy_reasons`. 3. Cancel the prompt and use the desktop for a minute. 4. `grep -nE "is corrupt|vision capture watchdog" "$FP_DD/engine.log"` and look at the frames stored during the prompt.
  - Expected: no stored frame is all black; if capture saw the blanked desktop, the log has `captured frame on monitor N is corrupt (Black); not storing it` lines and `pipeline.frames_corrupt_black` went up; `frame_status` is not `stale` and there is no `vision_capture_stalled` reason because of the prompt; no watchdog restart line; frames resume right after the prompt closes.
  - Result:
- [ ] **SMK-W3-11-7** (Manual) Flat dark-green screens are stored, not rejected as decode garbage
  - Setup: engine recording with `RUST_LOG=screenpipe_engine=debug`; a browser; optionally a card game with a plain green felt (for example a solitaire game from the Microsoft Store).
  - Steps: 1. Note `pipeline.frames_corrupt_green` from `api /health`. 2. Open `data:text/html,<body style="background:green">` in the browser, press F11 for full screen and wait 30 s, then click once. 3. Repeat step 2 with `background:darkgreen`. 4. If you have the card game, maximise it and play a few moves for a minute. 5. `grep -c "is corrupt (Green)" "$FP_DD/engine.log"` and `sqlq "SELECT app_name, snapshot_path FROM frames ORDER BY id DESC LIMIT 10"`.
  - Expected: step 5 prints 0 and `pipeline.frames_corrupt_green` did not move; the newest frames include the browser (and the game) with non-empty `snapshot_path`, and their JPEGs show the green page; `api /health` reports no `vision_capture_stalled` reason.
