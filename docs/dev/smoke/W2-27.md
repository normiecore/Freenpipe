# W2-27 Windows smoke checks

### W2-27 App startup hardening: argv helper modes, autostart, focus handoff, env, AVX2, WER, opener

Unless an entry says otherwise, use the isolated dev app: quit the installed screenpipe,
`source scripts/dev/dev-env.sh smoke` (port 3035, focus port 11436, `FP_DD`), then
`scripts/dev/app-dev.sh`. Extra arguments reach the app through tauri's and cargo's separators:
`scripts/dev/app-dev.sh -- -- -- --autostart`. `$EXE` below is the dev executable that run built
(`$CARGO_TARGET_DIR/debug/screenpipe-app.exe`, or `target/debug/screenpipe-app.exe` in the app
crate). Debug commands are run from the Home window's devtools console with
`await window.__TAURI_INTERNALS__.invoke("<command>")`. Logs are in `$FP_DD` (the newest
`screenpipe-app.*.log`).

- [ ] **SMK-W2-27-1** (UI smoke) A launch with `--autostart` starts in the background
  - Setup: dev app not running, onboarding completed in `$FP_DD` (run the dev app once and finish or skip it).
  - Steps: 1. Start the dev app with `--autostart` (see above). 2. Wait 30 s. 3. Run `curl -s -o NUL -w "%{http_code}\n" http://127.0.0.1:3035/health`. 4. Search the app log for `background launch`.
  - Expected: no Home window (and no onboarding window) appears; the tray icon is there and its menu works; `/health` returns 200 (the engine started). The log shows `background launch: Home window not shown (reason=Autostart, restart_home_visible=None, autostart=true)`. Clicking the tray icon or the Settings item opens Home normally.
  - Result:

  - Expected: step 1 exits with 0 within about 2 s, no window opens and the running app's log shows `focus request ignored: duplicate --autostart launch while the app is running`. Step 2 exits with 0 and the running app brings Home to the front (log `focus request: args_count=1, deep_link_present=false, target=None`).

Repeat step 1 with `"launch_exe"` set to the dev executable's own path written with forward slashes and different letter case (for example `c:/users/.../SCREENPIPE-APP.EXE`). 5. In the app, open a screen that shows app icons (Settings > Recording, the window filter list) and the notification bell.

Host "rebind.evil.example" is not local`. Step 4 prints `200` and focuses Home (same file, other spelling). - [ ] **SMK-W2-27-5** (Manual) A fail-fast crash leaves a minidump in `<data dir>\crash-dumps`
  - Setup: build the helper with a static C runtime and put it beside the dev executable: `RUSTFLAGS="-C target-feature=+crt-static" cargo build --release -p screenpipe-wer-helper --target-dir target/wer-helper`, then copy `target/wer-helper/release/screenpipe_wer_dump_helper.dll` into the directory of `$EXE`. Windows Error Reporting must not be disabled by policy.
  - Steps: 1. Start the dev app. 2. Check the log for `fail-fast crash dumps enabled: WER helper ... registered` and `reg query "HKCU\Software\Microsoft\Windows\Windows Error Reporting\RuntimeExceptionHelperModules"` for a value named after the DLL's full path. 3. Run `await window.__TAURI_INTERNALS__.invoke("debug_force_native_crash")`. 4. Wait until WerFault finishes (the process is gone), look into `$FP_DD/crash-dumps/pending`. 5. Start the dev app again and look into `$FP_DD/crash-dumps`. 6. Open the dump in WinDbg or Visual Studio (optional).
  - Expected: step 3 ends the app at once. After step 4 `pending` holds one `screenpipe-app-<pid>-<UTC time>.dmp` (a few MB) and no `.partial` file. After step 5 the dump has moved to `$FP_DD/crash-dumps`, `pending` is empty, and the log shows `recovered 1 crash minidump(s) into ... (kept locally, never uploaded)`. Without the DLL beside the executable the log says `fail-fast crash dumps unavailable: ... is not installed beside the app (expected in dev builds)` instead. No network traffic is caused by the dump (the app sends nothing; Windows' own WER consent settings are unchanged).
  - Result:

On a normal machine the log shows `cpu-smoke: native start-up passed (avx2=yes, compat_mode=false)` and nothing changes.
