# W2-26 Windows smoke checks

### W2-26 App engine supervision: auto-respawn, port-conflict classification, safe relaunch

All entries use the isolated dev app: quit the installed screenpipe, `source scripts/dev/dev-env.sh smoke`
(port 3035, focus port 11436, `FP_DD`), then `scripts/dev/app-dev.sh`. Debug commands are run from the
Home window's devtools console (right-click > Inspect, or Ctrl+Shift+I) with
`await window.__TAURI_INTERNALS__.invoke("<command>")`; a `bun run tauri dev` build is a debug build, so
they are allowed (in a release build turn on developer mode first). Logs are in `$FP_DD` (the newest
`screenpipe-app.*.log`).

- [ ] **SMK-W2-26-1** (UI smoke) A killed engine is respawned within the configured checks
  - Setup: dev app recording normally (tray shows recording) for at least 60 s after launch.
  - Steps: 1. Run `await window.__TAURI_INTERNALS__.invoke("debug_kill_engine")` and note the time. 2. Run `curl -s -o NUL -w "%{http_code}\n" http://127.0.0.1:3035/health` a few times over the next 30 s. 3. Search the app log for `respawning it` and `engine respawn finished`.
  - Expected: the command returns `engine on port 3035 stopped; ...`; `/health` fails (code `000`) for a short while, then returns 200 again within about 25 s of step 1 (3 samples 5 s apart, plus the restart). The log shows `engine unreachable for 3 checks while recording is on; respawning it (1 respawn(s) in the last 10 min)` followed by `engine respawn finished`. The timeline shows new frames after the respawn.
  - Result:
- [ ] **SMK-W2-26-2** (UI smoke) Paused recording is not respawned
  - Setup: as SMK-W2-26-1.
  - Steps: 1. Pause recording from the tray. 2. Run `debug_kill_engine` and wait 60 s. 3. Resume recording from the tray and wait 30 s.
  - Expected: during step 2 the log has no `respawning it` line and `/health` stays down (the recording intent is off while paused). After step 3 the engine comes back (the log shows `respawning it` or a normal start) and the tray shows recording again.
  - Result:
- [ ] **SMK-W2-26-3** (UI smoke) Respawns are rate-limited to 3 per 10 minutes
  - Setup: freshly started dev app, recording for at least 60 s.
  - Steps: 1. Run `debug_kill_engine`, wait until `/health` on 3035 answers again. 2. Repeat step 1 two more times. 3. Run `debug_kill_engine` a fourth time and wait 2 minutes.
  - Expected: the first three kills are each followed by `respawning it (1|2|3 respawn(s) in the last 10 min)` and the engine comes back. After the fourth the log shows `auto-respawn is paused after too many attempts in 10 min; next attempt in <n>s` once, `/health` stays down, and the engine comes back by itself when the 10-minute window from the first respawn has passed.
  - Result:
- [ ] **SMK-W2-26-4** (Manual) Quit from the tray finishes within the teardown budget
  - Setup: dev app recording for at least 2 minutes, a meeting or audio device active if possible, Task Manager open on the Details tab.
  - Steps: 1. Click Quit in the tray menu and start a stopwatch. 2. Watch for the app's process (`screenpipe-app.exe` in a dev build) to disappear. 3. Read the end of the app log.
  - Expected: the process is gone in under 28 s (normally a few seconds). The log ends with `pre-exit teardown finished in <n>ms: capture=Done/... engine=Done/... http_drain=... sqlite_pools=Done/... pi=...`; if a step overran, the log says `overran its 25s budget` and `forcing process exit`, and the process is still gone within 28 s. Clicking Quit twice quickly logs `quit request from tray ignored (TeardownRunning)` for the second click.
  - Result:
- [ ] **SMK-W2-26-5** (Runtime) A foreign process on the API port is never killed
  - Setup: dev app not running. Python 3 installed.
  - Steps: 1. In a separate terminal run `python -m http.server 3035 --bind 127.0.0.1` and leave it running. 2. Start the dev app and wait 90 s. 3. Check that the Python server still answers `curl -s -o NUL -w "%{http_code}\n" http://127.0.0.1:3035/`. 4. Stop the Python server with Ctrl+C and wait 30 s.
  - Expected: after step 2 the Python process is still running, the app shows a "Port 3035 is busy" notification naming `python.exe (pid N)`, and the log has `port 3035: python.exe (pid N) classified as foreign` and `engine respawn skipped, the API port is held`. Nothing logs `terminating`. After step 4 the log shows `API port is free again and recording is on; restarting the engine` and `/health` on 3035 returns 200 within about 15 s.
  - Result:
- [ ] **SMK-W2-26-6** (Runtime) A healthy screenpipe-like holder is never killed
  - Setup: dev app not running. Save this as `$FP_DD/fake_health.py`: a `http.server.BaseHTTPRequestHandler` whose `do_GET` answers 200 with body `{"status":"healthy","frame_status":"ok","audio_status":"ok"}` for every path, served by `http.server.HTTPServer(("127.0.0.1", 3035), Handler).serve_forever()`.
  - Steps: 1. Run `python -I "$FP_DD/fake_health.py"`. 2. Start the dev app and wait 90 s. 3. Stop the fake server and wait 30 s.
  - Expected: after step 2 the fake server is still running, the app shows an "Another screenpipe is running" notification naming `python.exe`, and the log classifies it as `healthy`; nothing logs `terminating`. After step 3 the engine starts on 3035 within about 15 s.
  - Result:
- [ ] **SMK-W2-26-7** (UI smoke) Safe relaunch keeps Home's visibility and the data dir
  - Setup: dev app recording, Home window closed (app in the tray only), Task Manager on the Details tab showing PIDs.
  - Steps: 1. From any window's devtools console (open the timeline or chat window if Home is closed) run `await window.__TAURI_INTERNALS__.invoke("debug_relaunch_app")`. 2. Note the new process PID. 3. Open Home, then run the command again from Home's console.
  - Expected: after step 1 the old PID disappears and a new one appears within a few seconds; Home does not stay open (it may flash) and the new process's log has `startup_window_restore outcome=home_kept_closed`. Recording resumes in the same `$FP_DD` (new frames in the timeline). After step 3 the new instance opens Home and logs `outcome=home_restored`. The old log ends with `safe relaunch: replacement pid <n> started` and the teardown summary.
  - Result:
- [ ] **SMK-W2-26-8** (UI smoke) Safe relaunch releases the tray icon and the single-instance lock
  - Setup: dev app recording with Home open, Sysinternals Process Explorer running (optional, for step 3).
  - Steps: 1. Run `await window.__TAURI_INTERNALS__.invoke("debug_relaunch_app")` from Home's console. 2. Wait 10 s, then move the mouse over the notification area (tray overflow included). 3. In Process Explorer open the new process > Properties > Environment. 4. Launch the dev app a second time (run its exe again, or `scripts/dev/app-dev.sh` in a second terminal).
  - Expected: after step 2 exactly one Freenpipe tray icon is left (no dead icon that vanishes on hover) and the new process is still running. The old log ends with `safe relaunch: replacement pid <n> started` and has no `exited at once` line (if it has one, it is followed by a second `replacement pid` line and the app is still running). In step 3 `SCREENPIPE_DATA_DIR` is listed and `SCREENPIPE_RELAUNCH_HOME_VISIBLE` is not (the replacement removes it once read). In step 4 the second launch brings the running instance's window forward and exits; there is still one tray icon.
  - Result:
- [ ] **SMK-W2-26-9** (Runtime) A busy control port is reported without posting to it
  - Setup: dev app not running. Python 3 installed. Windows notifications allowed for the dev app.
  - Steps: 1. In a separate terminal run `python -m http.server 11436 --bind 127.0.0.1` and leave it running. 2. Start the dev app and wait 60 s. 3. Read the Python terminal and the app log. 4. Stop the Python server.
  - Expected: a Windows toast titled "Port 11436 is busy" names `python.exe (pid N)`. The Python terminal shows only `GET /health` requests from the classifier and no `POST /notify` line. The app log has `control server port 11436: python.exe (pid N) classified as foreign` and `telling the user through the system notification centre`; nothing logs `terminating`. The Python process is still running after step 2.
  - Result:
