# W2-18 Windows smoke checks

Entries follow the format in [../windows-smoke-checklist.md](../windows-smoke-checklist.md). Run
them on a W2-18 (or later) build in the isolated dev setup: `FP_DD`, port 3035,
`SCREENPIPE_API_KEY`. Point the exclusion list at the dev data dir so nothing reads or writes
`~/.screenpipe`: `export SCREENPIPE_AUDIO_EXCLUSIONS_PATH="$FP_DD/audio-exclusions.json"` in the
shell that starts the engine (and the app, for entry 5).

Every engine log line from the new loopback engine starts with `wasapi-local:`.

### W2-18 Windows WASAPI loopback engine and exe-based audio exclusions

- [ ] **SMK-W2-18-1** (Hardware) Browser audio is recorded through the WASAPI loopback engine
  - Setup: release-dev engine build; `source scripts/dev/dev-env.sh smoke` with a fresh `FP_DD`; speakers or headphones as the default output; no `audio-exclusions.json`.
  - Steps: 1. `target/release-dev/screenpipe.exe record --port $FP_PORT --data-dir "$FP_DD" > "$FP_DD/engine.log" 2>&1 &`. 2. `grep "wasapi-local" "$FP_DD/engine.log"`. 3. Play a video with clear speech in Edge or Chrome for two minutes. 4. `sqlite3 "$FP_DD/db.sqlite" "select file_path from audio_chunks order by id desc limit 5"`. 5. `sqlite3 "$FP_DD/db.sqlite" "select device, count(*) from audio_transcriptions where is_input_device = 0 group by device"`.
  - Expected: step 2 shows `wasapi-local: capturing <default device> (output) as default-render-endpoint at <rate> Hz` and the per-process support line (`available (Windows build N)` on Windows 11 / Server 2022 and later); no `falling back to the cpal stream` line. Step 4 lists chunk files named after the output device. Step 5 shows the output device with a count above 0, and `api '/search?content_type=audio&limit=5'` returns words from the video.
  - Result:
- [ ] **SMK-W2-18-2** (Hardware) An excluded browser is left out while another app is still recorded
  - Setup: as entry 1, on Windows build 20348 or later. Write `$SCREENPIPE_AUDIO_EXCLUSIONS_PATH` with `{"excluded_apps":[{"bundle_id":"chrome.exe","name":"Google Chrome"}]}` before starting the engine. Chrome installed and running; a second player (Spotify, VLC or the Media Player app) with spoken audio.
  - Steps: 1. Start the engine as in entry 1. 2. `grep "wasapi-local" "$FP_DD/engine.log"`. 3. Play speech in Chrome for one minute while the second player is paused. 4. Pause Chrome and play speech in the second player for one minute. 5. Wait one minute, then search for words from each: `api '/search?content_type=audio&q=<word>&limit=5'`.
  - Expected: step 2 shows the exclusion list being read and the stream captured as `exclude-process-tree:<chrome root pid>`. Words from step 3 are not found; words from step 4 are. With Chrome closed and reopened during the run, the log shows `exclusion target changed (... -> ...)` and the exclusion follows the new Chrome pid within about ten seconds.
  - Result:
- [ ] **SMK-W2-18-3** (Hardware) Switching the default output device rebuilds the loopback
  - Setup: as entry 1, with two output devices (for example speakers plus a USB or Bluetooth headset). Three runs: (a) `useSystemDefaultAudio` on (default settings); (b) only the speakers pinned in the app's audio device list; (c) both devices pinned. For run (c) also write `{"excluded_apps":[{"bundle_id":"chrome.exe"}]}` to `$SCREENPIPE_AUDIO_EXCLUSIONS_PATH` and keep Chrome open.
  - Steps: 1. Start recording and play speech. 2. In Windows Sound settings change the default output to the headset. 3. Keep playing speech for one minute. 4. Switch back. 5. `grep -E "wasapi-local|DEVICE_RECOVERY" "$FP_DD/engine.log"`. 6. `sqlite3 "$FP_DD/db.sqlite" "select device, count(*) from audio_transcriptions where is_input_device = 0 group by device"`.
  - Expected: each switch logs `default render endpoint changed (<old id> -> <new id>)`. Run (a): the device monitor starts the new device and stops the old one within a few seconds (`[DEVICE_RECOVERY] system default output changed`) and the headset speech from step 3 is transcribed under the headset's name, with no gap longer than about 5 s. Run (b): the speakers stream logs that it is no longer the default output and is captured in full as `endpoint:<speakers name>`; nothing is recorded twice, and headset speech is not recorded (the headset is not pinned), as in the base app. Run (c): the speakers stream drops to `endpoint:<speakers name>` and the headset stream logs that it is now the default output, then `exclusion target changed (... -> exclude-process-tree:<chrome pid>)`; step 6 shows each sentence under one device only, never under both.
  - Result:
- [ ] **SMK-W2-18-4** (Hardware) A tap that cannot start falls back instead of going silent
  - Setup: as entry 2, but list an executable whose process exits right away or is protected (for example `{"excluded_apps":[{"bundle_id":"audiodg.exe"}]}`; `audiodg.exe` runs as a protected service process).
  - Steps: 1. Start the engine and play speech in any browser for one minute. 2. `grep "wasapi-local" "$FP_DD/engine.log"`. 3. Search for words from the speech.
  - Expected: if the tap cannot be activated, exactly one `cannot be excluded ... trying again in 60s` warning appears for that process tree and the stream stays on `default-render-endpoint`; either way the speech is found in step 3. No repeating warning every poll. With `RUST_LOG=screenpipe_audio=debug`, later tries show as `still cannot be excluded ... next try in <N>s` debug lines with N doubling from 120 up to 900, about one per interval and never more often than once a minute.
  - Result:
- [ ] **SMK-W2-18-5** (UI smoke) The exclusions panel picks an .exe and allows one app on Windows
  - Setup: installed screenpipe quit; `source scripts/dev/dev-env.sh smoke`; `SCREENPIPE_AUDIO_EXCLUSIONS_PATH` exported as above; `scripts/dev/app-dev.sh` on Windows build 20348 or later.
  - Steps: 1. Open Settings, Recording. 2. Find "Exclude apps from system audio" (the "CoreAudio system audio capture" toggle must not be shown on Windows). 3. Click "+ add app"; the dialog opens in `C:\Program Files` and filters `.exe`. 4. Pick `chrome.exe` (under `Google\Chrome\Application`). 5. Save. 6. Open `$SCREENPIPE_AUDIO_EXCLUSIONS_PATH` in a text editor. 7. Try to add a second app. 8. Pick a `.txt` renamed to `.exe` instead.
  - Expected: step 4 shows a badge with the Chrome icon and the name "Google Chrome"; step 6 contains `"bundle_id": "chrome.exe"` with name and a `data:image/png;base64,` icon; in step 7 the add button is hidden and a note says only one app can be left out on Windows; step 8 shows an error toast saying the file is not a Windows executable.
  - Result:
- [ ] **SMK-W2-18-6** (Hardware) Losing the captured output device hands the stream back without a crash
  - Setup: as entry 1, with a USB or Bluetooth headset as the default output and the built-in speakers disabled in Sound settings (so the headset is the only output).
  - Steps: 1. Start the engine and play speech for one minute. 2. Unplug (or turn off) the headset and wait one minute. 3. Plug it back in and play speech for one minute. 4. `grep -E "wasapi-local|DEVICE_RECOVERY|falling back" "$FP_DD/engine.log"`.
  - Expected: step 2 logs that the loopback stopped working (`the audio device was removed or reconfigured`), then either the device monitor stops the stream or, after a few rebuild retries with growing delays, `giving up on ... handing the device back to the device monitor`; no endless retry loop, and the engine keeps running (screen capture continues). After step 3 the device monitor starts output capture again (through the engine, or through cpal after three engine failures in 15 minutes, which is logged once) and the speech from step 3 is transcribed.
  - Result:
- [ ] **SMK-W2-18-7** (Hardware) An exclusion tap does not record call audio twice
  - Setup: as entry 2, with two output devices: speakers as the default device and a USB headset as the default communications device (Sound settings, Playback, right-click the headset, "Set as Default Communication Device"); `useSystemDefaultAudio` on. Chrome listed in `$SCREENPIPE_AUDIO_EXCLUSIONS_PATH` and running.
  - Steps: 1. Start the engine; check the log shows both the speakers stream on `exclude-process-tree:<chrome pid>` and the communications output started. 2. Start a test call in Teams or Zoom (their echo-test call works) so the call audio plays on the headset; play nothing else for one minute. 3. `sqlite3 "$FP_DD/db.sqlite" "select device, transcription from audio_transcriptions where is_input_device = 0 order by id desc limit 20"`.
  - Expected: record what happens, for open question 9 in `docs/clean-room/open-questions/W2-18.md`. Pass when the call audio appears under the headset only. If the same sentences also appear under the speakers device, the exclude-mode tap carries other endpoints too; note it in the Result line so a later WP pauses the communications stream while an exclusion tap runs.
  - Result:
