# W2-01 Windows smoke checks

Entries follow the format in [../windows-smoke-checklist.md](../windows-smoke-checklist.md). Run
them on a W2-01 (or later) build in the isolated dev setup: `FP_DD`, port 3035,
`SCREENPIPE_API_KEY`. `api` and `sqlq` are the helpers from PLAN.md section 4. The unit and
integration tests (`cargo test -p screenpipe-db --lib` and `--test runtime_hardening_test`) cover the
logic on Linux; these entries check it on Windows, where the ownership lock is `LockFileEx`.

### W2-01 DB runtime hardening: pragmas, WAL maintenance, preflight, planner stats, cancellable reads

- [ ] **SMK-W2-01-1** (Runtime) On-demand checkpoint uses RESTART, never TRUNCATE
  - Setup: release-dev engine on `$FP_PORT` with a fresh `FP_DD`, logging to `$FP_DD/engine.log`; let it record for two minutes.
  - Steps: 1. `api /data/checkpoint -X POST`. 2. `grep -E "wal checkpoint" "$FP_DD/engine.log"`. 3. `grep -c TRUNCATE "$FP_DD/engine.log"`.
  - Expected: step 1 answers JSON with `busy`, `log` and `checkpointed` (busy 0 on an idle engine); step 2 shows `startup wal checkpoint (RESTART)` (if the WAL was not empty) and `on-demand wal checkpoint (RESTART)`; step 3 prints 0.
  - Result:
- [ ] **SMK-W2-01-2** (Runtime) Planner statistics report appears with a shortened interval
  - Setup: release-dev engine started with `SCREENPIPE_PLANNER_MAINTENANCE_INTERVAL_SECS=30` and a fresh `FP_DD`.
  - Steps: 1. Let it record for two minutes. 2. `cat "$FP_DD/sqlite-planner-maintenance.json"`. 3. `sqlq "select count(*) from sqlite_stat1"`.
  - Expected: the file exists and parses; `latest` and `last_success` are present with `status` `succeeded`, a `started_at` time and `analyzed_tables` listing tables such as `frames`; no `.tmp-` file is left next to it; step 3 is above 0.
  - Result:
- [ ] **SMK-W2-01-3** (Runtime) A second recorder is refused and a killed owner is taken over at once
  - Setup: release-dev engine A recording on `$FP_PORT` with `FP_DD`.
  - Steps: 1. Start engine B with the same `--data-dir` on port 3036. 2. Run `target/release-dev/screenpipe.exe status --data-dir "$FP_DD"` while A records. 3. Kill A hard: `taskkill /F /PID <pid of A>`. 4. Start engine B again on port 3036 with the same data dir.
  - Expected: step 1 exits with `failed to initialize database` and "owned by another running process"; step 2 prints frame counts (not "error reading db"); step 4 starts recording at once without deleting `db.sqlite.owner`, and its log shows "taking over database ownership".
  - Result:
- [ ] **SMK-W2-01-4** (Runtime) A database written by screenpipe opens unchanged
  - Setup: a copy of a screenpipe v2.7.104 data dir (never the live `~/.screenpipe`) as `FP_DD`.
  - Steps: 1. Start the release-dev engine on that copy. 2. `api /health`. 3. `api "/search?limit=5"`. 4. `dir "$FP_DD"`.
  - Expected: the engine starts (no preflight or version error in the log), health is served and search returns the existing rows; `db.sqlite.owner` exists next to `db.sqlite` and no other file in the dir was rewritten apart from `db.sqlite`, `-wal` and `-shm`.
  - Result:
- [ ] **SMK-W2-01-5** (Runtime) The WAL stays bounded during a long recording
  - Setup: release-dev engine recording screen and audio for one hour with normal desktop use, including a few searches from the app or `api "/search?q=a&limit=200"`.
  - Steps: 1. Every 15 minutes note the size of `$FP_DD/db.sqlite-wal`. 2. `grep -E "wal checkpoint (deferred|still deferred|backlog drained)|escalated" "$FP_DD/engine.log"`.
  - Expected: the `-wal` file never grows past a few hundred MB and is back under 64 MB at the end; any "deferred" line is followed by a "backlog drained" line; there are no `wal checkpoint (PASSIVE) failed` warnings.
  - Result:
- [ ] **SMK-W2-01-6** (Runtime) A search dropped by the client stops in the database
  - Setup: release-dev engine on a data dir with at least a day of recordings.
  - Steps: 1. `api "/raw_sql" -X POST -H 'Content-Type: application/json' -d '{"query":"WITH RECURSIVE n(i) AS (SELECT 1 UNION ALL SELECT i+1 FROM n) SELECT count(*) FROM n"}' --max-time 2`. 2. Within 5 s, `api /health` and `api "/search?limit=1"`. 3. `grep -E "interrupted (read|query)|read transaction" "$FP_DD/engine.log"`.
  - Expected: step 1 times out on the client after 2 s; step 2 answers promptly; the engine's CPU use drops back within a second (Task Manager); no "closing it instead of returning it" warning appears.
  - Result:
- [ ] **SMK-W2-01-7** (UI smoke) The app reports a file that is not a database instead of crashing
  - Setup: dev app (`scripts/dev/app-dev.sh`) on a fresh isolated data dir; quit it after the first start.
  - Steps: 1. Rename `db.sqlite` in the data dir and put a text file named `db.sqlite` there (delete `db.sqlite-wal`/`-shm` if present). 2. Start the dev app. 3. Quit it and restore the original `db.sqlite`.
  - Expected: the app stays up and shows a boot error containing "Failed to initialize database" and "(code: 26) file is not a database"; the text file is unchanged; after step 3 the next start records normally.
  - Result:
