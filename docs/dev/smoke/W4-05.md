# W4-05 Windows smoke checks

Entries follow the format in [../windows-smoke-checklist.md](../windows-smoke-checklist.md). Run
them on a W4-05 (or later) build in the isolated dev setup: `FP_DD`, port 3035,
`SCREENPIPE_API_KEY`, the installed screenpipe quit, app started with `scripts/dev/app-dev.sh`. Any
working chat preset will do (a small local Ollama model is fine). Commands are run from the app
window's devtools console (`window.__TAURI__.core.invoke`), since the chat UI for some of them
arrives with later WPs.

### W4-05 Chat runtime commands and per-turn connections context

- [ ] **SMK-W4-05-1** (UI smoke) Each user turn carries a fresh connections block that the chat does not show
  - Setup: the app running as above; in Settings > Connections connect one credential integration (for example Obsidian with any folder as the vault, or ntfy with a test topic URL).
  - Steps: 1. Open a new chat and send "which integrations are connected?". 2. Without restarting anything, connect a second integration (or disconnect the first) in Settings. 3. Back in the same chat send "and now?". 4. Open the newest session file under `$FP_DD/pi-agent/pi-config/sessions/` (Pi's own log) and search for `<connections_context>`. 5. Look at both user bubbles in the chat, and reopen the chat from the sidebar.
  - Expected: the reply to step 1 names the first integration; the reply to step 3 reflects the change from step 2 without a restart (no `agent_terminated` in the log); step 4 finds one block per user turn, each listing the connections as they were at that turn; the bubbles in step 5 show only the typed text, before and after reopening.
  - Result:
- [ ] **SMK-W4-05-2** (Runtime) No credential reaches the block or Pi's log
  - Setup: as SMK-W4-05-1; connect Discord (or Zapier/Make/n8n) with a webhook URL you can recognise, and Telegram with a dummy bot token.
  - Steps: 1. Send any chat message. 2. Search `$FP_DD/pi-agent/pi-config/sessions/` and the app log for the webhook URL's last path segment and for the bot token.
  - Expected: neither value is found; the block lists Discord and Telegram with `[redacted]` in place of the values.
  - Result:
- [ ] **SMK-W4-05-3** (Runtime) A busy session is neither restarted nor stopped
  - Setup: a chat with a slow reply (ask the model for a 500-word story); note its session id (`commands.piInfo` or the sidebar row).
  - Steps: while the reply streams, in the console run 1. `invoke("pi_stop_if_idle", {sessionId})`, 2. `invoke("pi_start_and_prompt", {sessionId, projectDir: "<FP_DD>/pi-chat", userToken: null, providerConfig: null, message: "hi", images: null, displayPreview: null})`, 3. `invoke("pi_request_state", {sessionId})`; after the reply ends, run 1 again.
  - Expected: step 1 returns `outcome: "busy"` with a reason and the reply keeps streaming; step 2 returns `outcome: "busy"` and no "hi" turn appears; step 3 shows `busy: true`, `agentActive: true` and a `piState` object with `isStreaming: true`; the final step 1 returns `outcome: "stopped"` and the process is gone from Task Manager.
  - Result:
- [ ] **SMK-W4-05-4** (Runtime) A failed start names its stage and leaves no process
  - Setup: the app running; Task Manager open on the Details tab, filtered to `bun.exe`.
  - Steps: 1. `invoke("pi_start", {sessionId: "smoke-a", projectDir: "", userToken: null, providerConfig: null})`. 2. Start `smoke-b` with a provider config whose provider is `custom` and whose `model` is not served by its URL, then send it a prompt with `pi_prompt`. 3. Temporarily rename `$FP_DD/pi-agent/node_modules` and start `smoke-c` (restore the folder afterwards).
  - Expected: step 1 fails with `Pi start failed at stage 'requested': Project directory is required`; in step 2 the prompt error comes back in the chat events and a second prompt is accepted at once (no 5-minute wait); step 3 fails with an error naming a stage and no new `bun.exe` stays in Task Manager.
  - Result:
- [ ] **SMK-W4-05-5** (Runtime) Thinking level changes on a running session and survives a restart
  - Setup: a chat on a reasoning-capable model (or any model; Pi then reports `off`).
  - Steps: 1. `invoke("pi_get_thinking_level", {sessionId})`. 2. `invoke("pi_set_thinking_level", {sessionId, level: "high"})` and watch the devtools for an `agent_event` with `thinking_level_changed`. 3. Restart the session with `pi_start` (same arguments as the chat uses) and repeat step 1. 4. Try `level: "loud"`.
  - Expected: step 1 lists the model's levels; step 2 returns the level in effect and the event carries `level`, `requestedLevel: "high"` and `previousLevel`; step 3 still reports that level; step 4 is refused with the list of valid levels.
  - Result:
- [ ] **SMK-W4-05-6** (Runtime) Extension dialogs can be answered, and stale answers are refused
  - Setup: a project-local Pi extension in `$FP_DD/pi-chat/.pi/extensions/ask.ts` that registers a tool calling `ctx.ui.confirm("Proceed?", "smoke")` and returning the answer; start a new chat so it loads.
  - Steps: 1. Ask the agent to use that tool; note the `extension_ui_request` id from the `agent_event` log. 2. `invoke("pi_extension_ui_response", {sessionId, response: {id, value: null, confirmed: true, cancelled: null}})`. 3. Send the same call again. 4. Trigger the tool once more and press stop in the chat instead of answering.
  - Expected: step 2 lets the tool finish with `true`; step 3 fails saying no dialog with that id is waiting; in step 4 the turn stops and `pi_request_state` lists no pending dialog.
  - Result:
- [ ] **SMK-W4-05-7** (Runtime) Chat files are listed newest first
  - Setup: the app running with a few saved chats. The chat saves them in `%USERPROFILE%\.screenpipe\chats` even in the dev setup (`lib/chat-storage.ts` does not follow `FP_DD`/`SCREENPIPE_DATA_DIR`), and the command lists that same directory.
  - Steps: 1. `invoke("list_chat_entries_by_mtime", {offset: null, limit: 5})`. 2. Send a message in the oldest chat, wait for the save, repeat step 1.
  - Expected: step 1 returns up to 5 `{name, path, mtimeMs, sizeBytes}` entries whose `path` is under `%USERPROFILE%\.screenpipe\chats`, newest first; after step 2 that chat is first.
  - Result:
- [ ] **SMK-W4-05-8** (UI smoke) Services the engine reports itself reach the chat
  - Setup: the app running as above with no credential integration connected; the agent's own browser (owned webview) ready, or WhatsApp paired in Settings > Connections.
  - Steps: 1. In a new chat send "which integrations are connected?". 2. Open the newest Pi session file under `$FP_DD/pi-agent/pi-config/sessions/` and read the turn's `<connections_context>` block. 3. Stop the engine with `invoke("stop_screenpipe")` from the console and send another message (start it again afterwards).
  - Expected: step 1's reply names the browser (or WhatsApp) and the block in step 2 has its `## <name> (<id>)` section with the control (or gateway) endpoints, and a last line pointing at `GET /connections`; it does not say nothing is connected. In step 3 the block says the engine did not answer instead of claiming the list is complete.
  - Result:
- [ ] **SMK-W4-05-9** (UI smoke) A preset switch refused while the session is busy is applied later
  - Setup: a chat with two presets whose system prompts differ (so switching restarts Pi).
  - Steps: 1. Ask for a long reply, and while it streams send two follow-ups so they queue. 2. Switch to the other preset while the reply streams. 3. Watch the toasts until the queued follow-ups have been answered. 4. With nothing running, ask "which model are you?".
  - Expected: step 2 shows "model will switch after this response finishes"; when the reply ends and the runtime still has queued work, a toast says the model will switch once the assistant is idle; no error toast appears; step 4 is answered with the new preset (the app log shows one `Pi start` after the queue emptied). Pressing stop while a turn runs never leaves the chat unable to restart.
  - Result:
