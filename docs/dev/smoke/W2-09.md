# W2-09 Windows smoke checks

Entries follow the format in [../windows-smoke-checklist.md](../windows-smoke-checklist.md). Run
them on a W2-09 (or later) build in the isolated dev setup: `FP_DD`, port 3035,
`SCREENPIPE_API_KEY`. `api` and `sqlq` are the helpers from PLAN.md section 4.

### W2-09 Response formats, calendar time literals, tag autocomplete

- [ ] **SMK-W2-09-1** (Runtime) The acceptance checks pass against a recording engine on Windows
  - Setup: release-dev engine build; `source scripts/dev/dev-env.sh smoke` with a new `FP_DD`; engine recording on `$FP_PORT` for a few minutes with an editor or browser in front.
  - Steps: 1. `api '/search?start_time=today&limit=1' -o /dev/null -w "%{http_code}\n"`. 2. `api '/search?start_time=nonsense&limit=1' -i`. 3. `api '/search?format=csv&fields=content.text&limit=3&start_time=today' -i`. 4. `api '/search?format=xml&limit=1' -i`. 5. `ID=$(sqlq "select id from frames order by id desc limit 1" | tr -dc 0-9)` then `api "/tags/vision/$ID" -X POST -H "Content-Type: application/json" -d '{"tags":["work","project:atlas"]}'`. 6. `api '/tags/autocomplete?q=wo'`. 7. `api "/frames/$ID/elements?format=tsv&fields=role,text" -i`.
  - Expected: step 1 prints `200`; step 2 is `400` and its body names an RFC 3339 timestamp, `today`/`yesterday`/`YYYY-MM-DD` and a relative time; step 3 is `200` with `content-type: text/csv; charset=utf-8`, an `x-total-count` header and a first line `content.text`; step 4 is `400` with ``{"error":"unknown format `xml` (expected json|csv|tsv)"}``; step 6 is `[{"name":"work","frame_count":1,"audio_count":0,"memory_count":0}]`; step 7 is `200` with `content-type: text/tab-separated-values; charset=utf-8` and a `role`, a tab, `text` header line.

- [ ] **SMK-W2-09-2** (Runtime) Calendar days follow the Windows time zone, including on a DST change
  - Setup: as SMK-W2-09-1. Windows time zone set to one with daylight saving (for example "(UTC-05:00) Eastern Time" or "(UTC+01:00) Amsterdam, Berlin"), "Adjust for daylight saving time automatically" on.
  - Steps: 1. In PowerShell: `(Get-Date).Date.ToUniversalTime().ToString("yyyy-MM-ddTHH:mm:ssZ")` and `(Get-Date).Date.AddDays(-1).ToUniversalTime().ToString("yyyy-MM-ddTHH:mm:ssZ")` (local midnight today and yesterday, as UTC). 2. `api '/search?content_type=ocr&start_time=today&limit=1'` and `api '/search?content_type=ocr&start_time=<today UTC from step 1>&limit=1'`; compare `pagination.total`. 3. The same pair for `yesterday` and the step 1 yesterday value. 4. The same pair for `start_time=<today as YYYY-MM-DD>`. 5. Switch the Windows time zone to one several hours away, restart the engine, and repeat steps 1 to 3. 6. If a DST change happened in the last few days in the chosen zone (or set the clock zone to one that changed recently), repeat step 3 for the date after the change.
  - Expected: every pair reports the same `pagination.total`; after the time-zone switch the calendar values move with the new zone; on the day after a DST change `yesterday` still lines up with PowerShell's local midnight (no one-hour shift).
