# W3-08 Windows smoke checks

Entries follow the format in [../windows-smoke-checklist.md](../windows-smoke-checklist.md). Run
them on a W3-08 (or later) build in the isolated dev setup: `FP_DD`, port 3035,
`SCREENPIPE_API_KEY`. `api` and `sqlq` are the helpers from PLAN.md section 4. The unit tests
(`cargo test -p screenpipe-engine --lib meeting_`) already cover the matching rules, the
ownership check, excluded apps and entries, and the lock pause against an in-memory database; these
entries check them with a real calendar, browser, call and lock screen.

### W3-08 UI-scan meeting detector: calendar binding and lock awareness

- [ ] **SMK-W3-08-1** (Manual) A browser call binds to the calendar entry with the same conference link
  - Setup: dev app (`scripts/dev/app-dev.sh`) on the isolated data dir with screen capture on and Google Calendar connected (or a Windows calendar entry whose location holds the link). One entry that started a few minutes ago, with a Google Meet link and two invitees, and a second overlapping entry without a link.
  - Steps: 1. Open the entry's Meet link in Chrome or Edge and join the call (a second account or phone is enough). 2. Keep the Meet tab in front for at least 30 s. 3. `sqlq "select id, title, attendees, calendar_event_id, detection_source from meetings order by id desc limit 1"`. 4. `grep -E "calendar entry bound|calendar match skipped" "$FP_DD/screenpipe-app.log" "$FP_DD"/*.log`.
  - Expected: the newest meeting has `detection_source` `ui_scan`, the entry's title and invitees, and the entry's id in `calendar_event_id`; the log shows `method=exact_conference_url`. The entry without a link is not used.
  - Result:
- [ ] **SMK-W3-08-2** (Manual) A call that only overlaps a calendar entry in time stays unbound
  - Setup: as SMK-W3-08-1, with an entry happening now whose link is a different Meet room (or no link).
  - Steps: 1. Join a different Meet room (or a Zoom desktop call) and stay in it for a minute. 2. Run the query from SMK-W3-08-1 step 3. 3. Search the logs for `calendar match skipped`.
  - Expected: the meeting has no title, no attendees and an empty `calendar_event_id`; the log shows one skipped match with `method=time_only` for that meeting, not one per scan.
  - Result:
- [ ] **SMK-W3-08-3** (Manual) A declined calendar entry is ignored
  - Setup: as SMK-W3-08-1, but decline the entry in Google Calendar (or mark it "Free") and wait a minute for the publisher.
  - Steps: 1. `api "/connections/google-calendar/events?hours_back=1&hours_ahead=2"` and find the entry. 2. Join its Meet link as in SMK-W3-08-1. 3. Run the query from SMK-W3-08-1 step 3.
  - Expected: step 1 shows `"excludeFromMeetingDetection": true` for the entry; the detected meeting is not bound to it and carries no title from it.
  - Result:
- [ ] **SMK-W3-08-4** (Manual) An app in "ignored meeting apps" is never detected
  - Setup: dev app with Zoom (or Teams) desktop installed; add `Zoom` to the ignored meeting apps setting and restart recording.
  - Steps: 1. Join a Zoom call for two minutes. 2. `sqlq "select id, meeting_app, meeting_start from meetings order by id desc limit 3"`. 3. Remove the entry, restart recording and join again.
  - Expected: no meeting row appears while Zoom is ignored; after removing it the call is detected.
  - Result:
- [ ] **SMK-W3-08-5** (Hardware) Locking the screen pauses detection and the meeting survives the unlock
  - Setup: dev app on Windows with audio capture in `meetings-only` mode and a call detected by the UI scan (`api /meetings/status` shows it active).
  - Steps: 1. Stay in the call and press Win+L; wait three minutes. 2. Unlock and stay in the call for another minute. 3. `api /meetings/status` and `sqlq "select id, meeting_end, end_reason from meetings order by id desc limit 2"`. 4. `grep -E "screen unlocked after|Ending -> Idle" "$FP_DD"/*.log`. 5. Leave the call and wait one minute.
  - Expected: steps 1 to 3 show the same meeting still open (no `meeting_end`, no second row) and the log shows the resume line after the unlock with no end in between; audio keeps recording for that meeting after the unlock. After step 5 the meeting ends with an empty `end_reason` about 30 s after the call controls disappear.
  - Result:
- [ ] **SMK-W3-08-6** (Runtime) `meeting_ended` carries the segment count
  - Setup: dev engine on `$FP_PORT` with audio capture on; a websocket client on `/ws/events` (for example `websocat "ws://127.0.0.1:$FP_PORT/ws/events?api_key=$SCREENPIPE_API_KEY"`).
  - Steps: 1. `api /meetings/start -X POST -H 'Content-Type: application/json' -d '{"app":"smoke"}'` and speak for a minute. 2. `api /meetings/stop -X POST`. 3. Read the `meeting_ended` event on the socket.
