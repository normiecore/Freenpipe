# W3-02 Windows smoke checks

Entries follow the format in [../windows-smoke-checklist.md](../windows-smoke-checklist.md). Run
them on a W3-02 (or later) build in the isolated dev setup: `FP_DD`, port 3035,
`SCREENPIPE_API_KEY`. The `api` and `sqlq` helpers are the ones from PLAN.md section 4.

### W3-02 Search v2: parsed content, starred, actor and related filters

- [ ] **SMK-W3-02-1** (Runtime) Starred filters and flags on a live recording
  - Setup: release-dev engine build; `source scripts/dev/dev-env.sh smoke` with a new, empty `FP_DD`.
  - Steps: 1. Start `screenpipe.exe record --port $FP_PORT --data-dir "$FP_DD"` and use a few apps for 4 minutes. 2. Star the second and third minute: `curl -s -X POST -H "Authorization: Bearer $SCREENPIPE_API_KEY" -H "content-type: application/json" -d "{\"id\":\"6f1c1d4e-2b8a-4f0e-9a51-0d6c7f3b2a10\",\"start\":\"<start RFC3339 UTC>\",\"end\":\"<end RFC3339 UTC>\",\"hd_requested\":false,\"revision\":0}" http://127.0.0.1:$FP_PORT/starred-sessions`. 3. `api '/search?content_type=all&start_time=10m%20ago&limit=20&starred_only=true'`. 4. `api '/search?content_type=all&start_time=10m%20ago&limit=20'`. 5. `api '/search?starred_session_id=6f1c1d4e-2b8a-4f0e-9a51-0d6c7f3b2a10&limit=5'`.
  - Expected: step 3 returns only hits whose timestamps fall inside the starred range, each with `"starred": true`, and `pagination.total` counts only those; step 4 returns the same kinds of hits as before W3-02 with `"starred": true` on exactly the hits inside the range and `false` on the rest; step 5 matches step 3 (up to the limit). The app's search page still shows results normally.
  - Result:
- [ ] **SMK-W3-02-2** (Runtime) Parsed content from a synthetic database
  - Setup: release-dev engine build; `source scripts/dev/dev-env.sh smoke-parsed` with a new, empty `FP_DD`. Start `screenpipe.exe record --port $FP_PORT --data-dir "$FP_DD"` once so it creates the schema, stop it, then seed invented parsed content: `python -I docs/dev/smoke/W3-02-seed.py "$FP_DD/db.sqlite"`. Note the ids it prints (`chat`, `notes`, `empty_run`, `plain`, `ada`). Start the engine again on the same `FP_DD`.
  - Steps: 1. `api '/search?content_type=parsed&q=xylophone&limit=5'`. 2. `api '/search?content_type=parsed&limit=10'`. 3. `api '/search?content_type=all&q=xylophone&limit=20'`. 4. `api '/search?content_type=parsed&actor_id=<ada>&limit=5'`. 5. `api '/search?content_type=parsed&frame_id=<chat>'`. 6. `api '/search?content_type=ocr&actor_id=<ada>'`.
  - Expected: step 1 returns the `chat` and `notes` frames (newest first, `notes` first), each `"type": "Parsed"` with parser metadata (`parser_id` `smoke.parser`, `parser_version`, `run_id`), a readable `text`, typed `items` (`conversation`, `message`, `document`) and, for `chat`, `actors` naming `Ada Smoke` and `Bob Smoke`; `pagination.total` is 2. Step 2 also returns exactly those two (never `empty_run` or `plain`). Step 3 contains no `Parsed` items. Step 4 returns only `chat`, whose `items` hold Ada's message and its conversation but not Bob's message. Step 5 returns exactly `chat`. Step 6 is a 400 saying `actor_id` only applies to `content_type=parsed`. The engine log shows no `parsed search: skipping` warnings.
  - Optional (owner only, not a fixture): the same steps 1 to 5 against a *copy* of a screenpipe v2.7.104 database with parsed content, with words, actors and frames picked from that copy. Quit screenpipe, copy `~/.screenpipe/db.sqlite` (plus `-wal`/`-shm`) into another scratch `FP_DD`, work only on the copy and delete it afterwards. Skip it if you do not want to copy real data. This checks that Freenpipe reads data screenpipe wrote; the synthetic entry above is the check of record.
  - Result:
- [ ] **SMK-W3-02-3** (Runtime) Related tags and a slow search answer cleanly
  - Setup: the engine from SMK-W3-02-1, still recording.
  - Steps: 1. Tag two recent frames: `curl -s -X POST -H "Authorization: Bearer $SCREENPIPE_API_KEY" -H "content-type: application/json" -d "{\"tags\":[\"project:atlas\",\"person:ada\"]}" http://127.0.0.1:$FP_PORT/tags/vision/<frame_id>` (frame ids from `api '/search?content_type=ocr&limit=2'`), then the same with `["project:atlas","person:bob"]` on another frame. 2. `api '/search?content_type=ocr&tags=project:atlas&include_related=true'`. 3. Stop the engine, add synthetic bulk frames to its data dir: `python -I docs/dev/smoke/W3-02-seed.py "$FP_DD/db.sqlite" --bulk-frames 2000000` (about 1.3 GB; 200,000 frames took a few seconds in a Linux test run), start the engine again, and run an unbounded broad search, timing it: `api '/search?q=a&limit=20'`. Delete the data dir afterwards.
  - Expected: step 2 returns the two frames and `"related": {"person": ["person:ada", "person:bob"]}`; step 3 returns results or, after at most about 30 s, a 504 with a JSON `error` that mentions the 30 s limit; it never hangs, and the app keeps recording.
