# W2-11 Windows smoke checks

Entries follow the format in [../windows-smoke-checklist.md](../windows-smoke-checklist.md). Run
them on a W2-11 (or later) build in the isolated dev setup: `FP_DD`, port 3035,
`SCREENPIPE_API_KEY`, with the `api` and `sqlq` helpers from PLAN.md section 4. Start the engine
with `target/release-dev/screenpipe.exe record --port $FP_PORT --data-dir "$FP_DD" --disable-telemetry > "$FP_DD/engine.log" 2>&1 &`.
Capture rows land in `frames` with `device_name` `monitor_<id>`.

### W2-11 Per-monitor vision control and display layout persistence

- [ ] **SMK-W2-11-1** (Runtime) `/vision/device/status` lists every monitor with the interop keys
  - Setup: engine running as above on a PC with two monitors, default monitor selection (all).
  - Steps: 1. Wait 10 s after start. 2. `api /vision/device/status`. 3. `api /vision/list`.
  - Expected: a JSON array with one object per monitor, keys exactly `id`, `name`, `active`, `user_disabled`; `id` values match the `id`s in `/vision/list`; every row has `"active":true,"user_disabled":false`.
  - Result:
- [ ] **SMK-W2-11-2** (Runtime) Pausing one monitor stops its frames for 30 s; resuming brings them back
  - Setup: as SMK-W2-11-1. Pick the secondary monitor's id `N` from `/vision/device/status`. Keep working on both monitors (switch windows, type) during the whole check so both would normally produce frames.
  - Steps: 1. `api /vision/device/stop -X POST -H 'Content-Type: application/json' -d '{"monitor_id": N}'`. 2. `api /vision/device/status`. 3. Wait 30 s, then `sqlq "select device_name, max(timestamp), count(*) from frames where timestamp > strftime('%Y-%m-%dT%H:%M:%S', 'now', '-30 seconds') group by device_name"`. 4. `api /vision/device/start -X POST -H 'Content-Type: application/json' -d '{"monitor_id": N}'`. 5. Wait 30 s and repeat the query from step 3. 6. `api /vision/device/stop -X POST -H 'Content-Type: application/json' -d '{"monitor_id": 999999}' -i`.
  - Expected: step 1 returns `{"success":true,...}` with a message saying screen recording was paused on monitor N; step 2 shows monitor N with `"active":false,"user_disabled":true` and the other monitor unchanged; step 3 lists the other monitor but no `monitor_N` row; `engine.log` has "user paused vision capture on monitor N" and, within 5 s, at most one "monitor watcher: monitor N stays idle" line (not one every 5 s); step 4 returns success and the status row goes back to `active:true,user_disabled:false`; step 5 lists both monitors again; step 6 returns HTTP 404 with `"success":false`.
  - Result:
- [ ] **SMK-W2-11-3** (Hardware) A paused monitor stays paused across unplug/re-plug and a capture restart
  - Setup: as SMK-W2-11-2 with monitor N paused. For part B use the desktop app (UI smoke, `scripts/dev/app-dev.sh`, app port 3035).
  - Steps: Part A: 1. Unplug monitor N, wait 15 s, plug it back in, wait 15 s. 2. `api /vision/device/status`. 3. Run the frames query from SMK-W2-11-2 step 3. Part B (app): 4. Pause monitor N with the step-1 call of SMK-W2-11-2 against the app's engine. 5. Stop recording from the tray menu (its stop/start recording item), wait 10 s, then start recording again. 6. Repeat steps 2 and 3. 7. Resume monitor N with `/vision/device/start`.
  - Expected: after re-plugging and after the pause/resume cycle, monitor N (possibly under a new `id`; then the log shows "monitor <old> reappeared as monitor <new>; it stays paused by the user") is listed with `user_disabled:true`, and no `monitor_N` frames arrive; the other monitor records throughout; after step 7 frames from monitor N arrive again. Quitting and relaunching the app clears the pause (expected: in-memory only).
  - Result:
- [ ] **SMK-W2-11-4** (Runtime) `display_layout` gets a startup row, a change row per rearrangement, and nothing on an unchanged restart
  - Setup: a fresh `FP_DD`; two monitors.
  - Steps: 1. Start the engine, wait 10 s. 2. `sqlq 'select id, reason, layout_json from display_layout'`. 3. Settings > System > Display: drag the secondary monitor to the other side of the primary and apply. 4. Wait 10 s and repeat step 2. 5. Stop the engine, start it again with the same `FP_DD`, wait 10 s, repeat step 2.
  - Expected: step 2 shows exactly one row with reason `startup` and a JSON array sorted by `id`, each object with keys `id, stable_id, name, x, y, width, height, is_primary` in that order and the coordinates Windows shows for the arrangement; step 4 adds one `change` row with the new `x`/`y`; step 5 adds no row (the layout matches the newest row). `engine.log` has one "display layout snapshot stored" line per new row.
  - Result:
- [ ] **SMK-W2-11-5** (Runtime) Clicks carry `element_ancestors`, and password fields leak nothing
  - Setup: engine running as above with UI event capture on (default). Notepad and a browser page with a password field (any sign-in form).
  - Steps: 1. Click in Notepad's text area, on a menu item and on a toolbar button in File Explorer. 2. In the browser, click into the password field, type a dummy password, click a button on the form. 3. Wait 10 s. 4. `sqlq "select element_role, element_name, element_value, element_bounds, element_ancestors from ui_events where event_type='click' and element_ancestors is not null order by id desc limit 10"`.
  - Expected: rows exist for the clicks; each row's `element_role`, `element_name` and `element_bounds` describe the clicked element itself, as before this change (the toolbar button row has the button's own role, label and small bounds, not a container's); `element_ancestors` is a compact JSON array, outermost container first (for example a `Window` or `Pane` entry before `Document`/`ToolBar`/`Group` entries), each `{"role":...}` with an optional `"name"`; no entry is the desktop root; arrays are at most 16 entries and 2048 bytes; the password-field click row has no `element_value` and the dummy password appears in no column (`sqlq "select count(*) from ui_events where element_ancestors like '%<dummy>%' or element_value like '%<dummy>%'"` is 0).
