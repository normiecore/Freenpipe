# W2-13 Windows smoke checks

Entries follow the format in [../windows-smoke-checklist.md](../windows-smoke-checklist.md). Run
them on a W2-13 (or later) build in the isolated dev setup: `FP_DD`, port 3035,
`SCREENPIPE_API_KEY`, engine started with
`target/release-dev/screenpipe.exe record --port $FP_PORT --data-dir "$FP_DD" > "$FP_DD/engine.log" 2>&1 &`.
`api` is the curl helper from the checklist (`api /health | python -m json.tool` pretty-prints).

### W2-13 Health v2, vision metrics and recording coverage

- [ ] **SMK-W2-13-1** (Manual) `/health` v2 fields are present and recording coverage grows while the PC is in use
  - Setup: engine running as above for at least 2 minutes with vision and audio enabled; use the desktop normally (type, click, switch windows) for the whole check.
  - Steps: 1. `api /health > "$FP_DD/h1.json"`. 2. Keep using the desktop for 3 more minutes. 3. `api /health > "$FP_DD/h2.json"`. 4. Compare the two files.
  - Expected: both files contain, in this order, `dependencies`, `runtime`, `startup`, `unhealthy_reasons` near the top, `vision_reason`, `loop_stage`, `loop_stage_age_secs`, `audio_capture_mode` after `frame_status`, `capture_status` after `device_status_details`, and `recording_coverage` between `ui_recorder` and `pool_stats`, followed by the five `write_queue_*`/`write_pool_reopens`/`persistent_failure_signals` fields. `recording_coverage` has `recording_secs, active_stalled_secs, active_paused_secs, idle_secs, active_secs, coverage_ratio` in that order; in `h2.json` `recording_secs` is about 180 higher than in `h1.json` and `coverage_ratio` is above 0.9. `startup.phase` is `running`, `vision_reason` is `ok`, `status` is `healthy`, `unhealthy_reasons` is `[]` and `loop_stage_age_secs` is below 10. `dependencies.ffmpeg.status` is `ok` with `source` `bundled` (installed build) or `system` (dev build) and a version string, and `version_probe_error` is `null` (the bundled build prints a long configuration banner; the probe must not time out on it).
  - Result:
- [ ] **SMK-W2-13-2** (Manual) Locking the screen pauses without alarms, and idle time is counted as idle
  - Setup: as SMK-W2-13-1; note `recording_coverage.idle_secs` from `api /health`.
  - Steps: 1. Press Win+L and leave the PC locked for 7 minutes. 2. Unlock and immediately run `api /health > "$FP_DD/h3.json"`. 3. Wait one minute of normal use and run `api /health > "$FP_DD/h4.json"`.
  - Expected: in `h3.json` `frame_status` is `ok` (not `stale`) and `status` is not degraded because of vision; `recording_coverage.idle_secs` grew by roughly 2 minutes or more (the time after 5 minutes without input; `recording_secs`/`active_stalled_secs` grew by at most about 5 minutes for the start of the lock); while locked `capture_status.status` would have read `screen_locked` if no device was delivering audio. In `h4.json` `recording_secs` grows again and `loop_stage` is `heartbeat`, `trigger-wait` or `capture` with an age below 10.
  - Result:
- [ ] **SMK-W2-13-3** (Manual) `/vision/metrics` exposes the new counters and they move
  - Setup: as SMK-W2-13-1.
  - Steps: 1. `api /vision/metrics > "$FP_DD/m1.json"`. 2. Use the desktop for 1 minute. 3. `api /vision/metrics > "$FP_DD/m2.json"`.
  - Expected: both have 34 fields in the order `uptime_secs ... ocr_empty, avg_ocr_latency_ms, ocr_gate_skips, ocr_gate_crop_ocr, ocr_gate_detects, avg_ocr_gate_detect_latency_ms, ... frames_dropped_timeout, frames_dropped_error, silent_loss, silent_loss_rate, ... last_capture_loop_heartbeat_ts, capture_loop_heartbeats, capture_attempts, dedup_skips, frames_corrupt_black, frames_corrupt_green`. Between the two files `capture_loop_heartbeats` grows by at least 200 per monitor (the loop polls every 250 ms), `capture_attempts` grows, `last_capture_loop_heartbeat_ts` is within a second of now, and `silent_loss` stays 0 (or the same) on a healthy machine.
  - Result:
- [ ] **SMK-W2-13-4** (Manual) Pausing a microphone and a missing OCR language show up in `capture_status` and `vision_reason`
  - Setup: as SMK-W2-13-1 with exactly one microphone recording (check `api /audio/device/status`). For part B, a language whose Windows OCR pack is not installed (Settings > Time & language > Language & region; for example Korean when only English is installed).
  - Steps: Part A: 1. `api /audio/device/stop -X POST -H "Content-Type: application/json" -d '{"device_name":"<the microphone name from /audio/device/status>"}'`. 2. `api /health` and read `capture_status`. 3. Start the device again with `/audio/device/start` and the same body. Part B: 4. Restart the engine with `--language korean` (or the missing language). 5. Open a terminal emulator that is OCR-only (WezTerm or Alacritty) and type in it for 30 s. 6. `api /health`.
  - Expected: Part A step 2: `capture_status.status` is `mic_paused` (or `no_input_device` if the stop removed it from the paused set) with `paused_audio_devices` 1 and `active_audio_devices` 0; after step 3 it returns to `recording` or `waiting_for_voice` within 10 s. Part B: `vision_reason` is `ocr_unavailable`, `unhealthy_reasons` contains `vision_ocr_unavailable` with severity `warning`, and `status` is unchanged by it; the engine log has the "Windows OCR unavailable" warning from the OCR call.
  - Result:
- [ ] **SMK-W2-13-5** (Hardware) `/ws/metrics` reports `mic_capture_active`
  - Setup: as SMK-W2-13-1 with a working microphone; a websocket client (`bunx wscat` or the browser console: `new WebSocket("ws://127.0.0.1:3035/ws/metrics")` with the API key query or header the dev setup requires).
  - Steps: 1. Connect to `/ws/metrics` and watch a few messages while speaking. 2. Mute the microphone in Windows (Settings > System > Sound > Input > device properties > disallow, or the hardware mute switch) and watch for 10 s. 3. Unmute.
  - Expected: `audio.mic_capture_active` is `true` while the microphone delivers audio, becomes `false` within about 5 s of the device delivering only silence or stopping, and returns to `true` after unmuting. `audio.audio_level_rms` is still present.
  - Result:
- [ ] **SMK-W2-13-6** (Manual) A blocked database shows as a classified vision stall and clears afterwards
  - Setup: as SMK-W2-13-1, Python on `PATH`; keep using the desktop for the whole check.
  - Steps: 1. In a second terminal hold the database write lock for 4 minutes: `python -I -c "import sqlite3,sys,time;c=sqlite3.connect(sys.argv[1],isolation_level=None);c.execute('BEGIN EXCLUSIVE');time.sleep(240)" "$FP_DD/db.sqlite"`. 2. About 3 minutes in, run `api /health > "$FP_DD/h5.json"`. 3. When the Python command has exited, wait 1 minute and run `api /health > "$FP_DD/h6.json"`. 4. `grep "vision stalled" "$FP_DD/engine.log"`.
  - Expected: `h5.json` has `status` `degraded`, `vision_db_write_stalled` `true`, `vision_reason` `capture_stalled`, and `unhealthy_reasons` contains `vision_write_stalled` whose message ends with the sentence about frames reaching the database writer without their writes finishing (a `database` reason may appear too). The log has at most one `health_check: vision stalled (writer_not_committing): ...` line per minute while the lock is held, with `timed_out=` greater than 0 in its "since last saved frame" part. `h6.json` is `healthy` with `unhealthy_reasons` `[]`, and `recording_coverage.active_stalled_secs` grew by roughly the lock time minus two minutes.
