# W3-30 Windows smoke checks

### W3-30 Low-disk recording guard and keep-awake

The low-disk entries need a small volume to fill safely; never fill the system drive. Create a
6 GiB virtual disk once, from an elevated Command Prompt (`diskpart`, then type each line):

```
create vdisk file=C:\fp-lowdisk.vhdx maximum=6144 type=expandable
attach vdisk
create partition primary
format fs=ntfs quick label=FPLOW
assign letter=R
exit
```

(Detach later with `select vdisk file=C:\fp-lowdisk.vhdx` and `detach vdisk`, then delete the file.)
On a 6 GiB volume the guard's threshold is 2 GiB and recovery needs more than 3 GiB free.

Then run the isolated dev app with its data dir on that volume: quit the installed screenpipe,
`export FP_DD=/r/fp-lowdisk` before `source scripts/dev/dev-env.sh smoke` (port 3035, focus port
11436), then `scripts/dev/app-dev.sh`. Logs are the newest `screenpipe-app.*.log` in `R:\fp-lowdisk`.
Commands are run from the Home window's devtools console (right-click > Inspect, or
Ctrl+Shift+I) with `await window.__TAURI_INTERNALS__.invoke("<command>", { ... })`.
`fsutil volume diskfree R:` shows the free bytes ("Total free bytes").

- [ ] **SMK-W3-30-1** (UI smoke) Low space stops capture and notifies once; space coming back resumes it
  - Setup: dev app recording on the R: data dir for at least 60 s (tray shows recording, timeline has frames). `stopRecordingOnLowDisk` at its default (on).
  - Steps: 1. In a Command Prompt, read the free bytes of R: and create two filler files: `fsutil file createnew R:\fill-a.bin 1073741824` (1 GiB) and `fsutil file createnew R:\fill-b.bin <N>` with N = free bytes minus 2684354560 (so about 1.5 GiB stays free). 2. Wait up to 40 s. 3. Click the notification's "Review storage" button. 4. Open `R:\fp-lowdisk\disk-pressure-notification-state.json`. 5. Delete `R:\fill-a.bin` (about 2.5 GiB free: inside the hysteresis band) and wait 90 s. 6. Delete `R:\fill-b.bin` and wait up to 40 s. 7. Open the state file again.
  - Expected: after step 2 the log shows `disk pressure: 1.5 GiB free on the volume of ..., at or below the 2.0 GiB threshold` and `low-disk guard: stopping capture`; the tray shows recording paused, the timeline gets no new frames, `/health` still answers on 3035, and one notification "Recording paused: the disk is nearly full" quotes about 1.5 GiB and 2.0 GiB. The notice ends with "To record anyway, start recording again, or turn off "Pause recording on low disk" in the storage settings." Step 3 opens the settings window on the Storage section, where the "Pause recording on low disk" switch is on and its description quotes "2.0 GiB". The state file has `"incident_active": true` and `"notified": true`. During step 5 capture stays paused and no further notification appears. After step 6 the log shows `past the 3.0 GiB needed to re-arm` and `low-disk guard: capture started again`, a "Recording resumed" notification appears, and the timeline gets new frames. The state file now has `"incident_active": false` and `"notified": false`.
  - Result:

In step 4 recording starts and keeps running. After step 5 the log shows `low-disk guard started (..., incident in progress: true)` and capture is stopped again, but no new notification appears. After step 6 recording starts again with a "Recording resumed" notice.

- [ ] **SMK-W3-30-5** (Manual) `set_keep_awake` holds a SYSTEM power request until turned off
  - Setup: dev app running (any data dir); an elevated Command Prompt.
  - Steps: 1. Run `powercfg /requests`. 2. In devtools run `await window.__TAURI_INTERNALS__.invoke("set_keep_awake", { enabled: true })`. 3. Run `powercfg /requests` again. 4. Run `await window.__TAURI_INTERNALS__.invoke("set_keep_awake", { enabled: false })`, then `powercfg /requests`. 5. Open Task Manager > Details, add the Threads column, or use Process Explorer to list the app's threads.
  - Expected: step 2 resolves without an error and the log shows `keep-awake enabled: the computer will not sleep while idle`. In step 3 the SYSTEM section lists `[PROCESS] \Device\HarddiskVolume...\screenpipe-app.exe` (or `freenpipe.exe` in a release build) with the reason `Freenpipe keeps this computer awake (Keep computer awake is on)`; DISPLAY does not list it. After step 4 the entry is gone and the log shows `keep-awake disabled`. In step 5 a thread named `screenpipe-keep-awake` exists (Process Explorer shows thread names).
  - Result:
