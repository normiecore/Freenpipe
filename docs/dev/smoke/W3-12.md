# W3-12 Windows smoke checks

### W3-12 Dedicated Windows OCR worker and OCR availability reporting

- [ ] **SMK-W3-12-1** (Runtime) The engine log names the `screenpipe-windows-ocr` thread and OCR text lands
  - Setup: release-dev engine build of the W3-12 commit; `source scripts/dev/dev-env.sh smoke`; a Windows display language with OCR support installed (en-US has it by default).
  - Steps: 1. Start the engine with `record` on `$FP_PORT`, logging to `$FP_DD/engine.log`. 2. Open an app with little accessibility text (an image viewer showing a screenshot of text, or a game launcher) for 30 s. 3. `grep -n "screenpipe-windows-ocr" "$FP_DD/engine.log"`. 4. `curl -s -H "Authorization: Bearer $SCREENPIPE_API_KEY" "http://127.0.0.1:$FP_PORT/search?limit=5&content_type=ocr"`.
  - Expected: the log has "OCR worker thread screenpipe-windows-ocr started" and "windows OCR engine thread screenpipe-windows-ocr ready" with a `max_image_dimension`; "screen text recognition (OCR) is available" appears once at startup; the search returns recent items whose text came from the screenshot.
  - Result:
- [ ] **SMK-W3-12-2** (Runtime) With the OCR language pack removed, health says `ocr_unavailable` and accessibility capture continues
  - Setup: a test Windows account or VM where no installed language has OCR (Settings > Time & language > Language & region: remove the optical character recognition feature of every language, or use `Get-WindowsCapability -Online -Name "Language.OCR*" | Remove-WindowsCapability -Online` in an elevated PowerShell, then sign out and in). Release-dev engine, dev env.
  - Steps: 1. Start the engine with `record` on `$FP_PORT`. 2. Use Notepad and a browser for 2 minutes. 3. `curl -s -H "Authorization: Bearer $SCREENPIPE_API_KEY" http://127.0.0.1:$FP_PORT/health`. 4. `curl ... "/search?limit=5&content_type=accessibility"`. 5. Re-add the OCR language feature afterwards.
  - Expected: the log warns once that OCR is unavailable with the install hint; `/health` has `"vision_reason":"ocr_unavailable"`, `frame_status` `ok` and an `unhealthy_reasons` entry `vision_ocr_unavailable` (severity `warning`); new frames keep arriving and the accessibility search returns Notepad/browser text; there are no repeated per-frame OCR warnings.
  - Result:
- [ ] **SMK-W3-12-3** (Runtime) The `FREENPIPE_OCR_FAULT` hook gives the same health answer on a machine with OCR
  - Setup: release-dev engine, dev env, a normal machine with OCR languages.
  - Steps: 1. `FREENPIPE_OCR_FAULT=unavailable target/release-dev/screenpipe.exe record --port $FP_PORT --data-dir "$FP_DD"`. 2. After 30 s, call `/health`. 3. Restart the engine without the variable and call `/health` again after 30 s.
  - Expected: with the variable, `vision_reason` is `ocr_unavailable` and frames still arrive; without it, `vision_reason` is `ok`.
  - Result:
- [ ] **SMK-W3-12-4** (Runtime) A burst of on-demand OCR does not starve live capture
  - Setup: release-dev engine with a few minutes of recording that includes frames without stored OCR text.
  - Steps: 1. Pick 10 frame ids from `/search?content_type=accessibility&limit=10`. 2. Fire `POST /frames/<id>/text` for all 10 at once (for example a Git Bash loop with `&`). 3. Watch `$FP_DD/engine.log` and `/health` for a minute.
  - Expected: at most 2 requests run at a time (log lines "on-demand OCR started" with `inflight` 1 or 2); the others answer 503 with an `error` and `frame_id`; a retry later returns 200 with `text_positions`; capture keeps writing frames (`last_frame_timestamp` advances) and `/health` stays `ok`.
  - Result:
- [ ] **SMK-W3-12-5** (Hardware) Large and multi-monitor frames are OCRed without errors
  - Setup: a 4K or larger monitor, or two monitors; release-dev engine.
  - Steps: 1. Record for 3 minutes while switching between text-heavy windows on each monitor. 2. `grep -nE "OCR refused the image|OCR engine error|panicked" "$FP_DD/engine.log"`.
  - Expected: no matches; OCR text appears for frames from every monitor; any "OCR queue full" warning appears at most once a minute.
  - Result:
- [ ] **SMK-W3-12-6** (UI smoke) The app shows the OCR notice once per session
  - Setup: `scripts/dev/app-dev.sh` with `FREENPIPE_OCR_FAULT=unavailable` exported before launch (or the machine from SMK-W3-12-2).
  - Steps: 1. Start the app and let recording run for 2 minutes. 2. Keep it running for 5 more minutes.
  - Expected: one notification panel says screen text recognition is unavailable, with the Windows language-settings hint; it does not reappear in the same session; the app log has "showing the OCR notice" once.
