# W2-12 Windows smoke checks

Entries follow the format in [../windows-smoke-checklist.md](../windows-smoke-checklist.md). Run
them on a W2-12 (or later) build in the isolated dev setup: `FP_DD`, port 3035,
`SCREENPIPE_API_KEY`. Engine logs at `info` level carry the WGC lifecycle lines quoted below; set
`RUST_LOG=screenpipe_screen=debug` to also see the border, cursor and update-interval lines.

### W2-12 Native WinRT/D3D11 Windows Graphics Capture and frame-diff hardening

- [ ] **SMK-W2-12-1** (Hardware) `wgc_smoke` writes 10 non-black JPEGs per monitor and the monitor ids match xcap
  - Setup: Windows 10 2004 or later with every monitor awake and showing a normal desktop (not a black wallpaper); `source scripts/dev/msvc-env.sh`.
  - Steps: 1. `cargo run -p screenpipe-screen --example wgc_smoke --profile release-dev -- --out "$FP_DD/wgc-smoke"`. 2. Read the output. 3. Open a few JPEGs in `$FP_DD/wgc-smoke`.
  - Expected: one "id and stable_id match xcap" line per monitor; for every monitor a "10/10 non-black frames on the hardware device" line; the last line is `PASS` and the exit code is 0. The JPEGs show the right monitor at its native resolution with no mouse cursor drawn in and no yellow capture border (on Windows 11).
  - Result:
- [ ] **SMK-W2-12-2** (Manual) Changing display scaling while recording keeps capture going and the stable_id unchanged
  - Setup: release-dev engine running with `record --port $FP_PORT --data-dir "$FP_DD"`; note `api /vision/list` output first.
  - Steps: 1. Settings > Display: change "Scale" on one monitor (for example 100% to 150%). 2. Use that monitor for a minute (switch windows, type). 3. Change the scale back. 4. `api /vision/list`. 5. `grep -iE "WGC|frame pool|persistent capture" "$FP_DD/engine.log"`. 6. Open the timeline (or `api '/search?limit=5&content_type=ocr'`) for the last two minutes.
  - Expected: `/vision/list` shows the same `id` and `stable_id` (format `\\.\DISPLAYn_WxH_X,Y`) as before the change, matching what a pre-W2-12 build reports on this PC; frames keep arriving during and after the change; the log shows no "persistent capture disabled" line. If Windows reports a new pixel size during the switch the log has "display size changed from ... recreating the WGC frame pool" and capture continues afterwards.
  - Result:
- [ ] **SMK-W2-12-3** (Manual) Changing resolution or orientation recreates the frame pool
  - Setup: as SMK-W2-12-2.
  - Steps: 1. Settings > Display: change the resolution of one monitor (or rotate it to portrait), keep the change. 2. Wait 30 s, interacting with that monitor. 3. Revert. 4. Check `engine.log` and the newest frames.
  - Expected: one "display size changed from AxB to CxD; recreating the WGC frame pool" line per change; new frames have the new size (not cropped, not black, no garbage strip at the edge); no "persistent capture disabled" line.
  - Result:
- [ ] **SMK-W2-12-4** (Hardware) GPU reset or driver restart is recovered without restarting the engine
  - Setup: as SMK-W2-12-2. Graphics Tools optional feature installed for `dxcap`, or admin rights for Device Manager.
  - Steps: 1. Force a GPU timeout: `dxcap -forcetdr` from an elevated prompt (or press Win+Ctrl+Shift+B, or disable and re-enable the display adapter in Device Manager). 2. Keep using the desktop for a minute. 3. `grep -iE "device|WARP|WGC" "$FP_DD/engine.log"`.
  - Expected: a "D3D11 device lost (GPU reset or driver update)" line, then "created hardware D3D11 device for WGC capture" (or a WARP fallback line while the adapter is disabled, followed within about a minute of re-enabling by "hardware D3D11 device is available again"); new frames keep arriving after the reset; the engine does not crash.
  - Result:
- [ ] **SMK-W2-12-5** (Hardware) Unplugging and re-plugging a monitor closes and reopens its session
  - Setup: two monitors; engine recording as SMK-W2-12-2.
  - Steps: 1. Unplug the secondary monitor. 2. Wait 30 s. 3. Plug it back in. 4. Wait 30 s and check `engine.log` and `/vision/list`.
  - Expected: "WGC capture item for monitor N closed (monitor unplugged or session invalidated)" after unplugging; the primary monitor keeps recording throughout; after re-plugging, the monitor shows up in `/vision/list` with its old `stable_id` and a "persistent WGC capture started for monitor ..." line appears when its capture loop restarts.
  - Result:
- [ ] **SMK-W2-12-6** (Runtime) An hour of recording keeps one persistent session per monitor and steady memory
  - Setup: as SMK-W2-12-2, normal desktop use.
  - Steps: 1. Record for 60 minutes. 2. Count `grep -c "persistent WGC capture started" "$FP_DD/engine.log"` and `grep -c "persistent capture disabled" ...`. 3. Note the engine's memory in Task Manager at 5 and at 60 minutes.
  - Expected: "persistent WGC capture started" appears once per monitor plus once per return from an idle (Cold) period ("released persistent WGC session" lines pair with them); no "persistent capture disabled" line; memory at 60 minutes is within about 100 MB of the 5-minute value.
