# W3-13 Windows smoke checks

Entries follow the format in [../windows-smoke-checklist.md](../windows-smoke-checklist.md). Run
them on a W3-13 (or later) build in the isolated dev setup: `FP_DD`, port 3035,
`SCREENPIPE_API_KEY`, the engine started with
`target/release-dev/screenpipe.exe record --port $FP_PORT --data-dir "$FP_DD" > "$FP_DD/engine.log" 2>&1 &`
(add the extra flags an entry names). `api` and `sqlq` are the helpers from PLAN.md section 4. The
identity and URL-policy lines quoted below are logged at `debug`; start the engine with
`RUST_LOG=screenpipe_a11y=debug,screenpipe_engine=debug` for those entries.

### W3-13 URL domain rules, Windows window identity, input-hook watchdog

- [ ] **SMK-W3-13-1** (Manual) Calculator and Settings frames carry the real app name
  - Setup: engine recording as above with `RUST_LOG=screenpipe_a11y=debug`, plus `--ignored-windows CalculatorApp` for step 5 only (restart the engine for it).
  - Steps: 1. Open Calculator, click a few digits and wait 10 s. 2. Open Settings (Win+I), click two pages and wait 10 s. 3. `sqlq "SELECT app_name, window_name FROM frames ORDER BY id DESC LIMIT 20"`. 4. `sqlq "SELECT event_type, app_name FROM ui_events WHERE event_type IN ('app_switch','click') ORDER BY id DESC LIMIT 20"` and `grep -c "resolved the UWP app inside the frame host" "$FP_DD/engine.log"`. 5. Restart with `--ignored-windows CalculatorApp`, focus Calculator for 20 s, then repeat step 3.
  - Expected: Calculator rows have `app_name` `CalculatorApp.exe` (Windows 11; `Calculator.exe` on Windows 10) and `window_name` `Calculator`; Settings rows have `SystemSettings.exe`; no row written while either app was focused says `ApplicationFrameHost.exe`; the ui_events rows from steps 1 and 2 name the same apps; the grep count is above 0; after step 5 no new Calculator frame appears while it is focused.
  - Result:
- [ ] **SMK-W3-13-2** (Manual) A UWP frame without its app keeps the host name, never an empty one
  - Setup: engine recording with `RUST_LOG=screenpipe_a11y=debug`.
  - Steps: 1. Open Calculator, then minimise it and restore it from the taskbar three times in a row, quickly. 2. Close Calculator while it is focused. 3. `sqlq "SELECT app_name FROM frames WHERE app_name IS NULL OR app_name = '' OR app_name LIKE '%FrameHost%' ORDER BY id DESC LIMIT 10"`. 4. `grep -n "frame host shows no app window yet" "$FP_DD/engine.log" | tail -3`.
  - Expected: no row has an empty `app_name`; any row named `ApplicationFrameHost.exe` belongs to the moment the app was launching, suspended or closing (step 4 may show the matching debug lines); the engine log has no panic.
  - Result:
- [ ] **SMK-W3-13-3** (Runtime) The watchdog reinstalls input hooks that Windows removed silently
  - Setup: engine recording as above (`RUST_LOG=info` is enough); Notepad open; Sysinternals Process Explorer running as the same user.
  - Steps: 1. In Process Explorer open the `screenpipe.exe` properties, Threads tab, and find the thread named `a11y-input-hooks`. 2. Suspend that thread, type and move the mouse for about 3 s (input lags while Windows waits for the hook), then resume the thread. 3. Type a sentence in Notepad, pause 5 s, click a few times. 4. `grep -n "input hooks" "$FP_DD/engine.log"`. 5. `sqlq "SELECT event_type, text_content, timestamp FROM ui_events ORDER BY id DESC LIMIT 10"`.
  - Expected: step 4 shows one `input hooks received no callbacks while the system reported input; reinstalled them` line with `attempt=1` a few seconds after you started typing in step 3 (if Windows kept the hooks through the suspension, there is no such line and step 5 still passes); no reinstall line repeats while you keep typing normally; the sentence from step 3 (or the part typed after the reinstall) is in a `text` row and the clicks are `click` rows; no log line contains any typed text.
  - Result:
- [ ] **SMK-W3-13-4** (Runtime) Lock screen and UAC input never trigger a reinstall
  - Setup: engine recording as above.
  - Steps: 1. Lock the PC (Win+L), wait 10 s, type the password and log back in. 2. Run any program as administrator and answer the UAC prompt with the keyboard. 3. Use the PC normally for a minute. 4. `grep -n "reinstall" "$FP_DD/engine.log"`.
  - Expected: no reinstall line; typing in Notepad after step 3 shows up in `ui_events` as before.
  - Result:
- [ ] **SMK-W3-13-5** (Runtime) The input hook thread runs at highest priority and the worker keeps up
  - Setup: engine recording as above; Process Explorer.
  - Steps: 1. In the Threads tab of `screenpipe.exe`, note the base priority of `a11y-input-hooks` and that `a11y-input-worker` exists. 2. Type quickly in Notepad for 30 s while a heavy app (a browser with many tabs) loads. 3. `grep -n "fell behind" "$FP_DD/engine.log"`.
  - Expected: `a11y-input-hooks` shows base priority 10 (Highest in a normal-priority process); no noticeable input lag while typing; step 3 prints nothing (a line there would carry only a count).
  - Result:
- [ ] **SMK-W3-13-6** (Manual) Website allow list and structured block rules in Chrome and Edge
  - Setup: engine started with `--included-urls '*.wikipedia.org' --included-urls github.com --ignored-urls en.wikipedia.org` and `RUST_LOG=screenpipe_engine=debug,screenpipe_a11y=debug`; Chrome and Edge installed.
  - Steps: 1. In Chrome open `https://de.wikipedia.org`, wait 10 s, scroll. 2. Open `https://en.wikipedia.org`, wait 10 s. 3. Open `https://github.com`, wait 10 s, then `https://gist.github.com`, wait 10 s. 4. Open `https://example.com`, wait 10 s. 5. Repeat steps 1 and 4 in Edge. 6. Focus Notepad and type for 10 s. 7. `sqlq "SELECT app_name, browser_url FROM frames ORDER BY id DESC LIMIT 40"`. 8. `grep -cE "refused by the browser URL policy|not yet verified against the URL policy" "$FP_DD/engine.log"`.
  - Expected: frames exist for `de.wikipedia.org` and `github.com` (Chrome and Edge); none for `en.wikipedia.org` (block beats allow), `gist.github.com` (the github.com rule has no subdomains) or `example.com`; Notepad frames are recorded as usual; step 8 is above 0; no log line contains a blocked URL.
  - Result:
- [ ] **SMK-W3-13-7** (Manual) An unverifiable browser tab is not recorded under an allow list
  - Setup: engine started with `--included-urls example.org` and `RUST_LOG=screenpipe_engine=debug`; Firefox installed.
  - Steps: 1. In Firefox open `https://example.org`, wait 10 s. 2. Open a new empty tab (`about:newtab`) and wait 10 s. 3. `sqlq "SELECT app_name, browser_url, snapshot_path FROM frames WHERE app_name LIKE '%firefox%' ORDER BY id DESC LIMIT 20"`. 4. `grep -c "not yet verified against the URL policy" "$FP_DD/engine.log"`.
  - Expected: step 2 adds no frame; every Firefox frame from step 1 has `browser_url` on `example.org`. If Firefox's accessibility tree does not expose the URL, step 1 adds no frame either and step 4 is above 0: that is the intended fail-closed behaviour, and worth noting in the result because it means Firefox cannot be recorded under an allow list on this machine.
  - Result:
