# W2-09 open questions

Decisions taken while building response formats (`format=` / `fields=`), calendar time literals
and tag autocomplete (api-001, api-002, api-009).

## 1. The `table` format alias

- **Question:** api.md lists `table` as an alias of `tsv`; the verifier notes in vision.md
  (vision-elements-formats) found no evidence for it, and the target's error text lists only
  `json|csv|tsv`.
- **Decision:** `table` is not accepted. `format=table` gets the same 400 as any unknown format:
  ``{"error":"unknown format `table` (expected json|csv|tsv)"}``.
- **Reason:** the verified evidence is stronger, and accepting a value the error message does not
  list would make the message wrong.

## 2. How format names and field lists are read

- **Question:** the spec gives the accepted values but not case, whitespace or empty handling.
- **Decision:** `format` is trimmed and matched without regard to ASCII case (`CSV` works); absent
  or empty means `json`. The error echoes the raw value. `fields` is split on commas, each entry is
  trimmed, empty entries are dropped and a repeated path is kept once at its first position. A
  `fields` value with no path left (`fields=` or `fields=,`) means no projection. A numeric path
  segment indexes an array (`content.tags.0`). A path that names an object or array selects the
  whole value.
- **Reason:** forgiving parsing for hand-typed agent queries, while `format=json&fields=` stays
  byte-identical to the default response.

## 3. JSON rows with `fields`

- **Question:** the spec says rows become flat objects keyed by the dotted path; key order, missing
  paths and the envelope are not pinned down.
- **Decision:** each row of `data` becomes an object holding the requested paths in request order.
  A path the row lacks is left out (a present `null` stays `null`). Everything outside `data`
  (`pagination`, `cloud`) is unchanged.
- **Reason:** matches "missing paths emit omitted keys" in api-002 and keeps paging usable.

## 4. CSV/TSV columns and the flattening rule for nested values

- **Question:** without `fields`, which columns appear, and how are nested objects and arrays
  written?
- **Decision:** columns are the union of every leaf path across all rows, in first-seen order (for
  `/search` that starts with `type`, then `content.*`). Objects flatten into dotted column names
  (`bounds.left`). **Arrays are never expanded**: an array, including an array of objects, is one
  cell holding its compact JSON (`["a","b"]`). An empty object is one cell `{}`. Null and missing
  values are empty cells; numbers and booleans are written as JSON text (`0.25`, `true`). With
  `fields`, the columns are exactly the requested paths, and a path naming an object or array is
  one cell of compact JSON. Timestamp cells follow the JSON response's time zone (question 14).
- **Reason:** one fixed column per path keeps the header stable within a response and the output
  lossless; expanding arrays into numbered columns would make the header depend on the longest
  array.

## 5. Escaping and line endings

- **Question:** api-002 marks the exact escaping as inferred.
- **Decision:** CSV follows RFC 4180: CRLF after every line (header included); a cell containing a
  comma, a double quote, CR or LF is wrapped in double quotes with its quotes doubled. TSV ends lines
  with LF and has no quoting: each tab, CR, LF, or CRLF pair inside a cell becomes one space (a run
  of several is not merged). The header names go through the same escaping.
- **Reason:** RFC 4180 is lossless and what spreadsheet tools read; TSV readers generally do not
  understand quoting, so the separators are removed instead.
- **Formula injection:** cells are written exactly as captured. Screen, OCR or audio text that
  starts with `=`, `+`, `-` or `@` stays that way, so a spreadsheet that evaluates formulas would
  treat it as one. This is deliberate: the output is lossless input for agents and scripts, not an
  export meant to be opened in a spreadsheet, and prefixing such cells (the usual `'` escape) would
  change the data. An opt-in escape can be added later if a spreadsheet export is wanted.

## 6. Empty results, totals and size bounds for tabular output

- **Question:** what does an empty result look like, can a CSV caller page, and how large can a
  response get?
- **Decision:** with `fields`, an empty result is the header line alone; without `fields` no
  columns are known, so the body is empty. When the JSON carried `pagination.total`, CSV/TSV send it
  as an `x-total-count` header (the envelope itself is dropped, as the spec says). Tabular output is
  rendered from the same rows the JSON response would carry, so `limit`/`offset` bound it exactly as
  they bound JSON; there is no separate cap. `/frames/:id/elements` stays unpaged as in the base
  (W3-03 adds `limit`/`offset` there).
- **Reason:** the extra header lets agents page CSV without breaking anything the spec requires;
  bounding by the existing paging keeps the two formats consistent.

## 7. Formats that belong to W3-03

- **Question:** api-004 lists `outline`, `automation` and `preferred` for `/elements`. Rendering
  them is W3-03's work, and DECISIONS 6 parks W3-03, so they may stay unimplemented for a long
  time. Meanwhile screenpipe-era clients send them: per vision-elements-formats (MCP mapping
  `0xa0d6447`) the target's MCP element tool always sends one of the three.
- **Decision:** on `/elements` and `/frames/:id/elements` only, `outline`, `automation` and
  `preferred` (matched like the other names: trimmed, any ASCII case) are answered exactly as
  `format=json`: the default JSON body, with `fields` projected when given. That is what the
  routes sent for any `format` before this WP, when the parameter was ignored. Every other unknown
  value is still the 400, and `/search` still rejects all three, because it never served them. The
  error text keeps listing `json|csv|tsv`, the formats actually rendered. The names live in
  `PENDING_ELEMENT_FORMATS` (`routes/response_format.rs`); W3-03 takes them out of that list as it
  implements each one.
- **Reason:** DECISIONS 1 requires screenpipe-era pipes and MCP configs to work unchanged, and the
  calling tool cannot avoid the value because the MCP picks it. A JSON body is the pre-WP behaviour
  those clients already handle; a 400 on every element call would break them with no planned end.

## 8. The search cache and format validation order

- **Question:** should `format`/`fields` be part of the `/search` cache key?
- **Decision:** no. The cache holds the JSON response before shaping, so one cached query serves
  every format. `format` is validated before the query runs, so `format=xml` costs no database work.
- **Reason:** shaping is a pure function of the cached response.

## 9. Calendar time literals

- **Question:** case, whitespace, strictness of `YYYY-MM-DD`, which time zone, and DST edge cases.
- **Decision:** `today` and `yesterday` are matched without regard to case and surrounding space.
  `YYYY-MM-DD` must be exactly four, two and two digits and a real date (`2026-7-4` and `2026-02-30`
  are rejected). The zone is the machine's local zone (`chrono::Local`, which reads the Windows time
  zone settings on Windows). The value is the first instant of that local day: local midnight; the
  earlier instant when a DST change repeats midnight; the moment the clocks jump when midnight is
  skipped; and for a date the calendar skipped entirely (Samoa, 2011-12-30) the start of the next
  existing day. `yesterday` is computed on calendar dates, never as "today minus 24 hours", so 23 h
  and 25 h days keep the boundary on midnight. `tomorrow` is not accepted. Order of attempts:
  RFC 3339, calendar day, relative, so RFC 3339 input behaves exactly as before.
- **Reason:** the spec's behaviour, made precise for the zones whose DST change happens at midnight
  (Havana, historically Sao Paulo and others).

## 10. The 400 for a bad time

- **Question:** the spec gives the new error text only by offset.
- **Decision:** the text is our own and names all three families: an RFC 3339 timestamp, a local
  calendar day (`today`, `yesterday`, `YYYY-MM-DD`) and a relative time (`now`, `30m ago`). It is
  still delivered the way the base delivered bad times: axum's query rejection, a `400` with a
  `text/plain` body that embeds the message. The CLI's `--start`/`--end` share the parser, so they
  accept the same input; their help text was updated.
- **Reason:** keeps the existing error transport that clients already handle.

## 11. Tag autocomplete matching, ranking and limits

- **Question:** api-009 marks the sort order as inferred and does not say how `q` matches.
- **Decision:** `q` is trimmed and one leading `#` is dropped (tags are shown as `#name`). A tag
  matches when its name contains `q`, ignoring ASCII case; `%`, `_` and `\` in `q` match literally.
  Results are ordered: names that start with `q`, or whose part after a `namespace:` does
  (`ada` finds `person:ada`), first; then the most used (frames + audio + memories); then by name.
  An empty `q` lists the most used tags. `limit` defaults to 50 and is clamped to 1..500; a
  non-numeric `limit` is a 400.
- **Reason:** autocomplete should surface what the user is typing first, while a substring match
  still finds inner words; the frontend asks for 50 or 100 entries.

## 12. Which tags autocomplete counts

- **Question:** how to merge the junction tags with the memory JSON tags.
- **Decision:** `frame_count` and `audio_count` count `vision_tags` and `audio_tags` rows per tag;
  `memory_count` counts memories whose `tags` JSON array holds the name as a string (a name listed
  twice in one memory counts once). Names merge on exact, case-sensitive equality. A memory whose
  `tags` is not a valid JSON array is ignored rather than failing the call. A `tags` row with no
  remaining uses (all its junction rows were removed) is not listed. Case-insensitive matching is
  ASCII only (SQLite `LIKE`).
- **Reason:** the counts the frontend renders, without letting one malformed memory break the
  picker.

## 13. Where `/tags/autocomplete` is mounted

- **Question:** the handler belongs in `routes/content.rs` (target `content::autocomplete_tags`),
  but new routes mount through `routes/ext.rs`.
- **Decision:** `content.rs` gains `documented()`/`router()` like a feature module, and `ext.rs`
  lists `content` once. The route needs the API key like other reads. Its OpenAPI response type is
  named `TagAutocompleteItem` (the target's name for it was not recovered).
- **Reason:** keeps `server.rs` untouched and the operation id matching the target's handler path.

## 14. Timestamps in tabular output

- **Question:** the base timestamp middleware (`routes/timezone.rs`) rewrites UTC timestamps to
  local time with an offset, unless the request has `timezone=utc`, but only in `application/json`
  bodies. Should CSV/TSV cells follow it?
- **Decision:** yes. The middleware marks, for the duration of the request, whether local time is
  wanted (a tokio task-local read by `timezone::localize_requested`). When it is, tabular rendering
  converts every string value the JSON rewrite would convert (same rules, `localize_timestamp`;
  values inside arrays too, keys never) before writing cells. So `/search?format=csv` cells carry
  the same timestamp text as the JSON response, and `timezone=utc` keeps UTC `...Z` text in both.
  Outside the middleware (unit tests, direct calls) cells stay UTC, as JSON does there.
- **Reason:** the same query should report the same times whatever the format; the request-scoped
  flag keeps the `timezone=utc` decision in the middleware instead of adding a parameter to every
  query struct.
