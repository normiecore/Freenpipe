# W2-26 open questions

Decisions taken while building engine supervision (shell-012) and the shared teardown and safe
relaunch (shell-013). Each one is the worker's call; the owner can overturn any of them.

## 1. Where the teardown and relaunch code lives

- **Question:** shell-013 names a new `process_exit` module; PLAN.md and the W1-03 seam declare
  `relaunch.rs`.
- **Decision:** the teardown, the quit gate, the force-exit and the safe relaunch all live in
  `src-tauri/src/relaunch.rs`. No `process_exit.rs` is added.
- **Reason:** the W1-03 seam already declares the module in `main.rs`; adding a second module would
  need another `mod` line in a shared hotspot file for no gain.

## 2. What "healthy", "unhealthy" and "foreign" mean for a port holder

- **Question:** the spec says a "screenpipe-like" holder that is unhealthy may be killed. The plan
  and the coordinator say only an unhealthy instance of Freenpipe's own executable may be killed.
- **Decision:** a holder is *ours* only when its image path equals `std::env::current_exe()`
  (case-insensitive and verbatim-prefix-insensitive on Windows). Ours and silent (no HTTP answer
  to `GET /health` within 3 s, twice, 2 s apart) is `unhealthy` and is the only class ever
  terminated. Ours and answering anything is `healthy`. Not ours and answering with a screenpipe
  health document is `healthy`; anything else not ours is `foreign`. That includes an unresponsive
  copy of the installed screenpipe and any process whose image path cannot be read.
- **Reason:** decision 7 (commercial-ready builds) and the owner's capture-reliability priority:
  terminating someone else's process is never acceptable, and a name match ("screenpipe.exe") is not
  proof of identity because Freenpipe's CLI and the vendor's share that name.

## 3. Guarding against PID reuse and busy instances before terminating

- **Question:** how sure must Freenpipe be before it terminates its own unresponsive copy?
- **Decision:** the holder must fail a confirming probe 2 s after the first, and right before the
  kill its PID must still resolve to our executable and still listen on the port. Healthy or
  foreign holders on the same port block the reclaim entirely (killing ours would not free it).
  At most three classify/terminate rounds run; then the user is told the port could not be freed.
- **Reason:** a busy instance gets a second chance, and a PID reused between the probe and the kill
  can never be hit.

## 4. Which netstat listing and kill method

- **Question:** the target runs `netstat -ano -p tcp` and `taskkill /PID n /F`.
- **Decision:** Windows uses exactly that listing (IPv4 TCP, which is what the engine binds) and
  `taskkill /F`. macOS and Linux use `lsof -nP -iTCP:<port> -sTCP:LISTEN -Fpc` and `kill -TERM`, then
  `kill -KILL` after 2 s. Image paths come from `QueryFullProcessImageNameW` on Windows (limited
  query rights, which work for most elevated processes) and from `sysinfo` elsewhere.
- **Reason:** matches the observed behaviour on the primary platform and keeps the other platforms
  working with tools they already ship.

## 5. Focusing another instance

- **Question:** "try to focus it" when a healthy screenpipe holds the port. Which instance?
- **Decision:** only a healthy copy of our own executable is asked to show its window, through
  `POST /focus` on the control port, and only when that same PID owns the control port. A healthy
  vendor screenpipe is never contacted; the notification asks the user to quit it or change the port.
- **Reason:** decision 1 says Freenpipe does not run alongside the installed screenpipe; poking its
  windows would be confusing and serves no purpose.

## 6. Watchdog constants and timeouts

- **Question:** the spec gives suggested constants (check every 5 s, respawn after 3 misses, at most
  3 respawns per 10 minutes) but the health loop runs at 1 Hz and `/health` can time out for 10-20 s
  under database-pool pressure while recording continues.
- **Decision:** the watchdog samples the 1 Hz health result every 5 s. Three consecutive samples
  where the engine is absent or refuses the connection trigger a respawn; samples where our engine
  exists but `/health` only times out (or returns an unparseable body) need twelve in a row (60 s).
  At most 3 respawns per 10 minutes; a failed respawn retries after 1, 2, 4, then 5 minutes. No
  sample is taken in the first 30 s after launch, during boot phases, while a start is in flight,
  or while the app is quitting.
- **Reason:** keeps the spec's constants for a dead engine without killing a healthy engine that is
  only slow, which is the failure the base app's 30-sample debounce was written for.

## 7. What "recording is intended" means

- **Question:** the spec respawns only "while the user intends recording ON", but the app has no
  explicit intent flag.
- **Decision:** a process-wide flag that starts on (the app starts recording at launch).
  `spawn_screenpipe` and `start_capture` set it; `stop_capture` (pause) and `stop_screenpipe` clear
  it; the teardown clears it. A paused recording is never respawned, even if the engine dies.
- **Reason:** respawning starts capture as well as the server, so respawning while paused would
  silently resume recording, which is a privacy problem.

## 8. Teardown order

- **Question:** shell-013 lists: stop capture, drain HTTP (3 s), stop schedulers, shut down audio
  (15 s), close SQLite pools, stop Pi.
- **Decision:** stop capture (6 s), shut the engine down (pipe scheduler, workers and the audio
  manager with its 15 s cap; 17 s), drain the engine's HTTP runtime (3 s), close the SQLite pools
  (3 s), stop Pi sessions (3 s), all clipped to a 25 s overall budget. A guard thread ends the
  process 3 s after the budget even if the teardown task is wedged.
- **Reason:** the engine's HTTP server, scheduler and audio tasks all live on one runtime and the
  engine exposes no separate graceful-HTTP hook. Draining HTTP first would cancel the audio tasks
  before the audio manager can release its GPU resources (the macOS ggml abort the old code warns
  about). Draining after the audio shutdown keeps that safe; adding an HTTP shutdown hook would need
  an engine change in a hotspot file.

## 9. When a previous engine generation has "drained"

- **Question:** a new generation may open the database only after the previous one drained. How is
  that observed?
- **Decision:** every shut-down `ServerCore` leaves a weak handle to its `DatabaseManager`. The
  generation has drained once nothing holds that manager any more (its runtime, HTTP server, workers
  and write queue are gone, which also closes its pools). A new start waits up to 15 s for that, then
  logs a warning and starts anyway. Engine threads started by `spawn_screenpipe` wake at once when a
  generation retires and stop their runtime with a 10 s ceiling.
- **Reason:** works for every generation, including the boot-time one that `main.rs` starts, without
  editing the startup region. Refusing to start after the timeout would leave recording down
  forever behind a leaked handle.

## 10. Which data directory the replacement gets

- **Question:** the relaunch passes `SCREENPIPE_DATA_DIR=<active data dir>`.
- **Decision:** it passes the base directory this process uses (`default_screenpipe_data_dir()`,
  which already honours an inherited `SCREENPIPE_DATA_DIR`), not the custom recording directory
  from settings.
- **Reason:** in Freenpipe the settings store lives in the base directory and points at the custom
  recording directory. Passing the recording directory would make the replacement read a different
  (usually empty) settings store.

## 11. Arguments of the replacement process

- **Question:** should the relaunch forward the original command line?
- **Decision:** no arguments are forwarded.
- **Reason:** the original arguments can hold a deep link (which would fire again) or `--autostart`
  (which would contradict `SCREENPIPE_RELAUNCH_HOME_VISIBLE=true`). The "relaunch deferred because
  the recording mode could not be carried over" case has nothing to carry in Freenpipe yet; when a
  search-only or headless mode lands, it should pass its mode to the replacement explicitly.

## 12. Honouring `SCREENPIPE_RELAUNCH_HOME_VISIBLE` without editing the startup region

- **Question:** the replacement should start with Home closed when the old instance had it closed,
  but the startup window code in `main.rs` belongs to W2-27.
- **Decision:** `relaunch::on_ready` runs at `RunEvent::Ready` and hides Home when the flag is
  `false` (log `startup_window_restore outcome=home_kept_closed`). Home may flash briefly.
- **Reason:** keeps this WP's `main.rs` edit inside the `RunEvent` handler. W2-27 can remove the
  flash by checking `relaunch::parse_home_visible` before it shows Home (follow-up).

## 13. `restart_after_screen_recording_permission` off macOS

- **Question:** what should the command do on Windows and Linux?
- **Decision:** on macOS it safe-relaunches with Home visible. Elsewhere it returns `Ok` without
  doing anything.
- **Reason:** only macOS needs a new process to see a screen-recording grant; frontend.md says
  macOS-only commands compile everywhere and are inert elsewhere.

## 14. Debug commands

- **Question:** the acceptance check kills the engine "via a debug command", and safe relaunch has no
  user-facing trigger on Windows yet.
- **Decision:** two Freenpipe-only commands, `debug_kill_engine` and `debug_relaunch_app`, refuse to
  run unless the build is a debug build or developer mode (`devMode`) is on.
  `debug_kill_engine` stops the engine's runtime and puts the dead `ServerCore` back in state, which
  is what a crashed engine thread leaves behind.
- **Reason:** gives the smoke checks a trigger without exposing a footgun to ordinary users.

## 15. Analytics names

- **Question:** the target records `app_relaunch_requested` and `relaunch_window_state`.
- **Decision:** both are local log lines only.
- **Reason:** telemetry stays off (CLAUDE.md).
