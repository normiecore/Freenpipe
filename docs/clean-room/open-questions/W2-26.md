# W2-26 open questions

Decisions taken while building engine supervision (shell-012) and the shared teardown and safe
relaunch (shell-013). Each one is the worker's call; the owner can overturn any of them.

## 1. Where the teardown and relaunch code lives

- **Question:** shell-013 names a new `process_exit` module; PLAN.md and the W1-03 seam declare
  `relaunch.rs`.
- **Decision:** the teardown, the quit gate, the force-exit and the safe relaunch all live in
  `src-tauri/src/relaunch.rs`. No `process_exit.rs` is added.
- **Reason:** the W1-03 seam already declares the module in `main.rs`; adding a second module would
  need another `mod` line in a shared hotspot file for no gain.

## 2. What "healthy", "unhealthy" and "foreign" mean for a port holder

- **Question:** the spec says a "screenpipe-like" holder that is unhealthy may be killed. The plan
  and the coordinator say only an unhealthy instance of Freenpipe's own executable may be killed.
- **Decision:** a holder is *ours* only when its image path equals `std::env::current_exe()`
  (case-insensitive and verbatim-prefix-insensitive on Windows). Ours and silent (no HTTP answer
  to `GET /health` within 3 s, twice, 2 s apart) is `unhealthy` and is the only class ever
  terminated. Ours and answering anything is `healthy`. Not ours and answering with a screenpipe
  health document is `healthy`; anything else not ours is `foreign`. That includes an unresponsive
  copy of the installed screenpipe and any process whose image path cannot be read.
- **Reason:** decision 7 (commercial-ready builds) and the owner's capture-reliability priority:
  terminating someone else's process is never acceptable, and a name match ("screenpipe.exe") is not
  proof of identity because Freenpipe's CLI and the vendor's share that name.

## 3. Guarding against PID reuse and busy instances before terminating

- **Question:** how sure must Freenpipe be before it terminates its own unresponsive copy?
- **Decision:** the holder must fail a confirming probe 2 s after the first, and right before the
  kill its PID must still resolve to our executable and still listen on the port. Healthy or
  foreign holders on the same port block the reclaim entirely (killing ours would not free it).
  At most three classify/terminate rounds run; then the user is told the port could not be freed.
- **Reason:** a busy instance gets a second chance, and a PID reused between the probe and the kill
  can never be hit.

## 4. Which netstat listing and kill method

- **Question:** the target runs `netstat -ano -p tcp` and `taskkill /PID n /F`.
- **Decision:** Windows uses exactly that listing (IPv4 TCP, which is what the engine binds) and
  `taskkill /F`. macOS and Linux use `lsof -nP -iTCP:<port> -sTCP:LISTEN -Fpc` and `kill -TERM`, then
  `kill -KILL` after 2 s. Image paths come from `QueryFullProcessImageNameW` on Windows (limited
  query rights, which work for most elevated processes) and from `sysinfo` elsewhere.
- **Reason:** matches the observed behaviour on the primary platform and keeps the other platforms
  working with tools they already ship.

## 5. Focusing another instance

- **Question:** "try to focus it" when a healthy screenpipe holds the port. Which instance?
- **Decision:** only a healthy copy of our own executable is asked to show its window, through
  `POST /focus` on the control port, and only when that same PID owns the control port. A healthy
  vendor screenpipe is never contacted; the notification asks the user to quit it or change the port.
- **Reason:** decision 1 says Freenpipe does not run alongside the installed screenpipe; poking its
  windows would be confusing and serves no purpose.

## 6. Watchdog constants and timeouts

- **Question:** the spec gives suggested constants (check every 5 s, respawn after 3 misses, at most
  3 respawns per 10 minutes) but the health loop runs at 1 Hz and `/health` can time out for 10-20 s
  under database-pool pressure while recording continues.
- **Decision:** the watchdog samples the 1 Hz health result every 5 s. Three consecutive samples
  where the engine is absent or refuses the connection trigger a respawn; samples where our engine
  exists but `/health` only times out (or returns an unparseable body) need twelve in a row (60 s).
  At most 3 respawns per 10 minutes; a failed respawn retries after 1, 2, 4, then 5 minutes. No
  sample is taken in the first 30 s after launch, during boot phases, while a start is in flight,
  or while the app is quitting.
- **Reason:** keeps the spec's constants for a dead engine without killing a healthy engine that is
  only slow, which is the failure the base app's 30-sample debounce was written for.

## 7. What "recording is intended" means

- **Question:** the spec respawns only "while the user intends recording ON", but the app has no
  explicit intent flag.
- **Decision:** a process-wide flag that starts on (the app starts recording at launch). Only the
  user-facing entry points set it: the `spawn_screenpipe` command and `start_capture`.
  `stop_capture` (pause) and `stop_screenpipe` clear it; the teardown clears it. A paused recording
  is never respawned, even if the engine dies. The watchdog's respawn shares the engine start
  (`start_engine`) but never touches the flag, and every engine thread (the boot one included)
  starts capture only while the flag is on and no quit is under way, then checks both again when it
  stores the new session, under the capture and server locks. `stop_capture` clears the flag before
  it takes the capture lock, so a pause made at any moment of a respawn either finds the new session
  and stops it or is seen when the session would be stored, and the session is stopped instead. The
  engine itself stays up (search and pipes keep working); the tray shows the pause.
- **Reason:** respawning starts capture as well as the server, so respawning while paused would
  silently resume recording, which is a privacy problem. The first version set the flag inside the
  shared start, so a pause made during a respawn's 20-odd seconds was undone by the respawn itself.

## 8. Teardown order

- **Question:** shell-013 lists: stop capture, drain HTTP (3 s), stop schedulers, shut down audio
  (15 s), close SQLite pools, stop Pi.
- **Decision:** stop capture (6 s), shut the engine down (21 s), drain the engine's HTTP runtime
  (3 s), close the engine's read pool (3 s), stop Pi sessions (3 s), all clipped to a 29 s overall
  budget. A guard thread ends the process 3 s after the budget (32 s) even if the teardown task is
  wedged. The engine limit is `ServerCore::shutdown`'s own worst case on a normal machine: the
  background workers' 5 s grace, then the pipe scheduler (aborted, which lands at once; 1 s is
  allowed), then the audio manager's 15 s cap. The 5 s and 15 s are constants in `server_core.rs`
  that the budget is computed from, so a test fails if they change without it. Only a scheduler that
  ignores its abort or a pipe call holding the manager lock can still overrun the step, which then
  counts as critical. The engine step also waits for any engine another task is starting or
  stopping at that moment (see 29). The write pool is private to the database manager and closes
  with it, so the pool step closes only the read pool; it logs `all SQLite pools of the engine are
  closed` only when `http_drain` saw the manager go, and `engine read pool closed; the write pool
  stays open ...` otherwise. Adding a close for both pools would be a change in `screenpipe-db`,
  outside this WP.
- **Reason:** the engine's HTTP server, scheduler and audio tasks all live on one runtime and the
  engine exposes no separate graceful-HTTP hook. Draining HTTP first would cancel the audio tasks
  before the audio manager can release its GPU resources (the macOS ggml abort the old code warns
  about). Draining after the audio shutdown keeps that safe; adding an HTTP shutdown hook would need
  an engine change in a hotspot file.

## 9. When a previous engine generation has "drained"

- **Question:** a new generation may open the database only after the previous one drained. How is
  that observed?
- **Decision:** every shut-down `ServerCore` leaves a weak handle to its `DatabaseManager`. The
  generation has drained once nothing holds that manager any more (its runtime, HTTP server, workers
  and write queue are gone, which also closes its pools). A new start waits up to 8 s for that, then
  logs a warning and starts anyway. Engine threads started by `spawn_screenpipe` wake at once when a
  generation retires and stop their runtime with a 10 s ceiling. `CaptureSession::stop` now aborts
  the speaker-identification loop, which had no shutdown signal and outlived every capture session
  started from a Tauri command.
- **Reason:** works for every generation, including the boot-time one that `main.rs` starts, without
  editing the startup region. Refusing to start after the timeout would leave recording down
  forever behind a leaked handle. One leak remains outside this WP: the engine's auto-naming loop in
  `start_speaker_identification` (`calendar_speaker_id.rs`) is spawned detached and also holds the
  database; until it gets a shutdown signal, a restart after a paused-and-resumed capture can wait
  the full 8 s.

## 10. Which data directory the replacement gets

- **Question:** the relaunch passes `SCREENPIPE_DATA_DIR=<active data dir>`.
- **Decision:** it passes the base directory this process uses (`default_screenpipe_data_dir()`,
  which already honours an inherited `SCREENPIPE_DATA_DIR`), not the custom recording directory
  from settings.
- **Reason:** in Freenpipe the settings store lives in the base directory and points at the custom
  recording directory. Passing the recording directory would make the replacement read a different
  (usually empty) settings store.

## 11. Arguments of the replacement process

- **Question:** should the relaunch forward the original command line?
- **Decision:** no arguments are forwarded.
- **Reason:** the original arguments can hold a deep link (which would fire again) or `--autostart`
  (which would contradict `SCREENPIPE_RELAUNCH_HOME_VISIBLE=true`). The "relaunch deferred because
  the recording mode could not be carried over" case has nothing to carry in Freenpipe yet; when a
  search-only or headless mode lands, it should pass its mode to the replacement explicitly.

## 12. Honouring `SCREENPIPE_RELAUNCH_HOME_VISIBLE` without editing the startup region

- **Question:** the replacement should start with Home closed when the old instance had it closed,
  but the startup window code in `main.rs` belongs to W2-27.
- **Decision:** `relaunch::on_ready` runs at `RunEvent::Ready` and hides Home when the flag is
  `false` (log `startup_window_restore outcome=home_kept_closed`). Home may flash briefly.
- **Reason:** keeps this WP's `main.rs` edit inside the `RunEvent` handler. W2-27 can remove the
  flash by calling `relaunch::relaunch_home_visible()` before it shows Home (follow-up). That
  function only returns the value `main` captured at start-up; it never reads the environment (see
  23).

## 13. `restart_after_screen_recording_permission` off macOS

- **Question:** what should the command do on Windows and Linux?
- **Decision:** on macOS it safe-relaunches with Home visible. Elsewhere it returns `Ok` without
  doing anything.
- **Reason:** only macOS needs a new process to see a screen-recording grant; frontend.md says
  macOS-only commands compile everywhere and are inert elsewhere.

## 14. Debug commands

- **Question:** the acceptance check kills the engine "via a debug command", and safe relaunch has no
  user-facing trigger on Windows yet.
- **Decision:** two Freenpipe-only commands, `debug_kill_engine` and `debug_relaunch_app`, refuse to
  run unless the build is a debug build or developer mode (`devMode`) is on.
  `debug_kill_engine` stops the engine's runtime and puts the dead `ServerCore` back in state, which
  is what a crashed engine thread leaves behind.
- **Reason:** gives the smoke checks a trigger without exposing a footgun to ordinary users.

## 15. Analytics names

- **Question:** the target records `app_relaunch_requested` and `relaunch_window_state`.
- **Decision:** both are local log lines only.
- **Reason:** telemetry stays off (CLAUDE.md).

## 16. Edits outside the owner paths: `tray.rs` and `notifications/client.rs`

- **Question:** the plan's owner paths do not list `tray.rs` or `notifications/client.rs`, but both
  changed.
- **Decision:** `tray.rs`: the Quit item now calls `relaunch::request_quit` instead of its own stop
  sequence (and drops the unused `RecordingState` import). `notifications/client.rs`: `/notify` is
  posted to `SCREENPIPE_FOCUS_PORT` when it is set instead of a hard-coded 11435.
- **Reason:** shell-013 asks for one teardown used by every way the app ends; leaving the tray's
  copy would keep an unbounded quit path next to the bounded one. The dev builds run the control
  server on 11436, so the hard-coded port sent dev notifications to an installed screenpipe (or
  nowhere), which made the port-conflict notices impossible to smoke-test in isolation.

## 17. A pending `app.restart()` and an overrunning exit teardown

- **Question:** the exit teardown force-exits when it overruns, which on macOS and Linux would kill
  the process before Tauri starts the replacement for an update or rollback.
- **Decision:** the `ExitRequested` handler records a restart request (`RESTART_EXIT_CODE`) and the
  binary and arguments Tauri would start. After the exit teardown: no overrun, or an overrun only in
  `http_drain`, `sqlite_pools` or `pi`, returns to Tauri (logged), which cleans up and restarts when
  a restart is pending, and simply exits otherwise (see 24). An overrun in `capture` or `engine` (or
  a panicked teardown thread) runs `cleanup_before_exit` and force-exits with status 1, starting the
  pending replacement itself first when there is one. The guard thread that ends a wedged teardown
  also starts the replacement first when a restart is pending.
- **Reason:** returning into C++ static destructors while capture or the audio pipeline is half
  stopped is what the force-exit exists to avoid, but an update must never end with no app at all.
  The target's own log lines (a pending restart that spawns the replacement and force-exits) match
  this. The replacement gets the same arguments Tauri would pass; on macOS it is started from the
  current binary path rather than through `Info.plist` (Freenpipe's bundle executable name does not
  change between versions).

## 18. When a safe relaunch releases the tray icon and the single-instance lock

- **Question:** Tauri's restart calls `cleanup_before_exit` before it starts the new process. Should
  the safe relaunch do the same?
- **Decision:** the relaunch starts the replacement first, then (on the main thread, waiting up to
  2 s) releases the single-instance lock and runs `cleanup_before_exit`, then force-exits. If the
  main thread does not answer, the lock is still released from the relaunch task (closing the mutex
  handle frees it); the release runs at most once. If the replacement exits within 1 s (what it does
  when it still found the lock and handed its arguments to us), it is started once more.
- **Reason:** when the replacement cannot be started this instance keeps running, and it still needs
  its tray icon (the only way to quit it) and its lock; releasing the lock early would also make the
  plugin close the same handle a second time at exit. The release takes milliseconds while the
  replacement needs far longer to reach its single-instance check, and the 1 s watch covers the rare
  case where it gets there first. A hard exit never reaches the plugin's own `RunEvent::Exit`
  release, so without this the replacement could defer to a dying process on Windows and macOS.

## 19. Which holder a `/health` probe describes

- **Question:** one probe of `127.0.0.1:<port>` was applied to every listener, so an answer from
  one holder (often this process's own closing engine) could classify another.
- **Decision:** the probe is used only when exactly one process listens and it is not this one.
  While this process is one of several listeners nothing is decided: each round waits up to 10 s for
  it to let go and then looks again; if it never does, the others are reported without a probe and
  none is touched. With several other listeners, a copy of our executable is `unverified` (a new
  class, never terminated) and anything else is `foreign`. The confirming look before a kill repeats
  the whole classification, so a listener that appears in between also stops the kill.
- **Reason:** "never let one holder's answer classify another" is the only rule that keeps the kill
  path safe when several sockets share a port (Windows lets a loopback bind sit next to a wildcard
  one). A shared port is rare, and blocking with a clear notice is better than guessing.

## 20. How port-conflict notices reach the user

- **Question:** the conflict notices went through `notifications::client`, which posts to the
  control port, including for a conflict on the control port itself.
- **Decision:** a control-server conflict is logged and shown as an operating-system notification
  (`tauri-plugin-notification`), never posted to the busy port. An engine-port conflict uses the
  in-app panel only while this process's control server is bound (a flag held by the running server)
  and the OS notification otherwise. The wording names another screenpipe-family app (the
  `screenpipe_family` field) separately from other programs.
- **Reason:** posting to a port someone else holds hands our message to that process. The OS
  notification needs no port and is already used for update notices.

## 21. Time limits for a watchdog respawn

- **Question:** a respawn whose stop never returned kept the watchdog's "respawn in flight" flag set
  forever, which turned the watchdog off.
- **Decision:** the stop half is limited to 45 s and the start half to 30 minutes (the same ceiling a
  caller of `spawn_screenpipe` gives an in-flight start; a large migration takes minutes). A timeout is
  reported as a failed respawn, so the watchdog's 1/2/4/5-minute backoff continues, and the start
  flags are cleared so the next attempt is not mistaken for a start in progress. A timed-out step is
  cancelled, not left running in the background.
- **Reason:** a stop that keeps running detached could later take the next generation's server out of
  state; cancelling it is the safer of the two.

## 22. Boot phases a failed start leaves behind

- **Question:** a start that failed without calling `set_boot_error` (for example `ServerCore::start`
  failing to create the data directory) left a phase such as `starting`, which the watchdog reads as a
  boot in progress forever.
- **Decision:** `ServerCore::start` now sets the boot error when it cannot create the data directory
  (a small edit outside the owner paths). `spawn_screenpipe` ends every other failed start with
  `fail_boot_if_pending`, which writes an error only over a non-terminal phase (a capture failure after
  the server came up keeps `ready`), and also clears the start flags when its thread cannot be
  spawned. Independently, the watchdog treats a non-terminal phase older than 30 minutes as abandoned
  (logged once). A panic in an engine thread is handled where it happens: `spawn_screenpipe` sees its
  result channel dropped and clears the start flags, and the boot-time thread in `main.rs` carries a
  `StartPanicGuard` that, when the thread unwinds before its start is over, clears `is_starting` and
  calls `fail_boot_if_pending`. Without it the flag stayed set with no engine in state, which the
  watchdog reads as a start in progress (and `respawn_engine` skips on) forever. The guard is
  disarmed once the start is over, so a later panic cannot clear a newer start's flag. A start that
  hangs rather than panics keeps the watchdog off, as it keeps a caller of `spawn_screenpipe`
  waiting; a respawn would race it on the database.
- **Reason:** both halves are needed: the first fixes the known paths, the ceiling covers a phase that
  a start left behind in a way nobody anticipated. The phase ceiling alone did not cover the start
  flag, which is why the panic guard exists.

## 23. Clearing `SCREENPIPE_RELAUNCH_HOME_VISIBLE`

- **Question:** the replacement kept the variable in its environment, so anything it started later
  (Tauri's restart, the update installer's relaunch) inherited a stale relaunch flag.
- **Decision:** `relaunch::capture_relaunch_flag()` reads the variable, removes it from the process
  environment and caches the answer. It is the first call in `main`, before any thread or async
  runtime exists (see 27). `relaunch_home_visible()` and `on_ready` only read the cached answer.
  `SCREENPIPE_DATA_DIR` stays set.
- **Reason:** the flag describes one hand-over and must not outlive it, while the data directory is
  the process's real configuration and should reach its children. Removing an environment variable
  while another thread may call C `getenv` (a library, a runtime worker) is undefined behaviour on
  Linux and macOS, so the removal happens while the process still has a single thread; the first
  version removed it at `RunEvent::Ready`, when many threads were already running.

## 24. Which late teardown steps justify a forced exit

- **Question:** an ordinary quit can see `http_drain` time out: after a pause and resume a detached
  engine task (the auto-naming speaker loop) keeps holding the `DatabaseManager`, and the boot
  generation's keep-alive loop noticed a retired generation only on its 5 s poll. Tray quit then
  exited with status 1, and the bare `RunEvent::Exit` path hard-exited without
  `cleanup_before_exit`, which leaves a dead tray icon on Windows.
- **Decision:** a late `http_drain`, `sqlite_pools` or `pi` step is logged and never forces the
  exit, on every path. Tray quit leaves with status 0 through `app.exit(0)` on Windows (`_exit(0)`
  on Unix, as for a clean quit); `RunEvent::Exit` returns to Tauri, which finishes its cleanup and
  exits (or restarts); a safe relaunch logs it and goes on with the replacement. Only a `capture` or
  `engine` step that did not stop in time, or a panicked teardown thread, forces the exit with status
  1, after `cleanup_before_exit` (on the main thread; tray quit waits up to 2 s for it). The guard
  thread that ends a teardown that is itself stuck keeps status 1. The decision is a pure function
  (`TeardownSeverity::of`, `quit_exit`, `exit_follow_up`) covered by unit tests. The boot
  generation's keep-alive loop now uses the same `hold_engine_generation` as the generations
  `spawn_screenpipe` starts, so a retire notification wakes it at once.
- **Reason:** once capture and audio are stopped there is no native work left for a destructor to
  trip over, which is the only reason the forced exit exists. A database handle that is still open is
  released by the OS with the process, and a Pi process that did not stop in time is not stopped any
  better by a forced exit. Forcing the exit for them would only add the stale tray icon and a failure
  status for a quit that worked. The detached speaker task itself is engine code outside this WP
  (follow-up).

## 25. Telling a step's own limit from the overall budget in the log

- **Question:** the log used one wording for a step that used up its own limit and for a step cut
  short because the 25 s overall budget ran out, so a tester could not tell which limit was hit.
- **Decision:** a late step is recorded as `TimedOut` (its own limit ended it) or `OutOfBudget` (the
  budget left was shorter than its own limit, or already gone). Each has its own warning line
  (`hit its own <n>ms limit`, `cut off by the overall budget after <n>ms`, `not run: the overall
  budget was already used up`), and the closing line either says the teardown finished within its
  overall budget and names the steps over their own limit, or says it ran out of the overall budget
  and names the steps of each kind. SMK-W2-26-4 lists the lines.
- **Reason:** the two cases point at different fixes (one slow step versus a budget that is too small
  for the machine), so the log should not make the tester guess.

## 26. How a respawn learns that its start found the port held

- **Question:** the respawn read a process-wide "last engine block" to decide between `PortHeld` and
  `Failed`. A value left over from an earlier attempt, or written by a concurrent start, could make it
  report `PortHeld` for a start that failed for another reason (or the other way round).
- **Decision:** the body of `spawn_screenpipe` is now `start_engine`, which returns a typed
  `StartError`. Only its own port check returns `StartError::PortHeld`, and the respawn maps that to
  `RespawnError::PortHeld`; every other failure is `Failed`. The shared value and the calls that
  cleared it (`spawn_screenpipe` on success, the watchdog's port-freed and recovered actions) are
  gone. The Tauri command still returns the message string.
- **Reason:** the classification belongs to one start attempt; carrying it in that attempt's return
  value cannot go stale or be overwritten.

## 27. Edits in `main.rs` outside the `RunEvent` handler

- **Question:** the relaunch flag must be removed before any thread starts, but `#[tokio::main]`
  builds its multi-threaded runtime, worker threads included, before the first statement of `main`
  runs. W2-27 owns the startup region.
- **Decision:** `main` is now a plain function that calls `relaunch::capture_relaunch_flag()` and then
  `app_main()`, the former `#[tokio::main] async fn main` with its body unchanged. In the boot engine
  thread the 5 s keep-alive loop is replaced by `recording::hold_engine_generation` and the runtime is
  stopped with `recording::stop_engine_runtime`, as for the generations `spawn_screenpipe` starts.
  Its phase 1 and phase 2 (server core, then capture, then storing both) are now one call to
  `recording::start_generation`, the same code the `spawn_screenpipe` thread runs (see 7, 28 and 29),
  and a `recording::StartPanicGuard` is armed at the top of the thread (see 22). The setup before the
  start (API key, health probe, permissions, owned browser) is unchanged.
- **Reason:** these are the smallest edits that do what the review asked. W2-27's early argv dispatch
  can go in `main` after the capture call or at the top of `app_main`; anything placed before the
  capture must not start a thread.

## 28. A capture failure after the engine started

- **Question:** when capture fails to start after `ServerCore::start` succeeded, both engine threads
  stored the core "so pipes and search still work" and then returned, which stopped the generation's
  runtime and with it the HTTP server and every engine task. The watchdog then saw an engine that
  refuses connections and restarted it in full (audio and models included) on its 1/2/4/5-minute
  backoff for as long as the cause lasted. (`CaptureSession::start` fails only when the audio options
  cannot be built or applied, which happens before it starts any capture task; a vision start that
  finds no monitor is logged and retried by the monitor watcher inside a running session.)
- **Decision:** the thread keeps the runtime running (`hold_engine_generation`), so the core it stored
  really serves pipes, search and the API. Nothing is being captured then, and a pause or quit still
  stops what there is. The start still reports the capture error to its caller, and the watchdog sees
  a serving engine, so it does not restart anything. Capture comes back when the user resumes or
  restarts recording, as in the base app.
- **Reason:** this is what the stored core was for. Restarting the whole engine every few minutes to
  retry capture costs a model load each time and cannot fix a missing monitor; a capture-only retry
  belongs with the recording-health incidents of W3-29 (`overlay_restart_recording`,
  `retry_screenpipe`), not with engine supervision.

## 29. A respawn or start in flight when a quit or relaunch begins

- **Question:** a respawn that was stopping the old engine, or starting the new one, when the user
  quit could finish after the teardown's capture and engine steps: the teardown found nothing to stop,
  and the new engine and capture came up while the app was leaving (on Windows through `app.exit`,
  with capture and audio still running).
- **Decision:** three rules. (a) `start_engine` and `start_generation` refuse to start once a teardown
  has begun. (b) An engine thread whose start finishes after a teardown began does not store it: it
  stops the new capture (if any) and retires the core through `shutdown_server_core` itself; capture is
  not even started then. (c) Every engine generation in flight counts as an `EngineTransition`: from
  the moment `ServerCore::start` returns until the core is stored or retired, and for the whole of
  every `shutdown_server_core` (a respawn's stop, a full restart, the teardown's own). The teardown's
  engine step waits, within its limit, until none is left. A generation still inside
  `ServerCore::start` when the quit begins is not waited for: it has opened the database and built its
  audio manager but started no capture, the process ending takes it with it, and waiting would make a
  quit during a long migration hang until the step limit.
- **Reason:** the quit must not end the process while another task still has an engine's capture or
  audio running, which is the reason the forced exit exists at all (24). Counting transitions instead
  of holding a lock keeps the teardown's locks short and needs no change to the watchdog.
