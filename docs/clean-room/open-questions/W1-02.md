# W1-02 open questions

Settings schema v2 and store compatibility (shell-001..003, shell-037, shell-M02, frontend-053,
audio-028, cloud-033..035).

1. **Does `experimentalCoreaudioSystemAudio` default to on, as in the target?**
   - Decision: no. The default stays off (base value) and Freenpipe does not run the target's
     `coreaudioTapMigrationV3` step. A store where screenpipe already switched it on keeps its value.
   - Reason: the effect is macOS-only, and the base macOS capture path still loses meeting audio
     through the process tap (the base V2 migration exists because of it). The target pairs the
     default with meeting piggyback, which Freenpipe does not implement yet. Stability over features
     (VISION.md); the audio WP that ships piggyback can flip it with the V3 sentinel.

2. **`experimentalMeetingPiggyback` default: audio-028 says Freenpipe `false`, its verification note
   says the target's effective default is `true`.**
   - Decision: `true` in Rust, the CLI and the frontend.
   - Reason: cloud-033 says to use the shipped remote-control defaults as plain local defaults, and the
     shipped default of `smart-recording-control` is on. Nothing reads the key until the audio WP
     implements piggyback.

3. **What does a store without `audioCaptureMode` mean?**
   - Decision: `always` (the historical behaviour). Brand-new stores are written with
     `meetings-only` (Rust `SettingsStore::default`, the frontend defaults). The CLI keeps `always`
     unless `--audio-capture-mode` is given. Unknown values also mean `always`.
   - Reason: an existing user should not silently lose all-day audio after an update; new installs get
     the target default.

4. **`autoUpdate` default `true` versus DECISIONS.md 3 (updater off by default).**
   - Decision: the setting defaults to `true` (Rust, frontend, missing key). The updater itself stays
     off through its own status (`updates.rs`: no release feed or signing key = disabled, the manual
     check opens the releases page), so nothing is downloaded by default.
   - Reason: the setting only decides whether an available update installs on its own; DECISIONS.md 3
     is about whether the updater runs at all, which this WP does not change.

5. **Defaults the target does not show (`redactAgentSessionSecrets`, `piiRedactionColumns`,
   `captureMaxWidth`).**
   - Decision: `redactAgentSessionSecrets` true; `piiRedactionColumns` unset (`null` = the built-in
     set); `captureMaxWidth` unset (follow `videoQuality`).
   - Reason: privacy-first where the key protects secrets; unset where the engine already has a
     documented fallback.

6. **Remote-control keys (`remoteControlPreferences`, `remoteControlPolicy`, the legacy
   `semanticContext*` keys).**
   - Decision: kept exactly as stored and never read; no applier, no folding of the legacy keys.
   - Reason: cloud-033 allows "tolerate and ignore". The setting keys they controlled
     (`enableSemanticContext`, `experimentalMeetingPiggyback`, `aecMode`, ...) are the only source of
     truth in Freenpipe.

7. **Workflows sharing (`workflowSharing`, `workflowSharingPromptSeen`).**
   - Decision: `workflowSharing` is dropped on load by both loaders. `piiBackend` goes back to its
     `priorBackend` when that is a local backend, otherwise to `local` if it is a remote one.
     `workflowSharingPromptSeen` is kept and ignored.
   - Reason: cloud-035.

8. **Remote support-log collection.**
   - Decision: `remoteLogCollectionEnabled` is forced to `false` on every load (Rust and frontend) and
     defaults to `false`; `remoteLogCollectionUserId` is kept as stored.
   - Reason: cloud-034; screenpipe reading the store back sees consent withdrawn, which is safe.

9. **`enterpriseManagedSettings`.**
   - Decision: dropped on load.
   - Reason: shell-002 step 11 deletes it on unmanaged devices, and a Freenpipe device is never managed.

10. **What is `cloud.auth_token` in Freenpipe?**
    - Decision: the slot of the cached screenpipe account token, nothing else. At startup the app
      moves a non-empty `settings.user.token` into the secret store under `cloud.auth_token` and only
      then removes it from `store.bin` (and from `store.bin.last-good`); a failed secret write leaves
      the token where it was. `get_cloud_token` reads that key, then the legacy `auth.json`. The token
      is never sent anywhere. `set_cloud_token` keeps its W0-06 meaning (push the AI gateway key into
      the running engine) and does not write `cloud.auth_token`. The frontend does not hydrate
      `user.token`; when saving it leaves the token out only if `get_cloud_token` returns the same
      value.
    - Reason: Freenpipe has no account (W0-04, W0-06): the gateway key is a different credential, and
      putting a vendor token into the gateway slot would forward it to the user's gateway. Hydrating
      it would also hand it to code that treats `user.token` as an API key. The secret store is the
      one in the data dir's `db.sqlite`, as for the other app secrets.

11. **When does settings-store initialisation "fail closed"?**
    - Decision: when the store file cannot be opened (unparseable after the `.last-good` restore, or
      encrypted without a usable key) or `settings` is not a JSON object. The app logs the error, shows
      an error dialog naming the file, and exits on OK. A store whose values have unexpected types
      still loads: such a value keeps its default in memory and is written back unchanged (lenient
      load, `screenpipe_config::lenient`). A missing or `null` `settings` is a new store.
    - Reason: shell-003 (never overwrite a real store with defaults) without turning a single odd value
      into a refusal to start.

12. **Types of the new onboarding fields (shell-M02).**
    - Decision: the timestamps, phase, chat id, notification id and error are optional strings,
      `firstRunSummaryTelemetryVersion` an optional integer, `trialActivationFreshInstall` an optional
      bool (accepted and ignored). A stored value of another type is kept as stored (lenient load into
      the struct's `extra`).
    - Reason: the serde field names are observed, their types are not.

13. **`hideThinkingBlocks` (shell-037).**
    - Decision: kept in Rust and the frontend with its default `true`.
    - Reason: the spec allows keeping it; removing it would drop a user preference.

14. **AIPreset `enterpriseManaged`.**
    - Decision: added as an optional bool that is not written when absent.
    - Reason: the preset struct has no catch-all map, so a screenpipe preset carrying the key would
      otherwise lose it when the Rust side saves.

15. **Notification preference defaults (meetings_memory-040, frontend-040).**
    - Decision: the master switch is `notificationsEnabled` and the pause allow-list
      `allowDuringPause` (the names meetings_memory-040 observed); `meetingReminderLeadSeconds`
      defaults to 60. Existing preference objects gain missing switches on load, and a missing
      `meetingReminders` copies `meetingLiveNotes`.
    - Reason: the lead-time default is not observed; one minute is the middle of the offered values.

16. **Frontend-only keys the target defaults that Freenpipe leaves out.**
    - Decision: `dataSyncEnabled` and `acquisitionSource` get no default (vendor data sync and
      acquisition analytics); `userGoalCategory` is not seeded on load.
    - Reason: decloud for the first two; the goal picker is a feature WP's to seed.

17. **`ignoredUrls` in the frontend type.**
    - Decision: the generated type is `UrlRule[]` (string or domain rule) while the hook's `Settings`
      extension keeps `string[]`, so the current privacy UI keeps compiling. `urlRulePattern()` in
      `lib/settings-schema.ts` gives a display string for either shape.
    - Reason: the website-rules UI belongs to the privacy settings WP (vision-url-domain-rules,
      frontend-038), which should switch the editor to `UrlRule[]`.

18. **`enhancedAI` for imported stores (W0-06 review finding).**
    - Decision: the one-time privacy migration (`_freenpipePrivacyDefaultsApplied`) now also turns
      `enhancedAI` off, in Rust and in `lib/ai-gateway.ts`. Stores that already ran the migration keep
      their value.
    - Reason: re-running it under a new sentinel would override a choice made after the first run.

19. **Hand-offs from wave 0 that this WP does not do.**
    - W0-06 question 13 (move every AI provider key into the secret store): deferred. Only the account
      token moves here; moving the gateway, preset, Deepgram and OpenAI-compatible keys changes every
      settings page and the synchronous engine config path, which is a dedicated secrets WP.
    - W0-09 question 10 (model mirror): deferred. The v2 schema has no `ModelMirror` settings key (the
      target has none; W0-09 question 2 keeps mirrors in environment variables), so there is nothing to
      pass to `hf_source.rs` yet.
