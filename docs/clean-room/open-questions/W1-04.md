# W1-04 open questions

Decisions taken while registering the enterprise and plan-gate commands as inert stubs
(frontend-052, cloud-043, agents_pipes-041, agents_pipes-045, api-035, meetings_memory-042).

## 1. Return type of `apply_enterprise_ui_visibility`

- **Question:** frontend-052 says the command returns `false`; cloud-001 and cloud-043 say it takes
  no arguments and returns unit. Which shape do the bindings get?
- **Decision:** `apply_enterprise_ui_visibility() -> bool`, a plain (not Result-wrapped) promise that
  resolves `false`. The value is `enterprise_policy::is_app_ui_hidden()`, so it is the same answer the
  tray and window code already use.
- **Reason:** frontend-052 is the item written from the target's generated bindings; the cloud items
  only saw the name in the ACL list. A caller that ignores the result works with either shape, and a
  caller that reads it learns that the UI stays visible.

## 2. Empty host identity: `null` or `""`

- **Question:** frontend-052 says `{machine_id_hash: null, os_user_id_hash: null}`; cloud-043 says
  empty strings.
- **Decision:** `EnterpriseHostIdentity { machine_id_hash: Option<String>, os_user_id_hash:
  Option<String> }`, both `None` (`null` on the wire, `string | null` in TypeScript).
- **Reason:** `null` says "no identity" instead of "an identity that happens to be empty", so no
  caller can mistake it for a real hash. Freenpipe never derives a machine or OS-user identifier at
  all.

## 3. Plain values or Result wrappers

- **Question:** the spec does not record which of these commands were Result-wrapped in the target.
- **Decision:** the read-only answers (`apply_enterprise_ui_visibility`, `get_enterprise_host_identity`,
  `is_history_access_restricted`, `list_managed_team_skills`) are plain values; the setters
  (`set_enterprise_recording_authorized`, `sync_managed_team_skills`, `set_activity_sync_enabled`)
  return `Result<(), String>` and always succeed, as frontend-052 asks ("others `Ok(())`").
- **Reason:** the W1-04 acceptance check expects `isHistoryAccessRestricted()` to resolve to `false`
  itself, which only a plain promise does. The setters keep a Result so a later implementation could
  report an error without changing the bindings.

## 4. What `set_enterprise_recording_authorized` does with its arguments

- **Question:** the target passes an admin verdict plus a credential type and credential (licence key
  or account token). Should `authorized: false` pause recording, and should the credential be kept?
- **Decision:** arguments `(authorized: bool, credentialType: string | null, credential: string |
  null)`. The verdict changes nothing, the credential is neither stored nor logged (only whether one was
  supplied), and the command returns `Ok(())`.
- **Reason:** recording in Freenpipe is controlled only by the user. An IPC call that could stop
  recording, or a place where a secret could end up in a log file, would be a liability with no
  feature behind it.

## 5. `sync_managed_team_skills`: result and payload shape

- **Question:** cloud-043 suggests `Ok(0)` or unit; frontend-052 says `Ok(())`. The shape of a
  `ManagedTeamSkill` entry is not in the evidence (only the type name is).
- **Decision:** `sync_managed_team_skills(skills: JsonValue[], pruneUnlisted: boolean) ->
  Result<(), string>`, always `Ok(())`. It installs nothing and removes nothing. The entries are taken
  as plain JSON so a payload in any shape is accepted. `list_managed_team_skills()` returns
  `ManagedTeamSkill[]`, always empty, where Freenpipe's `ManagedTeamSkill` has a single `name` field
  (the skill folder name), the least a UI needs to mark a skill as managed.
- **Reason:** without an organisation there is nothing to sync. Accepting any JSON avoids inventing a
  schema for input that is thrown away. Installing skills from an IPC payload would turn an inert stub
  into an install path for any script running in the webview.

## 6. `set_activity_sync_enabled` does not persist anything

- **Question:** cloud-037 says the command "stores the flag locally and does nothing else". Should it
  write a settings key?
- **Decision:** the command logs and returns `Ok(())`; it writes nothing. The `dataSyncEnabled`
  setting, if the UI needs one, belongs to the settings schema (W1-02) and is persisted by the frontend
  through the settings store like every other key. The engine routes `/data-sync/devices` and
  `/data-sync/search` from cloud-037 are not part of this WP.
- **Reason:** PLAN.md ground rule 7 keeps settings keys with W1-02, and Freenpipe has no upload worker
  for the flag to control.

## 7. No history-access call sites in the route handlers

- **Question:** meetings_memory-042 mentions "call sites in routes". Should `/frames/*`, `/elements`,
  exports, meetings, raw SQL and starred sessions call `history_access::access_for` before serving?
- **Decision:** no call sites. `crates/screenpipe-engine/src/history_access.rs` provides
  `access_for(read, oldest)`, `policy()` and `is_restricted()`, all answering `Unrestricted`;
  `HistoryAccess` has no restricted variant, so a caller cannot be handed a refusal. The wire code is
  kept only as the `HistoryAccessErrorCode::Limited` enum value (serialized with the screenpipe code
  name) and is never produced. The desktop app's `is_history_access_restricted` command reads
  `is_restricted()`.
- **Reason:** vision-history-access-stub says not to add the error path to those routes, and a guard
  that always passes would only add edits to route files other WPs own in later waves. The module is
  the one place to ask if a local policy is ever wanted.

## 8. Managed pipes and the pipe-count limit are not wired into the pipe runtime

- **Question:** should `PipeManager` consult `pipes::managed` before edits, toggles, deletes and loads?
- **Decision:** `crates/screenpipe-core/src/pipes/managed.rs` answers the questions
  (`is_pipe_managed` and `is_team_skill_managed` are false, `managed_team_skill_names` is empty,
  `pipe_count_limit` is `None`), and `list_managed_team_skills` in the app reads it. Nothing in
  `pipes/mod.rs` calls it.
- **Reason:** with nothing managed and no limit, a check would never change behaviour, and
  `pipes/mod.rs` is a shared hotspot that W1-03 edits in the same wave (PLAN.md section 6). Base has no
  limit to remove.

## 9. The frontend hook does not call the new commands

- **Question:** should `useEnterprisePolicy` ask `is_history_access_restricted` (and the other new
  commands) over IPC?
- **Decision:** no. The hook adds module-constant answers: `isManagedDeployment: false`,
  `historyAccessRestricted: false`, `isPipeManaged(name) -> false`, and the policy fields
  `managedSkills: []`, `recordingAllowed: true` and `requireAccountLogin: false`. The commands stay in
  `tauri.ts` for callers that use the bindings directly.
- **Reason:** the answers are fixed, so an IPC round trip on every mount would add latency and a
  failure mode for no information, and the hook's functions must stay referentially stable.
