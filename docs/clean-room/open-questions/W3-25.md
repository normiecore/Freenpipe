# W3-25 open questions

Decisions taken while building the local OpenAI-compatible proxy (agents_pipes-033, api-023) and
bring-your-own web search (agents_pipes-035, api-025). Each is the worker's call; the owner can
overturn any of them.

## 1. Where the web-search provider is configured

- **Question:** the spec asks for "a user-configured provider (e.g. SearXNG URL or a BYO search API
  key)" but names no settings key, and the W1-02 settings schema has none.
- **Decision:** configuration is environment-only for now: `SCREENPIPE_WEB_SEARCH_PROVIDER`
  (`searxng`, `brave`, `tavily`, `gateway`, `off`), `SCREENPIPE_WEB_SEARCH_URL` and
  `SCREENPIPE_WEB_SEARCH_API_KEY` (documented in `docs/env.md`, constants in
  `screenpipe_core::env`). With none of them set, an AI gateway the user already configured
  (`aiGatewayUrl` / `SCREENPIPE_AI_GATEWAY_URL`) serves searches at `{gateway}/web-search`, which is
  what W0-06 had the extension do. No settings key was invented.
- **Reason:** PLAN.md section 2 rule 7 and the coordinator brief: feature WPs must not add settings
  keys. **Follow-up for the owner:** approve settings keys (proposal: `webSearchProvider`,
  `webSearchUrl`, `webSearchApiKey`, the key better kept in the secret store) in a W1-02-style
  settings commit plus an AI-settings field, so desktop users can configure search without
  environment variables. `screenpipe_core::web_search::resolve_with` takes its inputs as arguments,
  so a settings source slots in without changing the route.

## 2. Which API-key providers

- **Question:** "a BYO search API key" does not say which service.
- **Decision:** Brave Search (`X-Subscription-Token`, `https://api.search.brave.com/res/v1/web/search`)
  and Tavily (bearer key, `https://api.tavily.com/search`). Their public endpoints are used only when
  the user names that provider and supplies a key; `SCREENPIPE_WEB_SEARCH_URL` can point either at
  a proxy instead. A key with no provider named is reported as a configuration error rather than
  guessed.
- **Reason:** both are common, third-party, user-initiated choices with simple JSON APIs. Neither is
  a vendor service, and nothing is used by default.

## 3. Status of an unconfigured web search

- **Question:** api-025 says 501 `{"error":"web_search_not_configured"}`; cloud.md (cloud-016) says
  the gateway-backed routes answer 503 `cloud_token_missing`.
- **Decision:** 501 `web_search_not_configured` with a `message` that says how to configure a
  provider. `/v1/chat/completions` (cloud-016, W0-06) keeps its 503.
- **Reason:** api-025 is the WP's own item and describes the BYO replacement; the 503 code in
  cloud-016 described the gateway-only design this WP replaces.

## 4. Error codes of `/v1/web-search`

- **Question:** the target's errors are 401 `cloud_token_missing`, 502 `upstream_unreachable` and
  504 `upstream_timeout`. What does a provider that answers with an HTTP error (bad key, rate limit)
  or with unreadable output get?
- **Decision:** 502 with `"error":"upstream_error"` and a message naming the provider, the status and
  a hint (key, quota, SearXNG's JSON format). 400 `invalid_request` for an empty or over-long query.
  `cloud_token_missing` is not used (there is no sign-in).
- **Reason:** `upstream_unreachable` would mislead for a provider that is up but refuses the key.
  Clients that only check the status still see a 502.

## 5. Error wording

- **Question:** the spec paraphrases the target's messages (no default preset, preset without base
  URL, provider unreachable) without quoting them.
- **Decision:** Freenpipe's own wording with the same meaning, in the OpenAI error shape
  `{"error":{"message","type","code"}}`. `type` is `invalid_request_error` for 4xx and `api_error`
  for 5xx. `code` adds a machine-readable reason (`no_default_preset`, `preset_missing_base_url`,
  `upstream_unreachable`, `upstream_timeout`, ...). The unreachable message is "could not reach the
  AI provider: " followed by the underlying error, with keys and URL credentials blanked.
- **Reason:** clean-room rules forbid copying the target's prose; the shape and the status codes are
  the interoperable part.

## 6. Preset resolution details

- **Question:** which preset, URL, key and model does the proxy use in edge cases?
- **Decision:**
  - Only the preset with `defaultPreset: true` counts. Presets without that flag give the
    missing-preset 400.
  - `native-ollama` without a URL falls back to `http://localhost:11434/v1` (loopback). Every other
    provider without a URL, `openai` included, gives the missing-base-URL 400: the proxy never fills
    in a hosted endpoint.
  - `screenpipe-cloud` / `pi` presets go to the user's AI gateway with the gateway credential, or
    get a 400 when no gateway is configured (api-023: "rejected or mapped").
  - `openai-chatgpt` presets get a 400: the ChatGPT sign-in speaks a different API than chat
    completions.
  - The preset's `model` replaces the request's `model`; the request's model is used only when the
    preset has none.
- **Reason:** the route exists so callers use "the user's model" without its key; letting callers
  switch models on the user's key, or defaulting to a hosted endpoint, would undo that.

## 7. Timeouts

- **Question:** the spec names no timeouts.
- **Decision:** chat proxy: 10 s to connect, 300 s until the provider's response starts (a local model
  can take minutes to load or to finish a non-streamed answer), 120 s of silence between streamed
  chunks; a silent SSE stream ends with a final OpenAI-shaped error event. Web search: 10 s to
  connect, 25 s for the whole exchange. Redirects are not followed, so a key never reaches a host the
  user did not name.
- **Reason:** bounded waits as the coordinator asked, generous enough for local models.

## 8. The extension's tool result

- **Question:** the target's tool returns `{text, sources, query}`; Pi tools return
  `{content, details}`.
- **Decision:** `content` carries the text and `details` is `{text, sources, query}`. The text starts
  with a one-line note that the results are untrusted third-party text. The chat's source chips read
  `details.sources`; `lib/source-citations.ts` now accepts both `sp_web_search` and the old
  `web_search` name so stored chats keep their chips.
- **Reason:** satisfies the spec's shape inside Pi's tool-result format.

## 9. When the extension is installed

- **Question:** W0-06 installed the web-search extension only for runs on the gateway-backed
  provider. Does that still hold?
- **Decision:** no. The tool now goes through the local engine, so any model provider may use it; it
  is installed whenever a search provider is configured and removed otherwise, for pipes
  (`screenpipe-core`) and chat (the app) alike. The two `web-search.ts` copies are identical and a
  test in each crate checks that.
- **Reason:** "disabled when unconfigured" (agents_pipes-035) without tying search to one LLM
  provider.
