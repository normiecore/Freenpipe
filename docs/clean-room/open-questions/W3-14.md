# W3-14 open questions

Decisions taken while building audio capture modes (audio-010), the device route changes
(audio-026) and the device status, fallback and capture health events (audio-018).

## 1. Default mode and stores without the key

- **Question:** audio-010 gives `meetings-only` as the default for new installs, and the
  coordinator asks that `always` keep today's behaviour exactly so existing users see no change.
- **Decision:** unchanged from W1-02 (its open question 3): a store without `audioCaptureMode`, an
  unknown value and the CLI without `--audio-capture-mode` all mean `always`; only a brand-new store
  is written with `meetings-only`. `always` runs exactly the base code path: every device may open,
  every chunk is kept, and the device monitor runs its base recovery logic.
- **Reason:** settings keys and their defaults belong to W1-02; this WP implements what the modes
  do. No settings key was missing.

## 2. One flag for "audio is off"

- **Question:** `disableAudio` and `audioCaptureMode=disabled` both turn audio off. Where is that
  decided?
- **Decision:** `RecordingConfig::from_settings` folds both into `disable_audio`, and the audio
  manager builder turns the `disabled` mode into `is_disabled`. Every startup path (CLI and app)
  reads that one flag, so with `disabled` the audio manager never starts, no device is enumerated,
  no model is loaded and the meeting detector is not created (base already skips it when audio is
  off). `/health` keeps reporting `audio_capture_mode` `disabled`.
- **Reason:** the spec says the audio manager never starts in this mode; reusing the existing flag
  means no startup code needed new branches.

## 3. Restart required, never half-applied

- **Question:** the spec marks `audioCaptureMode` (and `disableAudio`) as needing a restart. The
  app restarts only capture for most settings, which re-applies audio options to a long-lived
  audio manager but keeps the HTTP server (and its `audio_disabled` flag) from the old settings.
- **Decision:** both keys join the settings page's server-restart set, so saving either restarts
  the whole server and the toast says so ("server restarted with new settings"). The audio routes
  also read the audio manager's live options, and `apply_options` resets the mode state in one step
  while capture is stopped, so no path can run with the old mode in the server and the new one in
  the audio manager.
- **Reason:** the target's settings page lists both keys among the restart-required settings; a
  server restart is the only way every reader (routes, health, meeting detector) sees one mode.

## 4. What counts as a confirmed meeting

- **Question:** "streams open only between a confirmed `meeting_started` and `meeting_ended`". Which
  signals confirm a meeting, given that the UI-scan detector reopens a recent meeting without a
  `meeting_started` event and manual meetings work without a detector?
- **Decision:** the audio manager follows three event-bus events: `meeting_started` and
  `meeting_ended` (matched by `meeting_id`; an end for another meeting is ignored) and
  `meeting_status_changed` (`active` with `active_meeting_id`, emitted on every detector and route
  transition, including reopen). Ten seconds after capture starts it adopts a meeting that is
  already open in the database (a capture restart in the middle of a meeting), and every 15 s it
  checks that the confirmed meeting is still open, ending it if the end event was missed.
- **Reason:** events keep the audio crate independent of the engine's detector; the delayed seed
  gives the startup sweep of orphaned meetings time to close rows left by a crash, and the check
  stops a missed end from recording all day.

## 5. Grace period, late streams and chunk attribution

- **Question:** the spec says streams are released "after a grace period" and that chunks without
  a confirmed meeting are dropped. A 30 s chunk that straddles the meeting end holds meeting audio.
- **Decision:** streams close 30 s after the meeting ends unless another meeting starts first (a
  room change ends and starts a meeting back to back). Each recording task is stopped gracefully:
  it gets up to 3 s to flush its last partial chunk. A chunk is kept when its recording window
  overlaps a confirmed meeting (the running one or one of the last four that ended) and dropped
  otherwise, before it is written to disk or the database. The device monitor closes any stream
  still open on later idle passes ("late streams"), and a device that finishes opening after the
  meeting ended is closed at once. Session-device marks survive the stale-stream cleaner; only the
  release clears them.
- **Reason:** attribution by recording time keeps the end of a meeting and never keeps audio
  recorded entirely outside one, which is what "unattributed" means; the 30 s grace is the spec's
  inferred value.

## 6. Which devices a meeting opens

- **Decision:** the configured devices (`enabled_devices`, which in follow-system-default mode
  already holds the defaults), microphones first, skipping devices the user paused. The device
  monitor then runs its normal recovery for the length of the meeting (default switches, the
  Windows communications output, pinned-input fallback). While no meeting runs, the monitor skips
  all recovery and forgets its recovery state, so the next meeting starts clean.
- **Reason:** "opens the configured devices" (audio-010). The Bluetooth meeting gate and
  meeting-input resolution are audio-011 and audio-015, later WPs.

## 7. `/health` while meetings-only waits

- **Question:** with no stream open, the base `audio_status` logic reports `not_started` or
  `stale`, which the app turns into "audio stalled" notifications.
- **Decision:** while meetings-only waits for a meeting and no device is open, `audio_status` is
  `ok`; `capture_status.status` (W2-13) says `waiting_for_meeting` or
  `meeting_detector_unavailable`.
- **Reason:** waiting is the intended state, not a failure, and the legacy field's readers only
  distinguish healthy from failing (W2-13 open question 1).

## 8. Device route responses

- **Decision:** `POST /audio/start` and `POST /audio/device/start` answer `409 Conflict` with
  `{"success": false, "message": "Audio capture is disabled in settings"}` while audio is off
  (either setting). A device start that cannot open because meetings-only is waiting answers 200
  with `success: true` (the pause is lifted) and a message that starts with "capture is gated". A
  device start on a stopped pipeline restarts the pipeline first. `POST /audio/device/stop` and
  `POST /audio/stop` keep working in every mode. The stop route's error text now says "stop"
  (base said "start" by mistake).
- **Reason:** the spec allows 409 or 400; 409 fits "the server state forbids this". The device is
  resumed either way, so success is true and the message carries the gating.

## 9. `audio_device_status_changed` payload and producers

- **Decision:** `{device_name, is_running, is_user_disabled, reason}`; `reason` is a Freenpipe
  addition (`started`, `stopped`, `user_paused`, `user_resumed`, `stream_lost`, `meeting_ended`,
  `drm_paused`), skipped when absent and optional when parsing. The audio manager publishes it on
  every stream start and stop, every pause and resume, the stale-stream cleanup, the DRM output
  pause and a full capture stop, whether the API or the device monitor caused it. Publishing
  failures are logged at debug level and never affect capture.
- **Reason:** publishing at the manager catches every path; `reason` lets subscribers tell a lost
  stream from a deliberate stop without guessing.

## 10. `audio_device_fallback_unavailable`

- **Decision:** emitted once per outage when a pinned input has been missing past the 20 s grace,
  no input records, and nothing can stand in (no default input, the default is the missing device,
  or the user paused the default). When the device records again, `audio_device_fallback_cleared`
  follows with an empty `fallback_device` (the app shows it as "restored"); unpinning or a fallback
  engaging later drops the announcement quietly. In follow-system-default mode, losing the last
  microphone (the system reports no input at all) for 20 s emits it with `pinned_device`
  `__no_input__`, and the next input to record emits the matching `cleared`. A machine that never
  had a microphone in the session is not reported.
- **Reason:** the spec names these states and the placeholder; reporting only a loss (not a
  machine without a microphone) keeps desktop PCs without one from a notice at every start.

## 11. `audio_capture_health_*` producers

- **Decision:** the event types and names are defined (`custom_events/audio_health.rs`) and the
  app handles all three. This WP produces `mic_capture_failed` (a meetings-only session microphone
  fails to open; once per device per meeting) and `recovered` (that microphone opens later in the
  meeting). `speaker_silent` needs the render-endpoint activity query and the speaker watchdog of
  audio-017, so nothing emits it yet; the meeting-input path of audio-015 will reuse
  `mic_capture_failed`.
- **Reason:** those producers belong to later WPs; the payload and app handling are ready for them.

## 12. Which events notify, and how often

- **Decision:** fallback `engaged`, `cleared` (as "Microphone restored") and `unavailable` raise an
  operating-system notification. `mic_capture_failed` and `speaker_silent` use the in-app panel with
  a "restart recording" action (`restart_recording`, already handled by the panel); `recovered` is
  shown only after a failure of the same device was shown. `audio_device_status_changed` never
  notifies: streams open and close routinely (meetings-only, default switches, unlock rebuilds). All
  of them are forwarded to the webview as kebab-case events, and the home page refreshes its device
  list on `audio-device-status-changed`. A notice is shown only when `notificationPrefs` allows it
  (`notificationsEnabled`, `snoozeUntil`, `captureStalls`), at most once per event kind and device
  every 10 minutes, at most 3 audio notices in 5 minutes, and never for a device the user paused
  (tracked from the status events).
- **Reason:** the spec asks for notifications on the fallback and health events and to respect
  `captureStalls`; a flapping Bluetooth headset must not flood the user.
