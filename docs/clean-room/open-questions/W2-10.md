# W2-10 open questions

Decisions taken while building the frame media routes: thumbnails, preview samples, preview media,
typed `/frames/:id` errors and the end of the `/frames/*` auth exemption (api-010, api-011,
vision-thumbnail-endpoint, vision-preview-samples, vision-preview-media,
vision-frame-media-errors).

## 1. Thumbnail width and quality ranges

- **Question:** the spec observed range checks on `width` and `quality` but not their bounds.
- **Decision:** `width` 32 to 3840 (default 320), `quality` 1 to 100 (default 75). Out-of-range
  values get 400 `{"error", "error_type": "invalid_request"}`. A thumbnail is never wider than its
  frame, so `width=1000` on a 640 px frame serves 640 px and says so in
  `x-screenpipe-thumbnail-width`.
- **Reason:** the spec's inferred ranges; they cover every width the frontend asks for (320, 384,
  768, 1280).

## 2. Thumbnail cache: memory only, no disk tier

- **Question:** the spec asks for an in-memory LRU; the coordinator asked that the cache be bounded
  in memory and on disk and never serve a deleted frame.
- **Decision:** one process-wide moka cache weighed by encoded bytes, capped at 32 MiB, entries
  dropped after 30 idle minutes. Nothing is written to disk: snapshot JPEGs are read into memory and
  video frames are piped out of ffmpeg (`video_utils::extract_frame_jpeg_bytes`), so the disk bound
  is zero bytes. Every request reads the exact frame from the `frames` table before the cache is
  consulted, and the cache key includes a hash of the media file's identity (kind, path, frame
  position, size, mtime), so a deleted frame gets 404 and a re-pointed frame never gets an old
  thumbnail. Decoding is limited to 2 to 4 concurrent renders; video extraction shares the
  existing 3-slot ffmpeg semaphore.
- **Reason:** a persistent thumbnail directory would keep pixels of frames the user deleted until
  eviction, and would hold plaintext images while the vault is locked. Extraction cost after a
  restart is the only thing lost.
- **Note:** the cache lives in a static in `frame_thumbnail_cache.rs` rather than in `AppState`,
  because this WP may only touch `server.rs`'s auth exemption list. Keys carry absolute source paths,
  so two servers in one process (tests) cannot see each other's entries.

## 3. ETag value and what it identifies

- **Question:** the spec gives the prefix `"frame-thumbnail-` and an inferred
  `<frame_id>-<w>-<q>-<generation>` shape.
- **Decision:** `"frame-thumbnail-<frame_id>-<requested width>-<quality>-<16 hex digits>"`, where
  the hex part is the first 64 bits of a SHA-256 over the source identity, stable across restarts.
  When a nearby frame is served instead, the tag names the frame actually served. `If-None-Match`
  accepts lists, `W/` tags and `*`; a match gives 304 with the tag and
  `Cache-Control: private, no-cache`.
- **Reason:** a tag must change whenever the bytes could change, and a fallback image is a
  different representation from the exact frame's.

## 4. Thumbnail fallback scope and error codes

- **Question:** "nearby frames" is only described as the base `try_nearest_frame` logic on the same
  device.
- **Decision:** up to 3 frames backward, then 3 forward, of the same monitor, within 10 minutes of
  the requested frame (and within 2000 frame ids, which bounds the scan). With `fallback=false`, or
  when no neighbour works, the answer is 404 with `error_type` `snapshot_missing` when the exact
  frame's snapshot file is gone (after a re-lookup of the row) and `frame_unavailable` for every
  other cause (no media location, missing or damaged video, decode failure). A missing frame row
  is 404 `frame_not_found`; a frame from another device is 404 `remote_device`; a thumbnail that
  takes longer than 15 s is 503 `thumbnail_timeout`.
- **Reason:** the time window keeps a fallback from showing a screen from hours earlier; the base
  code had no window because it served whole frames for the timeline, where the client already
  knows the neighbourhood.

## 5. `/frames/:id` typed errors

- **Question:** the spec names `frame_media_unavailable`, `snapshot_read_failed` and a re-check
  before `snapshot_missing`, but not the status codes or whether fallback still applies.
- **Decision:** `frame_media_unavailable` is 404 (no snapshot and no video chunk with a file,
  including evicted media). `snapshot_read_failed` is 500 with `details` and does not fall back,
  because the file exists and a retry may succeed (Windows sharing violations are transient). Before
  that answer the read is tried once more after 100 ms (not for a missing file or a path that is
  not a regular file), so a writer or virus scanner that holds a fresh JPEG for a moment does not
  leave an empty image where the base code showed a neighbour. The same read, retry included,
  backs the thumbnail route. A
  missing snapshot triggers a second exact lookup; if the frame moved into an MP4 it is served from
  there, otherwise the nearest frame is tried as before and `snapshot_missing` (404) follows.
  The route now reads the `frames` table before its extracted-image cache, so a deleted or evicted
  frame is no longer served from a cached temp file.
- **Reason:** keeps the base fallback for the case it was written for (compaction races, deleted
  JPEGs) while giving clients distinct codes for "never had media", "unreadable" and "gone".

## 6. Preview-sample limits and spreading

- **Question:** the maximum `limit`, case sensitivity of `app_name` and the spreading rule are
  inferred.
- **Decision:** `limit` 1 to 12 (default 6); `app_name` required, 1 to 256 characters after
  trimming, matched case-insensitively; `start_time` and `end_time` required, start before end,
  at most 24 h apart (end exclusive); `browser_domain` optional and must be a bare host (letters,
  digits, `-`, `_`, dots), matching that host and its subdomains. The span from the first to the
  last matching frame is cut into `limit` equal slices, and each slice contributes its first frame
  whose file exists. Snapshot frames are `source: "snapshot"`; compacted frames whose chunk is a
  local `.mp4` are `source: "video"` with `video_chunk_id` and
  `video_offset_seconds = offset_index / video_chunks.fps`. Validation failures are 400
  `invalid_request`; a failed query is 500 `preview_samples_failed`.
- **Domain matching:** SQL pre-filters `browser_url` with `LIKE '%domain%'` and the host is then
  checked exactly. The pre-filter also passes URLs that name the domain outside the host (a search
  for `github.com` on google.com), so the edge lookups and each slice read rows a page (64 or more)
  at a time until they have their exact matches, the range has no more rows, or 5,000 rows were
  read (`PREVIEW_DOMAIN_SCAN_LIMIT`). Only a slice holding more than 5,000 such look-alike frames
  in a row can still come back short.
- **Reason:** spreading over the active span (rather than the requested range) still gives `limit`
  samples when the app was used for only part of the range.

## 7. Preview-media byte ranges

- **Question:** the spec asks for single-range support but not how bad ranges are handled.
- **Decision:** one `bytes` range per request (`a-b`, `a-`, `-n`); the result is clamped to the file.
  Malformed syntax, several ranges, a start past the end, an end before the start, `-0` and
  overflowing numbers all get 416 with `Content-Range: bytes */<len>`. Another range unit is
  ignored (200, whole file), and so is any `Range` sent with `If-Range`, because the route sends no
  validators. Only a local, regular (non-symlink) `.mp4` file is served; unknown, evicted, remote,
  non-MP4, empty or missing chunks are 404 `preview_media_not_found`, and lookup failures are 500
  `preview_media_lookup_failed`. Responses carry `Accept-Ranges: bytes`, `Content-Length` and
  `Cache-Control: private`.
- **Reason:** browsers only send single ranges for `<video>`; rejecting the rest keeps the reader
  simple and guarantees it never reads outside the file.

## 8. `/frames/*` auth and the desktop frontend

- **Question:** the spec says the `screenpipe_auth` cookie keeps `<img src>` working once
  `/frames/*` needs the token.
- **Decision:** the exemption is removed. The frame image URLs the desktop frontend builds for
  `<img>` tags and native live text (search modal, timeline fallback image, live text, chat
  attachment preview) now also carry `?token=` through `appendAuthToken`, which is a no-op when
  API auth is off.
- **Reason:** in the packaged Windows app the page origin is `http://tauri.localhost`, so a cookie
  set by the page is not sent to `http://localhost:3030`; without the token those images would get
  403 with API auth on (the default).
- **Agent skill:** the bundled `screenpipe-api` skill (compiled into the pi agent by `include_str!`
  in `crates/screenpipe-core/src/agents/pi.rs` and copied by the OpenClaw/Hermes agent cards
  through `lib/generated/screenpipe-skills.ts`) listed `/frames/*` among the routes that skip auth
  and fetched a frame with curl and no header. An agent following it would now save a 403 JSON body
  as the image while curl exits 0. The skill no longer lists `/frames/*` as exempt, its frame
  examples send the bearer header with `curl -f`, and it names `/frames/{id}/thumbnail` for cheap
  previews. `lib/generated/screenpipe-skills.ts` was regenerated with
  `bun scripts/gen-skill-content.js`. The developer mirror `.claude/skills/screenpipe-api/SKILL.md`
  (already "every route needs auth except `/health`") got the same header on its frame example.
  These edits sit outside the skill's Connections section and browser control block, which other
  WPs own.
- **Logging follow-up (not done here):** more `<img>` URLs now carry `?token=`. The engine's
  `TraceLayer` uses `DefaultMakeSpan` (`crates/screenpipe-engine/src/server.rs`, the router's last
  layer), which records the full URI at DEBUG, so with `tower_http` debug logging on the API key
  reaches the log. The `?token=` path already existed for WebSocket and `<video>` sources. A
  `MakeSpan` that drops the `token` query parameter needs a `server.rs` edit outside W2-10's region
  (the auth exemption list); the file's owner is W1-03 (merged), so it needs a follow-up WP.

## 9. Snapshot compaction bound the wrong frame ids (`write_queue.rs`)

- **Question:** while testing compacted-frame thumbnails, the last frame of every compaction batch
  kept its `snapshot_path` after the compactor deleted its JPEG, so its thumbnail and image fell
  back to a neighbour.
- **Decision:** fixed in `crates/screenpipe-db/src/write_queue.rs` (`CompactSnapshots`), a file
  outside W2-10's owner paths (W1-01 wrote it; W2-01, pending, owns its writer-pragmas region and
  W3-27 owns its admission gate). The statement mixed `?1` (the chunk id) with bare `?`
  placeholders for the `IN` list. sqlx numbers bare `?` from the first argument, so the list bound
  the chunk id in place of the first frame id and never bound the batch's last frame id. The batch
  then left its last frame on a deleted JPEG and could re-point an unrelated frame whose id equalled
  the chunk id. The `IN` list now uses numbered placeholders `?2..?N+1`, and
  `compaction_moves_exactly_the_batch_frames` (in `crates/screenpipe-db/tests/frames_preview_test.rs`)
  covers a chunk id that differs from every frame id. The hunk is three lines inside the
  `CompactSnapshots` arm, away from the pragmas and admission-gate regions, so W2-01 and W3-27
  should keep it as is when they merge.
- **Not repaired:** databases compacted by the old code keep their damage: the last frame of each
  batch still points at a deleted snapshot (the routes now answer `snapshot_missing` or fall back
  for it), and a frame whose id equalled a chunk id may have lost its `snapshot_path` and point
  into that chunk at a wrong position.
  A one-off repair (re-point frames whose snapshot file is gone and whose neighbours went into a
  chunk, or clear their `snapshot_path`) is a follow-up for the DB maintenance work (W2-01 or a new
  WP); it was left out because it rewrites user rows from a heuristic.
