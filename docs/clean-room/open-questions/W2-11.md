# W2-11 open questions

Per-monitor vision control and display layout persistence (vision-device-control, api-016,
vision-display-layout, db-007). Each decision is the worker's call; the owner can overturn any of
them.

1. **Is the status row keyed `id` or `monitor_id`?**
   - Decision: `GET /vision/device/status` returns `[{id, name, active, user_disabled}]`. The control
     routes take `{"monitor_id": n}`.
   - Reason: specs/vision.md (verified against the frontend) says the popover reads `e.id`, `e.name`
     and `e.user_disabled` and posts `{monitor_id}`; it marks api-016's `monitor_id` key as wrong.

2. **Does a user pause survive restarts, hot-plug and engine respawns?**
   - Decision: pauses live in memory in one process-wide registry (`VisionDeviceControl::global()`),
     not inside a `VisionManager`. They survive everything that happens inside one process: monitor
     unplug and re-plug, DRM and work-hours pauses (which stop and restart the manager), the app's
     capture stop/start cycles (each builds a new `VisionManager`), and in-process engine respawns by
     W2-26's watchdog. Nothing is written to disk, so quitting and relaunching the app, or restarting
     the CLI, starts with every monitor unpaused.
   - Reason: the vision spec found no store key, setting or file for paused monitors and treats the
     state as in-memory (api-016's "persisted across restarts" has no evidence); keeping the set
     outside the manager is what makes it hold across the restarts the owner asked about.

3. **What happens when a paused monitor comes back under a different id, or its id comes back as a
   different display?**
   - Decision: each pause remembers the display it was set on (`stable_id` and name). On every
     enumeration:
     - A paused id that is present under the same name stays paused, and its `stable_id` is refreshed
       (the display moved or changed resolution).
     - A paused id that is present under a different name now belongs to another display. The pause
       comes off that id, so the other display records and the popover shows it as not paused. The
       pause is kept, detached, for the display it was set on (at most 16 detached pauses, oldest
       forgotten first).
     - When a paused id has disappeared, or a pause is detached, and an unpaused monitor with the
       remembered `stable_id` appears, the pause moves to that id (logged at `info` as "monitor <old>
       reappeared as monitor <new>"). A vanished pause with no match stays on its old id.
   - Reason: Windows can hand out a new `HMONITOR` (our numeric id) after a reconnect, and can give an
     old value to a different display, so keying only on the id would either resume a display the user
     paused or silently pause one they did not. `stable_id` (name, size, position) is the base's
     reboot-stable identifier; the GDI device name (`\\.\DISPLAYn`) is the part of it that does not
     change when the user moves a display or changes its resolution.

4. **Which monitors does the status list, and where does it get them?**
   - Decision: the selected monitors (those passing `is_monitor_allowed`, including the stale
     allow-list fallback) of the latest enumeration, in the order the OS reported them. The
     enumeration is the one `VisionManager::start` and the monitor watcher (every 5 s) already make;
     the route itself makes no OS call. `active` is "a capture task is running and the monitor is not
     paused". With vision capture disabled the list is `[]`.
   - Reason: the spec infers "connected monitors that pass `is_monitor_allowed`". Serving a snapshot
     keeps the tray's frequent polling cheap and, on macOS, keeps the route from touching
     ScreenCaptureKit while the watcher has released it for DRM content.

5. **Status codes and bodies for refused control requests.**
   - Decision: success is `200 {"success": true, "message": ...}`. Failures use the same shape with
     `success: false`: `404` for a monitor id that is not connected (and not paused), `409` when vision
     capture is disabled or the monitor is excluded by the monitor selection, `500` when stopping or
     starting the capture task fails. Pausing an already paused monitor and resuming an unpaused one
     succeed.
   - Reason: the spec only gives `4xx/500 {"success": false, "message"}`; the success field mirrors the
     audio twin. Distinct codes let the popover's optimistic toggle roll back with a clear reason.

6. **What does resume do while capture is not running (DRM pause, outside work hours, start
   failure)?**
   - Decision: it lifts the pause and returns success; the monitor starts with the manager's next
     `start()`. While the manager is running, resume starts the monitor at once (404 if it is gone).
   - Reason: starting a single monitor while the rest of capture is deliberately stopped would defeat
     the DRM and schedule pauses.

7. **How does `VisionManager::start` count a start where every monitor is paused?**
   - Decision: if no task started only because every selected monitor is paused, `start` succeeds
     (status `Running`) and logs that the user paused all of them; the stale allow-list fallback is not
     triggered by that case. In the fallback path, paused monitors are skipped and the same rule
     applies. Zero enumerated displays now returns its own error saying the watcher will retry and
     classify the cause, instead of the stale-allow-list message.
   - Reason: matches the spec's start accounting; without it a fully paused setup would loop in the
     watcher's "start failed, retry" path or fall back to recording monitors the user paused.

8. **Is a `startup` row written when the layout is unchanged since the last run?**
   - Decision: no. The watcher's first pass compares the canonical JSON with the newest row
     (`SELECT layout_json FROM display_layout ORDER BY id DESC LIMIT 1`) and writes a `startup` row only
     when it differs (or the table is empty). Later passes write a `change` row whenever the JSON
     differs from the last row stored.
   - Reason: the spec infers "skip if identical to the latest row" from the latest-row query; the
     newest row still describes the arrangement, and W3-09's keep-newest delete rule preserves it.

9. **Timeout and retry for layout writes.**
   - Decision: one 5 s budget covers the read of the newest row and the insert. On a failure or
     timeout nothing is recorded as stored, a warning is logged once per failure run (then `debug`),
     and the next watcher pass (5 s later) re-reads the newest row before deciding, so a write that
     landed just before its timeout is not duplicated.
   - Reason: the spec says "bounded timeout (inferred ~5 s), retry on the next 5 s poll".

10. **Which displays go into a layout row, with which numbers?**
    - Decision: every enumerated display (selection and pauses do not matter), sorted by id with ties
      broken by `stable_id`; `x`, `y`, `width`, `height` are the integers `SafeMonitor` reports (on
      Windows the physical-pixel desktop coordinates W2-12 enumerates). An empty enumeration writes
      nothing. The reader accepts fractional numbers and rounds them.
    - Reason: the row exists to map global click points onto monitors, which needs every display;
      integers match the DDL comment's example; rows written by other builds may use floats.

11. **What exactly is stored in `ui_events.element_ancestors`?**
    - Decision: for a click, the containers of the hit element (not the element itself), outermost
      first, as `{"role": ..., "name": ...}` with `name` omitted when empty. The walk climbs the
      control view on Windows (stopping below the desktop root, class `#32769`) and `AXParent` on
      macOS (stopping below `AXApplication`), at most 16 levels and 40 ms. Names are trimmed,
      whitespace runs collapsed and cut to 100 characters; the JSON is capped at 2048 bytes by dropping
      the outermost entries first. Linux has no click element context in the base and stores `NULL`.
    - Reason: the spec gives the shape (root first, role and optional name) but no limits; the nearest
      containers say the most about the click, and the outer window is already in `window_title`.

12. **How are password fields kept out of the ancestor chain?**
    - Decision: an ancestor UIA marks `IsPassword` (or whose role is a password role, such as
      `AXSecureTextField`) keeps its role but never its name. The name-based password heuristic is
      not applied to containers. Separately, a clicked Windows element marked `IsPassword` no longer
      stores its `element_value`.
    - Reason: the coordinator asked that no text from password fields is ever captured. The name
      heuristic matches substrings such as "pin" and would strip names like "Shopping" from ordinary
      containers; containers do not hold typed secrets.

13. **Is `element_ancestors` returned by the ui-events read APIs?**
    - Decision: not yet. It is written on insert only; `UiEventRow`/`UiEventRecord` and their JSON are
      unchanged.
    - Reason: the spec records that the target selects the column but not the JSON key or location in
      any response; inventing one would be a guess at an interop shape.

14. **Should `/vision/device/status` be reachable without the API key, like `/audio/device/status`?**
    - Decision: not changed here; it uses the normal auth middleware.
    - Reason: the exemption list in `server.rs` belongs to W2-10, and the spec marks the target's
      read allow-list containing this path as unconfirmed. The app calls the route with its key.

15. **What happens to a resume that races a stop?**
    - Decision: `VisionManager::stop()` marks the manager `ShuttingDown`, then takes the same lock that
      single-monitor start, stop, pause and resume hold, and keeps it until the manager is `Stopped`.
      A resume already past its "is the manager running" check finishes inserting its task first, and
      the stop ends it; any later request sees the manager is not running and starts nothing.
      `start_monitor` refuses to start a capture task unless the manager is `Running`. The stop also
      ends HD recorders left behind by capture tasks that exited on their own.
    - Reason: `/vision/device/start` can arrive while a DRM or work-hours pause, a tray stop, a
      capture-session restart or a shutdown is stopping the manager. Without the lock a monitor could
      keep recording after the manager reported it stopped.

16. **Does the engine health say a fully paused setup is stalled?** (hand-off to W2-13)
    - Decision: not changed here. With every selected monitor paused, the manager is `Running` with
      no capture task, so `/health` reports `frame_status` `stale`. The app's capture-stall detector
      (`apps/screenpipe-app-tauri/src-tauri/src/health.rs`, the `vision_bad` check) counts that as a
      vision stall, and with restart notifications on (off by default) tells the user screen capture
      stalled.
    - Hand-off: health belongs to W2-13 (`routes/health.rs`, `vision_reason` and `capture_status`),
      which merged before this WP; the follow-up goes to whichever WP next edits those paths. The
      engine can tell from `VisionDeviceControl::global().status()`: when every returned row has
      `user_disabled: true` (and the list is not empty), vision is paused by the user, so health
      should report that reason and leave the monitors out of the frame-staleness signal.

17. **Which edits fall outside the owner paths?**
    - `crates/screenpipe-a11y/src/platform/windows_uia.rs` (later owned by W4-13) and
      `crates/screenpipe-a11y/src/platform/macos.rs` gained the ancestor walk for clicks
      (`element_ancestors`).
    - Two Windows behaviour changes go beyond the listed items, and the W4-13 merge has to keep them:
      `element_value` is no longer stored for an element UIA marks `IsPassword`, and
      `element_from_point(x, y, &config)` now builds its cache with the element-scope, full-mode
      walker request (`walker_cache_request`) instead of the subtree request, so the hit element has
      a live reference to climb from with `GetParentElementBuildCache`.
    - None of this compiles on the Linux VM: CI's windows job must build it, and SMK-W2-11-5 checks
      on Windows that clicks still record their own role, name and bounds.
