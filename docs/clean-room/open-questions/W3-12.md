# W3-12 open questions

Decisions taken while building the dedicated Windows OCR worker and OCR availability reporting
(vision-windows-ocr-worker).

## 1. Queue capacity and what "full" means

- **Question:** the spec infers a bounded channel of capacity 4 and a `try_send` that fails with
  "queue full"; it does not say whether the request being processed counts.
- **Decision:** up to 4 requests wait behind the one being processed (a `sync_channel(4)`), so 5 can
  be outstanding. A fifth waiting request is refused at once with `OcrWorkerError::QueueFull`; live
  capture stores the frame without OCR text and logs at debug level, with a warning at most once a
  minute that counts the skipped requests.
- **Reason:** matches the inferred capacity, never blocks the capture loop, and keeps the log quiet
  under sustained load.

## 2. Image size limit: scale down or refuse

- **Question:** the binary refuses images whose width or height is above the size limit; the spec
  infers that scaling down to `OcrEngine::MaxImageDimension` is better than failing.
- **Decision:** two limits. A source side above 32768 px is refused (`WidthTooLarge` /
  `HeightTooLarge`): no capture is that large, so it is a corrupt frame and must not drive an
  allocation. Anything else is scaled down, keeping the aspect ratio, to fit the engine's
  `MaxImageDimension` (read on the OCR thread; 10000 assumed until then) and a budget of 25
  megapixels (5K and 6K frames pass unscaled). The worker re-checks every image against the real engine limit before a
  `SoftwareBitmap` is created. Zero sizes, an empty buffer, a stride that does not fit whole BGRA
  pixels, a buffer shorter than the dimensions need, and arithmetic overflow are refused without a
  panic.
- **Reason:** an 8K or ultrawide monitor should still get OCR text; only impossible sizes are
  errors. Word boxes stay correct because they are normalised to the scaled bitmap.

## 3. Pixel path into WinRT

- **Question:** the base encoded every frame to PNG and decoded it with `BitmapDecoder`; the target
  validates a BGRA buffer against its dimensions, which implies a raw buffer.
- **Decision:** the caller converts the frame to tightly packed BGRA (scaled if needed) and the
  worker copies it into a `SoftwareBitmap` with `CreateCopyFromBuffer(Bgra8)`.
- **Reason:** drops a PNG encode and decode per frame, and gives the validation something exact to
  check.

## 4. Deadlines

- **Question:** the spec gives no OCR timeout.
- **Decision:** live capture waits at most 10 s (well under the capture loop's 15 s per-capture
  deadline, so a slow OCR becomes a frame without text rather than a dropped frame); the on-demand
  route waits 30 s. A caller that gives up drops its reply channel, and the worker skips that
  request when it reaches it.
- **Reason:** capture reliability first (DECISIONS.md 6).

## 5. Restart and stuck-thread policy

- **Question:** the spec names errors for a worker that exited before taking a request, a stopped
  worker and a failed start, but not when to restart.
- **Decision:** a panic answers its caller with an error and ends the thread; requests queued behind
  it get "worker stopped before it reached this request" instead of hanging; the next request starts
  a new thread. A thread busy with one request for more than 60 s is left behind and replaced, at
  most two at a time (then requests get `Stuck`). More than 5 restarts within a minute pause new
  starts with `StartFailed`. The lock around the worker slot recovers from poisoning instead of
  failing every later request.
- **Reason:** a crashed or wedged WinRT call must not stop OCR for the rest of the session, and a
  handler that always crashes must not spin.

## 6. On-demand concurrency

- **Question:** the spec says on-demand concurrency is tracked (`inflight`) but sets no limit.
- **Decision:** at most 2 on-demand OCR requests in flight; a third gets 503 with
  `{"error", "frame_id"}`. A full queue, a missing OCR engine, a timeout and an OCR thread that
  crashed or is being replaced are also 503; an image the engine refuses and other engine errors
  are 500. Nothing is cached in those cases, so the timeline retries later (the
  frontend already treats a non-2xx answer as "no text yet" and does not cache it). Each start logs
  `frame` and `inflight`.
- **Reason:** keeps at least half of the shared queue for live capture while the timeline scrubs, and
  stops a failed OCR from being cached as "this frame has no text" (the base returned 200 with an
  empty list).

## 7. Test override for "no OCR installed"

- **Question:** the acceptance check needs `/health` to report `ocr_unavailable` on a machine that
  has OCR, and the binary has no such switch.
- **Decision:** `FREENPIPE_OCR_FAULT=unavailable` (or `1`/`true`), documented in docs/env.md under
  "Freenpipe only", makes the probe and every OCR backend behave as if nothing were installed. It
  follows the existing `FREENPIPE_WHISPER_GPU_FAULT` hook. Tests use the in-process twin
  `ocr_availability::simulate_ocr_unavailable`.
- **Reason:** a Freenpipe-only name cannot collide with a screenpipe variable.

## 8. When availability is probed and what counts

- **Question:** "probed once at startup" does not say where, and whether Windows should fall back
  to tesseract when no WinRT language is installed.
- **Decision:** a background worker (`ocr_availability_probe` in the engine's worker registry) probes
  once per engine start. Windows: available when the OCR thread lists at least one recognizer
  language or can create an engine from the user's profile languages; a bundled or installed
  tesseract is logged but live capture does not fall back to it. macOS: Apple Vision is always
  available. Linux: available when a tesseract binary is found. Later OCR attempts keep updating the
  state (an engine created later clears the reason; three tesseract failures in a row set it).
- **Reason:** live capture on Windows only uses WinRT, so reporting tesseract as "available" there
  would hide the real problem.

## 9. Tesseract discovery and per-session disable

- **Question:** the spec lists the places a bundled tesseract may live but not their order.
- **Decision:** rusty-tesseract's own search first (`PATH`, working directory, the engine's folder
  and its `lib`, `~/.local/bin`), then `tesseract/`, `resources/tesseract/` and `Tesseract-OCR/`
  beside the engine, `$APPDIR/usr/bin` and `$APPDIR/bin`, then installer defaults
  (`%ProgramFiles%\Tesseract-OCR` and friends on Windows, Homebrew and MacPorts folders on macOS,
  `/usr/bin`, `/usr/local/bin`, `/snap/bin` on Linux). The binary found is started by its full path
  (Freenpipe builds the tesseract command line itself instead of going through rusty-tesseract's
  own lookup). Its language data folder is the user's `TESSDATA_PREFIX` when set, otherwise the
  first candidate folder holding `eng.traineddata` (next to the binary, beside the engine, under
  `$APPDIR`, then the distro paths the base already knew), and it is passed as `TESSDATA_PREFIX`
  to the tesseract child process only. Neither `PATH` nor `TESSDATA_PREFIX` of the engine process
  is changed (the base did set `TESSDATA_PREFIX` at runtime). With no binary, one warning says OCR
  is off for the session and suggests installing tesseract-ocr; OCR calls then return at once.
- **Reason:** GUI launches often have a short `PATH`, and failing on every frame wasted a process
  spawn and a log line each time. Changing the process environment at runtime races with other
  threads, and C libraries, that read it at the same moment.

## 10. The app's OCR notice

- **Question:** the spec says the app shows a one-time notification; "one-time" could mean once ever
  or once per session, and no settings key exists to remember it.
- **Decision:** once per app session, after `/health` has reported `ocr_unavailable` for 5
  consecutive checks, through the existing in-app notification panel (no actions, dismisses after
  45 s). The text is written fresh and gives a platform-specific fix. On macOS, while the overlay
  is open the notice is held back (the panel would steal its focus, as the stall notice already
  avoids) and comes due again after another 5 checks.
- **Reason:** no new settings key (those belong to W1-02), and a user who has not fixed the problem
  is reminded on the next launch only.
- **Scope note for the PR description:** the notice lives in
  `apps/screenpipe-app-tauri/src-tauri/src/health.rs`, which PLAN.md lists under W2-13 (merged), not
  under W3-12. The edit is one self-contained region (the OCR notice state and its check) added for
  this WP's "the app shows a one-time notification" item; nothing W2-13 wrote is changed. It adds
  no tauri command or exported type, so `lib/utils/tauri.ts` is unchanged.
