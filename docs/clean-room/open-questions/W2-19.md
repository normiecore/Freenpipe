# W2-19 open questions

Decisions taken while adding the GPU runtimes (audio-019, audio-020/shell-030), the bundled models
and runtime (audio-022, shell-029). Licences and sources of everything shipped or downloaded are
also listed in `docs/dev/bundled-runtime-licences.md`.

## 1. What `SCREENPIPE_DIRECTML` values mean

- **Question:** audio-020 reads the variable as "anything other than `true`/`1` disables DirectML",
  shell-030 as "a false value disables it". Which one, and what does an unset variable mean?
- **Decision:** Unset or empty: automatic (DirectML when an adapter qualifies). `1` or `true`
  (any case): on, still subject to the adapter checks. Any other value, `0`, `false`, `off` and typos
  included: CPU, logged as explicitly disabled.
- **Reason:** this is audio-020's reading, which the spec says to settle on, and it fails safe: an
  unrecognised value never turns a GPU path on. Treating unset as automatic keeps DirectML on by
  default in DirectML builds, which is what the shipped binary does.

## 2. Where the DirectML policy lives (audiopipe revision)

- **Question:** The target uses a newer audiopipe revision (b099a2e) for DirectML recovery and
  session recycling. Upgrade the vendored audiopipe, or implement it locally?
- **Decision:** Locally. Vendored audiopipe (2fd5c36) gains only an explicit execution-provider
  argument (patch `0003-explicit-execution-provider.patch`, recorded in `third_party/README.md`);
  adapter choice, recycling and CPU recovery are Freenpipe code in
  `transcription/parakeet_windows.rs`.
- **Reason:** the newer revision's licence has not been cleared (PLAN.md W2-19 asks for Freenpipe
  code until it is), and the policy is small enough to own.

## 3. Adapter choice and recycling interval

- **Question:** Which qualifying adapter wins, and after how many inferences are DirectML sessions
  rebuilt?
- **Decision:** Skip software and remote adapters and every adapter that fails `D3D12CreateDevice`
  at feature level 11_0 or the architecture query. Prefer a discrete adapter (not UMA), then the
  most dedicated video memory, then the lowest DXGI ordinal; the ordinal is the DirectML device id.
  Rebuild after 500 inferences (one 30-second chunk is one inference). A failed rebuild, a failed
  provider start or a failed DirectML inference moves Parakeet to CPU for the rest of the process.
  Before probing adapters the engine checks that `DirectML.dll` can be loaded (application folder
  or System32), because ONNX Runtime only loads it when the provider is first used.
- **Reason:** the spec asks for "discrete or high dedicated memory" and infers N = 500. A missing
  `DirectML.dll` would otherwise surface as a delay-load failure inside ONNX Runtime.

## 4. The `vulkan` feature and audiopipe's ggml backend

- **Question:** The base maps `vulkan` to `audiopipe?/vulkan-ggml` only; the spec says whisper must
  be built on ggml-vulkan. Keep both in one feature?
- **Decision:** `vulkan = ["whisper-rs/vulkan"]`. The old mapping moves to a separate opt-in feature,
  `vulkan-qwen3-ggml`, that no release enables.
- **Reason:** `audiopipe/vulkan-ggml` turns on audiopipe's ggml Qwen3 engine, which builds and
  statically links a second ggml next to whisper's (same library names), and Freenpipe's Qwen3 path
  uses the antirez engine, not ggml. The target's ggml-vulkan code sits in whisper-rs-sys.

## 5. Which Windows builds get Vulkan

- **Question:** Enable `vulkan` on both Windows release targets?
- **Decision:** x64 only (`release-app.yml` tauri-args). The ARM64 build keeps CPU whisper.
- **Reason:** the evidence is from the x64 install, and the ARM64 runner would need an ARM64 Vulkan
  SDK and loader that nobody has verified. Revisit when an ARM64 device is available for smoke tests.

## 6. Shipping `DirectML.dll`

- **Question:** The target ships Microsoft's DirectML redistributable. Decision 7 allows only
  permissive and weak-copyleft components. May Freenpipe ship it?
- **Decision:** Not by default. The DirectML build of ONNX Runtime (MIT) is bundled; `DirectML.dll`
  (NuGet `Microsoft.AI.DirectML` 1.15.4, pinned by SHA-256) is staged only with
  `FREENPIPE_BUNDLE_DIRECTML=1`, which no workflow sets. Without it ONNX Runtime loads the
  `DirectML.dll` that Windows 10 1903 and later provide in System32; when that copy is missing or
  too old for the provider, Parakeet falls back to CPU. Item for the release licence audit.
- **Reason:** the redistributable's terms are Microsoft's own proprietary licence (redistribution
  inside applications for Windows or Xbox, a data-collection clause), not one of the licences
  decision 7 lists. The audit can switch it on with one variable.

## 7. ONNX Runtime build and version

- **Question:** The spec infers `ort =2.0.0-rc.12` and a DirectML-capable ONNX Runtime. Bump `ort`?
- **Decision:** Keep `ort =2.0.0-rc.10` (ONNX Runtime API 1.22) and ship ONNX Runtime 1.22.0 from
  the `Microsoft.ML.OnnxRuntime.DirectML` NuGet package instead of the CPU-only release zip. The
  stage script pins the package by SHA-256, checks each DLL's PE machine type against the target
  architecture, and ships the package's `LICENSE` and `ThirdPartyNotices.txt` next to the DLLs.
  `tauri.windows.conf.json` takes ONNX Runtime only from `bundled/runtime/`; the CPU zip stays as an
  offline fallback for dev builds.
- **Reason:** the CPU build cannot register the DirectML provider at all (the base shipped
  `--features directml` with a CPU runtime, so DirectML never ran). An `ort` upgrade touches every
  ONNX user in the workspace and is not needed for DirectML.

## 8. Source and pin of `vulkan-1.dll`

- **Question:** Where does the shipped Vulkan loader come from, and how is it pinned?
- **Decision:** LunarG's `vulkan-runtime-components.zip` for the same SDK version the build uses
  (1.4.313.0), unpacked by `release-app.yml` and staged with its licence text as
  `VulkanRT-License.txt` (the SDK's licence file when the runtime package has none; the script
  refuses to ship the DLL without one). The workflow writes the DLL's SHA-256 and Authenticode
  status to the job summary and warns when the signature is not valid. A post-build step fails the
  release when `vulkan-1.dll` is missing next to the exe of a `vulkan` build.
- **Reason:** the build VM cannot reach sdk.lunarg.com, so no hash could be recorded here. Follow-up:
  pin the SHA-256 after the first release run. The loader is the Khronos Vulkan loader
  (Apache-2.0), allowed by decision 7 with its notice.

## 9. Silero VAD source, pin and cache compatibility

- **Question:** The base downloads `silero_vad.onnx` from silero-vad's `master` branch, a moving
  address whose file changes with new Silero releases. What does Freenpipe ship and download?
- **Decision:** Silero VAD v5.1.2, from snakers4/silero-vad at commit
  `6478567951ae5c9979ad7b234185b5515f4be7a1` (the commit the `v5.1.2` tag names), pinned by size and
  SHA-256, stored as `silero_vad_v5.onnx`. An installed copy must have the pinned size; a cache copy
  (`<cache>/screenpipe/vad/silero_vad_v5.onnx`) is used as it is when it is not empty, because
  screenpipe may have written any v5/v6 file there and the vad-rs fork reads both. A copy that fails
  to load is deleted from the cache (or skipped, when installed) and the pinned file is fetched.
- **Reason:** a fixed commit is the only way to make the download reproducible; the cache rule
  keeps drop-in compatibility with an existing screenpipe cache.

## 10. Silero in the repository

- **Question:** audio-022 suggests adding a silero copy to the repository next to the pyannote
  models. Commit the 2.3 MB ONNX file?
- **Decision:** No. Only its `NOTICE.md` is committed (`crates/screenpipe-audio/models/silero/`);
  the installer build downloads the pinned file and checks it.
- **Reason:** the pyannote files live in Git LFS, which cloud sessions cannot push to, and a pinned
  download from the original publisher gives the same guarantee.

## 11. Install layout of the speaker models

- **Question:** The target installs the speaker models flat in `<install>/models/`; Freenpipe's
  installer (W0-09) uses `<install>/models/pyannote/`. Switch?
- **Decision:** Keep Freenpipe's layout for shipping and search both: `models/pyannote/` first,
  then the flat `models/`, under every install root, before the cache.
- **Reason:** keeps the W0-09 layout (with its NOTICE) intact while reading a folder laid out the
  way screenpipe lays it out.

## 12. Model lookup order and the Tauri resource directory

- **Question:** audio-022 lists exe directory, Tauri resource directory, cache, download. How is the
  resource directory found without a Tauri handle in the audio crate?
- **Decision:** The install roots derived from the executable path (`install_roots`: the exe
  directory, macOS `Contents/Resources`, the Linux `/usr/lib/<product>` directories) stand in for
  the resource directory. On Windows the resource directory is the exe directory. No copy into the
  cache on first use.
- **Reason:** the spec marks copy-on-first-use optional, and the engine also runs as a bare CLI.

## 13. Downloads that do not match their pin

- **Question:** A pinned download returns different bytes. Retry?
- **Decision:** No. The bytes never reach the cache, and the URL is treated like a 404 for the rest
  of the process (waiters stop at once, no retry loop). A restart tries again.
- **Reason:** different bytes at a commit-pinned address do not fix themselves, and the silero
  waiter would otherwise download the file again and again.

## 14. Uninstall cleanup

- **Question:** shell-029 asks to remove `$INSTDIR\crash-dumps` and stray runtime folders. How far?
- **Decision:** `crash-dumps` is removed recursively; in `frames`, `vad`, `models` and
  `models\pyannote` only the named files the engine can write are deleted, and the folders are
  removed only when empty.
- **Reason:** a user can pick a shared folder as the install directory; recursive deletes of
  generic names such as `models` could remove their files.

## 15. Forcing a GPU failure for the acceptance check

- **Question:** The acceptance check asks to force a whisper GPU failure "via test env". Which
  variable?
- **Decision:** `SCREENPIPE_WHISPER_GPU_FAULT` (a Freenpipe-only name): `inference` (or `1`/`true`)
  fails GPU inference, `state` fails GPU state creation. CPU sessions are never affected.
- **Reason:** the target has no such hook; the name follows the `SCREENPIPE_*` convention and is
  documented in `docs/dev/windows-build.md`.
