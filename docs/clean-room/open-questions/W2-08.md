# W2-08 open questions

Decisions taken while building Meetings API v2: calendar binding, the summary save and status
routes and the room-change route (db-012, meetings_memory-025, -026, -032, -047, api-014).

## 1. Calendar binding outcomes

- **Question:** db-012 and meetings_memory-047 say a UNIQUE violation on
  `idx_meetings_calendar_event_id` means "already bound elsewhere" and must not fail the write, but do
  not say what happens to the rest of the request, nor what to do when the meeting already carries a
  different event.
- **Decision:** `bind_meeting_calendar_event` (in `ext/meetings_v2.rs`) runs inside one write
  transaction. It only fills an empty column, never overwrites an existing event, and reports
  `Bound`, `AlreadyBound`, `OwnedElsewhere`, `MeetingHasOtherEvent` or `MeetingMissing`. The owner is
  looked up first; the unique violation is still caught (matched on the column or index name) for a
  writer that bypasses the lookup. Ids are trimmed and a blank id means "no event".
- **Reason:** one event names at most one meeting, and a user's or detector's earlier choice is
  never silently replaced.

## 2. `PUT /meetings/:id` with a refused binding

- **Question:** meetings_memory-047 says "skip the bind, keep the title" on a conflict. Attendees
  are part of the same enrichment.
- **Decision:** when the bind is refused (owned elsewhere, or the meeting carries another event),
  the request's `title` and `attendees` are both dropped, every other field (`note`, times, app) is
  applied, and the route answers 200 with the meeting as stored. An unknown meeting is 404.
- **Reason:** title and attendees come from the event; applying them to a second meeting is the
  duplicate naming the index exists to prevent, while a note edit in the same request is the
  user's own text.

## 3. `POST /meetings/start` with `calendar_event_id`

- **Question:** meetings_memory-032 says "a failed claim is reported as an error" without saying
  whether the start fails.
- **Decision:** the meeting starts (or is adopted or resumed) as before, then the event is claimed.
  A refused claim is logged as a warning and a database error as a warning with the error; the
  start still returns 200 and keeps the title and attendees the user started with.
- **Reason:** a manual start is an explicit user action; refusing to record because the event was
  bound earlier (for example after a stop and restart from the same calendar entry) would lose the
  meeting. The title came from the user's own click, so it stays.

## 4. Manual start `detection_source`

- **Question:** api-014 lists `manual_start` and `manual_start_possible_missed_detection` as
  detection sources; the base writes `manual` and uses the second string only as a feedback label.
- **Decision:** inserted rows keep `detection_source = 'manual'`; the feedback label is unchanged.
- **Reason:** `close_orphaned_meetings` and the app key off `detection_source = 'manual'`, and rows
  written by screenpipe with either value read back unchanged. Changing the stored value is a
  detector decision (W3-08 / W4-12).

## 5. Status codes on start

- **Decision:** resuming `id` while a different meeting is active now answers 409 with
  `another meeting is already active`, the same as the `idx_meetings_single_open` race on insert
  (was 400).
- **Reason:** meetings_memory-032 maps "a different meeting is already open" to 409.

## 6. Summary body, failure check and section merge

- **Question:** the body field names, the failure heuristic and the section rules are inferred.
- **Decision:**
  - Body `{summary, title?}`. A leading `#`/`##`/`###` heading reading "Summary" is dropped, and
    level 1/2 headings inside the text (outside code fences) become level 3, so the section stays
    one block a later save replaces whole.
  - 400 for blank text and for text that reads as a failure notice. The check
    (`summary_rejection`, shared with the W3-06 finalizer) refuses:
    - a short reply (up to 160 characters) such as "N/A", "No transcript available.",
      "Nothing to summarize." or "Not enough transcript content";
    - a first sentence in which the assistant talks about itself (an apology, a first-person
      "I couldn't" / "I was unable", an `Error:` label, or "Unfortunately, I ...") and names the
      summary or its input (transcript, recording, audio, speech) with a lack word;
    - a first sentence that says the summary was not made without an "I": "Unfortunately" with
      "summar..." and an inability word ("could not", "unable", "not possible", "no summary"), or
      "Unable to" / "Failed to" followed by a task verb (summarize, generate, fetch, read...);
    - a short text that is a single clause opening with "Unfortunately" and saying the input is
      missing ("Unfortunately, no transcript was available.").

    Summaries are written in the third person, so "Unfortunately" on its own is not enough: "Unfortunately the launch
    slipped", "Unfortunately, the recording of the demo failed, so the team rescheduled it",
    "Unfortunately there's no recording of the first half; the second half covered ...",
    "Failed to ship the audio feature, so ..." and "No audio issues this week..." are accepted.
    When in doubt the check accepts: a saved odd summary can be edited, a refused real one is
    lost.
  - The last `## Summary` heading (case-insensitive, optional colon, outside code fences) starts
    the section, which runs to the next level 1 or 2 heading or the end; it is replaced in place.
    Without one, `\n\n## Summary\n<summary>` is appended. A non-blank `title` retitles the meeting.
  - The read, merge and write happen in one write transaction. 404 for an unknown meeting, 500
    when the row vanished right after the update.
- **Reason:** follows meetings_memory-026; a user section with the same heading earlier in the note
  is left alone because the agent's section is always the one it wrote last.

## 7. Summary status fields and derivation

- **Question:** meetings_memory-026 calls the field `state`; api-014 calls it `status`.
- **Decision:** both are returned with the same value (`idle`, `pending`, `running`, `ready`,
  `failed`). `execution_id`, `execution_status`, `error_type` and `error_message` are omitted when
  there is no run. The newest `pipe_executions` row of the pipe (`?pipe=`, default
  `meeting-summary`) with `trigger_event = 'meeting_ended'` and `trigger_key` equal to the meeting
  id or starting with `<id>:` (recovery runs) is used; `not_before` must be RFC 3339 (400
  otherwise) and is compared with the run's start (or finish when it never started). A
  `pipe_event_runs` claim claimed in the last 30 minutes (and not before `not_before`) with no
  execution row reports `pending`. `queued` is `pending`, `running` is `running`, `completed` is
  `ready`, anything else `failed`. `error_type = 'summary_not_saved'` reports a fixed message that
  the run ended without saving a summary. `auto_summary_enabled` is true when that pipe exists, is
  enabled and lists `meeting_ended` among its trigger events.
- **Reason:** keeps clients written against either name working. The 30-minute window keeps an old
  claim whose execution history was pruned from reading as queued forever. The scheduler does not
  record trigger keys yet (W3-06, meetings_memory-028), so real runs read as `idle` until then.

## 8. Room change without an audio-process detector

- **Question:** meetings_memory-029 has the audio-process detector raise the prompt and perform the
  switch after it hears `meeting_room_change_response`. That detector is W4-12 and does not exist.
- **Decision:** the route performs the switch itself. `switch` ends the meeting with
  `end_reason = 'room_changed'` and opens a successor for the same app with
  `detection_source = 'audio_process_room_change'` in one write transaction (no title, attendees,
  note or event), appends the old meeting's typed text as on any end, puts the successor in the
  manual slot, then emits `detector_stop_tracking`, `meeting_ended` (with `end_reason`),
  `meeting_started` and `meeting_room_change_response`. `keep` changes nothing and emits the
  response. The response is `{meetingId, token, decision, activeMeetingId, newMeetingId,
  resolvedBy}`; `activeMeetingId` lets a future detector adopt the successor instead of switching a
  second time.
- **What the manual slot gives the successor today:** the UI-scan detector stands down while it
  is open (no second row for the same call), `/meetings/status` and the stop button target it, and
  the streaming controller's inactivity auto-end targets it, but that controller only runs with
  live meeting transcription on. With local batch transcription nothing ends the successor when
  the call ends: it stays open until the user stops it, and the UI-scan detector scans nothing
  until then. Ending it with the call needs the detectors to adopt it (hand-offs below).
- **In-meeting flag:** the UI-scan detector's `detector_stop_tracking` branch lowers the audio
  pipeline's in-meeting flag without looking at the manual slot (meeting_detector.rs, W3-08), and
  while the slot is taken it never raises it again. So when the detector was tracking the old
  meeting, the successor would read as no meeting at all: batch transcription stops deferring, a
  `+HD` session drops to its short timer and `/health` reports `meeting_detected: false`. Until
  W3-08 changes that branch, the route spawns a small task that re-raises the flag (checked every
  second, under the slot's read lock) for as long as the successor holds the slot. The stop route
  and the detector's auto-end clear the slot under the write lock before they lower the flag, so
  the task never raises it after a real end, and it exits as soon as the slot holds anything else.
- **Hand-offs:**
  - **W3-08:** in the `detector_stop_tracking` branch, call
    `sync_meeting_flag(manual_meeting.read().await.is_some(), ..)` instead of
    `sync_meeting_flag(false, ..)`. The route's flag task can then go.
  - **W3-08 / W4-12:** the detector that raised the prompt (W4-12's audio-process detector, or
    the UI-scan detector if it ever raises one) listens for `meeting_room_change_response` and,
    after `switch`, adopts `activeMeetingId` as the meeting it tracks (and takes it out of the
    manual slot), so the successor ends with the call like any detected meeting.
- **Reason:** the acceptance check needs the switch to happen through the route today, and doing it
  in one place keeps a later detector from creating a third row.

## 9. Room-change tokens and errors

- **Question:** the token is one-time, but nothing issues offers yet; the error codes are given as
  "409/410".
- **Decision:** `register_room_change_offer(meeting_id, token)` records an offer in process (15
  minute lifetime, a newer offer replaces an older one); `withdraw_room_change_offer` lets the
  issuer settle it itself. An answer whose token matches consumes the offer. A token for a meeting
  with no registered offer is accepted (offers raised before a restart, or by no issuer at all).
  Errors: 400 `decision must be 'switch' or 'keep'` for any other decision (checked first), 400 for
  a missing `meetingId` or blank token, 404 for an unknown meeting, 410 when the meeting has ended,
  409 when a newer offer replaced the one being answered. `meeting_id` is accepted as an alias of
  `meetingId`, and the decision is case-insensitive. An answer accepted with no registered offer
  is logged at debug level.
- **Hand-off (W4-12):** nothing calls `register_room_change_offer` yet, so until W4-12 lands any
  non-blank token is accepted and the one-time rule is not enforced. W4-12 must call
  `register_room_change_offer(meeting_id, token)` when it emits `meeting_room_change_offer`, and
  `withdraw_room_change_offer` when it settles a prompt on its own. The route sits behind API
  auth, like `/meetings/stop`, which can end the same meeting.
- **Reason:** stale prompts must not end the wrong call; without an issuer, refusing every token
  would make the route unusable.

## 10. Transcript order and offsets

- **Decision:** `GET /meetings/:id/transcript?order=ascending|descending` (also `asc`/`desc`,
  default ascending, anything else 400). `audioStartTimeSecs` is the background row's
  `audio_transcriptions.start_time` (its offset inside `audio_file_path`); live rows return null.
- **Reason:** meetings_memory-032 names the field and the two orders; live rows have no chunk.

## 11. `q` over `meeting_app`

- **Decision:** `GET /meetings?q=` also matches `meeting_app`, and the term is matched literally:
  `%`, `_` and `\` are escaped and bound with `ESCAPE '\'`.
- **Reason:** a search box means a literal substring (same choice as W2-16's speaker search).

## 12. Export without audio

- **Decision:** `POST /export` takes `include_audio` (default true). `false` reads no audio chunks
  and writes a silent video; the response's `audio_chunk_count` is 0.
- **Reason:** api-014 gives the default; skipping the query also skips decoding audio files.

## 13. Stop event order

- **Decision:** `POST /meetings/stop` emits `detector_stop_tracking` before `meeting_ended` (the base
  sent it after), and the detector event uses the stored `meeting_app`.
- **Reason:** meetings_memory-032 gives the order; the detector must be idle before pipes react.

## 14. Bundled meeting-summary pipe

- **Decision:** the prompt is rewritten in our own words. It drops the base `screenpipe-cloud`
  preset, so runs use the user's own default AI preset. It finds the meeting (or uses the id it was
  given in chat), reads `/meetings/<id>/transcript` with an audio-search fallback, prints the
  section starting with `## Summary`, then saves through `POST /meetings/<id>/summary` with a body
  written by a JSON encoder, and stops without saving when nothing was said. The in-app
  "summarize with AI" instructions (`buildMeetingSummarizeInstructions`) save the same way.
- **Reason:** meetings_memory-026 and -027; the server merge replaces the read-modify-write that
  lost summaries.

## 15. Where the new routes are mounted

- **Question:** PLAN section 5 sends new routes through the `routes/ext.rs` seam, and section 6
  gives `server.rs` to W1-03, W2-10 and W2-13.
- **Decision:** `POST /meetings/:id/summary`, `GET /meetings/:id/summary-status` and
  `POST /meetings/room-change` are added to the existing `/meetings` block of the route table in
  `server.rs` (one import hunk and three route lines, no other change).
- **Reason:** the handlers live in `routes/meetings.rs` next to the routes they extend, and
  `ext.rs` has no meetings module: mounting there would mean a new module line in `routes/mod.rs`
  and a new entry in `ext.rs`, both W1-03 files, to move three lines out of a block that already
  holds every `/meetings` route. Keeping them in that block keeps one OpenAPI group, the same auth
  layer and one place to read the meetings route order. The hunks do not touch W2-10's
  auth-exemption list or W2-13's health ticker.
