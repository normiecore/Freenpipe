# W3-30 open questions

Decisions taken while building the low-disk recording guard (shell-006) and keep-awake
(shell-007). Each one is the worker's call; the owner can overturn any of them.

## 1. Threshold and recovery numbers

- **Question:** the spec observed the event fields but not the numbers. It suggests
  max(2 GiB, 2 % of the volume) with recovery 1 GiB higher.
- **Decision:** threshold = 2 % of the volume, clamped to at least 2 GiB and at most 10 GiB;
  recovery threshold = threshold + 1 GiB. Free space is "available to the caller"
  (`GetDiskFreeSpaceExW` free-bytes-available, `statvfs` `f_bavail`), so quotas and root-reserved
  blocks count as used. The volume is read once at start and then every 30 s
  (`checkIntervalSeconds` = 30); a read that takes over 10 s counts as failed and is not
  restarted until it ends.
- **Reason:** without a cap, 2 % of a 2 TB drive would stop recording with about 40 GB still
  free, which reads as a bug to the user. 2 GiB is many minutes of capture even at a high write
  rate, so 30 s reads leave plenty of margin. The 1 GiB headroom stops a volume that hovers
  around the threshold from stopping and starting capture repeatedly.

## 2. No threshold override for testing

- **Question:** the acceptance check talks about "a test threshold above free space", but the
  spec has no settings key or environment variable for the threshold.
- **Decision:** no new key or env var. Tests inject a fixed threshold rule and a scripted
  free-space probe (`ThresholdRule::Fixed`, `FreeSpaceProbe`); one test runs the real probe on a
  temp data dir with a threshold above its free space and then below it. The Windows smoke
  check uses a small VHD as the data dir and a filler file to cross the threshold.
- **Reason:** the coordinator asked for missing keys to be recorded rather than invented, and
  settings keys and env vars are interop identifiers.

## 3. Windows keep-awake mechanism

- **Question:** the spec (and the plan text) name `SetThreadExecutionState` on a dedicated thread;
  the coordinator asked for a power request (`PowerCreateRequest` / `PowerSetRequest` with a
  SYSTEM request) that `powercfg /requests` lists.
- **Decision:** the dedicated `screenpipe-keep-awake` thread takes a power request with
  `PowerRequestSystemRequired` and a reason string; if the request cannot be created or set, it
  falls back to `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` on the same
  thread. Disabling clears whichever was taken, from the same thread. The display may still
  turn off (no display request).
- **Reason:** both show under SYSTEM in `powercfg /requests`, but the power request carries a
  reason the user can read there and does not depend on thread state. Keeping the thread and
  the fallback preserves the observed design and works where power requests are restricted.

## 4. macOS and Linux keep-awake

- **Question:** the spec allows "equivalent assertion or no-op".
- **Decision:** macOS runs `caffeinate -i -w <pid>`; Linux runs
  `systemd-inhibit --what=idle:sleep --mode=block cat` with `cat` reading a pipe from the app. Both
  end on disable and when the app dies. Where neither tool exists, `set_keep_awake(true)` returns
  an error that names the missing tool.
- **Reason:** no new native dependencies, and the hold can never outlive the process. An honest
  error is better than a switch that silently does nothing.

## 5. Who saves `keepComputerAwake`

- **Question:** the spec says the setting is applied at startup and live through
  `set_keep_awake`, but not who writes the setting.
- **Decision:** `set_keep_awake(enabled)` only applies the value; the settings page saves
  `keepComputerAwake` like every other setting. Startup applies the saved value (only when it is
  on, so the thread does not exist otherwise). The quit teardown releases the hold in its last
  step (`keep_awake`, after the capture, engine, drain, pool and Pi steps, so a wedged keep-awake
  thread can never shorten the critical steps; the OS releases the hold at exit anyway), and a
  failed safe relaunch takes it again. An enable the thread does not confirm within 3 s returns an
  error and is undone: a release is queued right behind it, so the switch, which stays off, never
  leaves the computer held (review round 2). That also covers the startup apply: a saved "on" that
  times out is logged and not held, the same as when the OS refuses.
- **Reason:** writing the store from Rust while the frontend also writes it would race; this
  matches how the other settings switches work.

## 6. When the guard stops and restarts capture

- **Question:** the spec says stop capture on `disk_space_low` and that recovery re-arms the
  notification; it does not say what happens to a recording the user starts or pauses during an
  incident.
- **Decision:** the guard acts once on each fresh low reading. Every engine monitor run has its own
  generation (`DiskPressureStatus.generation`, a new number per `ServerCore` start), and a reading
  is fresh when the guard has not acted on that generation in the current incident. On a fresh
  reading with the guard on, it stops capture if recording is on (and notices: see 7), and
  remembers both the generation and the recording-intent epoch right after its stop
  (`health::recording_intent_epoch`, a counter of intent changes). Further low readings of the same
  run change nothing, so a recording the user starts after the guard acted keeps running until the
  next fresh reading. That is the way to record on a nearly full disk without touching settings.
  Which starts produce a fresh reading follows from where the monitor lives (a background worker of
  `ServerCore`, started and stopped with the engine, not with capture):
  - no new run, so the start stands: the tray's start, a `freenpipe://` start-recording link, a
    settings save that only restarts capture (`stop_capture` / `start_capture` in
    `recording-settings.tsx`), and the macOS mic-grant re-init (`start_capture`). That settings
    save restarts capture whether or not it was on, so it also ends a pause by the guard (or by the
    user) without the user asking to record; the fix belongs to W5-20 (see 15);
  - a new run, so the guard stops capture again (with a "Recording paused again" notice): a settings
    save that needs a server restart ("Apply & Restart": `stop_screenpipe` + `spawn_screenpipe`),
    an update or update rollback (`updates.rs`), a failed safe relaunch (`relaunch.rs`), the engine
    watchdog's respawn after a crash, and an app restart (without a notice, see 7).
  On recovery (a `disk_space_recovered` event, or a check that finds no incident) the guard starts
  capture again only if its own stop is still the last change: recording is off and the intent
  epoch has not moved since. Recovery means free space past the recovery threshold. A new monitor
  run whose first reading falls between the two thresholds reports no incident, because it never
  saw the drop; while the guard's own stop still holds, a check that reads such a status does not
  end the incident, so capture stays paused until the full headroom is there (review round 2: an
  engine restart inside the band used to resume early, and the next drop stopped and announced
  again). When the guard owes no restart (someone started or paused recording since its stop, or
  the app has just started and started capture itself), that reading ends the incident as before,
  and a later drop to the threshold is a new incident with its own notice. A recording the user paused, or started and paused again between two
  checks, stays paused. The switch works as well: turning `stopRecordingOnLowDisk` off during an
  incident starts capture again within one check if the guard's stop still holds, and turning it on
  during an incident makes the current reading fresh again, so capture stops (without a second
  notice if the incident was already announced). With the guard off, the incident is only logged,
  once. A new incident after a recovery is fresh even in the same run.
- **Reason:** the first version treated any start during an incident as the user choosing to record
  anyway; the second stopped every start, which left no way to record from the app while the disk
  was low (review round 1). The Rust side cannot tell a user's start from a programmatic one: the
  tray and deep links reach the same `start_capture` that a settings save uses. The monitor
  generation is a signal it does have, and it separates the two groups above along the line that
  matters: a capture start keeps the engine, an engine start re-checks the disk from scratch. An
  engine restart while the disk is still full is a moment to re-check, and the notice then says how
  to keep recording. The intent epoch keeps a recovery from overriding a pause the guard did not
  make, even when the start and the pause both fall between two 30 s checks.

## 7. Notifications

- **Question:** the spec lists the types `disk_space_low` and `disk_space_recovered` and a
  review-storage action; it does not say when the recovered one is sent.
- **Decision:** the low notice is sent once per incident, through the app's `/notify` panel with a
  "Review storage" button that opens `freenpipe://settings?section=storage`. It has three wordings:
  "Recording paused" when the guard stopped capture (recording starts again by itself once there is
  room), "The disk is nearly full" when recording was already off (no promise of an automatic
  start, since recovery leaves a paused recording alone), and "Recording paused again" when an
  engine restart during the incident found recording on and the guard stopped it. The two notices
  for a stop by the guard end with how to keep recording: start recording again, or turn off
  "Pause recording on low disk" in the storage settings. That text is the switch's label
  (`GUARD_SWITCH_LABEL` in `disk_pressure.rs`, `LOW_DISK_GUARD_LABEL` in `lib/low-disk-guard.ts`; a
  Rust test reads the TypeScript file and fails if they differ). An app restart during an announced
  incident stops capture without a notice (the state file says it was announced). The recovered
  notice ("Recording resumed") is sent only when the guard starts capture again. The
  enterprise-managed message variant is not built (ee).
- **Reason:** a recovery notice is only useful when something changed for the user, a notice must
  not promise a restart the guard will not make, and a notice that tells the user to flip a switch
  must name it the way the settings page does.

## 8. Format of `disk-pressure-notification-state.json`

- **Question:** the file name was observed, the contents were not.
- **Decision:** `{"incident_active": bool, "notified": bool, "since": RFC 3339,
  "available_bytes": u64, "threshold_bytes": u64}` (the last three only during an incident),
  written atomically. A missing or unreadable file means no incident. A status read showing no
  incident clears a stale file quietly (a recovery while the app was closed).
- **Reason:** snake_case matches the event payload fields; unknown fields are ignored, so a file
  written by screenpipe does not break startup.

## 9. Commands live in the feature modules

- **Question:** the spec puts `get_low_disk_guard_config` and `set_keep_awake` in `commands.rs`.
- **Decision:** they live in `disk_pressure.rs` and `power_awake.rs`. Command names, argument
  names and result fields match the spec (`set_keep_awake({ enabled })`,
  `get_low_disk_guard_config() -> { thresholdBytes, checkIntervalSeconds }`).
- **Reason:** tauri-helper collects commands from any module, and this keeps the WP out of the
  shared `commands.rs`.

## 10. `/health` reason: hand-off to W2-13

- **Question:** the low-disk state should show in `/health`. W2-13 (health v2 with the
  `unhealthy_reasons` list) was not merged when this WP was built.
- **Decision:** not wired here. The engine keeps the latest reading in
  `screenpipe_engine::disk_pressure::latest_status()` (`low`, `available_bytes`, `total_bytes`,
  `threshold_bytes`, `recovery_threshold_bytes`, `data_dir`, `checked_at`, `last_error`,
  `generation`). W2-13 has been merged since (its `routes/health_reasons.rs`); a follow-up adds
  one reason through its API: a warning while `low` is true (capture stopped to protect the disk),
  and one when `last_error` is set (the data-dir volume cannot be read).
- **Reason:** editing `routes/health.rs` while this WP was built would have conflicted with W2-13's
  rewrite of the same file, and the review round did not widen the WP to it.

## 11. CLI engine

- **Question:** the CLI (`screenpipe record`) runs the same background workers but has no app to
  stop capture.
- **Decision:** the monitor runs there too and publishes the events (visible on `/ws/events`)
  and logs; the CLI does not stop capture and does not apply keep-awake.
- **Reason:** the spec puts both behaviours in the app; no CLI flag was observed.

## 12. `get_low_disk_guard_config` on a slow or hung volume

- **Question:** the command reads the free space of the data-dir volume when the monitor has no
  answer; a hung network share could leave a blocked thread behind on every call.
- **Decision:** when the monitor's latest status is about the active data dir, the command
  returns the threshold the monitor applies, also after a failed read (then it is the last known
  value, or the 2 GiB minimum before the first good read), without reading the volume itself.
  Only without such a status (engine not running, or another data dir) does it read for itself,
  at most one read at a time per directory: a read that outlives the 5 s timeout is kept, and the
  next call for that directory waits on it, or takes its answer if it has finished in the meantime,
  instead of starting another. When no answer comes in time, it returns the 2 GiB minimum.
- **Reason:** the settings label then matches what the guard actually does, and a hung volume
  holds at most one blocked thread, the same rule the engine monitor follows. Taking a finished
  read's answer (rather than dropping it and reading again) also keeps the one-read rule exact
  when the read ends between two calls (review round 1).

## 14. Settings switches and the storage deep link (shared-file edits handed on)

- **Question:** the switches for `stopRecordingOnLowDisk` and `keepComputerAwake` and the deep
  link's `section` belong to WPs that are parked (decision 6): W8-02 (storage settings), W5-20
  (screen and audio settings, which lists keep awake) and W5-21 (deep links v2). Without them the
  notice pointed at a switch that did not exist.
- **Decision:** a minimal UI, built from the controls the neighbouring settings use (`Card`,
  `Switch`, `useSettings`):
  - `components/settings/low-disk-guard-setting.tsx` (new): "Pause recording on low disk", default
    on, with the threshold from `get_low_disk_guard_config` in its one-line description; switch id
    `stop-recording-on-low-disk` and test id `low-disk-recording-guard-toggle` as observed. The
    guard reads the setting at its next check, so no restart is needed.
  - `components/settings/keep-awake-setting.tsx` (new): "Keep computer awake", default off. It
    calls `set_keep_awake` and saves the setting only once the hold is taken (an error toast leaves
    it off); turning it off always saves. The logic is in `lib/low-disk-guard.ts`, covered by
    `lib/__tests__/low-disk-guard.test.ts`.
  - Shared-file edits, handed to the owners when they are scheduled:
    `components/settings/storage-section.tsx` (W8-02): one import, one search-index entry and the
    `<LowDiskGuardSetting />` line after the data-directory card.
    `components/settings/recording-settings.tsx` (W5-20; the coordinator's note named W6-14, but
    the plan gives keep awake to W5-20): one import, one search-index entry and the
    `<KeepAwakeSetting />` line at the top of the System group.
    `components/deeplink-handler.tsx` (W5-21): a `settings` (or `home`) link passes its `section`
    query value to `openSettingsWindow` when `isSettingsSectionId` accepts it, so the notice's
    "Review storage" button lands on storage; any other value opens the default section as before.
- **Reason:** the coordinator asked for the switches now, so the notice can name a control the user
  can find. Keeping each switch in its own component makes the hand-off a two-line move.

## 16. Where the monitor generation travels

- **Question:** the app needs the generation of a `disk_space_low` event, but the observed event
  payload has only `available_bytes`, `threshold_bytes` and `data_dir`.
- **Decision:** the payload keeps exactly those fields. `disk_space_recovered` carries
  `available_bytes`, `recovery_threshold_bytes` and `data_dir`: only `recovery_threshold_bytes` is
  specific to it in the evidence, and the other two are the low event's names for the same figures.
  An earlier draft also put `threshold_bytes` in it; review round 2 dropped that, since nothing
  observed it there and nothing reads it (the status has both limits). Reading ignores unknown
  fields, so a wider payload from another writer still parses. The generation is in the monitor's status
  (`latest_status().generation`, `#[serde(default)]` so older statuses still read), and the
  monitor stores a reading's status before it publishes the event, so the app reads the event's
  generation from the latest status. If the latest status is no longer low (a newer reading
  overtook the event), the app skips the event and acts on the next 30 s check instead.
- **Reason:** event payloads are an interop surface (they go out on `/ws/events`); the status is
  Freenpipe's own.
