# W1-01 open questions

Decisions taken while adding the v2.7.104 schema (db-001, db-005, db-006, db-027, meetings_memory-001).

## 1. How do sqlx checksums line up with screenpipe's for the 28 new migrations?

- **Question:** screenpipe's migration files carry its own comments inside the checksummed text, and
  Freenpipe writes its own comments, so the SHA-384 of our files can never equal what screenpipe
  stores. sqlx refuses to run when a stored checksum differs from the embedded one. How do the two
  programs share one database?
- **Decision:** pin the checksums. `crates/screenpipe-db/src/schema_migrations.rs` holds the 28
  versions with screenpipe's SHA-384 values from db.md (db-001), and `schema_migrations::migrator()`
  builds the migrator from the embedded files with those checksums substituted. A database
  screenpipe migrated therefore opens without any repair and without re-running anything, and a
  database Freenpipe migrated records exactly the checksums screenpipe expects. The base's repair
  fallback (rewrite stored checksums, then retry) and `set_ignore_missing(true)` stay, so a database
  touched by a build with different checksums, or by a newer screenpipe with extra versions, still
  opens. The 89 base migrations are unchanged, so their checksums already match.
- **Reason:** db.md lists pinning as the optional hardening and the rewrite path as the fallback.
  Relying on the rewrite alone would make every switch between the two programs rewrite
  `_sqlx_migrations`, and screenpipe would see Freenpipe's checksums as "modified" migrations.
  Pinning makes both directions a no-op. Anything that runs migrations against an existing database
  must use `schema_migrations::migrator()`, not `sqlx::migrate!`; the tests were switched over.

## 2. `IF NOT EXISTS` in the new DDL

- **Question:** some of the recorded DDL uses `IF NOT EXISTS` and some does not (the semantic tables,
  the activity ledger, `starred_sessions`).
- **Decision:** follow db.md statement by statement. Where the target omits the clause, so do we.
- **Reason:** the plan asks for the DDL as recorded. SQLite stores the same `sqlite_master.sql` text
  either way, but an unexpected pre-existing object should fail the migration loudly, as it would
  in screenpipe.

## 3. Late OCR on a frame that already has text

- **Question:** db.md shows only the start of the target's late-OCR update
  (`full_text = CASE WHEN ?2 != '' ...`, `text_json = CASE WHEN ?3 != '' ...`). Should OCR text
  replace existing `full_text`?
- **Decision:** `insert_ocr_text` fills `full_text` only when the frame has no text yet (the base
  behaviour, so accessibility text wins) and always stores non-empty word boxes in `text_json`.
  It uses two statements so that a boxes-only update does not touch `full_text` and does not re-index
  `frames_fts` through the `frames_au` trigger.
- **Reason:** keeps base search behaviour; the visible part of the target statement only says that
  empty inputs leave a column alone, which this matches.

## 4. Empty OCR box lists

- **Question:** OCR returns `[]` when it finds nothing. Store `[]` or NULL in `frames.text_json`?
- **Decision:** NULL. An empty string or an empty JSON array is "nothing to store" on every write
  path (snapshot insert, batch insert, late OCR).
- **Reason:** NULL is what the migration leaves for frames without boxes, so readers see one
  representation, and `text_json IS NOT NULL` keeps meaning "this frame has OCR boxes".

## 5. Delete counters and the `ocr_deleted` field

- **Question:** `DeleteTimeRangeResult.ocr_deleted` and the `/data/delete-range` JSON field have
  nothing to count once `ocr_text` is gone. gap_retention-v2-engine.md allows keeping the field at 0
  for a release.
- **Decision:** remove it from the struct and from both delete responses.
- **Reason:** the target no longer emits it (db.md, db-005), no Freenpipe client reads it, and the
  retention/archive logs now total frames + audio transcriptions + UI events as the target does.

## 6. `ocr_engine` in API payloads

- **Question:** the engine name has no column any more.
- **Decision:** search results keep the `ocr_engine` field and always return `""` (`'' as
  ocr_engine`, as the target does). The `/add` content API still accepts `ocr_engine` and ignores
  it. The `OcrEngine` type stays in screenpipe-db because screenpipe-screen and the config use it to
  pick an engine; it is just not stored.
- **Reason:** JSON field names are interop identifiers and existing clients send and read them.

## 7. Sync and archive export of OCR text

- **Question:** cross-device sync and the archive exported `ocr_text` rows and de-duplicated imports
  by `ocr_text.sync_id`.
- **Decision:** export `frames.full_text` for frames whose `text_source` is not `accessibility`
  (accessibility frames travel in the accessibility payload), with the same record shape. Import
  fills the imported frame's `full_text` (and an empty app or window name) only when the frame has
  no text yet, which also makes re-imports no-ops.
- **Reason:** the wire format stays compatible with existing peers while nothing reads or writes
  the retired table.

## 8. Redaction worker surface name

- **Question:** the worker's `TargetTable::Ocr` surface pointed at `ocr_text.text`.
- **Decision:** it becomes `TargetTable::FullText` (`frames.full_text`, stamped in
  `full_text_redacted_at`, label `frames:full_text`); serde still accepts the old name `ocr`.
- **Reason:** db-005 moves the surface onto `frames`, and the migration deliberately leaves
  `full_text_redacted_at` NULL so the worker re-checks folded text.

## 9. When the slow-migration notice is logged

- **Question:** the target logs a notice before the frames_fts rebuild and the ocr_text fold when
  they are pending.
- **Decision:** log each notice only when its migration is pending and the database already has
  frames (an old database without a migrations table but with frames counts as pending). A fresh or
  empty database logs nothing.
- **Reason:** the notice exists to explain a long pause, which only happens when there are rows to
  rewrite.
