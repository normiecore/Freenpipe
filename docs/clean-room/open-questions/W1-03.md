# W1-03 open questions

Decisions taken while building the integration seams (PLAN.md section 5). None of them changes
runtime behaviour; they decide the shape later work packages fill.

## 1. How a route stub exposes its OpenAPI registration

- **Question:** PLAN.md asks for "an oasgen registration function" per stub. oasgen's axum server
  type (`oasgen::Server<oasgen::server::axum::Router<S>>`) lives in a private module and cannot be
  named, so a stub cannot declare `fn register(server: Server<..>) -> Server<..>`.
- **Decision:** each stub exposes `documented() -> DocumentedRoutes`. A filled stub builds its own
  oasgen server and wraps it with the `documented_routes!` macro, which freezes it into the spec and
  router it produced. `routes/ext.rs` collects all stubs, `server.rs` merges their paths into the core
  spec before freezing it (so `/openapi.json` and `/openapi.yaml` still come from one spec) and merges
  their routers once. A second function, `router()`, carries routes oasgen cannot describe.
- **Reason:** keeps every stub independent of `server.rs` and of each other, with plain functions
  instead of a chain of macros. Same path with different methods is merged method by method, exactly
  as axum merges the routers; the same method twice is reported as a collision at startup and in the
  unit tests.

## 2. Which stubs to create

- **Question:** owner decision 6 schedules only the 32-WP core set, but PLAN.md section 5 names
  21 route stubs, 11 DB stubs, 6 connection route groups and an open-ended list of app modules,
  most of them for parked WPs.
- **Decision:** create every stub section 5 names, because the reviewer check compares that list
  with the files on disk, and add the planned new modules found in later WPs' owner paths:
  - DB: `ext/search_parsed.rs` (W3-02, core set) in addition to the eleven listed.
  - App: every `src-tauri/src/*.rs` path a later WP marks as new (33 files, plus
    `calendar/reminders.rs`, `notifications/db_recovery.rs` and `notifications/workflow.rs`).
  - Parked features get a one-line doc comment and nothing else; route, DB and connection stubs
    share one small shape (an empty `impl`, or empty `documented()`/`router()`/`routes()`).
  Not pre-declared: `crates/screenpipe-engine/src/history_access.rs` and
  `crates/screenpipe-core/src/pipes/managed.rs`, because W1-04 (same wave) creates them and an
  add/add conflict would be worse than its one `mod` line. Engine and core modules outside the
  section 5 seams (for example `local_chat.rs`, `recording_coverage.rs`) are left to their WPs: their
  `mod` lines sit in alphabetical lists that merge cleanly.
- **Reason:** declared-but-empty modules cost nothing at runtime and remove the main source of
  conflicts between parallel WPs (`main.rs`, `routes/mod.rs`, `ext/mod.rs`).

## 3. Where the pass-through middleware sits

- **Question:** the order of the request-origin and search-only layers relative to the existing
  stack is not specified.
- **Decision:** `request_origin_layer` runs outside the API-auth layer and inside CORS and the trace
  span, so rejected requests are still attributed to their client. `search_only_layer` runs inside
  the auth layer (an unauthenticated request gets 403 before any 503) and outside the vault-lock and
  pipe-permission layers. Both receive `State<Arc<AppState>>` so W2-24 and W3-28 can fill them
  without touching `server.rs`.
- **Reason:** matches what each feature needs (tracing every caller; gating only real API calls).

## 4. Pipe hooks: what they can do

- **Question:** should a `before_run` hook be able to veto a run (for example W3-06's event claims)?
- **Decision:** no. Hooks observe: `before_run`, `after_run` and `on_event`, awaited in
  registration order, panics contained. Event claiming stays in the scheduler's event-dispatch
  region that W3-06 owns. `after_run` fires on every run path, including a failed attempt that the
  sync path retries with a fallback preset (each attempt has its own execution row).
- **Reason:** a veto changes scheduling semantics, which is W3-06's call, not a seam's.

## 5. Extension installs in pipe setup now include the MCP bridge

- **Question:** the base pipe setup wrote context-pruning, orphan-guard, permissions and sub-agent;
  the Pi executor then wrote web-search, context-pruning, orphan-guard and mcp-bridge. A data-driven
  manifest writes every always-on entry wherever it syncs.
- **Decision:** pipe setup syncs the manifest with the permission and sub-agent conditions decided
  and web-search undecided, so it also writes `mcp-bridge.ts`. The executor syncs with web-search
  decided and leaves the permission and sub-agent files alone, exactly as before.
- **Reason:** the executor writes the same file a moment later in every run, so the end state of a
  pipe directory is unchanged. Undecided gates never delete files, which keeps the executor from
  removing the permission extension that pipe setup installed.

## 6. Environment names: which ones, and call sites

- **Question:** shell-025 lists the target's variables, including vendor-only ones.
- **Decision:** `screenpipe_core::env` holds every `SCREENPIPE_*` name the base code reads plus the
  target's new names. Left out: `SCREENPIPE_GLM_MODEL` (vendor model id) and the
  `SCREENPIPE_ENTERPRISE_*` family (enterprise policy is W1-04's no-op surface). `docs/env.md`
  documents each name and a unit test keeps it in step. Existing call sites keep their string
  literals; each moves to the constants when the WP that owns it touches it.
- **Reason:** rewriting dozens of call sites across crates now would collide with every parallel WP.

## 7. Background worker registry

- **Question:** what a registered worker receives and when it starts.
- **Decision:** a static `BACKGROUND_WORKERS` list in `screenpipe_engine::core`. Each worker gets the
  database, the data dir and a cancellation token; both startup sequences (CLI binary and the app's
  `ServerCore`) start the list once after the database opens and stop it on shutdown with a 5 s grace
  period, aborting stragglers. The list is empty, so nothing new runs.
- **Reason:** the two startup sequences were the edit hotspot for every new worker; a context with
  more fields can be added in `core.rs` alone because only `start_workers` builds it.
