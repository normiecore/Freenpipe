# W2-18 open questions

Decisions taken while building the Windows WASAPI loopback engine (audio-013) and the exe-based
audio exclusions (audio-014).

## 1. Where the engine lives

- **Question:** the spec names `core/process_tap/windows.rs` (with the macOS tap moved to
  `process_tap/macos.rs` behind a `mod.rs` facade); PLAN.md's owner paths name
  `core/process_tap.rs` and a new `core/wasapi_loopback.rs`.
- **Decision:** `core/process_tap.rs` is now the facade, the macOS tap moved to
  `core/process_tap/macos.rs` (one import path fixed, and a blank
  `SCREENPIPE_AUDIO_EXCLUSIONS_PATH` now counts as unset, as in the Windows reader and the app's
  commands), the Windows engine is `core/wasapi_loopback.rs`, and the platform-neutral rules sit
  in `core/process_tap/{exclusions,targets,pcm}.rs`.
- **Reason:** follows PLAN.md (binding for the file list) while doing the split the spec asks for.
  Keeping the rules outside `cfg(windows)` lets the Linux CI job and the VM test them. The macOS
  file keeps its own exclusion reader because no CI job compiles macOS; sharing it is a follow-up.
- **Headers and the verbatim gate:** `process_tap.rs` is an edited upstream file, so it keeps its
  original upstream header even though its body is now a new facade. `process_tap/macos.rs` is the
  base `process_tap.rs` moved as it was, apart from the import of `AudioStreamConfig`, the
  blank-override check and one test for it. The two lines the verbatim gate reports in it (lines 1
  and 3) are that file's original MIT attribution header, carried over with the moved code.

## 2. Which output streams the engine handles, and which follow the default

- **Question:** the spec says Windows output devices use the new client and that the
  default-endpoint stream rebuilds when the default changes, but the base device monitor already
  swaps output devices when recording follows the system default, and a pinned device must keep
  its name.
- **Decision:** every Windows output device goes through the engine, and a stream opened for a
  named device always records that device. While the device is the default, its stream is the
  system-audio stream (`default-render-endpoint` in logs) and honours the exclusions. When the
  default moves elsewhere, the stream is rebuilt as `endpoint:<name>` without exclusions (logged
  as `default render endpoint changed (<old id> -> <new id>)`), and if the new default device has
  a stream of its own, that stream becomes the system-audio stream within about a second. Only a
  stream opened for the `default` sentinel (or a meeting tap that fell back to the whole output)
  moves to the new default, after a 4 s grace. When recording follows the system default, the
  device monitor swaps the streams as before.
- **Reason:** device names in `audioDevices` and in the database stay true (the spec's interop
  rule), and two pinned outputs can never end up recording the same endpoint twice. A first cut
  moved a pinned stream onto the new default, which duplicated audio whenever the new default was
  itself pinned. A user who pins one device and switches the default to an unpinned one gets the
  base behaviour (the pinned device keeps being recorded); following the system default is the
  setting that records whatever the user hears.

## 3. Feature flag and cpal fallback

- **Question:** the spec puts the engine "behind a feature flag with cpal fallback" but names no
  flag, and settings keys belong to W1-02.
- **Decision:** no new setting or environment variable. The engine is on for Windows outputs; the
  cpal loopback takes over when the engine cannot start within 8 s or errors. A device where the
  engine failed 3 times within 15 minutes is opened with cpal until those failures are more than
  15 minutes old; then the engine is tried again. Each such period is logged once when it starts
  (`using the cpal loopback for it until those failures are more than 15 min old`) and once when
  it ends (`using the loopback engine for it again`).
- **Reason:** keeps the settings and env-name inventories identical to the target while still
  guaranteeing a working fallback. A user-facing switch can be added with a W1-02 key later.

## 4. Exclusion timing and multiple trees of one app

- **Question:** the spec says only the first running excluded app is honoured and that the stream
  rebuilds when the excluded app starts, exits or the list changes. It does not say how fast, or
  what happens when one executable runs as several independent process trees.
- **Decision:** the file and the process list are polled every 2 s. A new target must be seen on
  two polls in a row, and exclusion rebuilds are at least 5 s apart (the macOS tap uses 60 s).
  When the excluded executable runs as several trees, the tree with the most processes is
  excluded (lowest pid on a tie) and each other tree is logged once as still audible. At engine
  start the exclusion is applied before the first client opens, so no excluded audio leaks at
  startup. A tree whose activation fails or times out (or whose tap breaks and cannot be
  re-activated) leaves the stream on the plain loopback and is tried again after 60 s, then after
  120 s, 240 s and so on up to every 15 minutes while it keeps failing. A tap that works resets the
  delay. Only the first failure of a tree is a warning (`cannot be excluded ... trying again in
  60s`); later failures are debug lines, and the info line `now captures exclude-process-tree:<pid>`
  shows a retry that worked. Failures are not split into permanent and passing kinds: the HRESULTs
  the audio service returns cannot be checked from the VM, and a tree the service refuses outright
  fails fast, so retrying it every 15 minutes costs one call. A retry that times out blocks the
  capture thread for up to the 4 s activation timeout, which can drop that much system audio once
  per retry; the backoff keeps this to a few times an hour at most.
- **Reason:** fast enough that a browser opened mid-recording is excluded within seconds, slow
  enough that short-lived helper processes do not rebuild the stream twice. A failed tap is retried
  because most failures pass (the audio service is slow after wake, an endpoint is being swapped),
  and leaving an exclusion off for the life of a browser that stays open for days would record
  audio the user asked to leave out. A first cut gave up on a tree until it exited.

## 5. Per-process capture format

- **Question:** the virtual process-loopback device has no mix format; the spec only says to
  convert to mono f32 at the mix rate.
- **Decision:** per-process clients request 16-bit stereo PCM at the stream's current rate with
  `AUTOCONVERTPCM`; endpoint clients use the endpoint mix format. A client that runs at another
  rate after a rebuild (new default device) is resampled to the stream's original rate, because
  downstream code reads the rate once.
- **Reason:** 16-bit PCM is what Microsoft's application-loopback sample requests; matching the
  stream rate avoids resampling on every exclusion switch.

## 6. `bundle_id` on Windows

- **Question:** casing and form of the stored id are inferred in the spec.
- **Decision:** the app stores the lower-case file name (`chrome.exe`). The engine also accepts
  full paths (file name kept) and bare names without an extension (`.exe` added), compares
  case-insensitively, and ignores duplicates.
- **Reason:** hand-edited files should still work, and matching the ToolHelp process name is
  case-insensitive on Windows.

## 7. Reading `.exe` metadata

- **Question:** the spec names a FileDescription/ProductName lookup and a 32 px icon, but adding
  version-info APIs would need new `windows` features in the app crate, which this WP should not
  touch.
- **Decision:** the version strings are read by a small PE parser (headers, resource section,
  `RT_VERSION`, US-English string table first) that runs on every platform and is unit-tested on
  Linux with synthetic images. The icon comes from the vendored `windows-icons` crate, resized to
  32 px and encoded as a PNG data URL. A file without a PE signature is rejected with
  "`<path>` is not a Windows executable".
- **Reason:** no new app dependencies or features, and the parser is testable without Windows.

## 8. Meeting tap entry point

- **Question:** audio-013 includes the `process-tree:` target used later by the meeting tap
  (audio-016, not in this WP).
- **Decision:** the engine supports it (`AudioStream::from_process_tree(label, pids)`, multi-root
  and Teams-ancestry rules, stop when the tapped tree exits), but nothing calls it yet. The tap
  ends when the tree root exits even when no process handle could be opened for it, or while it
  runs on the whole-output fallback after a failed activation, or while its client is being
  rebuilt: the process list is checked every 2 s in those cases, so a tap never keeps recording
  the whole output after its meeting app has gone.
- **Reason:** the piggyback WP can use it without reopening the engine.

## 9. What an exclude-mode tap covers

- **Question:** the process-loopback device is not tied to one endpoint, and the spec does not say
  whether an `exclude-process-tree:` tap also carries audio that other apps render to a second
  endpoint, such as the communications device the device monitor records as an extra output.
- **Decision:** the tap is treated as the system-audio stream of the default device, with no
  special handling. Smoke check SMK-W2-18-7 checks on hardware whether call audio routed to a
  separate communications device is recorded twice while an exclusion is active.
- **Reason:** the Windows audio service decides this and the VM cannot observe it. The smoke result
  tells a later WP whether the communications stream has to be paused while an exclusion tap runs.
