# W2-04 open questions

Starred work sessions backend and HD binding (db-015, api-007, meetings_memory-010,
vision-starred-hd). Each decision is the worker's call; the owner can overturn any of them.

1. **What does `POST /starred-sessions` return?**
   - Decision: the stored session as a bare JSON object, `{id, start, end, hd_requested, revision,
     has_audio}`, with the new revision. `GET` returns `{data: [...], pagination: {limit, offset,
     total}}`.
   - Reason: the API spec says the save returns "the saved session" and that the frontend reads
     `data` only from the list. A bare object keeps `.revision` one step away for clients.

2. **Which status codes go with each refusal?**
   - Decision: 400 for a bad id or negative revision, unreadable timestamps, `end <= start`, the
     range rule and a start inside another session; 403 for pipe tokens; 404 for a non-zero revision
     on an id with no row; 409 for a revision mismatch (also a create for an id that exists), with
     `current_revision` in the body; 409 when HD is requested while screen recording is disabled in
     settings; 503 when HD is requested and the engine has no HD controller.
   - Reason: only the 409 for revision mismatches and the 403 for agents are evidenced. The others
     follow the engine's habits: 400 for bad input, 503 for a missing capability
     (`/capture/hd` already answers 503 without a controller), 409 for a request that conflicts with
     current settings. The start rule is a 400, not a 409, so clients that treat 409 as "reload and
     retry" do not loop on it.

3. **What exactly is the range rule?**
   - Decision: refused when the start is more than 2 s after the server's current time, when the
     session lasts 24 h or more, or when it ends more than 2 h after the current time. Times are cut
     to whole milliseconds first. Sessions in the distant past are accepted (Freenpipe has no
     history limit). The message is Freenpipe's own wording.
   - Reason: the spec paraphrases one rule: begins before now, lasts less than 24 h, ends no later
     than 2 h from now. The 2 s slack covers a client stamping `start = now` on the same machine
     within the same clock tick; the frontend creates sessions with `start: now`.

4. **When do the HD-availability checks apply?**
   - Decision: only when `hd_requested` is true and the session's end is still in the future. A past
     session can keep or change its HD flag whatever the capture settings are now.
   - Reason: HD for a finished session has no effect, and refusing edits of old sessions because
     recording is off today would make them uneditable for no gain.

5. **What counts as a non-user (agent) request?**
   - Decision: any request whose `Authorization` header carries a `Bearer sp_pipe_…` token, whether
     the token is registered or not. Requests without a token (the app) and with the user's API key
     may mark. `GET` stays open to pipes.
   - Reason: `sp_pipe_` tokens are the only agent credential the engine has; the permission
     middleware already treats unregistered pipe tokens as user requests for reads, which is too
     loose for a write that only a user should make. Freenpipe has no attribution header yet
     (api-012), so none is checked.

6. **How are ids and timestamps stored?**
   - Decision: the id is stored as sent (trimmed), after checking it is a 36-character hyphenated
     UUID in either case. `start` and `end` are written as RFC 3339 UTC with three fractional digits
     and `Z` (the `toISOString` shape). Reads compare through `julianday()` and normalise through
     `strftime()`, so rows another writer stored with an offset, other precision or a space
     separator still list, filter and enforce the start rule correctly. The handlers emit the
     canonical shape; as for every JSON route, the engine's response layer then rewrites UTC
     timestamps to local time with an offset unless the request carries `?timezone=utc`.
   - Reason: `CHECK (end > start)` and the `(start, end)` index compare text, so one fixed-width
     spelling keeps text order equal to time order for our rows, while read-side normalisation keeps
     interop with rows written by screenpipe.

7. **How is `has_audio` computed, and does a chunk at the session end count?**
   - Decision: true when an `audio_chunks` row with a non-empty `file_path` has a timestamp in
     `[start, end)`. The lookup narrows by a second-precision text range on `audio_chunks.timestamp`
     for both the `T` and the space spelling (both use `idx_audio_chunks_timestamp`), then compares
     exactly with `julianday()`. A chunk at exactly `end` does not count.
   - Reason: matches the spec's half-open session range and its "prefix range plus `julianday`"
     description; both spellings occur in real databases (sqlx writes RFC 3339, old rows use
     `CURRENT_TIMESTAMP`).

8. **How is the coverage-island query built?**
   - Decision: SQL selects the sessions overlapping the window; Rust clips them to the window and
     merges overlapping or touching ranges (`merge_coverage`). Touching ranges (`end == next start`)
     join one island.
   - Reason: the result is the same as the window-function SQL the spec describes, and the merge
     is a pure function that unit tests cover. Touching sessions are continuous starred time.

9. **May sessions overlap?**
   - Decision: only the start rule is enforced: a start may not fall inside another session
     (`other.start <= start < other.end`). A session that starts earlier and runs over another one is
     accepted; coverage and membership handle the overlap.
   - Reason: that is the rule the spec lists; nothing else was observed.

10. **What happens when the user stops HD from the tray while a starred HD session runs?**
    - Decision: `POST /capture/hd/stop` (`stop_session`) also stops every starred window running at
      that moment, for its current revision. The session row is untouched. Saving the session
      again (any edit, which bumps the revision) is a fresh request and HD resumes if it still asks
      for it.
    - Reason: without this the tray's "Stop HD recording" would be ignored for up to two hours
      while the starred binding kept HD on.

11. **What does "Extend HD" do when only a starred session raises HD?**
    - Decision: it starts a timer-bound session that ends `additional` (capped at 2 h) after the
      starred session's end. The starred session itself is not changed.
    - Reason: the starred range belongs to the store and is edited through `POST
      /starred-sessions`; the tray's extend action should still give the user more HD time instead
      of silently doing nothing.

12. **Which session kind does `/capture/hd` report when a manual session and a starred session are
    both active?**
    - Decision: the manual one (meeting, timer or prewarm), with its own remaining time; the
      starred one is reported as `{"kind":"starred"}` once no manual session is active.
    - Reason: the manual session is the one the tray's stop and extend actions act on first.
      `SessionKind` stays `Copy`, so the starred kind carries no session id; clients read the
      session itself from `/starred-sessions`.

13. **How does the controller learn about sessions, and how fast do edits and deletions apply?**
    - Decision: after every successful save the route re-reads the unfinished HD sessions and
      installs them in the controller, and a sync task (started by both the CLI and the desktop
      app's server core) repeats that every 15 s. Installs carry tickets taken before the read, so
      a slow read never overwrites a newer one. A session ends exactly at its `end` on every
      snapshot regardless of syncs; a row deleted outside the API stops HD within one tick (15 s).
    - Reason: there is no delete route, so deletions only come from outside the API; a short tick
      bounds them without a trigger or a change feed. The sync query reads a handful of rows.

14. **Can a wall-clock jump revive a finished starred session?**
    - Decision: no. A window that ended (or that the user stopped) is remembered by id and revision
      (the last 256) and never raises HD again; an edit creates a new revision and is evaluated
      afresh.
    - Reason: the coordinator asked that HD never stays stuck on after a session ends; a backward
      clock correction would otherwise reopen the window until its old end.

15. **Is there a `boundTo: "starred"` for `POST /capture/hd/start`?**
    - Decision: no. Starred HD is started only by saving a starred session with `hd_requested`;
      `/capture/hd` reports it with `kind: "starred"`.
    - Reason: the binding needs a session range from the store, which `/capture/hd/start` has no
      field for; the spec's HD mode list (`ask|always|never|timer|starred|prewarm_pending`) is
      satisfied by the reported kind.
