# W3-08 open questions

Decisions taken while building calendar binding, `excludeFromMeetingDetection`, the
`meeting_ended` payload and lock awareness for the UI-scan meeting detector
(meetings_memory-031, gap_health-lifecycle-internals HLI-013).

## 1. What "the detected call's conference URL" is

- **Question:** meetings_memory-031 binds on `exact_conference_url` "when the event's meeting URL
  matches the detected call", but the UI-scan detector finds calls by their call controls, not by a
  URL, and on Windows its browser matches carry window titles, not URLs.
- **Decision:** the call's URLs are the distinct `frames.browser_url` values captured in the last
  120 s, plus any URL the process scan reported, kept only when they contain one of the detected
  profile's `browser_url_patterns` (so a Meet tab cannot name a Zoom call). That filter only says
  which service a URL belongs to; whether it is the scheduled call is decided by exact identity
  (question 2). The database is only read when some calendar entry with a meeting URL is within its
  join window (question 3).
- **Reason:** the screen capture already records the address bar locally, so no new probe or network
  call is needed. Native apps that never show their conference URL (Zoom or Teams desktop without a
  launch tab) stay unbound, which is the conservative outcome the spec asks for.

## 2. Conference identity

- **Question:** the coordinator asks for scheme, host case and trailing-slash normalisation and
  forbids substring matches; invites and address bars also differ in query strings (`?pwd=`,
  `?authuser=`), fragments, `www.`, default ports and percent-escape case.
- **Decision:** identity is `host/path`: http, https or no scheme accepted (browsers hide it), host
  lower-cased without a leading `www.`, trailing dot or default port, query and fragment dropped,
  trailing slashes dropped, percent escapes upper-cased, the rest of the path compared as is. A URL
  without a path (`https://meet.google.com/`) has no identity. Equality only; Zoom's
  `zoom.us/j/123` and `us02web.zoom.us/wc/123/join` are different identities.
- **Reason:** the room lives in the path for every supported service; the query carries passwords
  and account hints that differ between an invite and the tab.

## 3. Which entries can bind

- **Question:** how close in time must an entry be, and which one wins when several share a link?
- **Decision:** an entry binds when its identity equals one of the call's and the call falls between
  15 minutes before its start and 15 minutes after its end. Among several exact matches the entry
  scheduled now wins, then the one starting closest to now, then the source whose ids are stable
  across devices (`google`, then `ics`, then `native`), then the id. Only that entry is tried: when
  the ownership check refuses it, no other entry is tried.
- **Reason:** a recurring meeting reuses one link, so the time window picks today's instance; two
  sources listing the same meeting are the same event, and binding the second copy would defeat the
  one-event-one-meeting rule. This relies on every occurrence having its own id (question 14).

## 4. Time-only matches

- **Decision:** when entries are scheduled now but none names the call's conference, the meeting is
  left without `calendar_event_id`, title and attendees, and one info log per meeting reports the
  skipped `time_only` match. The base filled title and attendees from any overlapping entry; that
  enrichment is gone.
- **Reason:** meetings_memory-031 (a) and W2-08 question 2: title and attendees come from the entry,
  and copying them onto a call that is not the entry's is the misnaming the binding rule prevents.

## 5. Binding order and later retries

- **Decision:** on a new detection the row is inserted without a title, the entry is bound through
  `bind_meeting_calendar_event` (conditional update plus ownership check), and only then is
  `meeting_started` emitted, carrying the entry's title and `calendar_event_id` when bound. Title
  and attendees are copied only into fields that are still empty; a user's title is never replaced.
  While a meeting is tracked and not settled, the match is retried every 30 s (the calendar may
  publish later, or the URL may reach the screen later). Bound, already bound, refused by the
  ownership check, or a vanished row settle it; time-only, no entry and database errors do not.
  A row that already carries a `calendar_event_id` when the detector starts tracking it (a
  reopened or re-attached meeting) is settled from the start: no retries and no time-only report.
  No attempt is made while the call's detection profile is unknown (a meeting re-attached at
  startup, or one kept alive by output audio alone, before a scan has seen its controls): without
  the profile no URL can be looked up, so an attempt could only log a time-only match that was never
  checked. The first scan that sees the controls supplies the profile and the attempt follows.
- **Reason:** binding first keeps the title and the binding consistent; the retry covers a meeting
  detected before its tab was captured or before the first calendar publish after a restart.

## 6. Rejoin across different scheduled calls

- **Question:** the 120 s rejoin reopens the app's last meeting. What if the new call exactly
  matches a different calendar entry than the one that meeting is bound to?
- **Decision:** the meeting is not reopened; the call gets its own row. A recent meeting without a
  binding is still reopened as before.
- **Reason:** two exactly identified, different scheduled calls are different meetings
  (meetings_memory-030 lists "a different conference room" as a reason not to reopen).

## 7. `excludeFromMeetingDetection`

- **Decision:** the field is a boolean on `CalendarEventItem` (default false, camelCase on the
  wire). The detector drops flagged entries, along with all-day entries and entries whose times do
  not parse, as they arrive: they never bind, title, keep a meeting alive or count as a time-only
  overlap. The engine's Google Calendar route sets it when the user's own attendee entry
  (`self: true`) says `declined`, when the entry is `transparent` (shown as free) or when it is
  `cancelled`; the app's Google publisher passes it through. The OS calendar (EventKit, Windows
  appointments) and ICS converters set false, because those bindings do not expose the user's
  response or free/busy state yet.
- **Reason:** connections-google-calendar-multi names declined and transparent entries; the other
  sources need new reads in `screenpipe-connect` (follow-up).

## 8. One calendar view across publishers

- **Question:** the OS calendar, Google and ICS publishers share the `calendar_events` topic, and
  the base detector kept only the last list, so the Google list replaced the OS list every minute.
- **Decision:** the detector keeps the latest list per `source` (absent means `native`). An empty
  list clears the native source only, because only the OS publisher sends empty lists; a source
  silent for 15 minutes is forgotten.
- **Reason:** matching must see every connected calendar; the ICS feeds refresh every 10 minutes.

## 9. `meeting_ended` payload

- **Decision:** every emitter (the UI-scan detector's grace end, process-exit end and auto-end,
  `POST /meetings/stop` and the room-change switch) sends `meeting_id`, `meeting_end`,
  `duration_secs` (whole seconds, never negative), `transcript_segments` and `end_reason` when the
  end has one (`auto_end`, `explicit_stop`, `room_changed`). The segment count is what
  `GET /meetings/:id/transcript` returns for the meeting (live segments plus background
  transcriptions in the window). A value that cannot be read is `null`; the event is still sent.
  The trivial-meeting threshold and the skip itself belong to the summary trigger (W3-06).
- **Count cost:** the emitters await the payload before sending, so that a room change still
  announces the old meeting's end before the new meeting's start (`calendar_speaker_id` and the
  live transcription controller react to any `meeting_ended`). Spawning the emit would reorder
  them. Instead the count is one SQL `COUNT` with the transcript query's predicates, whose
  background part first narrows `audio_transcriptions.timestamp` to calendar days around the
  window (an indexed range; one day of margin on each side covers stored UTC offsets) before the
  exact `julianday` test. A unit test pins the count to the length of
  `list_meeting_transcript_segments` over live, deduplicated, blank, cloud, hallucinated and
  out-of-window rows. A meeting start that does not parse falls back to counting the transcript.
- **Reason:** meetings_memory-027 lists those payload fields; one builder keeps the emitters in step.
- **Note for W3-06:** with local batch transcription, audio is transcribed after the meeting ends
  (it defers while a meeting runs), so `transcript_segments` can be 0 for a meeting full of speech.
  A gate on the count alone would skip those summaries; combine it with `duration_secs`, or re-count
  when the run starts.

## 10. Lock awareness (HLI-013)

- **Decision:** the lock check comes before the manual-meeting check and before any scan work. While
  `SCREEN_IS_LOCKED` is set the iteration is skipped and the state is untouched. On the first
  iteration after the unlock, the state's timers (confirm window, end grace, last seen) move forward
  by the time between the first locked and the first unlocked iteration, so the lock gap never ends
  or confirms anything by itself; the next scans decide from what is on screen with the grace that
  was left. Explicit stops and auto-end requests are still handled while locked. The meeting's
  start time is not changed, and a call that ended while the screen was locked ends after the
  normal grace once scans resume.
- **Reason:** the spec says skip with no state change and that a running meeting ends by the normal
  timeouts; counting the locked time against those timeouts would end meetings that are still going
  the moment the user returns.
- **Consequence for `meetings-only` audio (W3-14):** a meeting that was active when the screen
  locked stays open while it is locked, so its audio keeps recording; the in-meeting flag is not
  touched by skipped iterations. What can still end it during the lock is what does not depend on
  the scan: `POST /meetings/stop` and the live-meeting auto-end requests (inactivity, maximum
  duration). After the unlock the normal grace applies.

## 11. Detector stop and the manual slot

- **Decision:** the detector's `detector_stop_tracking` branch now keeps the audio pipeline's
  in-meeting flag raised when the manual slot is taken (the W2-08 room-change hand-off). The route's
  successor flag task stays as a safety net, since the detector only handles the stop on its next
  tick.
- **Reason:** W2-08 question 8.

## 13. The rest of meetings_memory-031

- **Question:** meetings_memory-031 also lists (c) active meetings kept across capture restarts,
  (d) output audio keeping a meeting alive when no meeting app is found, (e) trivial-meeting
  gating and (f) pid-scoped Windows UIA scans with panic isolation. Which of these does W3-08 do?
- **Decision:** none of them needed new code here. (c) and (d) were already in the detector
  (`close_orphaned_meetings_on_start`, the reattach at loop start, and the output-audio keep-alive
  in `handle_no_apps_running`), and (f) in the Windows `scan_process` (one process per scan, wrapped
  in `catch_unwind`). They are unchanged and their tests still pass. The gating in (e) belongs to
  the summary trigger (W3-06); W3-08 only adds the payload fields it reads (question 9).
- **Reason:** the W3-08 plan entry names calendar binding, exclusion, the payload and the lock
  skip; the other parts were checked rather than rewritten.

## 14. One id per occurrence of a recurring entry

- **Question:** the OS calendars give every occurrence of a recurring event the series id
  (EventKit `eventIdentifier`, the Windows appointment `LocalId`), and an ICS `UID` repeats for
  every `RECURRENCE-ID` instance a feed lists. `calendar_event_id` is unique across meetings, so
  the first occurrence of a weekly call would own the id and every later occurrence would fail the
  ownership check, staying untitled and unbound. Google instance ids (`singleEvents=true`) are
  already per occurrence.
- **Decision:** native and ICS entries get the id `<series id>_<occurrence start, UTC,
  YYYYMMDDTHHMMSSZ>` where the entries are built, in `screenpipe-connect`
  (`calendar_occurrence::occurrence_event_id`), so the app's publisher, the engine's
  `GET /connections/calendar/events` and `/connections/ics-calendar/events` and any manual start
  that passes an entry's id all use the same per-occurrence id. A blank series id stays blank (no
  identity to bind). ICS entries without a `UID` keep their existing `ics-<feed>-<start>` id. The
  detector itself binds the published id unchanged.
- **Reason:** a single place for the rule keeps `meetings.calendar_event_id` equal to the id every
  consumer sees; deriving an instance key inside the detector instead would let a manual start
  (`POST /meetings/start` with `calendar_event_id`) and the detector claim the same occurrence
  under two different ids. Side effect: the ICS feed merge no longer collapses instances of one
  series into one entry.
