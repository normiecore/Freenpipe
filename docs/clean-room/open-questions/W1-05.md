# W1-05 open questions

Decisions taken while making the shipped builds commercial-ready (owner decision 7 in
`docs/clean-room/DECISIONS.md`).

## 1. A configured enclave in a build without enclave support: search `filter_pii`

- **Question:** `privacy_filter.rs` fails closed when the enclave errors at runtime. Should a build
  without the `tinfoil-enclave` feature also fail every `filter_pii=true` search when
  `SCREENPIPE_PRIVACY_FILTER_ENCLAVE` (or `_URL`) and `_REPO` are set?
- **Decision:** No. The global filter drops the configured target, logs one warning at startup
  ("configured but unavailable", with the "not built with enclave support" reason) and redacts on the
  device with the deterministic pass plus the local ONNX model, as W0-06 built it.
  `PrivacyFilter::backend()` reports `FilterBackend::LocalEnclaveNotBuilt` for status surfaces. The
  enclave path itself (reachable only through an explicitly constructed filter) returns
  `FilterError::EnclaveUnavailable` before any network activity. Builds with the feature keep the
  fail-closed behaviour for real attestation or network failures.
- **Reason:** the setting can never work in such a build, so failing would turn a stale environment
  variable into a broken search API for every pipe that forces `filter_pii`. The local path never
  sends text anywhere, which is the stricter privacy outcome.

## 2. Keep the tinfoil adapters compiled without the feature?

- **Question:** Cfg out `adapters::tinfoil` and `adapters::tinfoil_image` entirely, or keep them?
- **Decision:** Keep both modules. Configuration resolution, the wire types and the new
  `EnclaveAvailability` (`NotBuilt`, `NotConfigured`, `Ready`) stay in every build; only the Tinfoil
  SDK client (the shared `attest()` helper) is behind `tinfoil-enclave`. Without it every request that
  would reach the enclave fails with `RedactError::Unavailable("not built with enclave support: …")`
  before the frame is read or anything is sent, and that check comes before "not configured".
- **Reason:** the app and the engine compile unchanged in both kinds of build, the settings command
  and the worker selection can say why the enclave is unavailable, and the request code keeps its
  test coverage on Linux.

## 3. Which "shipped builds" the licence gate checks

- **Question:** Which crate/feature/target combinations count as shipped?
- **Decision:** The default features of `screenpipe-engine` and the app crate on all targets
  (`cargo tree --target all`, a superset of every platform), every `args` and `tauri-args` feature set
  in `release-app.yml` on its literal target (plus `apple-intelligence` on aarch64 macOS, which the
  workflow appends when Xcode supports it), and every `cargo build -p screenpipe-engine` line in
  `release-cli.yml` (its literal target, or all targets when the target is a matrix template). The
  sets are parsed from the workflow files, so a release-flag change is checked automatically.
  Edges are `normal,build`: dev-dependencies do not ship.
- **Reason:** decision 7 names default builds and every release feature set; reading the workflows
  avoids a hand-kept list drifting from what is actually released.

## 4. Licence policy beyond the named families

- **Question:** The plan names CC BY-NC, AGPL, GPL (not LGPL), SSPL and missing licences. What about
  other identifiers?
- **Decision:** A reviewed allow-list of SPDX identifiers (permissive, public-domain, Unicode/CDLA
  data licences, CC BY, MPL-2.0 and LGPL as weak copyleft). GPL, AGPL, SSPL, BUSL, the Elastic
  licence and CC BY-NC are refused by name; any other identifier fails as "not on the reviewed list"
  until someone checks it and adds it. Dual licences pass when one branch is acceptable
  (`MIT OR LGPL-3.0-or-later`), `AND` needs every part. Weak-copyleft packages are listed in the job
  summary for the release audit.
- **Reason:** for a commercial release an unreviewed licence should stop the build, not slip through
  a deny-list.

## 5. Freenpipe's own crates without a `license` field

- **Question:** `screenpipe-app` and `screenpipe-secrets` declare no licence. Allow-list them, or fix
  their manifests?
- **Decision:** The gate treats path packages inside this repository and outside `third_party/` as
  Freenpipe's own code under `LICENSE.md`; no manifest outside this WP's owner paths was edited. The
  explicit allow-list (`DECLARED_ELSEWHERE`) holds only `tauri-nspanel` (Apache-2.0 OR MIT licence
  files, no field; listed in `third_party/README.md`). opf-rs, which also declares no licence, is
  never allowed and is refused by name in any case.
- **Reason:** the repository licence covers every first-party crate, including future ones;
  allow-listing them one by one would add churn without information.

## 6. Statically linked LGPL (mp3lame)

- **Question:** `mp3lame-encoder` / `mp3lame-sys` (LGPL-3.0) build LAME into the binary. Decision 7
  allows LGPL "as a separate or dynamically linked component". Should the gate refuse them?
- **Decision:** The gate accepts LGPL (as the plan specifies) and reports both crates in its summary.
  This needs an answer in the release licence audit before the first release: either keep static
  linking and meet LGPL-3.0 section 4 (the full application source is public under MIT, so users can
  relink; ship the LGPL text and a notice), or link LAME dynamically, or drop MP3 encoding.
- **Reason:** changing the audio encoder is outside this WP; the gate makes the dependency visible.

## 7. The engine CLI's enclave fallback trigger

- **Question:** The engine binary chose the enclave fallback when the legacy `TINFOIL_API_KEY` or
  `TINFOIL_BASE_URL` variables were set, although the adapter only reads
  `SCREENPIPE_PRIVACY_FILTER_*`.
- **Decision:** In `tinfoil-enclave` builds the fallback now uses `availability_for()` (the same
  check as the app: built in, enclave host from the endpoint switchboard, repo and API key). Without
  the feature the helper is compiled out and the order is v45 ONNX, then regex-only.
- **Reason:** the old trigger selected an adapter that would then fail every request as
  "not configured".

## 8. reqwest `stream` for the engine

- **Question:** `routes/cloud_proxy.rs` calls `Response::bytes_stream`, which needs reqwest's `stream`
  feature. It used to arrive only through the tinfoil SDK's dependency on reqwest.
- **Decision:** The engine's own `reqwest` dependency now asks for `stream`.
- **Reason:** removing tinfoil from the default graph broke the engine build otherwise; the engine
  should declare what it uses rather than rely on feature unification.
