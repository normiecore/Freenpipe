# W3-13 open questions

URL domain rules, Windows window identity and the input-hook watchdog (vision-url-domain-rules,
vision-windows-window-resolution, a11y-input-hook-watchdog). Each decision is the worker's call;
the owner can overturn any of them.

## Website rules (`ignoredUrls`, `includedUrls`)

1. **What happens to a browser capture whose URL cannot be confirmed while an allow list is set?**
   - Decision: the whole capture is skipped with the new `UrlValidationPending` reason: no
     snapshot, no OCR and no accessibility text. The tree walker reports it for its own snapshot,
     and a gate in `do_capture` applies the same policy to the resolved app and URL (the resolved
     app can come from the trigger, and a walk that found nothing has no URL). Nothing new was
     added to W3-11's pixel path: the skip is the existing `Skipped` path, and on macOS unfocused
     browser windows join W3-11's exclusion list, so its fail-closed probe (`pixels_withheld` while
     the list is unknown) covers them too.
   - Reason: the spec says a tab whose URL the engine cannot confirm is skipped and "no frame" is
     written. Storing the page text with only the pixels withheld would still record a site the
     user did not allow.

2. **What if the captured app itself is unknown under an allow list?**
   - Decision: on Windows the gate looks up the foreground window's app
     (`screenpipe_a11y::platform::foreground_app_name`, same naming as frames). If the app still
     cannot be named it is treated as a browser with an unknown URL and skipped. Without an allow
     list an unknown app is recorded as before (unless its URL is blocked).
   - Reason: an unnamed app may be a browser on a site that is not allowed; failing open would
     leak exactly what the allow list is meant to keep out. With the lookup this is rare on Windows.

3. **Which apps count as browsers for the allow list?**
   - Decision: an app whose name contains one of the spec's browser words
     (`chrome chromium firefox safari edge brave arc vivaldi opera zen comet epiphany helium`, plus
     `msedge`) as a whole word, after dropping `.exe`/`.app` and splitting on anything that is not a
     letter or digit (`url_filter::is_policy_browser`). Other apps that report a URL (Electron apps)
     are subject to the block list only.
   - Reason: the base `BROWSER_NAMES` uses substring matching, which would make `SearchHost.exe` or
     `ArcGIS Pro` "browsers" and silently stop recording them under an allow list. The spec says
     native apps are governed by the app filters.

4. **What do invalid stored rules do at runtime?**
   - Decision: a rule is never applied in a way that lets more through than the user asked for. A
     structured block rule that fails validation is applied as the legacy pattern of the host it
     names (that host and all of its subdomains, which is how the engine treated every structured
     rule before this WP). The host is read leniently: a leading `*.` or `.` is dropped, any scheme
     is accepted (`https://` is assumed without one), and a port, path, query or credentials are
     ignored, so `*.bank.com`, `bank.com/login`, `bank.com:443` and `ftp://bank.com` all block
     bank.com. Only when no host can be read at all (`bank .com`) is the rule's text kept as an old
     plain pattern, which may block nothing. An allow rule that fails validation allows nothing, and
     an allow list whose rules are all invalid still counts as set, so it allows nothing rather than
     everything. Each such rule is logged once at `warn` when the policy is built, saying what was
     applied in its place, and `UrlPolicy::rejected_rules` reports it (`applied_instead`).
   - Reason: the app validates rules before saving them, so invalid rules only come from hand-edited
     or foreign stores; failing closed is the safe direction for both lists.

5. **How are URLs without a host treated under an allow list?**
   - Decision: a readable URL with no host (`about:blank`, `data:`, `file:`, `view-source:`) is
     "not allowed" (`BlockedUrl` reason); a missing, empty or unparseable URL is "pending"
     (`UrlValidationPending`). An address without a scheme (`github.com/foo`, as address bars show
     it) is read as `https://`. A scheme is only recognised at the start of the address
     (`letters, digits, + - .` then `://`), so `bank.com/login?next=https://x` is still read as
     `https://bank.com/...`.
   - Reason: the spec asks for "record only if the URL is known and matches"; a host-less page is
     known but cannot match any domain rule.

6. **What exactly does validation accept?**
   - Decision: `validate_domain_rule` accepts a bare host (any case, one trailing dot, IDN, which is
     compared in its punycode form) or an `http://`/`https://` URL whose host is used. It rejects:
     an empty domain; other schemes; a URL without a host; text with whitespace, `/ ? # @ : * \ [ ] %`
     outside URL form (so no wildcards, ports or paths), empty labels, labels over 63 bytes or with
     a leading or trailing hyphen; a host without a dot; `excludedSubdomains` while
     `includeSubdomains` is off; an excluded subdomain that is not strictly below the domain (the
     domain itself included) or is itself malformed. Messages are written fresh
     (`UrlRuleError`'s `Display`). Blank entries in `excludedSubdomains` are ignored.
   - Reason: these are the checks the spec lists; the exact wording of the target's messages is not
     reused.

7. **Do legacy string entries change meaning?**
   - Decision: no. They go through the unchanged base matcher (`is_url_blocked`: exact host, any
     subdomain, a dot-less word matching a whole host label, and the substring fallback for URLs that
     do not parse). Structured rules only ever match the parsed host, so `bank.com` never matches
     `notbank.com`, `bank.com.evil.io`, a path or a query string. A test compares the policy against
     the base matcher for legacy strings.
   - Reason: existing users' block lists must keep their meaning (coordinator note).

8. **Skip reason texts.**
   - Decision: `BlockedUrl` now reads "refused by the browser URL policy" and covers both a blocked
     URL and a URL missing from the allow list; the new `UrlValidationPending` reads "browser URL not
     yet verified against the URL policy". `SkipReason` gained `as_str()` labels
     (`blocked_url`, `url_validation_pending`, ...) for health and diagnostics, and `Copy`/`Eq`.
     Skip logs never contain the URL.
   - Reason: the spec lists six display texts with one for the URL policy and one for pending
     validation. No health route reads skip reasons yet; the labels are there for the WP that adds
     them.

9. **Settings keys.**
   - Decision: no keys were added. `ignoredUrls` (`UrlRule[]`) and `includedUrls` (`DomainRule[]`)
     come from W1-02. Missing, and left to the settings UI work (frontend-038): the
     `categoryOwnedFilters` key (`{apps: [], domains: []}`) the privacy category switches use, and a
     zod schema for structured rules (`lib/utils/validation.ts` still describes `ignoredUrls` as
     strings and has no `includedUrls`). The Rust validation (`validate_domain_rule`) is ready for
     that UI; there is no Tauri command for it yet.
   - Reason: settings keys belong to W1-02 and the UI to the privacy settings WP; neither is needed
     for the engine to apply the rules.

10. **Unfocused browser windows on Windows.**
    - Decision: with an allow list, unfocused browser windows are left out of the capture on macOS
      (ScreenCaptureKit exclusion list; `window_excluded_from_capture`). On Windows the capture
      backend cannot leave single windows out of a monitor capture, so a browser window that is
      visible next to the focused app can still appear in that frame's pixels. This is the same
      limitation the base has for ignored windows on Windows.
    - Reason: fixing it needs per-window masking of the monitor image on Windows, a capture-backend
      change outside this WP (follow-up below).

## Window identity

11. **Which name does a UWP app get?**
    - Decision: the hosted app's executable name (`CalculatorApp.exe`, `SystemSettings.exe`), the
      same form every other Windows app name has in the base. The app is the process that owns a
      child window of the `ApplicationFrameWindow` frame other than the frame host, preferring a
      `Windows.UI.Core.CoreWindow` child; at most 64 children are looked at. While no such child
      exists (launching, suspended, closing) the host name `ApplicationFrameHost.exe` is kept; a
      name is never empty (`Unknown` when the process cannot be read, as before).
    - Reason: the spec's "normalise exe names to display names" would rename every Windows app in
      new frames and break existing ignore rules and searches; it is not done here. Resolving the
      host is the new behaviour the spec found in the target.
    - Consequence for existing rules: until now every UWP app (Calculator, Settings, Photos, Mail
      and Calendar, ...) was reported as `ApplicationFrameHost.exe`, so a user may have excluded
      them with an `ignoredWindows` rule (or an `excluded_apps` entry) naming
      `ApplicationFrameHost`. Such a rule keeps working: a resolved app keeps the host's name
      (`WindowIdentity::frame_host`) and exclusions, never inclusions, are checked against it as
      well, in the tree walker (frames and their text), the UIA tree worker, the app observer
      (app switches, window focus) and input attribution (`window_identity::should_capture_identity`,
      `frame_host_excluded`). What changes: an *include* rule naming `ApplicationFrameHost` no
      longer lets the resolved apps through (they are recorded less, never more); new rows, and
      searches by app name, use the app's own executable name; and the engine's fallback gate for a
      capture whose tree walk found nothing (`do_capture` in `event_driven_capture.rs`, W3-11's
      region) checks the resolved name only, so in that rare case an `ApplicationFrameHost` rule
      does not catch it. Release notes for the first tagged build must say: "UWP apps (Calculator,
      Settings, Mail, ...) are now recorded under their own app name instead of
      ApplicationFrameHost.exe. Rules that exclude ApplicationFrameHost still exclude them; to
      include or search for one of them, use its own name (for example CalculatorApp)."
      (`apps/screenpipe-app-tauri/public/CHANGELOG.md` has no release section yet.)

12. **Where does the resolved name apply?**
    - Decision: everywhere `get_effective_app_name` is used: the tree walker (frames), the app
      observer (app switches, window focus, input attribution) and now also the UIA worker's window
      snapshots (`windows_uia.rs::get_window_info`, a one-line change outside the owner paths).
    - Reason: one window must have one name in frames, `ui_events` and tree snapshots.

## Input-hook watchdog

13. **When are hooks considered removed, and how often is a reinstall tried?**
    - Decision: the hook thread checks every 500 ms. The hooks count as removed when system input
      (`GetLastInputInfo`) newer than both the last hook callback and the last install has gone
      unanswered for at least 1 s (time for its callback to arrive), and the hooks have been quiet
      for at least 3 s. Because the system only reports its newest input, the watchdog remembers the
      first unanswered input it saw and lets that one age, so hooks removed while the user types
      without a pause are still found after about 3 s (tested with input every 100 ms). Input
      counts as unanswered only when it is more than 100 ms newer than the last callback: the
      system's input time comes from the ~16 ms tick counter, and the input a callback has just
      answered can look slightly newer than that callback, which would otherwise read as a removed
      hook every time the user stops typing. Attempts back off 5 s, 10 s, 20 s ... up to 10 min; the streak ends once the
      hooks have answered input and stayed healthy for 60 s after the last attempt. A failed
      reinstall counts as an attempt. Input the hooks cannot see is set aside instead of acted on:
      input to a desktop the process cannot open (lock screen, UAC prompt; `OpenInputDesktop`
      fails), and input while the foreground window belongs to a process with a higher integrity
      level than the engine (an elevated terminal or installer while the engine is not elevated),
      or one whose level cannot be read at all (`hook_watchdog::hooks_can_see_input`).
    - Reason: the spec names the mechanism but no numbers. The grace period avoids a race with the
      callback for the newest input; the backoff keeps a hook that keeps failing from spinning (an
      hour of continuous failure gives 12 attempts, tested). Windows never calls a lower-integrity
      process's low-level hooks for input to a more privileged window, so without the integrity
      check every session spent typing into an elevated window would read as removed hooks and
      cause a needless reinstall (and a warning) every few minutes. Mouse input over an elevated
      window that is not in the foreground is not covered by the check; the backoff bounds it.

14. **Which thread reinstalls, and which hooks?**
    - Decision: the hook thread itself, from its own message loop, removes both of its hooks
      (ignoring the error for a hook Windows already dropped) and installs both again. The
      activity-only hook thread (`start_activity_only`) gets the same loop, watchdog and priority.
    - Reason: low-level hooks are serviced by the thread that installed them; `GetLastInputInfo`
      cannot tell keyboard from mouse input, so both are replaced.

15. **Raw input queue limits.**
    - Decision: soft cap 2048 raw events, hard capacity 2560. At the soft cap pointer motion is
      dropped; keys, clicks and wheel ticks are dropped only at the hard capacity. Drops are counted
      and reported at `warn` at most every 30 s, with the count only.
    - Reason: the spec names a soft-capped queue that drops when the worker falls behind; motion is
      the least valuable and most frequent input.

16. **Behaviour that moved from the hook thread to the worker.**
    - Decision: include/exclude checks, text and scroll aggregation and PII removal run on
      `a11y-input-worker`. Modifier state and caps lock are still read in the callback (as the base
      did) and travel with the raw event. Button-up messages are no longer queued, so they no
      longer end a scroll run; a click, the next non-wheel event or the 500 ms idle flush still
      does. The worker takes short locks only; the hook callbacks take none.
    - Reason: the callbacks must return within `LowLevelHooksTimeout`; anything that can block
      (locks, clipboard, regexes) caused the silent removals the watchdog repairs.

17. **Which window does queued input belong to?**
    - Decision: the window that was in front when the hook callback ran. The app observer
      publishes every focus change with a new epoch and its capture decision
      (`input_focus::FocusTracker`); each callback stamps the current epoch on its raw input (one
      atomic load); the worker attributes and filters input by the window of that epoch, however
      late it handles it. The history keeps the last 64 focus changes; input whose epoch has left
      it is dropped, never attributed to another window. The focused-element context is attached
      to a click only while its window is still in front. The base read the current app inside the
      callback, so it had the same (small) window between a real focus change and the observer
      noticing it; that is unchanged.
    - Reason: judging queued input against the window in front when the worker reaches it could
      store keys typed into an excluded app (a password manager) as text of the next app (review
      round 1).

18. **Where is the clipboard read?**
    - Decision: on its own thread, `a11y-clipboard`, started only when clipboard contents are
      recorded. A clipboard shortcut is handed to it 100 ms after the key press (the base read it on
      the next 100 ms timer tick); the reader reads, removes PII and emits the event. Up to 8 reads
      may wait for it; when it is stuck on a clipboard owner that does not answer, later shortcuts
      are recorded right away without their content. The thread is not joined when recording
      stops, and shortcuts whose read was not due yet at the stop are recorded without content, so
      stopping never waits on the clipboard (the base dropped them).
    - Reason: reading the clipboard can wait seconds on its owner (delayed rendering by a
      spreadsheet, remote-desktop or VM clipboards, a hung app); on the worker that wait would hold
      up all queued input.

19. **Caps lock.**
    - Decision: caps lock changes letters only, and inverts Shift for them (Shift with caps lock on
      types a lowercase letter, as Windows does); digits and punctuation follow Shift alone. The base
      treated caps lock as Shift for every key, so caps lock turned `1` into `!` in recorded text.
    - Reason: recorded text should match what was typed.

## Scope: edits outside the owner paths

PLAN.md lists `url_filter.rs`, `platform/windows.rs`, `tree/windows.rs` (identity region),
`events.rs` (SkipReason), `capture_screenshot_by_window.rs` and `vision_manager/manager.rs`. The WP
also edits these files; each edit is plumbing the items need (copy this list into the PR
description, so W4-14 and W5-05 know about the `do_capture` gate):

- `crates/screenpipe-a11y/src/tree/mod.rs`: `SkipReason` lives here, not in `events.rs`; it gains
  `UrlValidationPending`, `as_str()` labels and `Copy`/`Eq`, and `TreeWalkerConfig` gains
  `url_policy` / `effective_url_policy()` so the walkers apply the website policy.
- `crates/screenpipe-a11y/src/platform/mod.rs` and the new platform-neutral modules
  `hook_watchdog.rs`, `input_queue.rs`, `input_focus.rs`, `window_identity.rs`: the pure logic of
  the watchdog, the raw-input queue, input attribution and UWP identity, kept outside the
  `cfg(windows)` module so Linux tests cover it; `foreground_app_name()` for the engine gate.
- `crates/screenpipe-a11y/src/platform/windows_uia.rs`: the UIA tree worker uses the same window
  identity (resolved UWP name, frame-host exclusions) as frames and input.
- `crates/screenpipe-a11y/Cargo.toml`: three `windows` crate features for the watchdog
  (`Win32_Security`, `Win32_System_StationsAndDesktops`, `Win32_System_SystemInformation`).
- `crates/screenpipe-engine/src/event_driven_capture.rs` (shared hotspot; W3-11 this wave, W4-14
  and W5-05 next): `url_policy_skip` and a gate in `do_capture` after the capture metadata is
  resolved, which skips the whole capture (no pixels, OCR or text) when the website policy refuses
  the resolved app and URL. It reuses the existing `CaptureOutput::skipped` path; W3-11's
  `pixels_withheld` path is untouched. Later edits to `do_capture` must keep this gate after
  `resolve_capture_metadata`.
- `crates/screenpipe-engine/src/capture_exclusions.rs` and `hd_recorder.rs`: the exclusion probe
  and the HD recorder receive the policy, so with an allow list unfocused browser windows join
  W3-11's exclusion list (macOS).
- `crates/screenpipe-engine/src/recording_config.rs`: builds the policy from the stored
  `ignoredUrls` rules and `includedUrls` for the vision config.
- `crates/screenpipe-engine/src/vision_manager/wedge_watchdog.rs`: its test config gains the new
  `url_policy` field.
