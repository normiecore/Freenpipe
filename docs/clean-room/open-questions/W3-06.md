# W3-06 open questions

Decisions taken while building event-trigger idempotency, run outcome verification and the
meeting-summary finalizer (db-009, meetings_memory-027, meetings_memory-028, agents_pipes-001,
agents_pipes-002, agents_pipes-m01, api-039). The specs give the tables, keys and error types;
the behaviour below fills the gaps they leave.

## 1. Schema: no new migration

- **Question:** the coordinator asked for an additive migration for any new table, column or index.
- **Decision:** none was needed. `pipe_event_runs`, its `idx_pipe_event_runs_claimed_at` index and
  `pipe_executions.trigger_event` / `trigger_key` / `conversation_id` already come from W1-01's
  interop migrations `20260728000000_create_pipe_event_runs.sql` and
  `20260805000000_add_pipe_execution_conversation_id.sql`, with the DDL db-009 and
  meetings_memory-028 record from the shipped schema. This WP only reads and writes them.
- **Reason:** PLAN section 5 keeps migrations with W1-01 so the checksums match screenpipe.

## 2. Which events are claimed, and under which key

- **Decision:** `meeting_ended` is keyed by the payload's `meeting_id`; any event whose payload has
  `source_delivery_id` (connection triggers) by that value; other events (workflow events) by the
  payload's `id` or `event_id`. `pipe_completed:*` and the other `meeting_*` events are not claimed
  and run as before. Directed refresh runs (item 9) use the key the request carries.
- **Reason:** agents_pipes-002 gives these three derivations. `meeting_started` is not named, and
  claiming it would change what a rejoined meeting does for pipes listening to it.

## 3. Claim lifetime and release

- **Decision:**
  - The claim is taken right before the run is queued, after every check that could skip the run
    (busy pipe, setup mode, live PID file, agent not ready), so a skipped event never leaves a claim
    behind.
  - It is released when the run is stopped (queued or running; a stop means the event was not
    handled), when the agent never launched (executor error before a PID), and when the execution
    row was finished or cancelled before the run began (guarded running transition, item 5).
  - Failed, timed-out and interrupted runs keep their claim: the event was handled, just not
    successfully, and the summary status shows the failure.
  - Claims are pruned once they are 30 days old, at startup and in the scheduler's daily cleanup.
    Timestamps are compared with `julianday()`, so claims written with another offset or precision
    still age out.
  - When the claim itself cannot be written (database error), the run goes ahead without one and a
    warning is logged.
- **Reason:** the 30 days (inferred in the spec) are far beyond the 120 s rejoin window, so the
  second `meeting_ended` of a rejoined meeting always finds the claim. Failing open on a database
  error risks one duplicate run instead of a lost summary.

## 4. Several events in one scheduler pass

- **Decision:** as in the base, a pipe gets at most one event run per pass and an event for a pipe
  that is already running is dropped (debug log). A second delivery of the same instance in the same
  pass is therefore skipped without touching the claim table.
- **Reason:** defer and coalesce for busy pipes is W4-02's work (pipe scheduler v2). Only directed
  refresh runs are kept and retried here (item 9), because losing one would lose a recovery.

## 5. Execution rows, running transition and stale workers

- **Decision:** scheduled and event runs now create their `pipe_executions` row (status `queued`,
  with `trigger_event` / `trigger_key`) when the run is queued, before a scheduled run waits for the
  execution semaphore. The move to `running` only applies to a row still `queued` or `running` with no
  `finished_at`; `set_execution_running` reports whether it moved, and a run whose row did not move
  stops before launching the agent. A run stopped while it was running keeps the `cancelled` state
  `stop_pipe` wrote: the worker does not overwrite it when the agent exits. `stop_pipe` on a queued run
  (which used to do nothing) cancels its row (`error_type = 'cancelled'`), so it never starts.
- **Reason:** agents_pipes-001's guarded transition. The PID watcher's late update could reopen a
  finished row in the base; the guard closes that too.

## 6. Run outcome rules

- **Decision:**
  - A clean exit is a success only when the agent's JSON stream ends in an assistant message that
    finished normally (`stopReason` `stop`/`end_turn`/`stop_sequence`) with text, or with an empty
    closing message after the run made tool calls. Output that is not Pi JSON counts when it is
    non-empty.
  - Otherwise the run fails with error_type `no_final_result` (our name; the spec gives the behaviour
    but no identifier) and a message saying what was missing (no answer, cut off at the output limit,
    aborted, still waiting on a tool call).
  - `context_compaction` when an `*compaction_end` event carries an error or `aborted`, or an error
    text says compaction failed or stayed above the threshold (W2-23's patch).
  - `content_filter` for `content_filter` / content-policy markers; `refusal` for a `refusal` stop or
    finish reason, a safety refusal or a cybersecurity-risk flag. These markers are only read from
    stderr, provider error messages and stop reasons, never from the assistant's answer text.
  - `ai_preset_unavailable` when the error says the AI gateway or preset is not configured.
  - A failed exit with none of these keeps the older text-matched classes (`rate_limited`,
    `auth_failed`, ...). The executor's own failed verdict always wins, even if a good answer came
    later in the stream (Pi retried after a provider error).
  - The same rules apply to manual, scheduled and event runs.
- **Reason:** agents_pipes-m01. Keeping refusal matching out of answer text avoids failing a meeting
  summary that mentions a "content filter".

## 7. Finalizer scope and "saved" detection

- **Decision:**
  - The finalizer only looks at runs of the bundled `meeting-summary` pipe whose trigger event is
    `meeting_ended` (the original key or `<id>:...`); other pipes triggered by `meeting_ended` are
    left alone.
  - A run counts as having saved its summary when the note's last `## Summary` section exists after
    the run and differs from the one noted just before the run started (the before snapshot is taken
    by the `before_run` hook). This also covers refresh runs on a meeting that already had a
    summary.
  - Otherwise the last `## Summary` section the assistant printed (Pi `agent_end` / `message_end`
    text, or plain stdout) is saved through the same clean, check and merge path as
    `POST /meetings/:id/summary`. Tool results are not read.
  - With nothing usable, a run that completed without an error is marked `failed`:
    `nothing_to_summarize` when the meeting has no transcript segments at the time the run ends,
    `summary_not_saved` otherwise. Runs that already failed keep their own error.
- **Reason:** meetings_memory-027. The comparison is needed because the summary-status route reads
  a single newest run, and a refresh must not be reported as saved just because an old summary is
  there. The count is taken at run end because local batch transcription catches up only after the
  meeting.

## 8. Restart recovery bounds

- **Decision:** when the scheduler starts (after it subscribed to events), summary runs with
  `error_type = 'interrupted'` that finished in the last 24 hours and have no newer run for the same
  meeting (key or `<id>:...`) are asked for again, at most 20 per start. A meeting gets at most 4
  runs counted from one second before its end (the first run and three recoveries); after that the
  interrupted run is logged and left. The recovery key is `<id>:summary-recovery-<n>` with `n` the
  number of runs so far.
- **Reason:** the coordinator asked for a bound so a run that crashes the engine every time cannot
  loop; the spec's limit of 20 is per scan, not per meeting. The 24-hour window keeps a first start
  after an upgrade from re-running very old summaries.

## 9. Refresh requests (`meeting_summary_refresh_requested`)

- **Decision:** the payload is `{meeting_id, reason, trigger_key?, pipe?, transcript_updated_at?}`.
  The scheduler turns it into a directed run of `pipe` (default `meeting-summary`) recorded with
  `trigger_event = 'meeting_ended'` and the given key (or `<id>:summary-refresh-<ms>`), claimed like
  any event run. It only runs when that pipe is enabled and lists `meeting_ended` in its triggers (the
  same "auto summary" rule as `/meetings/:id/summary-status`). A directed run that cannot start yet
  (agent still installing, pipe busy, setup mode) is retried each pass for up to 10 minutes. The
  trivial-meeting gate does not apply to it. The event is also passed to run hooks and to pipes that
  list it as a trigger.
- **Reason:** after a restart the Pi agent is often still being installed when the scheduler starts,
  so a recovery must survive a few passes.

## 10. Trivial meetings

- **Decision:** a `meeting_ended` starts no event-triggered pipes (no claim, no run) when the
  meeting lasted under 120 seconds **and** has at most 2 transcript segments. The payload's
  `duration_secs` and `transcript_segments` are used when the emitter sends them (W3-08 adds them);
  otherwise the meeting row's times and, for a short meeting only, its transcript segments are read.
  When either value is unknown the meeting is not trivial. The event still reaches every other
  listener, and the skip is logged with the counts.
- **Reason:** the spec infers the threshold ("< 3 segments or < 2 min"). Requiring both keeps local
  batch transcription safe: its segments are written only after the meeting ends, so a long meeting
  can have zero segments when `meeting_ended` fires.

## 11. The event reaches the agent

- **Decision:** an event run's prompt gets a short block naming the event, its instance key and its
  payload (cut to 2,000 characters), and asking the agent to handle that instance only.
- **Reason:** without it a recovery or refresh run of the summary pipe would summarise "the latest
  ended meeting", which may be another one. The bundled pipe already uses a meeting it was told about.

## 12. Retranscribe response

- **Decision:** `transcript_updated_at` is the RFC 3339 time the replacement committed and is `null`
  when the pass produced no transcript (no chunks, nothing decoded); in that case no refresh is asked
  for. `summary_refresh_event_emitted` is true when the refresh event was sent, whether or not the
  summary pipe is on (the scheduler decides that, item 9). Both fields are always present.
- **Reason:** api-039 names the fields; a refresh of an unchanged transcript would spend a model call
  for nothing.

## 13. Paging and activity

- **Decision:** `PipeStore` gained keyset paging (`id < before_id`, newest first, output blanked unless
  asked for) and the per-pipe activity aggregate (finished runs only: count, newest id, its
  `COALESCE(finished_at, started_at)` and status, paged on the newest id). The HTTP routes
  (`GET /pipes/:id/executions?before_id&include_output`, `GET /pipes/activity`) are W5-01's (api-029,
  agents_pipes-005) and were not added here.
- **Reason:** keeps this WP inside its owner paths; the store surface is what W4-02 and W5-01 build on.

- `crates/screenpipe-engine/src/bin/screenpipe-engine.rs` and
