# W2-12 open questions

Native WinRT/D3D11 Windows Graphics Capture and frame-diff hardening
(vision-wgc-native-capture, vision-frame-comparison-hardening).

1. **Do monitor ids from `EnumDisplayMonitors` match the xcap ids stored in `monitorIds`?** (open
   question in specs/vision.md)
   - Decision: Windows now enumerates monitors natively and derives every field exactly as xcap 0.9.4
     does: id = low 32 bits of the `HMONITOR`, name = `szDevice` from `GetMonitorInfoW`, position and
     size from the current display mode (`EnumDisplaySettingsW`: `dmPosition`, `dmPelsWidth`,
     `dmPelsHeight`), primary from `MONITORINFOF_PRIMARY`. `id()` and `stable_id()` are therefore the
     same values base builds reported.
   - Reason: same system calls, same order, same truncation, so the values match by construction.
     `wgc_smoke` prints both lists and fails when an id or `stable_id` differs, which makes the
     hardware confirmation one command (SMK-W2-12-1). The per-frame fallback still finds monitors
     through xcap by the same id.

2. **What does a monitor report when its display mode cannot be read?**
   - Decision: position and size come from `rcMonitor` instead.
   - Reason: base builds reported 0x0 at 0,0 in that case (xcap errors mapped to `unwrap_or(0)`),
     which breaks capture and `stable_id`. The fallback only applies to a monitor whose mode query
     fails, so normal ids are unaffected.

3. **Which minimum update interval is "the capture cadence"?**
   - Decision: sessions request 33 ms by default (`wgc_capture::DEFAULT_MIN_UPDATE_INTERVAL`);
     `wgc_capture::set_min_update_interval` changes it for new sessions and zero keeps the OS default.
     Older Windows builds ignore it (logged at debug).
   - Reason: the event-driven loop captures right after an input event and reads the newest frame.
     With the 200 ms capture minimum as the update interval, a frame from before the event could be
     returned. 33 ms is the high-fps floor, so no capture mode is starved, and a 60-144 Hz desktop
     still delivers 2-4x fewer frames. Each delivered frame costs only a GPU-to-GPU copy.

4. **Where does the staging readback happen?**
   - Decision: `FrameArrived` copies the frame into a session-owned GPU texture and releases the pool
     buffer at once; `get_latest_image` copies that texture to a CPU staging texture, maps it and
     converts BGRA to RGBA only when the frame sequence moved since the last read (otherwise the
     previous image is returned). The frame pool keeps 2 buffers.
   - Reason: holding a pool buffer while reading would leave the 2-buffer pool without a free buffer
     and drop frames; reading back every delivered frame (what the xcap recorder did) wastes CPU and
     bus bandwidth on frames nobody asks for.

5. **One D3D11 device per monitor or one per process? When does WARP end?**
   - Decision: one shared device for all new sessions. A lost device (`GetDeviceRemovedReason`, or a
     `DXGI_ERROR_DEVICE_REMOVED/HUNG/RESET/DRIVER_INTERNAL_ERROR` result) closes the session and is
     dropped from the cache, so the caller's next session builds a fresh one. When hardware creation
     fails the WARP device is used, and new sessions try hardware again at most once a minute.
   - Reason: the spec describes the device as dropped so the next session recreates it. Sharing saves
     GPU memory on multi-monitor setups. Without the retry, a hardware failure during a driver update
     would keep every later session on the slower software device until the engine restarts.

6. **Reset the frame-diff baseline on a resolution change, or resize?**
   - Decision: resize, as base does. A current thumbnail of a new size is resampled to the baseline
     size, compared, and then becomes the new baseline.
   - Reason: the spec's verification note found no evidence for a reset and says to keep base's
     resize. The new code keeps the invariant that the two thumbnails have equal size before the
     histogram is computed, and never panics on a mismatch.

7. **What does the frame comparer return and log when the thumbnail cannot be allocated?**
   - Decision: `0.0` ("no change"), the previous baseline is kept, `FrameComparisonStats` counts the
     failure, and a warning with `source_width`, `source_height` and `failures` is logged on the first
     failure and then every 100th.
   - Reason: the spec asks for "no change" and one log per N failures but gives no N; 100 keeps a
     machine under memory pressure from logging every frame while still showing that the condition
     persists. Keeping the baseline means the next successful frame is compared against real content.

8. **What does the hash fast path hash now?**
   - Decision: the grayscale thumbnail bytes plus its width and height.
   - Reason: one grayscale thumbnail now serves both the hash and the histogram (the target's
     grayscale-thumbnail invariant). Changes visible only in colour were already invisible to the luma
     histogram, so the decision the capture loop makes is unchanged; including the size stops two
     differently shaped thumbnails with equal bytes from matching.

9. **What counts as a non-black frame in `wgc_smoke`?**
   - Decision: at least 0.5 % of a 64x64 sample grid has a channel above 8.
   - Reason: the acceptance check only says "non-black"; any real desktop (taskbar, text, icons)
     passes easily, while the all-zero frames WGC produces when capture silently fails do not.
