# W4-02 open questions

Decisions taken while building pipe scheduler v2 (agents_pipes-007, agents_pipes-042,
agents_pipes-m06). The spec records the log vocabulary, file names and environment variables;
the behaviour below fills the gaps it leaves. It builds on W3-06 (claims, run outcomes, the
meeting-summary finalizer) and replaces W3-06's in-memory "kept runs" list, as W3-06's
open question 17 asked.

## Deferred triggers

### 1. Backlog cap and what is dropped

- **Question:** the spec infers a cap of 32 and says excess deferred triggers are dropped with a
  warning. Per pipe or overall, and which trigger goes?
- **Decision:** at most 32 deferred runs per pipe (`backlog::DEFERRED_BACKLOG_CAP`). When a new
  one would go over, the pipe's oldest deferred run is evicted. Every eviction is logged at warn
  level with its reason and counted (`BacklogStats::dropped_full`). A run that was for one event
  instance (it has an instance key: a meeting id, a delivery id, a refresh key) is also recorded as
  a `pipe_executions` row with status `skipped` and `error_type = 'deferred_backlog_full'`; an
  unkeyed wake-up is only logged.
- **Reason:** a per-pipe cap bounds memory by the number of pipes and keeps one noisy pipe from
  pushing out another's runs. The newest trigger carries the newest state, so the oldest goes. The
  skipped row makes a lost meeting summary visible in `summary-status` (it reads as failed, so a
  refresh can be asked for). Unkeyed wake-ups are coalesced per event name, so a full backlog of
  them is very unlikely, and a row for each would only add noise.

### 2. What coalescing folds together

- **Decision:** two deferred runs are the same run when pipe, event name and instance key are all
  equal (an unkeyed event has no key, so repeats of `workflow_ready:<pipe>` or
  `pipe_completed:<pipe>` fold into one). The newer payload replaces the older one, while the
  entry keeps its queue position and the time it was first deferred. A repeat of the trigger whose
  run starts on the current pass folds into that run (with the newer payload) instead of waiting.
  Runs with different keys are never folded, so two meetings still get two runs, and a duplicate
  of one meeting that slips through is still stopped by W3-06's claim.
- **Reason:** "older duplicates for the same pipe are coalesced into the newest generation"
  (agents_pipes-007 item 3) without ever merging different event instances, which would lose a
  summary.

### 3. Every event kind is deferred now

- **Decision:** an event for a busy pipe is deferred whether or not it has an instance key. W3-06
  kept only keyed events and dropped the rest (base behaviour).
- **Reason:** the spec says busy events are deferred, not dropped. Coalescing keeps unkeyed
  wake-ups from piling up.

### 4. Deadline

- **Decision:** W3-06's 10 minutes (`DEFERRED_REQUEST_TTL`), counted from when a run was first
  deferred, apply only while the run cannot start for a reason other than a busy pipe: the agent
  is not ready, setup mode, another process holds the pipe's PID file, or the trigger context
  could not be written. Waiting behind a queued or running run of the same pipe never expires; that
  run ends within its own timeout. An expired keyed run is recorded as `skipped` with
  `error_type = 'deferred_expired'`; an unkeyed one is logged. The W3-06 stop rule is kept: copies
  of an event instance whose run `stop_pipe` stopped are dropped at the next pass, and a pipe that
  was turned off (or no longer lists the event) drops its deferred runs.
- **Reason:** with a cap in place the deadline only needs to cover pipes that are stuck; a long
  meeting summary must not make the next meeting's summary expire.

### 5. Persistence across restarts

- **Decision:** the backlog stays in memory.
- **Reason:** W3-06's restart recovery already asks again for interrupted meeting summaries, and
  the connection watcher (agents_pipes-008, W6-03) retries undelivered items itself. A persisted
  queue would need a table the target schema does not have (PLAN section 5: no new migrations).

## Event sources

### 6. `connection_trigger`

- **Decision:** the payload's `pipe_name` (or `pipe`) names the one pipe to run; the instance key
  is `source_delivery_id` (W3-06's key rule), the run is recorded with `trigger_type =
  'connection'` and `trigger_event = 'connection_trigger'`, and it bypasses the scheduled-run
  queue like other event runs. The named pipe must be on and either watch connected apps
  (`trigger.sources` is not empty) or list `connection_trigger` in `trigger.events`. Such a
  trigger is not matched against other pipes' trigger lists; run hooks still hear it. A payload
  that names no pipe is matched against `trigger.events` like any other event.
- **Reason:** agents_pipes-008 says the watcher fires the pipe whose sources matched and sends
  `pipe_name` and `source_delivery_id`; broadcasting it would start unrelated pipes.

### 7. `workflow_ready:<pipe>`

- **Decision:** read from the all-events subscription by prefix (like `pipe_completed:`), matched
  exactly against `trigger.events`. Unkeyed unless the payload has `id` or `event_id`.
- **Reason:** the event name embeds the pipe, so it cannot be subscribed by a fixed name.

## Trigger context file

### 8. Shape, content and failure handling

- **Decision:** `.trigger-context.json` in the pipe's folder holds `event`, `key`, `pipe`,
  `trigger_type`, `triggered_at` (RFC 3339 UTC, milliseconds) and `data` (the payload). The
  payload goes through a credential scrub first (`pipes/redact.rs`): fields named like a
  credential (`token`, `access_token`, `api_key`, `authorization`, `client_secret`, `password`,
  `cookie`, ... in any spelling) are replaced by `[redacted]`, and strings are scanned for bearer
  and basic credentials, `user:password@` in URLs, credential query parameters and well-known key
  prefixes. A payload over 64 KiB becomes an 8 KiB text preview with `data_truncated: true`. The
  file is written atomically (temporary file, then rename), owner-only on Unix. It is written
  after the claim; if it cannot be written the claim is given back and the run is deferred (the
  spec: "if it cannot persist source context the run is deferred"). Scheduled and manual runs
  remove the file before they start. The payload shown in the prompt (W3-06's trigger context
  block) is scrubbed the same way.
- **Reason:** the spec gives `{"event", "key", ...}`; the rest is what a prompt needs to find its
  event. The coordinator asked that the file never hold secrets. A stale file would make a
  scheduled run believe it was woken by an old event.

## Trivial meetings

### 9. Persisting the skip

- **Decision:** unchanged from W3-06 (decision 10): a trivial meeting starts no pipes and the skip
  is logged with its counts. No skipped row is written for it.
- **Reason:** a skipped row would turn the meeting's summary status from idle into failed, and the
  UI would then show an error for a meeting that simply had nothing to summarise; idle keeps the
  manual "summarize" action on offer.

## Presets

### 10. What `"*"` expands to

- **Decision:** the user's own presets from the AI settings (`store.bin` `settings.aiPresets`):
  the default preset first, then the others in the order the settings list them, without repeating
  a preset the list already names. `default` / `auto` in a list mean the default preset;
  `pi-agent` means `screenpipe-cloud`. Nothing is synthesised: Freenpipe has no vendor presets,
  and hosted presets imported from screenpipe were migrated to local ones or point at the user's
  own gateway (W0-06).
- **Reason:** agents_pipes-007 item 6 ("the user's configured presets"); the coordinator asked
  that `*` expand to the user's own presets only.

### 11. A missing named preset

- **Decision:** a list entry that names no preset of the user's (or one without a model) is passed
  over in favour of the list's next entry, with a warning. When nothing in the list is usable the
  run fails with `error_type = 'ai_preset_unavailable'` and a message that names the missing
  presets and lists the available ones (or says the settings could not be read). The run never
  falls back to the pipe's own `model` / `provider` fields, the default preset (unless the list
  says `default` or `*`) or any other provider. This holds for scheduled, event and manual runs; a
  manual run returns the message as its error and is recorded as a failed execution. A pipe with
  no `preset` list keeps the base behaviour: the user's default preset, else the pipe's own
  fields.
- **Reason:** "does not fall back to another provider" is about providers the pipe did not ask
  for; the entries of the list are the user's own declared fallbacks. Failing the whole list on its
  first missing entry would break pipes copied from screenpipe that say
  `preset: [screenpipe-cloud, "*"]` for every user without that preset, against decision 1 (drop-in
  pipes). Base silently used `config.model`, which could reach a provider the user never chose.

### 12. Fallback slots in scheduled runs

- **Decision:** scheduled and event runs now use the preset chain and its circuit breakers like
  manual runs: when an attempt fails (not a stop) and the chain has another slot (at most
  `MAX_FALLBACK_DEPTH` = 4 attempts), the next slot runs at once. The failed attempt keeps its
  execution row; the retry gets a new row with the same trigger event and key, and the event
  claim stays with the run. A status line `{"type":"status","kind":"model_fallback","requested",
  "used","model","reason"}` goes to the output stream (and the trajectory) when a run moves to a
  later slot, or starts on one because earlier entries were missing or cooling down. Run hooks,
  run logs and breaker updates happen per attempt; `pipe_completed`, the run-complete callback and
  the scheduler state happen once, with the final result. The background manual run
  (`POST /pipes/:id/run`) keeps one attempt as before.
  The note's `requested` is the preset the list's first entry resolves to (`default` / `auto` to
  the default preset, `pi-agent` to `screenpipe-cloud`, `"*"` to its first preset), or that entry as
  written when it names no preset, so `preset: auto` on the default preset reports no fallback.
- **Reason:** "retry on a failing preset moves to the next fallback slot" (item 6) is in the
  scheduler's vocabulary; base scheduled runs used only the first preset and ignored the rest of
  the list. Keeping the failed attempt's row keeps the history honest.

### 12a. Run state between attempts, and claims of runs that never started the agent

- **Decision:** once an attempt's agent has exited, the pipe stays claimed for a possible retry
  (the in-memory running entry and `run.pid` remain), but its process id is dropped at once: the
  handle and `run.pid` go back to the sentinel 0, the attempt's row leaves the running-row map, and
  the attempt's PID watcher no longer records an id after that point. A Stop that lands between
  attempts or during `after_run` hooks therefore signals no process and does not rewrite the
  finished row as cancelled; the worker writes the row whenever it still owns it. A retry that is
  stopped while it is being set up does not start the agent. When no attempt of a run started the
  agent (no usable preset, a launch error, a timeout before the process came up) the event claim is
  given back whatever the error type, so a later delivery of the same instance (a rejoined meeting
  ending again after the preset was fixed) can run. An attempt counts as started when the agent
  reported a process id or returned an output.
- **Reason:** base dropped the running state as soon as the single attempt's agent exited; keeping
  a dead id around could make Stop (`taskkill /F /T` on Windows) or the startup orphan cleanup
  signal whatever process reused it. W3-06 gave the claim back only on a launch error, which was the
  only way base could fail without starting the agent.

## Skipped runs

### 13. Status and reasons

- **Decision:** status `skipped`, with `error_type` `stale_one_off`, `deferred_backlog_full` or
  `deferred_expired` (Freenpipe's names; the spec gives the behaviour only) and a sentence in
  `error_message`. `PipeStore::record_skipped_execution` has a default implementation (create the
  row, then finish it), so the SQLite store needed no change.
- **Reason:** agents_pipes-007 item 7; the coordinator asked that skipped runs be persisted with
  their reason.

### 14. Stale one-offs

- **Decision:** an enabled `schedule: at <time>` pipe that has not fired and is more than an hour
  late (the base `ONE_OFF_STALE_THRESHOLD`) is switched off through the device-local override and
  recorded once as a skipped scheduled run. It does not run late.
- **Reason:** base already refused to fire stale one-offs but left them enabled forever without a
  trace; the spec adds the persisted skip.

## Trajectories

### 15. Switching on, location and retention

- **Decision:** off unless `SCREENPIPE_TRAJECTORIES_DIR` is set. `1`, `true`, `on` or `yes` use
  `<data dir>/trajectories`; `0`, `false`, `off`, `no` or an empty value mean off; a relative path
  is taken from the data directory and `~/` from the home directory. `SCREENPIPE_TRAJECTORIES_MAX_RUNS`
  defaults to 100 (values above 10,000 are capped; 0 or junk mean the default). Files go straight
  into the folder, one per attempt, named `%Y-%m-%dT%H-%M-%S%.3fZ.jsonl` (a `-<n>` suffix when two
  start in the same millisecond). After every run the folder is pruned to the newest files;
  files still being written and files with other names are never removed.
- **Reason:** the spec says "default a `trajectories` folder" and "off unless the env var is set
  (inferred)"; both hold when the variable doubles as an on switch. The count was not observed.

### 16. Content

- **Decision:** JSON lines with `type`, `seq` and `at`: `run_start` (pipe, execution id, trigger,
  event and key, model, provider, preset, attempt, prompt and system prompt), one `agent_event`
  per line of the agent's stream as it arrives (parsed JSON, else `text`), `status` notes,
  `truncated` once a file reaches 32 MiB (lines over 1 MiB are cut), and `run_end` (success,
  error type, duration, event count). Every record goes through the credential scrub of
  decision 8. Recorded for scheduled, event and manual runs.
- **Reason:** "JSONL recording of agent events per run (`jsonl_delta`)"; the bounds keep a looping
  agent from filling the disk. Trajectories can still contain screen content the agent read,
  which is why they stay opt-in and local.

## Log archive

### 17. Policy and schedule

- **Decision:** a sweep keeps each pipe's newest 50 run logs and any log younger than 7 days (by
  its name and by its modification time) in `logs/`; older ones are appended, one JSON line each
  (`{"file", "log"}`), as a gzip member to `logs/archive/<YYYY-MM>.jsonl.gz` and deleted only after
  the member is synced to disk. At most 2,000 logs per sweep. Month archives are kept for good:
  pruning exists (`ArchivePolicy::keep_months`) but is off by default. `logs/archive/<YYYY-MM>.names`
  lists the file names each month archive holds; a log already listed (an earlier sweep archived it
  but could not delete it, for example a file held open on Windows) is not appended again, only
  its delete is retried and counted as `already_archived`. A missing list is rebuilt from the
  archive, a list whose update failed is removed so the next sweep rebuilds it, and `read_archive`
  returns a log appended twice (a crash between the member and the list) once. Pipes with a run
  queued or running are skipped, as are files whose names the runtime did not write. The scheduler
  runs the sweep five minutes after it starts and then every six hours, on a blocking thread, one
  sweep at a time, and logs `pipe log archive: scanned=... archived=... bytes=... failed=...
  already_archived=... pipes=... skipped_running=... archives_removed=...`.
  `PipeManager::archive_pipe_logs` runs one on demand. Run logs of two runs started in the same
  second now get `_1`, `_2` suffixes instead of overwriting each other.
- **Reason:** the spec observed the task, its counts and the `%Y%m%d_%H%M%S` naming, not the
  retention or format. Base kept run logs forever, and for runs older than the 50 execution rows
  the database keeps they are the only record, so the archive compresses them but deletes nothing
  by default. Gzip JSON lines stay readable with standard tools. `flate2` (MIT or Apache-2.0,
  already in the lock file through other crates) is now a direct dependency of `screenpipe-core`.

## Files outside the owner paths

### 18. Why they changed

- `pipes/backlog.rs`, `redact.rs`, `trigger_context.rs`, `scheduled_run.rs`,
  `scheduler_tests.rs` (new): the backlog, the scrub, the context file, the scheduled-run worker
  (moved out of `start_scheduler`'s spawned closure so it can retry slots) and the tests, kept
  out of the 7.9k-line `pipes/mod.rs`.
- `pipes/event_runs.rs`: event name constants, `EventRun::trigger_type` and
  `EventRun::connection_trigger`, and the scrub of the prompt's payload.
- `pipes/test_support.rs`: the scripted agent records models and can fail on chosen models; the
  memory store lists rows per pipe.
- `pipes/mod.rs` outside `start_scheduler`: the shared preset choice (`choose_run_model`) used by
  the two manual run paths, trajectory recording and context-file removal in those paths, the
  `record_skipped_execution` store method, and `write_log_to_disk` using the collision-safe
  naming.
- Why trajectories are recorded inline rather than through `pipes/hooks.rs` (PLAN section 5):
  `PipeRunHook` has `before_run`, `after_run`, `on_event` and `on_scheduler_start` but no per-line
  callback for the agent's output stream, and a trajectory is mostly that stream (`agent_event`
  records as lines arrive, plus the fallback `status` notes). Recording through hooks would have
  meant adding a stream method to the hook trait, which other WPs implement, so the recorder
  (`pipes/trajectory.rs`) is called from the three places that already drain the stream: the two
  manual run paths in `mod.rs` and `scheduled_run.rs`. A later WP may add an `on_output_line` hook
  and move the recorder onto it.
- `crates/screenpipe-engine/src/pipe_store.rs` (a W3-06 owner path): a test only, for the SQLite
  side of `record_skipped_execution` (the method's default implementation lives in
  `screenpipe-core`); no runtime code changed.
- `paths.rs`: `PIPE_TRIGGER_CONTEXT_FILE`. `docs/env.md`: the trajectory variables' values.
  `Cargo.toml` / `Cargo.lock`: `flate2`.

## Follow-ups for later WPs

### 19. Hand-offs

- **W6-03 (connection triggers watcher):** send `connection_trigger` with `pipe_name` and
  `source_delivery_id`; detect the outcome by the `pipe_executions` row whose `trigger_key` is the
  delivery id (or `pipe_completed:<pipe>`), and give up after its own retry count (spec: 3).
- **W4-01 (workflows):** emit `workflow_ready:<task>` when a workflow task has work; repeats while
  the task runs fold into one more run.
- **W5-01 (pipes UI/API):** show `skipped` runs and the `stale_one_off`, `deferred_backlog_full`,
  `deferred_expired` and `ai_preset_unavailable` reasons in the run history (the current badge
  helper replaces only the first underscore), render `model_fallback` status lines, and offer
  `"*"` in the preset picker.
- **Background manual runs:** `POST /pipes/:id/run` still makes one attempt; moving it onto
  `ScheduledRun` would give it slot fallback too.
