# W2-27 open questions

Decisions taken while hardening the app's start-up (shell-017, shell-019, shell-020, shell-021,
shell-022, shell-024, shell-028) and closing the W2-26 follow-ups. Each one is the worker's call; the
owner can overturn any of them.

## 1. Where the helper-mode table lives and what an unbuilt helper does

- **Question:** shell-024 says `main` dispatches `--screenpipe-acp-runtime`,
  `--screenpipe-acp-process-guard`, `--screenpipe-portable-mcp` (and later `--render-workflow-video`)
  before any Tauri or single-instance work, but the features behind them belong to the agents, MCP and
  workflow work packages.
- **Decision:** `main.rs` holds the table (`HELPER_MODES`, one line per flag, as PLAN.md section 6
  expects later WPs to edit) and `startup.rs` the dispatch and the stand-ins. The flag must be
  `argv[1]` exactly. Until a feature lands, its stand-in prints a short usage message to stderr and
  exits with status 2. `--render-workflow-video` already follows its own contract: one JSON object
  `{"error": ...}` on stdout, and an argument-count error unless exactly one directory is given. A
  later WP replaces the `run` function of its line.
- **Reason:** the dispatch rule (before the single-instance handoff, before any thread) is this WP's
  part; inventing placeholder features would be wrong, and an exit code plus a message lets callers
  and the smoke test see the dispatch path working.

## 2. Order at the top of `main`

- **Question:** W2-26 requires `relaunch::capture_relaunch_flag()` to be the first call, with
  nothing before it starting a thread.
- **Decision:** `main` is `capture_relaunch_flag()`, then the helper dispatch, then `app_main()`.
  The dispatch only reads the command line. The AVX2 check is the first statement of `app_main`;
  the WER registration follows the panic hook.
- **Reason:** keeps W2-26's guarantee, and helpers never inherit a stale relaunch flag.

## 3. A `/focus` request without `launch_exe`

- **Question:** the target rejects handoffs from other executables; what about requests that send no
  executable at all (Freenpipe's browser extension sends only `target`, scripts and older builds send
  `{args, deep_link_url}`)?
- **Decision:** they are accepted as before, subject to the deep-link scheme check. Only a request
  that names an executable is compared.
- **Reason:** the extension's pairing flow depends on it, and such callers are local (see 6); the
  executable check exists to stop a second install handing off to the wrong one, and every Freenpipe
  build now sends `launch_exe`.

## 4. A `launch_exe` that cannot be resolved

- **Question:** the target logs that it could not verify the handoff executable, without saying what
  happens next.
- **Decision:** refused (403). Both paths are canonicalised and compared with
  `port_conflict::same_executable` (case-insensitive, slash- and `\\?\`-insensitive on Windows).
- **Reason:** failing closed is the safe reading; a running copy of the same executable always
  resolves.

## 5. What a refused second launch does

- **Question:** the spec lets the caller "continue starting or exit with a message".
- **Decision:** it exits with status 1 after telling the user why: a message box on Windows, an
  alert (`osascript`) on macOS, a desktop notification (`notify-send`) on Linux, and stderr
  everywhere. When the alert command is missing only stderr remains. The text follows the refusal
  kind the running copy reports (question 27): another install, an executable it could not
  verify, or a link for another build. A `--autostart` launch exits silently.
- **Reason:** continuing would fight the running install for port 3030, the control port and the
  database. Two installs both set to start at login would otherwise show a dialog at every sign-in.
  Off Windows the base focused the other install instead, so a refusal with no visible answer would
  look like a launch that did nothing.

## 6. Which origins and hosts count as local

- **Question:** the spec lists `tauri://localhost`, `http(s)://localhost*` and
  `http(s)://127.0.0.1*`.
- **Decision:** origins `tauri://localhost`, `http(s)://tauri.localhost` (WebView2's origin on
  Windows) and `http(s)://` on `localhost`, `127.0.0.1` or `[::1]` with an optional numeric port;
  hosts `localhost`, `127.0.0.1` and `[::1]` with an optional port. The names are parsed, so
  `localhost.evil.example` is not local. A request without `Origin` (pipes, the CLI, curl) is allowed;
  a request without `Host` is allowed too (browsers always send one). Browser-extension origins
  (`chrome-extension://`, `moz-extension://`, `safari-web-extension://`) may call `/focus` only.
  CORS answers only local and extension origins instead of `*`.
- **Reason:** without `tauri.localhost` the app's own notification bell and app icons would break on
  Windows; the `*` suffix in the spec reads as "any port", and a prefix match would let rebinding
  hosts through.

## 7. A duplicate `--autostart` handoff

- **Question:** what does the running instance answer?
- **Decision:** 200 with no window change, after the executable and scheme checks; the
  single-instance plugin path (when the control server is not up yet) ignores `--autostart` too.
- **Reason:** the second process should exit quietly as "handed off".

## 8. How the login entry is written on Windows

- **Question:** the autostart plugin (auto-launch 0.5) writes `<exe> --autostart` unquoted and
  re-enables the Task Manager entry on every `enable()`, which the base app called at every start.
- **Decision:** on Windows the app writes the HKCU `Run` value itself as `"<exe>" --autostart`, under
  the same value name the plugin uses (the product name). At start-up it only adds a missing entry or
  rewrites an outdated one and never touches `StartupApproved`, so a Task Manager "disabled" stays.
  Switching autostart on in settings writes the entry and marks it enabled in Task Manager. macOS and
  Linux keep the plugin, now configured with `--autostart`.
- **Reason:** the spec asks for a quoted command and for the Task Manager choice to be respected.

## 9. Dev isolation for autostart

- **Question:** the target skips autostart registration "under dev isolation".
- **Decision:** debug builds (or `TAURI_ENV_DEBUG=true`, the same test as the updater's) never touch
  the login entry, neither at start-up nor from the settings toggle, which returns success and logs.
- **Reason:** a dev build must not replace or remove the installed app's entry, which has the same
  name.

## 10. `--autostart` with unfinished onboarding, and the relaunch flag

- **Question:** should a login launch stay hidden when onboarding is not done, and what wins between
  `--autostart` and `SCREENPIPE_RELAUNCH_HOME_VISIBLE`?
- **Decision:** unfinished onboarding always shows the onboarding window. Otherwise the relaunch flag
  decides when present (a safe relaunch never forwards `--autostart`), then `--autostart` keeps Home
  closed. `relaunch::relaunch_home_visible()` is read before Home is first created, so a relaunch
  with Home closed no longer flashes it (W2-26 open question 12).
- **Reason:** a user who never finished onboarding would otherwise only ever see a tray icon.

## 11. `SCREENPIPE_SKIP_ONBOARDING` values

- **Decision:** `1`, `true`, `yes` and `on` (any case) mark onboarding complete before the first
  window is chosen; the `onboarding` E2E seed does the same and stays for tests. The local copy used
  for the window decision is updated, and the managed state is stored after the change (the base
  stored it before, so the seed opened onboarding anyway).

## 12. `SCREENPIPE_DATA_DIR` against the `dataDir` setting

- **Question:** shell-021 says the variable wins over `dataDir` for the process; W2-26 (its open
  question 10) passes the base directory to every safe-relaunch replacement.
- **Decision:** the variable wins (`config::resolve_data_dir`), logged once per run when it overrides
  a custom setting. The safe relaunch now passes `SCREENPIPE_DATA_DIR` only when this process was
  started with it (the replacement inherits it anyway); otherwise the replacement reads `dataDir` as
  before.
- **Reason:** with the new precedence, passing the default directory would move a user's custom
  recording folder back to `~/.screenpipe` after every relaunch. The precedence itself protects dev
  and E2E runs: a copied settings store can no longer send their recordings to the real folder it
  names.

## 13. Which directories get a runtime scope grant

- **Decision:** the base directory and the recording directory, unless they are inside
  `~/.screenpipe` (covered by the static asset and fs scopes); both the fs plugin scope and the asset
  protocol scope, recursively. Failures are logged and do not stop the start.

## 14. Detecting AVX2, and the overlap with W2-23

- **Question:** W2-23 adds `screenpipe_core::cpu_features` with its own CPUID reading; it has not
  landed yet.
- **Decision:** `cpu_compat.rs` uses the standard library's `is_x86_feature_detected!("avx2")`
  (CPUID plus the OS's XSAVE state), so it repeats no CPUID logic and needs nothing from W2-23. When
  W2-23 lands, `cpu_compat::detect` can call its helper instead; the decision logic stays here.
- **Reason:** one less dependency between two WPs built in parallel; both answers come from the same
  registers.

## 15. What compatibility mode turns off in Freenpipe

- **Question:** the target keeps "the ONNX-based Qwen build on Windows"; Freenpipe's Qwen3-ASR is the
  antirez C build on every platform (`qwen3-asr-antirez-blas`).
- **Decision:** every Whisper engine and `qwen3-asr` switch to Parakeet (or to `disabled` when a
  build has no Parakeet), including a Whisper fallback picked for a cloud engine without its key. The
  switch is a new fallback reason, so the existing notification explains it: `cpuCompatMode` when
  Parakeet takes over, `cpuCompatModeNoLocalEngine` when no local engine is left (only builds
  without the `parakeet` feature, none of the release builds). The switch is logged as a warning
  once per process and at debug level after that, because the resolution is recomputed for every
  recording config. The Whisper pre-download is skipped; `BootPhaseSnapshot` gains
  `cpuCompatMode`. Cloud engines stay available.
- **Reason:** Freenpipe has no ONNX Qwen build yet; if W2-19 adds one for Windows, `qwen3-asr` can
  come off the list there. The settings UI does not explain compatibility mode yet (follow-up).

## 16. AVX2 code at static initialisation

- **Question:** the spec warns that whisper/ggml must be built so no AVX2 code runs during static
  initialisation on such CPUs.
- **Decision:** not changed here; the `cpu-smoke:` log line marks that start-up got past native
  static initialisation, and SMK-W2-27-12 checks it on a CPU without AVX2.
- **Reason:** the ggml build flags belong to the audio build WPs (W2-18, W2-19); changing them blind
  could slow every other machine.
- **Follow-up (tracked):** both of those WPs have merged, so the item is recorded in
  `docs/clean-room/open-questions/W2-19.md` ("Follow-ups from later WPs") for the owner to assign:
  check whether the release builds of whisper.cpp/ggml (and the antirez Qwen3-ASR build) run AVX2
  instructions before `main`, and build them so they do not. The Windows x64 release sets
  `/arch:AVX2` in `CFLAGS`/`CXXFLAGS`, so that risk is real there. Until then compatibility mode
  only helps when native static initialisation survives; SMK-W2-27-12 is the check.

## 17. WER helper: where dumps go and what the DLL does

- **Question:** the target's evidence shows the mechanism but not the exact paths.
- **Decision:** the crate is `crates/screenpipe-wer-helper`, building `screenpipe_wer_dump_helper.dll`
  (the shipped file name). The app passes, as the registration context, a block holding
  `<data dir>\crash-dumps\pending` (magic `FPWR`, version 1, up to 1023 UTF-16 units); the DLL reads it
  out of the crashed process with `ReadProcessMemory` and falls back to `crash-dumps` next to itself.
  It writes `<exe>-<pid>-<UTC>.dmp` through a `.partial` file (threads, referenced memory, handles,
  unloaded modules: a few MB), stops at 5 waiting dumps, and never claims the crash, so WER's own
  handling is unchanged. At the next start a thread named `screenpipe-wer-dump-harvest` moves finished
  dumps from both places into `<data dir>\crash-dumps`, deletes `.partial` files older than an hour,
  and keeps the newest 10. "Data dir" is the base directory (where `last-panic.log` lives). Nothing
  uploads a dump.
- **Reason:** writing straight into the data directory needs no install-dir write access; the
  pending folder makes "recovered N dumps" countable and keeps half-written files out of the
  collected set.

## 18. WER registration details

- **Decision:** the allow-list value goes under HKCU only (`REG_DWORD` 0 named after the DLL's full
  path); stale values for a DLL of the same name that no longer exists are removed, others are left
  alone. A context path too long for the block registers with a null context. Registration failures
  are logged, never fatal.
- **Reason:** per-user installs cannot write HKLM. If a smoke test shows WER ignoring the HKCU value,
  the per-machine installer hook will have to add the HKLM value (follow-up).

## 19. Building and shipping the DLL

- **Decision:** `stage_bundled_runtime.js` stages it into `src-tauri/bundled/native/` (mapped to the
  install directory in `tauri.windows.conf.json`) when `FREENPIPE_BUILD_WER_HELPER=1`,
  `FREENPIPE_WER_HELPER_DLL=<path>` or `FREENPIPE_REQUIRE_BUNDLED_RUNTIME=1` is set; `release-app.yml`
  sets the first for Windows. The build uses `-C target-feature=+crt-static` in its own target
  directory.
- **Reason:** WerFault.exe loads the DLL with System32's search path, where the vcruntime140.dll
  bundled beside the app is not found; a static C runtime removes that dependency. Dev builds skip it,
  and the app then logs that the helper is missing (as the target does).

## 20. A debug command to force a crash

- **Decision:** `debug_force_native_crash` (debug builds or developer mode, like W2-26's debug
  commands) calls `std::process::abort()`, which is a `__fastfail` on Windows.
- **Reason:** the acceptance check needs a reproducible fail-fast crash in a test build.

## 21. Opener allow-list syntax

- **Question:** shell-028 quotes the target's compiled regexes; the opener plugin in this repository
  matches its `url` scope with glob patterns, so the existing `^https?://.*`-style entries never
  matched anything (http, https, mailto and tel worked only through `opener:default`).
- **Decision:** the list is written as globs: `http://*`, `https://*`, `mailto:*`, `tel:*`,
  `x-apple-reminderkit://*`, `obsidian://*` (kept), and the new
  `claude://claude.ai/new[?]q=*`, `cursor://anysphere.cursor-deeplink/prompt[?]text=*`,
  `codex://threads/new[?]prompt=*` (`[?]` is a literal question mark). A test runs the real glob
  matcher over `capabilities/main.json`.
- **Reason:** same allowed set as the target's regexes, in the syntax the plugin applies.

## 22. An engine start in flight when a quit or relaunch begins (W2-26 open question 29)

- **Question:** a start still inside `ServerCore::start` was not waited for, so the process could run
  native destructors, or a relaunched process open the database, while it was still coming up.
- **Decision:** `start_generation` counts as an engine transition from before its quit check, through
  `ServerCore::start`, until the core is stored or retired. The teardown's engine step waits for it
  within its 21 s limit; a start that outlasts that makes the quit a forced exit (`hard_exit`, which
  skips the destructors). A safe relaunch then waits up to 30 s more before starting the replacement,
  and relaunches anyway after that (this process exits right away).
- **Reason:** waiting is the only safe option: cancelling a start mid-migration could leave tasks
  holding the database. The forced exit was already the teardown's answer to an engine that will not
  stop.

## 23. Which file names the install when the app runs from a Linux AppImage

- **Question:** the handoff compares `launch_exe` with the running app's executable, but an AppImage
  runs its binary from a mount (`/tmp/.mount_*`) that changes on every run, so two launches of the
  same AppImage never had the same executable. Single-instance is off on Linux, so this HTTP handoff
  is the only one there, and deep links were lost.
- **Decision:** when `$APPIMAGE` is set and the executable lies inside `$APPDIR`, the canonicalised
  `$APPIMAGE` names the install, both in the `launch_exe` a second launch sends and in the identity
  the running app compares it with. Otherwise the canonicalised executable does, as before. The two
  variables are only read on Linux.
- **Reason:** the image file is what the user installed and launches, and it stays put between runs.
  The `$APPDIR` check stops an inherited `$APPIMAGE` (a process started by an AppImage app) from
  relabelling an unrelated binary as that AppImage.

## 24. A 403 on the focus port from something other than the app

- **Question:** a second launch treated any 403 from the focus port as "another install refused",
  and exited.
- **Decision:** only a JSON body of the control server's shape, `{"success": false, "message": ...}`
  with a string message, counts as a refusal. Any other 403 (plain text, HTML, other JSON) means no
  instance: the app starts normally, and the port-conflict check reports the foreign listener.
- **Reason:** an unrelated local service on the focus port must not be able to keep Freenpipe from
  starting.

## 25. Crash-dump directories on other platforms

- **Decision:** `crash-dumps/pending` is created, and earlier dumps are collected, on Windows only;
  elsewhere `wer::log_and_harvest` returns after the (empty) registration log.
- **Reason:** no other platform has a helper that writes dumps there, so the directory and the
  harvest thread would only be noise in the data directory.

## 26. Release builds for another target triple

- **Decision:** when `SCREENPIPE_RELEASE_TARGET` is set, the WER helper is built with
  `--target <triple>` and staged from `<target-dir>/<triple>/release/`; unset or empty keeps the host
  build in `<target-dir>/release/`.
- **Reason:** the Windows ARM64 matrix entry must ship a helper built for ARM64, not for the host.

## 27. Telling the refused launch why

- **Question:** the refused launch only received a message string, so it could not say whether the
  running copy is another install, could not verify it, or belongs to another build.
- **Decision:** a `/focus` 403 also carries `reason`: `otherExecutable`, `unverifiableExecutable`
  or `foreignDeepLink` (Freenpipe's own field, next to `success` and `message`). The refused launch
  words its message from it; a refusal without `reason`, or with one it does not know (an older or
  newer running copy), gets a general "another copy refused this launch" text. Question 24's shape
  check is unchanged: `reason` is optional.
- **Reason:** an extra field leaves callers that read only `{success, message}` working.

## 28. Changes outside the owner paths (for the PR description)

  compatibility-mode reasons and the call to `cpu_compat::apply_to_resolution` (question 15). The
