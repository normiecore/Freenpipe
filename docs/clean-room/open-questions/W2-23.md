# W2-23 open questions

Decisions taken while building the Pi runtime upgrade (agents_pipes-015): the 0.84.1 pins, the
isolated Pi config, the baseline bun, the bash probe and the runtime patch. Each one is the
worker's call; the owner can overturn any of them.

## 1. Licences of the pinned packages (decision 7)

- **Question:** are Pi 0.84.1 and everything the runtime pins usable in a commercial build?
- **Decision:** yes. Checked on the public npm registry (the only source the runtime installs
  from) on 2026-10-20: `@earendil-works/pi-coding-agent`, `pi-ai`, `pi-agent-core`, `pi-tui`,
  `pi-client`, `pi-protocol` and `pi-telemetry` 0.84.1 are MIT (0.84.1 was published 2026-08-07);
  `@anthropic-ai/sdk` 0.91.1 is MIT; `cross-spawn` 7.0.6 is MIT; `hosted-git-info` 9.0.3 and
  `lru-cache` 11 are ISC. bun 1.3.10 (the baseline build comes from bun's own GitHub release) is
  MIT. All are permissive, so nothing needs an opt-in feature.
- **Reason:** decision 7 allows only permissive and weak-copyleft components in default builds.

## 2. Which overrides are pinned

- **Question:** the spec lists overrides for the two Pi packages, `@anthropic-ai/sdk` and
  `tinfoil`.
- **Decision:** `overrides` pins every package of the Pi family that 0.84.1 pulls in
  (`pi-coding-agent`, `pi-ai`, `pi-agent-core`, `pi-tui`, `pi-client`, `pi-protocol`,
  `pi-telemetry`) to 0.84.1, `@anthropic-ai/sdk` to 0.91.1 (the exact release `pi-ai` 0.84.1
  declares), and keeps the nested `hosted-git-info` > `lru-cache` override, now `^11.1.0`.
  `tinfoil` is not pinned or installed, and is removed from the managed `package.json` when a
  manifest written by another build lists it.
- **Reason:** the family packages depend on each other with caret ranges, so without overrides a
  later 0.84.x of one of them could be mixed in and the runtime patch (which checks exact file
  hashes) would stop applying. The old `lru-cache ^10` override would now break
  `hosted-git-info` 9, which requires 11. `tinfoil` is AGPL-3.0 and only serves the vendor's
  hosted confidential-inference provider (`screenpipe-tinfoil`, cloud-only, agents_pipes-036);
  decision 7 keeps it out of default builds.

## 3. Install command and the npm fallback

- **Question:** the spec gives `bun add ... --force --ignore-scripts`; the app used `bun install`
  with an npm fallback on bun cache failures.
- **Decision:** both the app and the engine now run one shared procedure
  (`agents/pi_install.rs`): seed `package.json`, then `bun add <pins> --force --ignore-scripts`
  with `BUN_INSTALL_CACHE_DIR=<install>/.bun-cache`. The npm fallback stays for bun's Windows
  `EPERM` cache failures and also passes `--ignore-scripts`. A process-wide lock keeps the app's
  and the embedded engine's start-up installs from running in the same directory at once.
- **Reason:** one procedure means the pins, the baseline bun and the patch are applied the same
  way whichever side installs first. Lifecycle scripts never run, so an install cannot execute
  package code.

## 4. What is seeded into the isolated config

- **Question:** the spec lists `auth.json`, `trust.json`, `settings.json` `packages` and
  `sessions/`, guarded by `.migration.lock` and the `.migrated-from-global` marker. How are
  conflicts, failures and concurrency handled, and is `models.json` carried over?
- **Decision:** the seed runs once per config directory and never overwrites anything the isolated
  directory already has (`packages` is merged in only when the isolated `settings.json` has none).
  Besides the four listed items it also carries over the user's own `models.json` providers:
  each provider entry the isolated `models.json` lacks is copied, except the gateway entries
  (`screenpipe`, which screenpipe pointed at its hosted gateway and Freenpipe writes from the
  gateway the user configured, and any `screenpipe-*` name). Those are the only vendor-pointing
  entries screenpipe or Freenpipe ever wrote; an entry the user added by hand is the user's own
  setup and is copied as it is, the same as their own `pi` uses it. The rest of the
  global `settings.json` is not copied. Sessions are copied last. The lock is created exclusively
  and holds the seeder's PID. Code about to start Pi (the chat, a pipe run, the shellPath write)
  never waits for a seed another thread or process is running: it starts Pi at once. The app and
  the engine seed from their start-up thread before installing, and that thread waits up to 10 s
  for another process's seed. A lock whose PID is no longer running is taken over at once; when
  the PID cannot be read, a lock older than 10 minutes is. The marker is a small JSON record (time,
  source, what was copied, what failed) and is written even when there is no global config, so
  later starts only test for one file. Copy failures are recorded in the marker and logged; they
  never stop Pi from starting.
- **Owner question:** carrying `models.json` providers over is a Freenpipe addition (the spec does
  not list it). It keeps a base-era user's custom providers (a groq or bedrock entry, an API key
  kept in `models.json`, an `ollama` `baseUrl` on another machine) working once Pi runs against
  `pi-config`; the runtime's own provider merge already keeps such `baseUrl` and `apiKey` values.
  If the owner prefers the spec's four items only, drop `seed_models_providers` in
  `pi_runtime.rs` and say in the release notes that custom Pi providers must be added again.
  screenpipe v2.7.104 users are not affected either way: their data dir already has `pi-config`.
- **Reason:** the user's global Pi setup must never be modified by Freenpipe, and a one-shot copy
  keeps that promise while carrying sign-ins, installed Pi packages and the user's providers
  over. Starting Pi must not stall an async worker on another seeder.

## 5. Where the global config is read from

- **Question:** which directory is "the user's global Pi config"?
- **Decision:** `PI_CODING_AGENT_DIR` when it is set in Freenpipe's own environment and does not
  point at the isolated directory, else `~/.pi/agent`.
- **Reason:** that is the directory the user's own `pi` would use.

## 6. `SCREENPIPE_PI_AGENT_DIR`

- **Question:** the spec names `SCREENPIPE_PI_AGENT_DIR` and `PI_CODING_AGENT_DIR` together.
- **Decision:** when `SCREENPIPE_PI_AGENT_DIR` is set for Freenpipe it overrides the config
  directory; either way both names are exported to every Pi process with the directory in use,
  together with `PI_SKIP_VERSION_CHECK=1`, `JITI_TRY_NATIVE=0` and `PI_TELEMETRY=0`
  (`SCREENPIPE_CLI` was already set by the CLI runtime). `PI_OFFLINE` is not set.
- **Reason:** extensions and nested tools can find the config through the screenpipe-named
  variable. `PI_TELEMETRY=0` keeps Pi's own install telemetry off (telemetry stays off). `PI_OFFLINE`
  would also stop Pi from installing the user's own Pi packages at start.

## 7. Pipe session history follows the isolated config

- **Question:** pipe history (`--continue`, the execution's session file, "clear history") looked
  in `~/.pi/agent/sessions`.
- **Decision:** it now looks in `<config dir>/sessions`, with Pi 0.84's directory naming (one
  leading separator dropped, `/`, `\` and `:` turned into `-`). The old naming kept `:` and so
  never matched on Windows drive paths. The "optimise pipe" prompt in the pipes settings points
  at the new directory too. Older sessions under `~/.pi/agent/sessions` are carried over by the
  one-time seed.
- **Reason:** Pi writes its sessions under its config directory; the pipe runtime has to read
  the same place.

## 8. When the baseline bun is used

- **Question:** the spec describes the baseline bun as the fallback after a `0xC000001D` crash;
  the coordinator asks for an AVX2 check as a pure function.
- **Decision:** on Windows x64 the baseline build is chosen when CPUID (with the OS's XCR0 state)
  shows no usable AVX2, when a stock bun already died with `0xC000001D` on this machine (a marker
  file in the install directory remembers it), or when `SCREENPIPE_FORCE_BASELINE_BUN=1` (a
  Freenpipe addition, for testing). It is downloaded from bun's GitHub release 1.3.10
  (`bun-windows-x64-baseline.zip`), checked against the release's published SHA-256, unpacked under
  `<install>/bun-baseline/` and then used for every bun the runtime starts (Pi, the install, the
  MCP server). Until it is unpacked the stock bun stays in use. Other platforms always use the stock
  bun.
- **Reason:** checking CPUID first avoids a crash on the first start of a non-AVX2 machine; the
  crash marker still covers CPUs or VMs that report AVX2 but cannot run it.

## 9. Bash probe

- **Question:** the spec gives the probe as `printf screenpipe-bash-ok` with a timeout.
- **Decision:** each candidate runs `bash --noprofile --norc -c "printf <token>"` with a 5 s
  limit. The token text is Freenpipe's own; only its presence on stdout matters. A candidate that
  times out is stopped with its whole process tree (`taskkill /T`, because Git for Windows'
  `bin\bash.exe` starts the real bash as a child) and probed once more with a 20 s limit, for a
  cold first start under on-access scanning; only then is it rejected. Candidates are the managed
  PortableGit, Git for Windows under each Program Files directory and
  `%LOCALAPPDATA%\Programs\Git`, then `where bash`. WSL launchers in `System32`, `Sysnative` and
  `SysWOW64` and Store app aliases are never tried. A working bash is cached for the process and a
  rejected one is not probed again. The bash found is written to Pi's `shellPath` setting in the
  isolated config by both the app and the engine.
- **Reason:** the token is not an interoperability identifier. Skipping rejected candidates keeps a
  hanging bash from slowing every Pi start, and the one retry keeps a slow first start from
  sending the user to the 50 MB PortableGit download.

## 10. How the runtime patch is shaped

- **Question:** the spec describes a pinned diff applied to Pi's dist files with marker comments
  (`screenpipe-context-compaction-v1`, ...), and says to write the compaction independently.
- **Decision:** the behaviour lives in one Freenpipe module, `freenpipe-compaction.js` (written for
  this project), copied into the installed package. A small patch file in Freenpipe's own format
  (`assets/pi-patches/pi-0.84.1.fpatch`) adds one-line calls to it in four Pi files. Each hunk
  carries a `freenpipe-patch:<id>` marker instead of the vendor's marker names. The patch is applied
  only when both Pi packages are exactly 0.84.1 and every edited file matches its recorded stock
  SHA-256 (or is already fully patched). Every hunk must match exactly once, all files are checked
  before any is written, and the module is written before the hooks that import it. On any
  mismatch nothing is written and Pi keeps running the files it has, without Freenpipe's patch;
  the reason is logged once per process. When the mismatch is in 0.84.1 files (an older build's or
  another vendor's patch) the install is rebuilt from stock files (see 15). The patch is re-applied
  after every install and on every start (cheap when already applied).
  `SCREENPIPE_DISABLE_PI_PATCHES=1` (a Freenpipe addition) removes it by reversing the hunks.
- **Reason:** "refuse to run if the installed runtime does not match the patch" is read as "refuse
  to patch": a failed patch must leave a working Pi rather than no Pi. Own markers keep the code
  and the files it writes distinct from the vendor's.

## 11. Compaction behaviour details

- **Question:** the spec gives the behaviour only in outline.
- **Decision:**
  - after a step that ran tools, the session compacts through Pi's own auto-compaction as soon
    as the estimated context passes 70% of the model's window. The next model call sees the
    compacted messages;
  - reserve and keep-recent budgets are only ever lowered: each is a share (25% and 30%) of the
    window minus the prompt overhead, with a floor of 1,024 tokens. The overhead is the provider's
    last prompt-token count minus the estimated size of the messages it covered, or, before any
    usage figure, the size of the system prompt and tool schemas. During a mid-run compaction the
    keep-recent budget is raised to cover the latest step (its assistant message and tool results,
    plus 64 tokens), because Pi only cuts at user or assistant messages and a large tool result
    would otherwise leave it nowhere to cut;
  - the summariser reads one JSON record per message (role, text, thinking, tool calls, tool
    output, errors), with string values cut to a head-and-tail excerpt of at most 8,000 characters
    (less on windows under about 40K tokens, never under 1,200);
  - a summary is rejected when it was cut off at the output limit, was aborted, has under 40
    characters, or lacks key headings of the format Pi asks for: `Goal`, `Progress` and
    `Next Steps` for the history summary, `Original Request` and `Early Progress` for the summary
    of a split turn's first part;
  - a failed compaction during a run, or two compactions in a row that still leave the context
    over the threshold, end the run with an error instead of carrying on;
  - transport errors get the recognised socket, DNS, undici, TLS and bun connection error codes
    from their cause chain appended (for example `Connection error. (ConnectionRefused)` under bun,
    `fetch failed (ECONNREFUSED)` under Node);
  - a patch left by an older build (every marker present, different hook text) is reported as
    stale, and a 0.84.1 file that is neither stock nor carries every marker (another vendor's
    patch, an older build with other hunks) as foreign. Nothing is written in either case; the
    installer rebuilds the install beside the live one (see 15).
- **Verification:** besides the unit tests, the patch was applied to a real 0.84.1 install from the
  registry and Pi was run against a local fake OpenAI-compatible server with a 16K-token model:
  after the third 5,000-token tool result the session compacted mid-run (the summariser received
  the JSON records) and the next call carried about a third of the context. With summaries
  missing their headings the run ended with the compaction error instead of continuing. A
  refused connection read `Connection error. (ConnectionRefused)`.
- **Reason:** these are the smallest choices that implement each listed behaviour, and they
  only tighten Pi's own logic. Large-window models keep Pi's defaults.

## 12. Pipe `effort:` (W2-22 open question 20)

- **Question:** does agents_pipes-015 cover passing a pipe's `effort` to Pi?
- **Decision:** yes, its "pipe streaming using provider/model/effort" line is the pipe streaming
  path. `AgentExecutor::run_streaming` takes a thinking level, the three pipe call sites pass
  `effort`, and Pi gets `--thinking <low|medium|high>`. The managed `models.json` entries still
  do not declare `reasoning`, so Pi lowers the level to "off" for those models. Effort takes effect
  for models Pi knows to reason, including the user's own Pi providers. The chat's per-session
  thinking level (`pi_set_thinking_level`) belongs to W4-05.
- **Reason:** turning reasoning on for every BYO model would make Pi send reasoning parameters to
  local models that reject them.

## 13. Gateway headers

- **Question:** the spec lists the extra headers `x-screenpipe-latency`, `x-screenpipe-workload`
  and `sendSessionAffinityHeaders` on the provider entries.
- **Decision:** not added.
- **Reason:** cloud.md records them as headers sent to the vendor's hosted gateway, and the
  evidence gives no values. Freenpipe's gateway provider is the user's own (BYO), which does not
  need them.

## 14. Where the patch assets live

- **Question:** the plan lists `apps/screenpipe-app-tauri/src-tauri/assets/pi-patches/` as the
  owner path.
- **Decision:** the patch, the module and its bun tests live in
  `crates/screenpipe-core/assets/pi-patches/` and are compiled into screenpipe-core with
  `include_str!`.
- **Reason:** the engine (pipes) and the app (chat) both apply the patch through screenpipe-core.
  Keeping one copy there avoids two copies drifting apart.

## 15. Rebuilding an install that does not take the patch

- **Question:** a healthy 0.84.1 install can still be unfit for the patch: an older Freenpipe
  build's patch (stale), a screenpipe v2.7.104 `pi-agent` whose dist files carry the vendor's patch
  and whose `package.json` lists `tinfoil` (foreign), or a manifest that lists an excluded package.
  Wiping `node_modules` and reinstalling in place would pull the tree from under a Pi that was
  started meanwhile, and on Windows a running Pi's open files can make the wipe fail half-way.
- **Decision:** such an install is rebuilt beside the live one: the live `package.json` is copied
  into `<install>/.rebuild`, the pins are applied there (dropping excluded packages), `bun add`
  runs there with the live install's bun cache, and the result is checked and patched there. Only
  then the live `node_modules` is renamed to `.node_modules.old`, the rebuilt one is moved into
  place, the manifest and lockfile follow, and the old tree is removed. When the live tree cannot
  be moved (a running Pi holding files on Windows) or anything before fails, the live tree is
  untouched, the staging directory is removed, and the next start tries again. A swap cut short by
  a crash is undone at the next start. A rebuild is tried once per process, and once it succeeded a
  `.rebuilt-for-patch` record (Pi release and a fingerprint of this build's patch) stops it from
  being repeated for the same build even if the rebuilt files still do not take the patch.
- **Reason:** the stock files are needed for the patch and for a manifest without `tinfoil`, and
  building them beside the live tree means no Pi ever runs from a half-replaced one. The once-per-
  build record keeps a patch that never applies from turning every start into a reinstall.

## 16. Clear cache and the isolated config (hand-off to W8-02)

- **Question:** Settings > Storage "clear cache" (`list_cache_files` in `commands.rs`) lists the
  whole `pi-agent` directory as "AI agent cache", which now also holds `pi-config` (Freenpipe's
  Pi sign-ins and Pi sessions), and still lists `~/.pi/agent`, the user's own global Pi config that
  Freenpipe no longer uses.
- **Decision:** not changed here; `commands.rs` and the storage section are outside this WP.
  W8-02 (storage and retention settings, which owns the cache list and delete in frontend-039)
  should list only the rebuildable parts of `pi-agent` (`node_modules`, `.bun-cache`,
  `bun-baseline`), never `pi-agent/pi-config`, and drop `~/.pi/agent` from the list.
- **Reason:** owner paths. Deleting `pi-agent` today loses the isolated config, which the next start
  seeds again from the global config; sign-ins made only in Freenpipe have to be repeated.

## 17. Files outside the owner paths

For the merger: besides the owner paths this WP edits `crates/screenpipe-core/src/pipes/mod.rs`
(the `effort` pass-through and Pi 0.84 session-dir naming, see 7 and 12, and `is_process_alive`
made crate-visible for the seeding lock), `apps/screenpipe-app-tauri/components/settings/pipes-section.tsx`
(the optimise-pipe prompt now names the Pi config dir by `PI_CODING_AGENT_DIR` instead of a fixed
path), new files under `crates/screenpipe-core/src/agents/` and `src/cpu_features.rs`, and the
patch assets under `crates/screenpipe-core/assets/pi-patches/` (see 14).
