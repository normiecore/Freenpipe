# W3-02 open questions

Search v2 (api-003, meetings_memory-011, meetings_memory-024): parsed content, starred filters
and flags, the input-context filter, the parsed-only filters, the related-tags map, and the
timeout and busy answers. Each decision is the worker's call; the owner can overturn any of
them. Interop names (query parameters, JSON fields, table and column names) match the spec;
everything else is Freenpipe's own.

## 1. Where does a hit's `starred` flag go?

- **Decision:** next to `type` and `content`: `{"type": "OCR", "content": {...}, "starred": false}`.
  `SearchResponse.data` is a list of `StarredSearchHit`, which flattens the existing `ContentItem`
  and adds the flag. Every hit carries it, also without a starred filter.
- **Reason:** the spec names a separate `StarredSearchHit` type, which only makes sense as a
  wrapper around the content item. Readers that ignore unknown keys (the app, the MCP server,
  `PaginatedResponse<ContentItem>` in Rust) keep working.

## 2. Which hits can be starred, and what does the starred filter do to memories?

- **Decision:** a hit is starred when its capture time lies in `[start, end)` of a starred
  session: frames (OCR, accessibility, parsed) by `frames.timestamp`, audio by the transcription
  or live-segment time, input by the event time. Memories have no capture time: they are never
  starred, and `starred_only` or `starred_session_id` with `content_type=memory` returns no data
  (total 0), and the related map leaves memories out under a starred filter.
- **Reason:** the spec defines starred for "frame/audio" hits by their timestamp; input events are
  captures too. A memory's `created_at` is when an agent wrote it, not when it happened on screen.
  The same "no data rather than ignoring the filter" rule already applies to tags on input and
  accessibility.

## 3. `starred_session_id` validation

- **Decision:** the value is trimmed; empty means not given. It must be a 36-character hyphenated
  UUID (the same check `POST /starred-sessions` uses), else 400. An id with no stored session is a
  404 (`starred session not found`), not an empty result. `starred_session_id` implies the starred
  filter; `starred_only` may be given too.
- **Reason:** an agent asking about a session that was deleted should learn that, instead of
  concluding nothing happened.

## 4. More than 100 starred intervals

- **Decision:** the sessions overlapping the requested range (or all time when no range is given)
  are merged into disjoint intervals (touching ones join). More than 100 is a 400 whose message
  names the count and asks to narrow `start_time` and `end_time`. The wording is our own.
- **Reason:** the limit and the advice are from the spec. Without a range a long-time user can hit
  it, which is the point: the starred filter wants a bounded window.

## 5. Window boundaries and the time range

- **Decision:** sessions are half-open `[start, end)`. Search's `end_time` is inclusive (`<=`) as
  before, so the windows are clipped at `end_time + 1 ms`. The indexed time range of every query
  is narrowed to the windows' hull widened by one second on each side; membership itself is exact:
  each table is range-scanned per window by a second-precision text bound on its timestamp index,
  then compared with `julianday()`, so `Z`, `+00:00` and any number of fractional digits are judged
  by the instant (W2-04 question 6). `meeting_transcript_segments` uses its `julianday(captured_at)`
  expression index.
- **Reason:** keeps the filter before pagination (pages are full and `total` is right) while the
  cost follows the rows inside the starred time, not the table size. Plans are checked with
  `EXPLAIN QUERY PLAN` on a seeded database (`ext/search_parsed.rs` tests). The full screen-text
  and input search statements, with their `(? IS NULL OR ...)` time bounds, were also explained on
  a 300,000-frame, 300,000-event database: SQLite drives both from the window ids
  (`SEARCH ... USING INTEGER PRIMARY KEY`), and a 20-row page took about 1 ms with or without a
  time range.
- **Known limit:** like the existing `start_time`/`end_time` filters, the text range only finds
  rows stored in the `T` spelling; legacy `ui_events` rows written as `YYYY-MM-DD HH:MM:SS UTC`
  cannot be read by `julianday()` and never match a window.

## 6. Caching and freshness of starred results

- **Decision:** queries with a starred filter are never served from the 60 s search cache. For all
  other queries the cache keeps the response without flags, and the flags are recomputed on every
  request with one lookup over the time span the hits cover. If that lookup fails or the budget runs
  out, the flags stay `false` and a warning is logged; the search itself still succeeds. Starred
  filtered responses set every hit to `starred: true` without a second lookup.
- **Reason:** a session starred a second ago must show up at once (the app's "ask about this
  session" flow stars, then searches). One small query per search is cheap.

## 7. `input_context_only`

- **Question:** the spec lists the parameter without semantics.
- **Decision:** with `content_type=input` it keeps events that carry input context: non-blank
  `text_content` (typed or copied text) or a non-blank `element_name` (the UI element the event
  hit). Bare pointer moves, scrolls and key codes are dropped. Other content types ignore it. The
  count uses the same condition.
- **Reason:** the name points at input events that tell an agent what the user did and where;
  ignoring it elsewhere is harmless because `all` does not include input.

## 8. `frame_id` and `actor_id` outside `content_type=parsed`

- **Decision:** 400 (`<name> only applies to content_type=parsed`). Values must be positive (400
  otherwise). An empty value (`frame_id=`) means not given.
- **Reason:** the spec scopes both to parsed; silently ignoring them would return unrelated data.

## 9. What `actor_id` does to a parsed frame

- **Decision:** a frame matches when its run holds an item assigned to the actor. Its `items` are
  narrowed to that actor's items plus every item containing one of them (so a message keeps its
  conversation), and `actors` and `text` follow. With `q` as well, one item must match both the
  text and the actor. `q` alone returns the whole frame (all items), like an OCR hit returns the
  whole frame text.
- **Reason:** the acceptance check says `actor_id` filters parsed items; keeping the containers
  preserves the context an agent needs to read a message.

## 10. Parsed search filters and order

- **Decision:** `content_type=parsed` returns one hit per frame whose `semantic_run_id` points at a
  `handled` run (frames with an `empty` run or none are left out), newest first (`timestamp`, then
  frame id), paged by `limit`/`offset`, with `total` from the same filters. It honours `q` (FTS over
  `semantic_items_fts`, terms quoted as in W2-05), the time range, `app_name`, `window_name` and
  `browser_url` (case-insensitive substrings, wildcards taken literally), `focused`, `machine_id`,
  `tags` (frames carrying all of them), `frame_id`, `actor_id` and the starred filter. `q` empty
  browses parsed frames. `focused` or `browser_url` do not switch parsed searches to OCR (they do
  for the other types, as before). A run or item row holding a value this build does not know
  (a newer screenpipe) is skipped with a warning instead of failing the search. Parameters that
  describe other stores (`frame_name`, `device_name`, `min_length`/`max_length`, the speaker
  filters, `on_screen`) do not apply to parsed items and are ignored.
- **Reason:** mirrors the OCR search's filters where frames have the column; the spec's frame
  detail join (`frames.semantic_run_id` to a handled run, items by `sort_order` with resolved
  actor names) is what the loader does.
- **Query plan:** the page and count queries join `frames` to `semantic_runs` with `CROSS JOIN`,
  which keeps `frames` as SQLite's outer loop, so every plan starts from a frames index (time
  range, window ids, the run ids selected by `q`/`actor_id`, or the non-null part of
  `idx_frames_semantic_run_id`). Without it the planner chose a full scan of `semantic_runs` for a
  browse without filters. A browse without a time range is still linear in the parsed frames, as
  its `total` has to be; `start_time` keeps it bounded.

## 11. The `ParsedContent` field list

- **Question:** api.md and meetings_memory.md list slightly different item fields (`timestamp` vs
  `occurred_at`, `text/body` vs `title`, `body`, `status`).
- **Decision:** `ParsedItem` carries `item_id, local_id, parent_local_id, kind, item_key,
  identity_quality, title, body, actor, occurred_at, timestamp_precision, status, source_nodes`.
  `ParsedActorReference` carries `item_id, local_id, actor_id, name, observed_name,
  assignment_source`, one per item with an assigned actor. `source_nodes` is the decoded node id
  list (null when the stored blob is not in the 4-byte layout, W2-05 question 2). `item_id` on the
  item is our addition so a client can call the actor reassignment API without a second lookup.
- **Reason:** the union of both lists, using the column names the schema stores.

## 12. The compact `text` of a parsed frame

- **Decision:** one line per item in run order, two spaces of indent per nesting level, written
  `actor: title - body` and leaving out missing parts; the assigned actor's name wins over the
  parser's label; whitespace runs collapse to one space; items with neither title nor body are
  skipped. `max_content_length` middle-truncates `text` and every item `title` and `body`.
  `filter_pii` redacts `text`, item titles, bodies and actor labels, and actor names.
- **Reason:** the spec calls it "compact corrected text" without a layout; this keeps a
  conversation readable in one string and keeps the truncation and redaction promises of the other
  content types.

## 13. The `related` map

- **Decision:** present only with `include_related=true` and at least one tag (otherwise the key is
  absent, no error). It maps namespace (the part before the first `:`) to full tag names
  (`person:ada`), most frequent first, then by name, at most 20 per namespace; tags without a
  namespace go under `other`. It counts the other tags on the items carrying all requested tags in
  the time range and starred windows, from the stores the content type reads: frames for `ocr`,
  frames with a parser run for `parsed`, audio chunks for `audio`, both for `all` (frames only when
  `focused` or `browser_url` switch it to OCR), memories for `memory`, nothing for `input` and
  `accessibility` (`{}`). `q`, app and window filters do not narrow it. A pipe whose permissions
  restrict data (app, window or content rules, hours or days) gets a 403 for `include_related`;
  endpoint-only permissions do not count.
- **Reason:** the spec marks the exact shape as inferred and gives `{"person": [...], "project":
  [...]}`. Full names can be passed straight back as `tags=`. The 403 follows api-038; without it a
  restricted pipe could read tags from apps it may not see.

## 14. Timeout status code and wording

- **Decision:** the 30 s budget covers all database work of a request (starred lookup, search,
  count, related map, starred flags); when it runs out the answer is 504 with the base engine's
  existing timeout message (`ERR_SEARCH_TIMEOUT` in `routes/search.rs`, MIT base text, unchanged),
  which names the 30 s limit and suggests a narrower range or more filters. The base answered 408
  with the same text. Redaction and frame extraction run after the budget as
  before.
- **Reason:** the spec asks for 504 and a message that names the limit and the remedy, which the
  existing text already does.

## 15. When is search "busy"?

- **Decision:** at most 8 searches query the database at once; a request that cannot get a slot
  within 5 s (or before its budget ends), or whose query fails with SQLite busy/locked or a read-pool
  timeout, gets 503 `{"error": "search is busy — retry shortly", "retry_after_ms": 1000}` (the error
  text is the exact client-visible string). Cache hits skip the slots. Pipe requests still pass the
  pipe back-pressure layer first.
- **Reason:** the spec gives the message and 503 but not the limit; 8 leaves the read pool room for
  the timeline and capture reads, and the short queue absorbs a burst of keystroke searches.

## 16. `UiContent.event_source` and `InputContent.click_count`

- **Decision:** `event_source` is the frame's `capture_trigger` (`app_switch`, `click`,
  `typing_pause`, ...), left out of the JSON when unknown. `click_count` is `ui_events.click_count`,
  left out when null. This value of `event_source` is **inferred**: the spec only names the field.
- **Reason:** accessibility hits are frames, and the trigger is the event that produced them.
  Leaving the fields out when empty keeps responses for older rows byte-identical.
