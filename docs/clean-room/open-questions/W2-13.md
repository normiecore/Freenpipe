# W2-13 open questions

Health v2, vision metrics and recording coverage (api-033, vision-pipeline-metrics,
gap_health-lifecycle-internals-001..003, audio-027).

1. **Does `audio_status` switch to the target's richer vocabulary (`recording`, `waiting_for_voice`, ...)?**
   - Decision: no. `audio_status` keeps the base values (`ok`, `disabled`, `not_started`, `active_no_data`,
     `stale`). The target vocabulary is reported in the new `capture_status.status`.
   - Reason: the desktop app (base and W2-26) counts `stale`/`not_started` to raise notifications, and the
     onboarding screen waits for `ok`/`disabled`; changing the values would silently break both. The only
     instruction for this WP is to add fields. A later WP that updates those readers can switch the field.

2. **What does `capture_status` describe, and in what order are its states decided?**
   - Decision: the audio side (its other fields are audio device and transcription counts). First match
     wins: `disabled` > `screen_locked` (locked and no device delivering) > `meeting_detector_unavailable` /
     `waiting_for_meeting` (meetings-only mode, no running device) > `mic_paused` (every device user-paused) >
     `audio_not_started` (no device during the first 120 s) / `no_input_device` (no device after that) >
     the legacy failure states (`audio_not_started`, `active_no_data`, `audio_stalled`) > `transcript_paused`
     > `transcript_pending` > `waiting_for_voice` (no transcript for 300 s after 300 s of uptime) >
     `recording`. `reason` is a short sentence written for this fork.
   - Reason: deliberate states first, then failures, then transcript-level detail of a working recorder, so
     the status names the most actionable fact. The target's thresholds are not in the evidence; 120 s is the
     base grace period and 300 s matches the coverage idle window. `ok` from the vocabulary is left to the
     legacy `audio_status`; a healthy `capture_status` says `recording`.

3. **Which `unhealthy_reasons` codes, severities and texts?**
   - Decision: codes `vision_capture_stalled`, `vision_not_started`, `vision_permission_denied`,
     `vision_no_displays`, `vision_ocr_unavailable`, `vision_change_detection_degraded`,
     `vision_write_stalled`, `frame_drop_rate_high`, `write_latency_high`, `audio_not_started`,
     `audio_stalled`, `audio_active_no_data`, `audio_loopback_fallback`, `transcription_write_stalled`,
     `transcription_queue_full`, `audio_transcript_pending`, `database` and `health_snapshot_timeout`.
     `component` is `vision`, `audio`, `database` or `health`; `severity` is `error` (data is not being
     recorded) or `warning`. The list is derived from the same signals as the base `status`, so a healthy
     response has an empty list, except three warnings that do not change `status`:
     `vision_ocr_unavailable`, `vision_change_detection_degraded` (item 21) and `audio_loopback_fallback`
     (item 22). Messages and remediations are written fresh.
   - Reason: the evidence names the code families (`vision_*`, `audio_*`, ...) and the five fields but not
     the members or wording. Deriving them from the base gates keeps `status` and the list consistent.

4. **What do the write-queue fields mean, and does a failing writer change `status`?**
   - Decision: `write_queue_consecutive_fatal` / `_contention` count failed batches since the last committed
     batch (fatal = the writer connection broke, closed pool or failed COMMIT; contention = semaphore or pool
     acquire timeout, `SQLITE_BUSY`). `write_queue_degraded` = one fatal batch, or two contended batches in a
     row. `write_pool_reopens` counts writer connections discarded so the pool opens a fresh one (detach after
     a broken BEGIN/ROLLBACK/COMMIT, acquire retries). `persistent_failure_signals` is a `u64` counter that
     goes up once each time a run reaches 3 fatal or 5 contended batches (with one WARN line). A degraded
     queue makes `status` `degraded` (503) and adds the `database` reason and a `database` system to the
     message.
   - Reason: the evidence gives only the names, and the base has no such counters; these definitions are the
     smallest that tell "blip" from "wedged writer". The field sits in a run of counters, so a number fits
     better than a list. A writer that cannot commit loses everything captured, which is exactly what
     `/health` must surface.

5. **What are `dependencies`, `runtime` and `startup`?**
   - Decision: `dependencies` = `{ffmpeg, ffprobe}`, each `{status, path, source, version,
     version_probe_error}` with status `ok`/`degraded`/`missing`/`unknown` and source `bundled`/`system`,
     probed once in the background at server start (`-version`, 5 s timeout). `runtime` = the four audio
     model components `transcription`, `vad`, `speaker_segmentation`, `speaker_embedding` (states `ok`,
     `init_failed`, `init_timed_out`, `missing`, `not_required`, `degraded`, `unknown`) plus
     `degraded_features`; states come from `screenpipe_audio::metrics::report_model_component`, falling back to
     what the metrics show, and are `not_required` when audio is off. `startup` = `{phase, phase_since,
     engine_started_at, uptime_secs}` with phase `starting` until every enabled pipeline produced output or
     120 s passed, then `running`.
   - Reason: the field names follow the `health-startup.json` vocabulary (specs/shell.md shell-M01,
     audio.md audio-021). The file itself, preflight checks, `last_failed_start` and the ONNX init watchdog
     are unowned or owned by later WPs; the registry is the seam they report into. `uptime_secs` is a
     Freenpipe addition.

6. **Is `frame_status` "stale" while capture is paused on purpose?**
   - Decision: `ok` whenever the capture loop's own pause gate is closed: screen locked (base already did
     this), DRM content paused, outside work hours, or a power profile that pauses capture.
   - Reason: base reported `stale`/503 after 60 s of a DRM or schedule pause, a false alarm the app turned
     into "screen capture stopped" notifications. The coverage classifier already counts those periods as
     `active_paused`, not stalled. `drm_content_paused` and `schedule_paused` still say why.

7. **Where do the `vision_reason` inputs come from?**
   - Decision: `no_displays_expected` / `permission_denied` from the outcome of the latest monitor
     enumeration (new `screenpipe_screen::last_monitor_list_outcome`, refreshed by the 5 s monitor watcher);
     `screenshots_disabled_by_config` from `disableScreenshots` as published by `RecordingConfig`;
     `screenshots_disabled_by_power_profile` when the active power profile stores no screenshots or pauses
     capture; `ocr_unavailable` when the last Windows OCR engine creation failed (no OCR language pack).
     Precedence is the one in specs/vision.md.
   - Reason: these are the only places the facts exist without a system call in `/health`. The capture loop
     honouring `disableScreenshots` is W5-05; reporting the user's explicit setting now is still correct.

8. **How is `audio_capture_mode` known to `/health`?**
   - Decision: `RecordingConfig::to_audio_manager_builder` publishes the mode it builds the audio manager
     with; `/health` reports `disabled` when audio is off and `always` (the base behaviour) when nothing was
     published.
   - Reason: both startup paths (CLI and app) build the audio manager through that function, so no startup
     code changes; W3-14 implements meetings-only capture itself.

9. **Which `loop_stage` does `/health` report, and which stages are marked now?**
   - Decision: the monitor whose loop has been in its current stage the longest (ties to the lowest id),
     `null` when no loop runs. This WP marks `heartbeat` (every pass), `warm-wait`, `cold-wait`, `pause-gate`,
     `trigger-wait`, `visual-probe` and `capture`; the remaining six stage names exist in
     `CaptureLoopStage` for W3-11, which owns the full stage map and the wedge watchdog.
   - Reason: these are the places a loop can sit for seconds, so the age is meaningful today without
     reworking the loop that W3-11 restructures.

10. **What are `last_stream_timeout_at`'s type and position?**
    - Decision: `Option<u64>` Unix seconds, `null` until a stream times out, placed right after
      `stream_timeouts` in `AudioMetricsSnapshot`.
    - Reason: the spec says "timestamp (epoch secs)"; `null` is clearer than 0 for "never" in an `_at`
      field. The position is not in the evidence; next to its counter is the natural reading order.

11. **Is "order as packed" the declaration order of `MetricsSnapshot`?**
    - Decision: yes; the 34 fields are declared (and therefore serialised) in exactly the listed order.
    - Reason: serde emits fields in declaration order, and the packed list is the serializer's field run.

12. **Does the startup capture count as a capture attempt?**
    - Decision: yes, together with its timeout/error outcomes.
    - Reason: `silent_loss = attempts - (written + dedup + timeout + error + skipped)`. Base recorded the
      startup frame's write without an attempt, which made the identity off by one forever.

13. **What does the health budget do on overrun?**
    - Decision: one refresh runs at a time and every caller joins it; the computation runs in its own task and
      fills the cache when it finishes even if callers gave up. A caller that waits more than 2 s gets the last
      snapshot (or a 503 skeleton when there is none) with a `health_snapshot_timeout` reason appended; the
      cached `status` is kept. A refresh still running after 30 s is aborted and replaced. The overrun warning
      is logged at most every 30 s.
    - Reason: base dropped the late computation, so a slow DB made every poll time out in turn; sharing one
      task means a burst of pollers costs one computation, and the next poll gets fresh data.

14. **`mic_capture_active` window and inputs?**
    - Decision: true when a running input device delivered non-silent audio within the last 5 s, read from the
      per-device capture timestamps without the global fallback (which starts at process start time and would
      report a dead microphone as live for 5 s).
    - Reason: the spec infers 5 s; the per-device timestamp already only advances on real audio.

15. **Coverage ticker lifetime.**
    - Decision: one ticker per process, started at HTTP server start (also with vision disabled); a later
      server start in the same process points it at the new vision metrics, and a ticker whose runtime shut
      down is replaced. A DEBUG summary line is logged every 60 s; nothing else leaves the process.
    - Reason: the accumulator is process-global (HLI-001), so two tickers would double count; HLI-003 asks for
      no network sink and suggests the local log line.

16. **Counters whose producers belong to later WPs.**
    - Decision: `ocr_empty`, `ocr_gate_*` and `frames_corrupt_*` exist with recording methods and read 0
      until W3-12 (OCR call), W5-06 (OCR gate) and W3-11 (corrupt frame guard) call them. Their recording
      sites live in `paired_capture.rs` and `do_capture`, which those WPs own.
    - Reason: field presence and order are this WP's interop surface; the behaviour that produces the counts
      is specified under those other items.

17. **W2-18 engine state in audio metrics.**
    - Decision: only the backend choice is exposed (item 22), through a registry in
      `screenpipe_audio::metrics` and an `unhealthy_reasons` warning; no field is added to
      `AudioMetricsSnapshot`. The engine's current target (`default-render-endpoint`,
      `exclude-process-tree:<pid>`, `endpoint:<name>`) and its rebuild failures stay in the log.
    - Reason: `/audio/metrics` and `/health` field sets are an interop surface, and the target's lists do
      not have these fields. Reporting the target would mean editing the capture thread inside
      `wasapi_loopback.rs`, which the VM cannot compile; a later WP can push it into the same registry.

18. **Why does the field order not show on the wire, and what changes?**
    - Decision: the base timestamp middleware (`routes/timezone.rs`) parsed every JSON response into a
      `serde_json::Value` and wrote it back, which sorts keys alphabetically (serde_json is built without
      `preserve_order`), so no declared field order ever reached a client unless it passed `?timezone=utc`.
      It now rewrites UTC timestamp string values in the response text and leaves everything else
      byte-for-byte, so responses keep the order their handler serialised. Conversion rules are unchanged
      (same `try_convert_timestamp`; keys and escaped strings are never touched); `localize_json_string`
      for the websocket feeds uses the same path.
    - Reason: the WP's interop surface is field names and order (`HealthCheckResponse`, `MetricsSnapshot`,
      `recording_coverage`), and the acceptance check reads the order from `/health`. JSON readers ignore
      order, so consumers see no difference; turning on `preserve_order` workspace-wide instead would have
      changed every `Value` map in every crate, including code that relies on sorted keys.

19. **How is a vision stall classified, and from what?**
    - Decision: `PipelineMetrics` stores its outcome counters each time a frame lands (a DB write or a dedup
      skip), so "what the attempts since the last landed frame ended in" is a plain subtraction. A stall
      (`frame_status` `stale`, or `vision_db_write_stalled`) is then one of four causes, first match wins:
      `not_attempting` (no attempt in the 60 s window; the loop heartbeat tells "cycling but not attempting"
      from "stopped"), `writer_not_committing` (the write queue is degraded), and otherwise the outcome with
      the most attempts since the landing: capture deadline overruns (`writer_not_committing`), errors and
      similarity rejections (`backend_rejecting`), attempts with no outcome (`lost_before_writer`); ties in
      that order. The cause is logged in one WARN line at most once a minute, with the time since the last
      saved frame, the heartbeat age, the lifetime counters (`attempts`, `persisted`, `dedup`,
      `silent_loss`), the counts since the last saved frame, the change-detection counters and the pool
      figures, and its sentence is appended to the `vision_capture_stalled` / `vision_write_stalled`
      messages. The base WARN line (which called every stall a static screen) is replaced.
    - Reason: the spec names the four cases and the summary log's contents but not how to tell them apart.
      Lifetime counters cannot say what is happening now; the counts since the last landed frame are exactly
      the attempts the stall consists of. The base wording predates `record_dedup_skip` advancing
      `last_db_write_ts`: a static screen no longer looks like a stall, so that explanation was wrong.

20. **Is a pipeline that attempts captures but never lands a frame stalled?**
    - Decision: yes, once the vision pipeline has run for the 120 s warm-up plus the 60 s window with fresh
      attempts and no landing at all. It sets `vision_db_write_stalled` (so `status` is `degraded`) and
      `vision_reason` `capture_stalled`.
    - Reason: base only flagged a stall after at least one landing, to avoid warm-up false alarms. That
      left a capture path that fails on every attempt (for example a broken Windows capture backend)
      reported as healthy forever, while the coverage classifier already counts the same period as
      stalled. The startup capture lands (or fails) within seconds, so 180 s without a landing is not a
      warm-up.

21. **Should W2-12's frame-comparer failures reach `/health`?**
    - Decision: yes, as the warning `vision_change_detection_degraded` while thumbnail allocation failures
      are recent: a burst of failures stays reported until 300 s pass without one, and the message counts
      the failures of the current burst. Each capture loop feeds `FrameComparisonStats` into
      `PipelineMetrics` as deltas once per pass (`FrameDiffWatch`). Degenerate (empty) frames are counted
      too but only appear in the stall log line, not as a reason. `MetricsSnapshot` is unchanged.
    - Reason: a thumbnail that cannot be allocated makes the comparer report "unchanged", so changes on
      screen that come without input are not captured; that is a recording gap a user can act on (memory
      pressure). W2-12 logs empty frames at info level as a neutral event, so a warning for them would be
      noise. The 34-field snapshot is a fixed interop list.

22. **Should the Windows loopback engine falling back to cpal reach `/health`?**
    - Decision: yes, as the warning `audio_loopback_fallback` naming every recording output device whose
      latest stream runs on the generic cpal stream because the native backend failed to start it, or
      because the engine stepped aside after repeated failures. The stream builder reports `native`,
      `fallback_after_error` or `fallback_after_repeated_errors` per device
      (`screenpipe_audio::metrics::report_output_capture_backend`); macOS process-tap failures are
      reported the same way.
    - Reason: on the fallback, per-app audio exclusions are not applied, so audio the user asked to leave
      out can be recorded; that deserves more than a log line. Only recording devices are checked, so a
      stale entry for a removed device never shows.
