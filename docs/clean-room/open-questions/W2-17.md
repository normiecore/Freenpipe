# W2-17 open questions

Decisions taken while building stream-scoped live speakers and strict meeting-segment mapping
(audio-001, db-014, audio-008, audio-M01, audio-M05).

## 1. What a "stream" is and how its id looks

- **Question:** the spec says each live provider connection gets an opaque `stream_id` that changes
  after any reconnect, and that the selected-engine path uses "the session id"; the id format is
  inferred.
- **Decision:** the meeting-streaming controller mints a new id every time it opens a provider
  stream for one device of one meeting, which includes the reopen after a closed stream's 5 s
  backoff. The id is `<unix ms, hex>-<64 random bits, hex>` (`events::mint_stream_id`). The
  selected engine gets the same treatment: its "session" is the per-device stream the controller
  spawns, so a restarted local stream also gets a new id. Events from emitters that do not set a
  stream id deserialize with `stream_id = "legacy"`.
- **Reason:** the controller is the one place that knows when a connection starts, and per-device
  streams are what the provider's speaker labels are scoped to.

## 2. `session_speaker_id` and `item_id` shapes

- **Question:** both formats are inferred (`deepgram:<stream_id>:speaker:<n>`, `<stream>:turn:<n>`).
- **Decision:** `session_speaker_id = deepgram:<stream_id>:speaker:<label>` with Deepgram's 0-based
  diarization label; the gateway relay speaks the same wire format and uses the same prefix. The
  selected engine does not diarize and leaves it NULL. Turn ids are
  `deepgram:<stream_id>:turn:<channel>:<start_ms>` and
  `selected-engine:<stream_id>:turn:<captured_ms>:<sequence>`, replacing the base
  `deepgram:<channel>:<start_ms>` and `selected-engine:<type>:<ms>:<seq>`. The unique key
  `(meeting_id, provider, item_id, device_name, device_type)` is unchanged; rows written earlier keep
  their old ids.
- **Reason:** Deepgram's `start` restarts at zero on every connection, so without the stream id the
  first turns of a reconnected stream would be dropped as duplicates.

## 3. Dominant speaker of a `Results` payload

- **Question:** the base picked the most frequent word label by iterating a `HashMap`, so ties were
  decided by hash order.
- **Decision:** ties go to the lower label. Label 0 on an input device still takes
  `local_speaker_name` (`SCREENPIPE_MEETING_LOCAL_SPEAKER_NAME`) for `speaker_name`; its
  `session_speaker_id` stays the scoped label id.
- **Reason:** deterministic output for identical input.

## 4. Unscoped segment writes

- **Question:** which value non-live writers store.
- **Decision:** `NewMeetingTranscriptSegment` gained `stream_id: Option<String>` and
  `session_speaker_id: Option<String>`. A missing or blank stream id stores `'legacy'` and a blank
  session speaker stores NULL. Meeting re-transcription replacements and the old nine-argument
  `insert_meeting_transcript_segment` (kept for tests and the eval tool) write `'legacy'`. Live
  finals go through `insert_live_meeting_transcript_segment`, the 11-column `INSERT OR IGNORE`.
- **Reason:** `'legacy'` already means "not from a scoped live stream" for every pre-migration row;
  a batch re-transcription has no stream or provider labels either.

## 5. Transcript endpoint field

- **Question:** the meetings spec says the transcript API exposes `sessionSpeakerId`; the audio spec
  writes `session_speaker_id`.
- **Decision:** `MeetingTranscriptSegment` (serialized camelCase like its other fields) gains
  `sessionSpeakerId`; background rows return null. `stream_id` is not added to the row; the spec
  does not list it and `sessionSpeakerId` already contains the stream. Grouping the meeting UI on
  `COALESCE(sessionSpeakerId, speakerName)` is frontend work owned by the meetings dimension and is
  left to it (see Follow-ups, item 1).
- **Reason:** camelCase is the established shape of that struct; the frontend files are outside
  this WP.

## 6. Guarded backfill condition (b): "overlaps"

- **Question:** "no diarization segment of the chunk overlaps or names a different speaker" can mean
  the `overlap` flag or a time overlap between segments.
- **Decision:** a segment of the chunk with `overlap != 0`, or with a non-NULL `speaker_id` other than
  the candidate, blocks the update. Time overlap between segments is not checked separately: inside
  one run two labels already fail condition (c), and labels of different runs (for example a live
  and a background run) are not comparable.
- **Reason:** the flag is what the diarizer records for overlapping speech; a cross-run time check
  would block every chunk that two passes looked at.

## 7. Guarded backfill condition (d): live evidence

- **Question:** what counts as "one non-empty stream-scoped identity", and how live rows match
  segments.
- **Decision:** a mirrored `live` row matches a segment with the same `julianday` instant, device
  name, direction (`is_input_device` against `device_type`) and identical text. The identity of a
  match is `stream_id || ':' || COALESCE(NULLIF(TRIM(session_speaker_id), ''),
  NULLIF(TRIM(speaker_name), ''))`, so legacy rows scope their `speaker_name` to the `legacy` stream
  and the same label in two streams is two identities. A match with no label at all blocks the
  update, as does a matched segment already mapped to a different global speaker or a live row with
  no matching segment. As a consequence, chunks whose live mirrors come from an unlabelled stream
  (the selected engine on an output device) are never auto-labelled.
- **Reason:** the guard exists to avoid stamping one voice on a mixed chunk; unlabelled evidence
  cannot rule that out.

## 8. Strict mapping details (audio-M01)

- **Question:** the window, the limit and which rows count are not given.
- **Decision:** the ± window is the caller's `MEETING_SEGMENT_SPEAKER_WINDOW_SECS` (minimum 1 s) and
  only narrows the `idx_audio_transcriptions_timestamp` range scan; its bounds are built with
  `strftime('%Y-%m-%dT%H:%M:%f', …)` so they compare correctly with the stored RFC 3339 text. The
  match itself is exact (instant, device, direction, text, `transcription_engine = 'live'`). Up to
  500 unmapped segments, newest first, are considered per pass. Mirrors without a speaker do not
  count; the remaining ones must share one distinct `speaker_id`. A twin is any other segment with
  the same device name, direction, text and instant, in any meeting.
- **Reason:** the base 500-row pass size is kept; a twin in another meeting is as indistinguishable
  to the mirror as one in the same meeting.

## 9. Timeline `is_live` and ids (audio-M05)

- **Question:** the spec writes `is_live=1`; the JSON type is not stated.
- **Decision:** `is_live` is a JSON boolean on timeline audio entries (DB rows, the hot cache, the
  `/stream/frames` payload and its `audio_update` messages), like `is_input`. It is true for live
  meeting segments and for their `live` mirrors in `audio_transcriptions`. Live segments use
  `audio_chunk_id = -meeting_transcript_segments.id`. Live segment rows now show the resolved
  global speaker's name before the provider label (db-014 display precedence); their `speaker_id`
  stays null because there is no chunk to reassign.
- **Reason:** booleans are what the rest of the payload uses for flags; truthiness checks work
  either way.

## 10. Invalid timeline offsets

- **Question:** what "invalid" means for the new offset guard.
- **Decision:** a `start_time`/`end_time` that is not finite, negative, above 24 h, or an end before
  the start. Such a row is placed at its chunk timestamp, its offsets are reported as null (so
  `start_offset` is 0) and its duration as the SQL duration when that is plausible, else 0. The
  note is logged at debug level, once per row.
- **Reason:** keeps the transcript visible instead of misplacing it or overflowing the date
  arithmetic, without flooding the log on a damaged database.

## 11. Reassign and session speakers

- **Question:** W2-16's seam note suggests moving the other segments of the same
  `(meeting_id, stream_id, session_speaker_id)` along with a reassigned chunk.
- **Decision:** not done here. No item of this WP asks for it, and it changes reassign semantics
  owned by audio-006.
- **Reason:** scope; recorded under Follow-ups, item 2.

## Follow-ups

Work this WP leaves open, with the place that owns it. Neither item is in any open WP's item list
yet, so the coordinator should attach each one when that WP is started.

1. **Group meeting transcripts on `COALESCE(sessionSpeakerId, speakerName)`.** The transcript
   endpoint now returns `sessionSpeakerId` (question 5), but the meeting views still group and label
   lines by `speakerName`, so two different "speaker 1"s from a reconnected stream still read as one
   person. Owner: the meetings frontend, W5-17 (Meetings workspace UI, frontend-024), which rebuilds
   the meeting transcript view; W3-07 (live meeting overlay websocket) should key its live lines the
   same way. Spec: audio.md audio-001, behaviour item 6.
2. **Move same-session segments on reassign.** When a chunk is reassigned, also move the other
   segments with the same `(meeting_id, stream_id, session_speaker_id)`, recording the moved rows in
   `old_segment_assignments` so undo restores them. The change belongs in `move_chunk_meeting_segments`
   in `crates/screenpipe-db/src/db.rs` (W2-16 seam note, open-questions/W2-16.md section 9). Owner: the
   speakers dimension, audio-006, whose WP W2-16 is merged; this needs a new speakers WP or a fix
   branch assigned by the coordinator.
