# W2-05 open questions

Decisions taken while writing the semantic projection store (db-008, meetings_memory-019,
meetings_memory-020) in `crates/screenpipe-db/src/ext/semantic.rs`. The schema itself is W1-01's
and matched the spec text exactly, so no migration was needed or added.

## 1. API shape for the parser crate (W2-06), the worker and actors API (W3-01) and search (W3-02)

- **Question:** the store is written before its callers. What should they call?
- **Decision:** a small set of `DatabaseManager` methods plus plain row types, all in
  `screenpipe_db::ext::semantic`. Every method returns `SemanticStoreError`
  (`InvalidInput` maps to HTTP 400, `NotFound` to 404, `Conflict`, `InvalidStoredValue` and
  `Database` to 500).

  | Caller | Method | Notes |
  |---|---|---|
  | worker | `find_semantic_run_by_fingerprint(&[u8; 32])` | cache check before parsing (`handled_cached`) |
  | worker | `store_semantic_run(&NewSemanticRun) -> StoredSemanticRun` | one transaction: run, items, run items, heuristic actors; `created == false` means the run already existed |
  | worker | `attach_semantic_runs_to_frames(&[SemanticFrameAttachment])` and `SemanticFrameAttachmentBuffer` (`push`, `is_due`, `flush`) | batched `UPDATE frames SET semantic_run_id`; `push` rejects non-positive ids with `InvalidInput` so they never enter a batch, each flush logs one debug line, and a failed flush (always a database error) requeues the whole batch |
  | search / frame detail | `get_semantic_run_for_frame(frame_id)`, `get_semantic_run_detail(run_id)` | items in `sort_order`, with the assigned actor name |
  | search | `search_semantic_items(&SemanticItemQuery)`, `search_semantic_frames(&SemanticItemQuery)` | FTS5 over `semantic_items_fts`, optional `actor_id` and `kind` filters |
  | actors API | `search_semantic_actors(q, limit, offset)`, `get_semantic_actor`, `create_semantic_actor`, `rename_semantic_actor`, `merge_semantic_actors(keep, merge)`, `reassign_semantic_item_actor(item, actor)`, `reassign_semantic_actor_alias(alias, actor)`, `find_semantic_actor_alias(source_key, label)` | ids must be positive (`"<field> must be positive"`); missing rows are `NotFound("semantic actor" / "semantic item" / "semantic actor alias")` |
  | retention (W3-09) | `gc_semantic_projection(grace) -> SemanticGcStats` | call after frames are deleted: `SEMANTIC_GC_DEFAULT_GRACE` for periodic retention, `Duration::ZERO` for user-initiated deletes; see question 5 |

  `NewSemanticRun` carries the run columns, `actor_source_key: Option<String>` and
  `items: Vec<NewSemanticItem>`. An item's `sort_order` is its index in that list. The parser fills
  `local_id`, `parent_local_id`, both fingerprints, `kind`, `item_key`, `identity_quality`,
  `title`, `body`, `actor`, `occurred_at` (`DateTime<Utc>`), `timestamp_precision`, `status`,
  `metadata` (a JSON object) and `source_node_ids: Vec<u32>`. The closed value sets are Rust enums
  (`SemanticAppPlatform`, `SemanticRunStatus`, `SemanticItemKind`, `SemanticIdentityQuality`,
  `SemanticAssignmentSource`) that serialize to the stored strings.
- **Reason:** the plan asks for a small documented API. Keeping the worker's batching and the route
  layer's HTTP mapping on the caller side keeps this WP to the DB layer, while the enums and
  validation keep every write inside the schema's CHECK constraints with a clear error instead of a
  constraint failure.

## 2. Encoding of `semantic_run_items.source_node_ids` (open interop question)

- **Question:** the spec calls it a packed blob of tree node ids but does not give the layout.
- **Decision:** each id is a `u32` written as 4 little-endian bytes, in order; an empty list is the
  empty blob (the column default). `encode_source_node_ids` and `decode_source_node_ids` are public.
  On read the raw blob is kept (`SemanticRunItemDetail::source_node_blob`). This layout is
  **inferred, not confirmed** by any evidence. Decoding can only reject a blob whose length is not a
  multiple of 4 (it returns `None`). A blob screenpipe wrote in another layout whose length happens
  to be a multiple of 4 (big-endian ids, pairs of 16-bit ids, varints that land on a 4-byte
  boundary) decodes without an error to **wrong** node ids. Nothing in this WP decodes blobs from
  other writers, so no stored data is affected today, but a reader of screenpipe-written rows would
  be.
- **Reason:** node ids index a budgeted compact tree, so 32 bits is ample. W2-06 must produce ids
  that fit in `u32`.
- **Interop question for W2-06 / REA:** confirm the byte layout screenpipe v2.7.104 writes into
  `source_node_ids` (id width, byte order, any length prefix or varint encoding), for example from
  the parser's serialisation code or a blob in a database the shipped binary wrote. If it differs,
  change only `encode_source_node_ids` and `decode_source_node_ids` (and their unit test); until it
  is confirmed, treat `source_node_blob` from rows this store did not write as opaque.

## 3. Alias source key and label columns

- **Question:** `source_key` scopes a label to its source but its format is inferred, and the spec
  does not say how `source_label`, `observed_label` and `normalized_label` differ.
- **Decision:**
  - `source_key` defaults to the run's `parser_id`, so aliases survive parser version bumps. A
    caller that knows a narrower scope (for example a chat workspace or a mail account) passes
    `actor_source_key`; blank means the default. At most 1024 characters.
  - `source_label` is the label as the parser emitted it, minus non-whitespace control characters
    (question 8), cut to 256 characters.
  - `observed_label` is the display form: non-whitespace control characters and invisible format
    characters removed (question 8), whitespace runs collapsed to one space, ends trimmed, cut to
    256 characters. A new actor created by the heuristic is named with it.
  - `normalized_label` is the display form lower-cased (Unicode `to_lowercase`), cut to 512
    characters. It is the lookup key with `source_key`.
  - A label with no visible characters (empty display form) is treated as absent: no alias, no
    assignment.
- **Reason:** the spec's inferred normalisation is trim, collapse whitespace and case-fold. Keeping
  the raw label in `source_label` preserves what was actually seen. Long labels sharing a 256- or
  512-character prefix collapse into one alias, which is acceptable for names.

## 4. Store-time rules the spec leaves open

- **Question:** what counts as a compatible existing run, and how strict is validation?
- **Decision:**
  - A run whose input fingerprint is already stored must match on `parser_id`, `parser_version`,
    `schema_version`, `app_platform` and `input_content_hash`; otherwise `Conflict`. App id,
    executable and version may differ. A compatible run is returned unchanged and the new items are
    ignored, because runs are immutable.
  - An item whose version fingerprint is already stored must match on `entity_fingerprint` and
    `kind`; otherwise `Conflict` and the whole run rolls back.
  - `status = 'empty'` requires no items and `status = 'handled'` at least one. `item_count` is the
    number of items. `text_bytes` and `parse_duration_us` come from the caller.
  - Local ids must be non-empty and unique; every `parent_local_id` must name an item of the same
    run, and parent links must not loop. These are checked before any write.
  - Heuristic assignment uses `INSERT OR IGNORE`, so an item that already has an assignment
    (including a reconciled one, or one from an earlier run that saw the same item) keeps it.
- **Reason:** these follow the spec's "read back and verify compatible metadata" and keep the
  deferred parent foreign key from failing at commit with an opaque error.

## 5. GC grace period

- **Question:** the observed GC deletes every run no frame points at. The worker stores a run first
  and attaches frames later in batches, so a GC pass in between would delete a fresh run.
- **Decision:** `gc_semantic_projection(grace)` only deletes unreferenced runs whose `created_at` is
  at least `grace` old (`SEMANTIC_GC_DEFAULT_GRACE` is 10 minutes; `Duration::ZERO` gives the
  observed behaviour). Items are deleted when no run item references them, with no grace (they are
  written in the same transaction as their run items). Both deletes run in batches of 2,000 rows per
  transaction. Attaching a frame to a run that GC already removed is skipped instead of failing the
  batch on the foreign key.
  The grace is for periodic retention passes, which pass `SEMANTIC_GC_DEFAULT_GRACE`.
  User-initiated deletes (W3-09: delete-range, `delete_by_machine_id`) must pass `Duration::ZERO`,
  so the deleted frames' runs, items and FTS text are gone when the call returns. The price is that
  a run stored moments before for a frame outside the deleted range, not yet attached, is collected
  too and that frame stays without a run until it is parsed again. The method's doc comment says
  the same.
- **Reason:** removes a race without changing what is stored, so interop is unaffected. Batching
  keeps retention from holding the write lock for a long time on large databases. A user who
  deletes data expects it gone, not kept for another ten minutes.

## 6. Actor operations

- **Question:** details the API spec does not pin down.
- **Decision:**
  - Actor search matches a case-insensitive (ASCII, SQLite `LIKE`) substring of the name or of any
    alias's `observed_label`; `%`, `_` and `\` in the query are literal. Order: item count
    descending, then name (case-insensitive), then id. Pages are clamped to 1..=1000.
  - Merge moves aliases and assignments (assignment sources unchanged), deletes the merged actor
    and touches the kept one.
  - Item reassignment needs an item whose observed `actor` label has visible characters (otherwise
    `InvalidInput`); it upserts `assignment_source = 'reconciled'`, keeps an existing
    `observed_alias_id`, and touches the new and previous actor.
  - Alias reassignment moves the alias and the `heuristic` assignments made through it
    (`observed_alias_id`), and touches both actors. Reconciled assignments stay.
  - Creating or renaming strips non-whitespace control characters, trims the name and requires 1 to
    256 characters with at least one visible character (question 8); anything else is
    `InvalidInput`.
- **Reason:** matches the behaviour listed in meetings_memory-023 and api-008 while keeping every
  write inside the schema's constraints.

## 7. Stored values validated on read

- **Question:** what happens when a row holds a platform, kind, identity quality, status or
  assignment source this build does not know (for example from a newer screenpipe)?
- **Decision:** reading it returns `InvalidStoredValue { column, value }`; `occurred_at` is
  returned as the stored text rather than parsed, and malformed `metadata_json` is also
  `InvalidStoredValue`. Timestamps this store writes use the same `YYYY-MM-DDTHH:MM:SS.sssZ` shape
  as the schema's defaults.
- **Reason:** db-008 says unrecognised stored values are errors. Keeping `occurred_at` as text
  avoids failing a whole read on a timestamp format another writer chose.

## 8. Control and invisible characters in labels, actor names and source keys

- **Question:** SQLite's `length()` counts the characters before the first NUL. A label starting
  with NUL (`"\0Ada"`) passed the old visibility check, then failed the alias table's
  `length(...) BETWEEN 1 AND ...` checks and rolled the whole `store_semantic_run` back; the same
  name given to create or rename an actor was a 500 instead of a 400. Labels made only of control
  characters (`"\u{1}\u{2}"`) or of directional marks became actors with invisible names. What
  should be stored?
- **Decision:**
  - Labels: NUL and every other control character (Unicode Cc) that is not whitespace are removed
    before anything is stored or matched. Whitespace controls (tab, line feed, carriage return and
    the like) still count as whitespace. The display and normalized forms also drop invisible
    format characters: soft hyphen (U+00AD), Arabic letter mark (U+061C), Mongolian vowel
    separator (U+180E), U+200B to U+200F (zero-width characters, LRM, RLM), U+202A to U+202E
    (embeddings and overrides), U+2060 to U+2064, U+2066 to U+206F (isolates and deprecated format
    characters), U+FEFF and U+FFF9 to U+FFFB. A label whose display form is empty is treated as
    absent (no alias, no assignment) and never fails the run.
  - Actor names (create, rename): non-whitespace control characters are removed and the ends
    trimmed; a name with no visible character is `InvalidInput` (400) with the message
    `name must contain a visible character`.
  - Source keys (`actor_source_key`, or `parser_id` when it is the default key): an identifier, so
    a key containing any control character is rejected with `InvalidInput` naming the field,
    before any write, rather than silently rewritten.
  - `semantic_items.actor`, `title` and `body` keep the parser's text unchanged; only the derived
    alias and actor columns are cleaned.
- **Reason:** the alias and actor rows must always satisfy the schema's checks, and a bad label from
  the screen must cost at most that item's assignment, never the run. Chat apps wrap phone numbers
  and right-to-left names in directional marks, so dropping them also keeps one person from
  splitting into two aliases. The extra characters only change the normalized key of labels that
  contain them, which are rare; if screenpipe's normalisation keeps them, an alias it wrote for such
  a label would not be found by this lookup (the same caveat as the zero-width characters in
  question 3).
