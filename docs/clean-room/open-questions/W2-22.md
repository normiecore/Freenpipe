# W2-22 open questions

Decisions taken while implementing pipe config v2 (agents_pipes-003, agents_pipes-004,
agents_pipes-m03, agents_pipes-m05). The spec records field names and shapes; the behaviour below
fills the gaps it leaves.

## Structured schedules (`schedule_config`)

### 1. Weekday numbering
- **Question:** the spec infers cron-style numbering (0 = Sunday) for `days_of_week`.
- **Decision:** 0 = Sunday .. 6 = Saturday, and 7 is accepted as Sunday too.
- **Reason:** the UI default `[1]` is Monday under both cron and ISO numbering; accepting 7 as well
  means a pipe written with either convention runs on the intended days.

### 2. Which weeks, days and months count for `interval` > 1
- **Question:** "every 2 weeks" needs an origin and a week boundary.
- **Decision:** periods are counted from `starting` (the day, Sunday-to-Saturday week, or month it
  falls in). Without `starting` the origin is 2000-01-01 00:00 in the schedule's zone, so the
  schedule is stable across restarts. Hour, day, week and month periods are counted on the wall
  clock of the schedule's zone, so "every 2 hours at :15" keeps to the same clock hours after a
  daylight-saving change (the repeated hour runs once). Minute periods are elapsed time from the
  origin: an interval that divides an hour stays on round clock times as long as the zone's offset
  changes by whole hours, which holds for daylight saving in all but a few zones.
- **Reason:** anchoring to install time or last run would drift; a fixed origin is deterministic.
  Counting minutes on the wall clock would pause an "every 15 minutes" pipe for the repeated hour.

### 3. Missing fields
- **Decision:** `interval` defaults to 1, `at_hour`/`at_minute` to 0, `timezone` to the machine's
  local zone, `days_of_week` to empty (an error for `weeks`), `day_of_month` to the day of
  `starting` (else the 1st). Nulls are accepted wherever a value may be missing.
- **Reason:** the acceptance request `{frequency:'days',interval:1,at_hour:9,at_minute:0}` omits
  most fields, and hand-written files should load.

### 4. `max_occurrences` and `ending`
- **Question:** the spec leaves occurrence-limit semantics inferred.
- **Decision:** `max_occurrences` counts schedule slots from `starting` (calendar "COUNT" meaning),
  not runs that actually happened, and it requires `starting`. Slots before `starting` do not count.
  `ending` is inclusive; a bare date covers the whole day; a timestamp without an offset is read in
  the schedule's zone.
- **Reason:** counting slots needs no extra persisted state and gives the same answer on every
  device; a count with no start would have no origin.

### 5. Short months, DST
- **Decision:** a `day_of_month` past the end of a month runs on that month's last day. A wall-clock
  time in a DST gap moves forward in quarter-hour steps until it exists; a repeated time uses its
  first occurrence.
- **Reason:** users who pick "the 31st" mean "end of month"; never skipping a run is the safer
  failure mode.

### 6. Weekly with no days, and other invalid schedules
- **Decision:** refused with 400 by `/pipes/schedule/preview` and by config updates. A pipe.md that
  already carries a `schedule_config` this build cannot use still loads. One of another shape (an
  unknown `frequency` such as `daily`, text where a number goes) is set aside as in question 15;
  one that reads but does not check out (weekly with no days, `at_hour: 30`) is kept typed and
  logged at debug level. Either way the pipe follows its `schedule` string, as if `schedule_config`
  were absent, and event triggers still work.
- **Reason:** the UI blocks preview for incomplete configs; loading must not fail over a schedule.
  The settings UI shows and edits only `schedule`, so falling back to it keeps what the pipe does
  in line with what the user sees.

### 7. Relation to the `schedule` string
- **Question:** "compiled to the effective schedule" could mean rewriting `schedule`.
- **Decision:** `schedule` is left as written. When a valid `schedule_config` is present the
  scheduler, the run lookback window and `next_run` follow it and ignore `schedule` (including a
  one-off `at ...`). `PipeConfig::schedule_label()` (used by `screenpipe pipe list`) shows the
  structured summary. A config update that sets `schedule` without `schedule_config` in the same
  body clears `schedule_config`: the client chose the string form.
- **Reason:** most structured schedules (intervals > 1, end dates, counts, zones) have no exact string
  form, and an approximate rewrite would silently change behaviour if `schedule_config` is removed.
  The shipping settings UI writes only `schedule`; without the takeover, choosing a new schedule
  (or `manual`) for a pipe that has a `schedule_config` (written by screenpipe, an agent or the API)
  would change nothing while the UI showed the new choice.

### 8. Ended schedules
- **Decision:** when a structured schedule has no slot left (past `ending` or out of occurrences) the
  scheduler switches the pipe off through the device-local override, as base does after a one-off
  fires. Enabling such a pipe (`POST /pipes/:id/enable` or `enabled: true` through a config
  update) is refused with an error naming `ending`/`max_occurrences`.
- **Reason:** spec says the pipe auto-disables; refusing the enable avoids an on/off flicker.

### 9. Preview response
- **Decision:** `next` lists 5 upcoming run times after now, RFC 3339 with the schedule zone's offset
  (`Z` for UTC). The summary sentence is Freenpipe's own wording ("Every 2 weeks on Monday and
  Thursday at 09:00 (Europe/Berlin), until 2026-12-31 23:59").
- **Reason:** the count was not observed; 5 fits a preview line. The offset form keeps the times
  readable in the schedule's own zone and parses as ISO in any client.

## Config updates (`POST /pipes/:id/config`)

### 10. What counts as an unknown field
- **Decision:** accepted keys are the typed frontmatter fields (`name, schedule, enabled, agent,
  model, provider, cloud_agent, effort, preset, connections, permissions, timeout, trigger,
  source_slug, installed_version, source_hash, subagent, history, run_in, privacy_filter, artifacts,
  schedule_config, event_read_only`), the display extras `title, description, icon` (text) and
  `featured, template` (true/false), plus `prompt_body` and `raw_content`. Anything else is 400,
  unless it repeats a free-form key the file already has with the same value (question 11). Other
  free-form frontmatter keys can still be written through `raw_content`.
- **Reason:** the acceptance check requires 400 for unknown fields; the display extras are the ones
  the spec lists as unchanged UI fields.

### 11. Per-field checks and atomicity
- **Decision:** only fields present in the body are checked, so an update never fails because of an
  unrelated field already on disk. A field sent with the value the pipe already has (as
  `GET /pipes` shows it) is left alone without checks, and inside `trigger` (per key, and per
  `sources` entry) and `artifacts` (per entry) the same holds, so the trigger editor's
  `{...trigger, events}` post and full-object saves pass over lenient values; an unknown key that
  repeats a free-form extra already in the file is such an echo too (also a legacy `config:` block,
  which otherwise counts as an envelope). A body with any invalid field changes nothing. `null`
  clears an optional field. `name` is accepted only when it equals the pipe id. A new `schedule`
  must parse (`manual`, interval, human form, cron or `at <RFC 3339>`); `timeout` must be a positive
  integer. `enabled: true` is refused, like `enable_pipe`, for a stale one-off or a structured
  schedule that has ended.
- **Reason:** the spec says each of `schedule_config`, `trigger`, `run_in`, `effort` and
  `cloud_agent` is validated separately; partial writes would leave confusing state.

### 12. `raw_content` combined with fields
- **Decision:** `raw_content` alone is written verbatim (comments and key order kept) after the
  checked fields it changes (`timeout, trigger, run_in, cloud_agent, artifacts, schedule_config,
  effort, history, event_read_only`, compared with the file on disk as clients read it) pass the
  same checks as when sent on their own; unchanged values are not re-checked. Sent together with
  other fields, those fields are applied on top of the parsed content and the file is
  re-serialized. The `schedule` string inside `raw_content` is not checked.
- **Reason:** full-file saves from the editor should keep formatting, and should not start failing on
  schedule strings v1 accepted or on a lenient value (question 15) the user did not touch.

### 13. Status codes
- **Decision:** 400 for an envelope body, unknown field, invalid value or invalid pipe id; 404 for an
  unknown pipe; 403 for a managed pipe (never happens in Freenpipe); 500 for other failures (disk
  errors, an unreadable existing pipe.md). Base used 400 for everything.
- **Reason:** clients can tell their own mistakes from server problems.

### 14. Value checks the spec does not give
- **Decision:** `effort` is `low|medium|high`, case-insensitive. `run_in.mode` must be
  `existing_chat` with a `chat_id` of 1-200 characters, no path separators, no control characters,
  no surrounding spaces, not `.`/`..`. `artifacts[].path` must be relative inside the pipe folder (no
  `..`, no root, no drive or `:`); `kind` is `html|json|markdown`; a given `title` must not be blank.
  `trigger.sources[].app` must be one of the apps in agents_pipes-008 (slack, notion, imap,
  google-calendar, outlook-email, github, linear, todoist, obsidian, voice) and `kind` one of its
  item kinds. `cloud_agent.provider` is `cursor|codex|claude`; `context_lookback_hours` 1-720 and
  `context_max_items` 1-1000; `send_screenpipe_context` defaults to false.
- **Reason:** bounds were not observed; these refuse obvious mistakes while leaving real values
  alone. A later WP that adds an app or kind extends the list.

### 15. Lenient loading
- **Decision:** loading accepts `history`/`event_read_only` as YAML booleans or `yes/no/on/off/1/0`,
  `effort` in any case, an artifact given as a bare path string, and nulls for list fields. Unknown
  `run_in.mode`, `cloud_agent.provider` or source `app` values load (kept as text) and are only
  refused when sent through the API. A value of `effort, history, run_in, artifacts,
  schedule_config, cloud_agent, event_read_only` or `trigger` that cannot be read at all (`effort:
  max`, `run_in` without `mode`, `cloud_agent` without `provider`, a source without `app`, a
  number where a list goes) is set aside instead of failing the file: the typed field stays empty,
  the value is kept as written among the free-form extras (a `trigger.sources` list under the
  trigger, which keeps its events) so a save writes it back, and `load_pipes` logs a warning naming
  the field. A file broken elsewhere still fails to load, as in base.
- **Reason:** a pipe that loads in screenpipe must load here, and a hand-written file should not
  disappear because of a spelling. Before these fields were typed they were inert extras; a bad
  value in one of them must not take the pipe (and its `schedule`) away.

## Status fields

### 16. `has_saved_context`, `is_bundled_builtin`, `next_run`, `execution_count`
- **Decision:** `has_saved_context` is true when a Pi session file exists for the pipe folder or
  `.screenpipe-acp-sessions.json` holds a non-empty map. `is_bundled_builtin` is a name match
  against the built-in pipes the app installs. `next_run` is null for disabled, manual-only or ended
  pipes and reports "now" for a run that is already due; cron strings are read in local time as the
  scheduler does. `execution_count` is filled only when `GET /pipes?include_execution_counts=true`
  is asked for (0 when nothing is recorded), from a new `PipeStore::count_executions_by_pipe`.
- **Reason:** these match how the scheduler and the history route already decide the same things.

## Pipe ids (agents_pipes-m05)

### 17. What a portable path component is
- **Decision:** refused: empty, longer than 255 bytes, `.`/`..`, `/` or `\`, control characters,
  `< > : " | ? *`, a leading dot, leading whitespace, a trailing dot or whitespace, and Windows device
  names with or without an extension (CON, PRN, AUX, NUL, CONIN$, CONOUT$, COM0-9, LPT0-9 and the
  superscript-digit forms), case-insensitively. Everything else, including inner spaces and
  non-ASCII letters, is allowed.
- **Reason:** existing pipe folders with such names keep working; the refused set is what can
  escape the pipes root or that Windows rejects or rewrites. A leading dot is refused so ids never
  collide with the pipes directory's hidden sidecar files.

### 18. Where ids are checked
- **Decision:** names that create a folder (install from file/folder/URL/store, pipe-sync manifests
  applied from another device) get the full rules. Operations on an installed pipe (enable, config
  update, delete, history, stop, store update, the CLI's name-taking subcommands) also accept the
  exact name of a folder already in the pipes directory: a directory listing only yields single
  components, so such a name cannot leave it. On Windows that exception covers only the leading-dot
  rule, since Win32 path handling drops trailing dots and spaces and maps device names, so such a
  folder could open as another pipe's. Folder names read back from the pipes directory are not
  re-checked, so an existing folder never stops loading.
- **Reason:** the spec names API and CLI names; sync manifests and install-derived names reach the
  same `pipes_dir.join(name)` calls. Pipes in folders named before these rules (a leading dot,
  `aux` or `name.` on Linux/macOS, `daily.md?raw=1` from an older URL install) keep loading and must
  stay manageable. URL installs now ignore a query string or fragment when deriving the name.

## Preamble (agents_pipes-m03)

### 19. Wording and placement
- **Decision:** a short "How to work with the user" block, written fresh, sits between the base
  preamble and the pipe body: read ratings from `GET /feedback?producer=pipe:<name>` (name
  percent-encoded) before regenerating recurring output; ask through notification action buttons;
  use sub-agents only for two or more independent parallel parts (only when `subagent: true`); keep
  stable preferences with the `user_profile` tool when that tool is available. The ratings
  directive is written only when `FEEDBACK_ROUTE_AVAILABLE` (in `pipes/mod.rs`) is true. It is
  false until **W2-03** adds `GET /feedback`; W2-03 switches it on (the preamble test covers both
  forms).
- **Reason:** `producer_ref` is `pipe:<name>` in the feedback spec; the profile tool ships with a
  later WP, so the directive is conditional instead of pointing at a tool that may be missing. Until
  the route exists, the ratings directive would cost every recurring run a tool call that ends in a
  404. The block is fixed per pipe, so it stays in the cacheable system prompt.

### 20. Fields typed here whose behaviour lands in later WPs
- **Decision:** `effort` is typed and validated but not yet passed to the agent (the executor
  interface has no effort argument). **W2-23** (Pi runtime, agents_pipes-015, whose spec section
  carries "pipe streaming using provider/model/effort") passes it as the Pi thinking level, and
  **W4-03** (ACP runtime) as ACP `reasoning_effort`. `event_read_only` is typed but
  not enforced (its semantics are inferred). `run_in`, `artifacts`, `cloud_agent` and
  `trigger.sources` are typed and validated; delivery, registration, cloud launch and the connection
  watcher belong to W6-02, W2-02, W4-04 and W6-03.
- **Reason:** keeps this WP inside its owner paths and leaves each behaviour to the WP that owns it.
