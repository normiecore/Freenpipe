# W4-05 open questions

Decisions taken while building the chat runtime commands (agents_pipes-018) and the per-turn
connections context (connections-chat-context-per-turn). Each one is the worker's call; the owner
can overturn any of them.

## 1. What a start stage means in an error

- **Question:** the spec lists the stages `requested`, `config_ready`, `waiting_for_pool`,
  `pool_acquired` and `process_spawned`, and a failed start must report "the stage it failed at".
  Is that the stage it reached or the one it was trying to reach?
- **Decision:** the stage it was in, i.e. the last one reached. `requested` covers preparing the
  project directory, skills, extensions, `models.json`, finding Pi and building the command line;
  `waiting_for_pool` covers the busy check and the capacity check; `pool_acquired` covers stopping
  the old process and spawning; `process_spawned` covers the immediate-exit check. The error reads
  `Pi start failed at stage '<stage>': <reason>` (the old reason text is kept inside, so existing
  frontend substring checks still match), and every stage, failed or not, is emitted on the
  Freenpipe event `pi_start_stage` (`{sessionId, source, stage, error}`).
- **Reason:** a stage name then always names something that happened, and the span of each stage
  is documented on `PiStartStage`. The event name is ours; the evidence gives only the stage names.

## 2. Preparing a start outside the pool lock

- **Question:** the base held the pool lock for the whole start, including the up-to-60 s wait for
  the background Pi install and, on Windows, the bash/PortableGit setup. Every other session's
  commands waited behind it.
- **Decision:** the `requested` stage runs without the pool lock. A per-session start lock keeps
  starts of one session in order (a second start sees the first one's process), while different
  sessions prepare in parallel. The pool lock is held only from `waiting_for_pool` to registering
  the new process. A start that fails after spawning kills its process and removes the session
  from the pool; one that fails earlier leaves no process at all.
- **Reason:** "no half-started process" plus not stalling other chats on a slow first start.
- **Shared files:** what different sessions' starts still share is written one start at a time
  under a process-wide lock (`SHARED_START_FILES`): the read-merge-write of the Pi config
  directory's `models.json` and `auth.json`, and the project directory's skills and extensions.
  The gateway's model list is fetched before the lock is taken. Both config files are written to
  a temporary file and renamed into place (written in place only if the rename is refused), so no
  reader ever sees a torn file; `auth.json` is made owner-only on Unix.

## 3. Which sessions count as busy

- **Question:** "refusal to restart a busy session" and `pi_stop_if_idle` need a definition.
- **Decision:** a session is busy while any of these holds: a reply is being generated, Pi is
  compacting, a steer waits for its turn, prompts are queued, a command was accepted and has not
  finished (a ticket taken under the pool lock, so nothing slips in between a check and a stop), an
  extension dialog waits for an answer, or a request/response call waits for Pi. A busy session is
  never restarted by `pi_start` (error at `waiting_for_pool`), never evicted to make room, and never
  stopped by `pi_stop_if_idle`. `pi_stop` still stops unconditionally.
- **Reason:** each of these is a moment where stopping the process loses something the user asked
  for. The old eviction check looked only at the (unused) response table, so it could evict a
  streaming session.
- **Behaviour change:** restarting a session mid-reply now fails with the busy error instead of
  killing the reply. The chat handles both places that relied on the old kill: a preset switch
  that is refused (the reply ended here but the runtime still counts the session busy, e.g. queued
  follow-ups or a compaction) tells the user it will apply once the assistant is idle, waits until
  `pi_request_state` reports `busy: false` (at most 2 minutes), and tries once more; a second
  refusal or the time limit ends in an error toast, as does any other failure (before, failures
  only reached the console). Interrupting a turn whose abort did not land within 1.5 s means to
  cut it short, so the chat stops the session with `pi_stop` and then starts it
  (`lib/chat/pi-busy.ts`, unit-tested).

## 4. Prompts to a busy session

- **Question:** "a prompt to a busy session is refused with a clear result, never queued without
  bound or silently dropped". The existing chat sends follow-ups mid-reply with `pi_queue_prompt`
  and `pi_steer`, and `pi_prompt` has always waited its turn.
- **Decision:** `pi_start_and_prompt` refuses outright: a busy session gets
  `{outcome: "busy", busyReason}` and nothing is queued. `pi_prompt` and `pi_queue_prompt` keep
  waiting in line (the existing chat depends on it), but at most `MAX_PENDING_PROMPTS` (16) prompts
  may wait per session; one more is refused with an error saying the queue is full. Commands no
  longer block on a full channel (they fail instead). Every prompt that does not reach Pi (cancel,
  abort, process death, write failure) still answers its caller with an error.
- **Reason:** keeps the current chat working while making every limit explicit.

## 5. `pi_start_and_prompt` on a running idle session

- **Question:** should it restart the session with the given provider config?
- **Decision:** no. A running idle session is reused as it is; the provider config, token and
  project directory are used only when the session has to be started. `pi_start` (or
  `pi_set_model`) applies a different config.
- **Reason:** the command exists to remove the start-then-prompt race; restarting on every call
  would throw away Pi's in-memory conversation.

## 6. Turn end, retries and compaction

- **Question:** Pi 0.84 sends `agent_end` with `willRetry`, `agent_settled`, and
  `compaction_start`/`compaction_end`; the queue treated every `agent_end` as the end of the turn.
- **Decision:** `agent_end` with `willRetry: true` keeps the turn running; `agent_settled` ends it
  too; prompts wait while a compaction runs (older `auto_compaction_*` names count as well). A
  `response` refusing a `prompt` ends that prompt's wait at once (before, the next prompt waited for
  the 300 s safety bound), and a refused `steer` clears the steer guard. Waits now register their
  wake-up before checking the condition, so a `done` that lands in between is not lost.
- **Reason:** writing a prompt while Pi retries or compacts makes it refuse the prompt.

## 7. `thinking_level_changed`

- **Question:** the UI consumes an agent event `thinking_level_changed`, but Pi's RPC protocol has
  no such event; `set_thinking_level` only answers with a `response`.
- **Decision:** the app emits it on the `agent_event` bus after `pi_set_thinking_level` changed a
  running session: `{type, level, requestedLevel, previousLevel}`, where `level` is what Pi's
  `get_state` reports afterwards (Pi lowers a level the model lacks). The chosen level is kept per
  session in memory and passed as `--thinking` at every start of that session; it is not persisted
  across app restarts (no settings key exists for it, PLAN.md section 2 rule 7). Levels accepted:
  `off, minimal, low, medium, high, xhigh, max` (Pi 0.84's list).
- **Reason:** the event is how the UI learns about a change; the per-session memory keeps a restart
  (crash recovery, eviction) from silently resetting the level.

## 8. Extension dialogs

- **Question:** `extension_ui_request` dialogs (`select`, `confirm`, `input`, `editor`) block the
  agent until `pi_extension_ui_response`. What if nobody answers, or an answer is stale?
- **Decision:** the runtime records each open dialog. An answer must name an open dialog and carry
  exactly one of `value`, `confirmed` or `cancelled`; anything else is refused, so a stale answer
  never reaches another dialog. A dialog with its own `timeout` is resolved by Pi; the record is
  dropped shortly after. A dialog without one is cancelled after 10 minutes. Aborting a turn
  (`pi_abort`, `pi_abort_active`) cancels open dialogs first. Fire-and-forget methods (`notify`,
  `setStatus` including the `screenpipe-confidential` key, `setWidget`, `setTitle`,
  `set_editor_text`) are only forwarded.
- **Reason:** until the chat renders these dialogs (later chat WPs), an unanswered dialog would
  otherwise hold a session busy for ever.

## 9. Request/response calls

- **Question:** `pi_request_state` and the thinking-level commands need Pi's answer while a turn may
  be running.
- **Decision:** they are written to stdin directly (not through the serialized queue) with their own
  id, and the reader hands the matching `response` to the caller only: it never moves the command
  queue and is not forwarded to the chat (a failing `get_available_thinking_levels` must not show as
  a chat error). Each waits at most 10 s. `pi_request_state` always returns the app-side state and
  adds Pi's `get_state` answer when it gets one (`piState`, else `piStateError`). A Pi that does
  not know a command answers with a refusal that has no id; the call's id therefore starts with
  `rpc_<command>_`, so such a refusal still reaches the waiting call (an older Pi without
  `get_available_thinking_levels` then yields an empty level list at once) and is never taken as
  the end of a queued command.

## 10. Where the connections block is built, and when

- **Question:** the spec says "before each prompt, render the redacted `render_context` output into
  a tagged block". Where, and how fresh?
- **Decision:** in the app's Rust runtime, by the session's command queue right before a `prompt`
  is written to Pi (after any wait for a running turn), so a queued follow-up gets the list as it is
  when its turn starts. The body is the engine's `render_context` plus the user's MCP servers
  (`mcp_servers::render_context`), read from the running engine's data directory and port (the
  engine's state lock is waited for at most 0.5 s; while it is held the directory seen last is
  used, and before any engine ran the one the `dataDir` setting resolves to). A block
  is sent on every turn, also when nothing is connected (it then says so), so a disconnect reaches
  the model too. If the list is not ready within 3 s the turn goes out with a block saying the list
  could not be loaded. Steers do not get a block (the turn they steer has one); internal title
  sessions (`__title:`) get none. A block already in the message (a re-sent turn) is replaced, so a
  turn carries exactly one. The block's wording is Freenpipe's own.
- **Reason:** the evidence puts the block in the app runtime next to the Pi provider strings; doing
  it at write time is what "refreshed per turn" means for queued prompts.
- **What the body holds (round 1):** `render_context` only knows saved connections. The services
  the running engine adds to its `GET /connections` listing (WhatsApp with its gateway port and
  endpoints, the browsers the agent can drive with their control endpoints, Apple Calendar on
  macOS, and anything added later) were in the old system-prompt list, which was built from that
  listing. Each turn therefore also asks the engine for its listing (with the local API key, at
  most 2 s, in parallel with `render_context`) and adds every connected entry whose id
  `render_context` does not print (the integration catalogue and `ics-calendar`) as
  `## Name (id)` plus the engine's description, before redaction. If the engine does not answer,
  the block says those services could not be checked. The block never claims to be complete: its
  last line says where `/connections` paths live and that `GET /connections` returns every
  integration and whether it is connected; with nothing found it says "no connected integration
  or MCP server was found for this message".
- **Pi commands:** a message that starts with a Pi command (`/name` or `/skill:name` followed by
  a space or the end of the message) gets no block, because Pi recognises commands only at the
  very start of the message. A message that starts with a path such as `/home/me/x` is not a
  command and gets the block.
- **Secret store per turn:** the store (and its pool on `db.sqlite`) is opened for each turn and
  closed before the turn is sent; nothing keeps the database open after the engine stops, and a
  change of the secret-encryption setting applies from the next turn.

## 11. Redaction without W2-20

- **Question:** `render_context` still prints the raw credentials of non-proxy integrations (the fix
  is connections-secret-redaction, W2-20, which is parked by decision 6).
- **Decision:** the chat block is redacted in the app without changing `render_context` (pipes keep
  their current context until W2-20): every credential value of a credential-based connection is
  blanked unless its field is declared non-secret and its name does not look secret (vault paths,
  chat ids and ntfy topic URLs stay; undeclared keys are blanked), and a second pass blanks anything
  shaped like a credential whatever printed it (bearer tokens, common API key formats, JWTs, bot
  tokens, Slack/Discord webhook paths, URL passwords, `token`/`key`/`code`/`secret`... query
  parameters). OAuth tokens are never printed by `render_context`. Since the block is redacted before
  it is sent, Pi's session log never holds the secrets either.
- **Consequence:** in chat, webhook integrations (Discord, Zapier, Make, n8n, Teams webhook) show
  as connected but without their URL, so the agent cannot post to them from chat until W2-20 adds
  the `webhook: POST …/proxy` line. That is the spec's intended end state.

## 12. Stripping the block from the transcript

- **Question:** "strip it in the transcript view" — where exactly, and what is stored?
- **Decision:** the frontend helper `lib/chat/strip-connections-context.ts` removes well-formed
  blocks (rules in its header and in question 13) at two points: where Pi's echo of a user turn is
  turned back into a chat message (foreground chat and background router, before the
  `<conversation_history>` prefix is taken off, so typed text and turn matching still work), and in
  the user-message render call, which also covers older or imported chats that still hold a block.
  The conversation file therefore keeps the text the user typed, exactly as for turns sent from the
  composer; Pi's own session log under the Pi config directory keeps the block, i.e. what the model
  saw.
- **Reason:** keeping the block in the conversation file would put stale lists into every later
  `<conversation_history>` the chat re-sends and into derived titles. The conversation file is the
  chat's own transcript (turns typed in the foreground chat are saved from the composer, before the
  runtime adds the block, so they never held it); the agent's stored history, the one Pi resumes
  from, is its session log, and that keeps exactly what the model saw.

## 13. Nested and malformed tags

- **Decision:** a closing tag pairs with the nearest unpaired opening tag before it; nested blocks
  are removed as a whole; an opening tag that never closes, a closing tag with nothing to close, and
  any other spelling (attributes, spaces) stay as text. The Rust builder replaces the tag text inside
  a body (a user-chosen instance or feed name could contain it) so a block can never close early.
- **Reason:** never hide text the user typed.

## 14. The system prompt no longer carries the list

- **Decision:** `buildProviderConfig` in the chat stops appending `buildConnectionsContext` to the
  system prompt, and the effect that restarted Pi whenever the connection list changed is removed
  (it also restarted on every refresh, since the system prompt embeds the current time).
  `buildConnectionsContext` stays in `lib/chat/system-prompt.ts` (with its tests) but is unused.
- **Reason:** the spec says to stop baking the list into the system prompt; the per-turn block
  replaces it without killing the session.

## 15. `list_chat_entries_by_mtime`

- **Question:** the spec only names the command.
- **Decision:** `list_chat_entries_by_mtime(offset?, limit?)` lists `~/.screenpipe/chats/*.json`,
  newest modification first, ties by name descending, as `{name, path, mtimeMs, sizeBytes}`; a
  missing directory is an empty list. The directory is the one `lib/chat-storage.ts` writes
  (`homeDir()` + `.screenpipe/chats`), which does not follow `SCREENPIPE_DATA_DIR`; an earlier
  draft used the data directory and listed nothing in the dev setup (`FP_DD`). The chat still lists
  files itself; switching it to the command, and deciding whether chats should follow the data
  directory, is left to the chat WPs that own that file.

## 16. `pi_stop_if_idle` result

- **Decision:** returns `{outcome: stopped | not_running | busy | starting, stopped, busyReason}`. A
  stopped (or dead) session is removed from the pool, freeing its slot; a session with a start in
  progress (or a `pi_start_and_prompt` still handing its prompt over) is left alone. The rule is the
  pure function `idle_stop_decision`, unit-tested: only a running idle session is stopped.
