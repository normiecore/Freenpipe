# W2-01 open questions

Decisions taken while building the database runtime hardening: connection pragmas, WAL maintenance,
the start-up preflight, the ownership sidecar, planner statistics and cancellable reads (db-016,
db-017, db-018, db-v2-01, with db-m03 folded into db-016).

## 1. How the `.owner` sidecar decides that an owner is alive

- **Question:** db-016 point 8 and db-m03 name the sidecar (`<db>.owner`) and the refusal, but not
  how a file left by a crashed process is told apart from a live owner.
- **Decision:** the owner holds an exclusive OS lock on `db.sqlite.owner` for as long as its
  `DatabaseManager` lives (`File::try_lock`: `flock` on Unix, `LockFileEx` on Windows). The lock is the
  only liveness signal. The pid, executable name and time written into the file are diagnostics, read
  back only for the error message (Windows keeps a locked file unreadable to other handles, so the pid
  is missing there). A file whose lock can be taken is taken over at once and rewritten, whatever it
  contains. The file stays in place when the owner closes. A file system without lock support, or a
  sidecar that cannot be opened for writing (read-only attribute, a directory in its place), logs a
  warning and keeps only the in-process guard. On Windows an open refused with a sharing violation is
  retried for about a second (scanners and backup tools let go quickly) and then read as "owned by
  another running process".
- **Reason:** the OS releases the lock when the process dies, however it dies, so a crash never leaves
  a state the user has to clean up by hand, and a recycled pid cannot look alive. Deleting the file on
  close would let a second process lock a fresh file of the same name while a third still holds the
  old one.

## 2. A second manager in the same process

- **Question:** the spec allows one live `DatabaseManager` per database path and process; the app
  restarts its engine in-process and sometimes opens the new generation before the old one has fully
  drained (it waits 8 s, then starts anyway).
- **Decision:** an owning open waits up to 10 s (`IN_PROCESS_RELEASE_WAIT`) for an earlier owner in
  the same process to be dropped, then fails with an error that says so. The app reports it as a boot
  error and its watchdog retries.
- **Reason:** two write queues on one file in one process only fight each other for the write lock,
  and the wait covers the normal generation hand-over.

## 3. Owning and attached opens

- **Question:** the CLI (`screenpipe status`, `search`, `export`, `backup`) opens the live database
  while the engine records. An ownership refusal there would break them.
- **Decision:** `DatabaseManager::new` claims ownership and runs maintenance;
  `DatabaseManager::attach` opens without a claim, without the start-up RESTART checkpoint and without
  maintenance. The four CLI commands use `attach`. A second recorder (`screenpipe record`, or the app
  next to a running engine) uses `new` and is refused with "owned by another running process".
  `ownership::ensure_not_owned_elsewhere` is there for the offline storage tools.
- **Reason:** the refusal text in the target is about recording and storage changes, not about
  reading.

## 4. Error codes of the header preflight

- **Question:** db-016 point 5 maps bad magic to `(code: 26) file is not a database` and "malformed"
  to `(code: 11) database disk image is malformed`, but lists the other header checks without a code.
- **Decision:** a wrong magic string, or a file too short to hold it, is code 26. Every other problem
  in a file that carries the magic string (header shorter than 100 bytes, invalid page size, file
  length not a whole number of pages, read/write versions outside 1..2, payload fractions other than
  64/32/32, schema format above 4, text encoding above 3) is code 11. The errors travel as
  `sqlx::Error::Database`, so their text is the familiar `error returned from database: (code: N) ...`.
- **Reason:** a file that claims to be SQLite but has a damaged header is a malformed database, not a
  foreign file; the existing classifiers (`is_fatal_sqlite_message`) already treat both texts as
  fatal.

## 5. Zero schema format and text encoding

- **Question:** the spec gives valid ranges 1..4 (schema format) and 1..3 (text encoding).
- **Decision:** 0 passes for both.
- **Reason:** SQLite leaves both fields at 0 until the first table is created, and the first schema
  write of a WAL database stays in the WAL until a checkpoint. A database whose first migration never
  ran, or a fresh one whose WAL was not yet checkpointed, would otherwise be refused at the next
  start. SQLite itself treats 0 as "unset".

## 6. A slow header read

- **Question:** "bounded" preflight: what happens when the 100-byte read does not return (offline
  network drive, antivirus hold)?
- **Decision:** the read runs off the async runtime with a 10 s limit. On timeout, and when the file
  is missing or unreadable, the preflight passes and SQLite gives its own verdict.
- **Reason:** the preflight must never be the reason a valid database does not open.

## 7. Pragma values

- **Question:** the spec infers `wal_autocheckpoint=0` from the packed literal.
- **Decision:** writers and readers set `wal_autocheckpoint=0`; readers add `query_only=ON`. Freenpipe
  also sets `journal_size_limit` to 64 MiB on every connection.
- **Reason:** with inline checkpoints off and no TRUNCATE checkpoint, `journal_size_limit` is what cuts
  the WAL file back after the log restarts, so a burst does not leave a large file behind for good. It
  is a per-connection setting and changes nothing in the database file.

## 8. WAL maintenance tuning and escalation

- **Question:** the spec describes a PASSIVE loop but no interval, and the coordinator asked that a
  stalled or busy loop cannot let the WAL grow without bound.
- **Decision:** PASSIVE every 30 s (`SCREENPIPE_WAL_MAINTENANCE_INTERVAL_SECS` overrides it). A tick
  waits up to 5 s for the write coordinator; after 3 ticks in a row without it, the loop checkpoints
  without it. When the log holds 128 MiB of frames or frames have waited 10 minutes, the loop runs one
  RESTART with a 2 s busy timeout (at most every 2 minutes). Deferrals are logged once when they start
  and as a warning every 10 minutes while they last; the drain is its own log line.
- **Reason:** PASSIVE never blocks recording; RESTART is the smallest step that lets the next writer
  restart the log, and the 2 s timeout bounds how long it can hold writes back. The base's TRUNCATE
  every 5 minutes waited up to 5 s each time.

## 9. Which faults stop the loop

- **Question:** db-016 point 4 stops maintenance for the database generation after a hard fault
  (db-019), whose fault set includes I/O errors and a full disk. db-019 is not built yet.
- **Decision:** the loop stops on `SQLITE_CORRUPT` and `SQLITE_NOTADB` from its own checkpoint, and
  `DatabaseManager::stop_wal_maintenance` lets db-019 stop it later. I/O errors and a full disk back
  off (doubling the wait, up to 5 minutes) and keep going.
- **Reason:** without db-019 nothing would restart a stopped loop, and a loop stopped by a full disk
  would let the WAL grow without limit once the user frees space.

## 10. On-demand checkpoint mode

- **Question:** db-v2-01 leaves the mode of `POST /data/checkpoint` as RESTART or FULL.
- **Decision:** RESTART, after waiting up to 10 s for the write coordinator; the response keeps
  `busy/log/checkpointed`, and the engine logs `on-demand wal checkpoint (RESTART): ...`.
  `repair_database` (no callers) moved from TRUNCATE to FULL.
- **Reason:** RESTART guarantees every frame is in the main file, like the old TRUNCATE, and also
  lets the next writer start the log from the beginning.

## 11. Planner statistics: schedule and table selection

- **Question:** the schedule is inferred ("once per maintenance tick"), and `PRAGMA
  main.optimize=0x10003` has the 0x1 bit set, which makes `optimize` report instead of act.
- **Decision:** the first run is 10 minutes after start-up and later runs every 6 hours; a run that
  found the writer busy or was interrupted is retried after 10 minutes
  (`SCREENPIPE_PLANNER_MAINTENANCE_INTERVAL_SECS` sets all three). The report-only `optimize` output is
  read as the `selecting_tables` stage; indexed tables without statistics are added, and empty tables
  that have no statistics are skipped. Each table gets `ANALYZE` with `analysis_limit = 1000` under the
  write coordinator, on a writer with `busy_timeout = 0` (restored to 5 s afterwards, or the connection
  is closed). The schema cookie is bumped only when something was analyzed. A degraded write queue
  skips the run.
- **Reason:** reading 0x10003 as a selection matches the `selecting_tables` stage and keeps SQLite's
  own heuristic; per-table locking keeps each pause in recording to one bounded ANALYZE.

## 12. Planner report field shapes

- **Question:** the report names `analyzed_tables` and `sqlite_code` without types, and the status and
  stage values are not recorded.
- **Decision:** `analyzed_tables` is a list of table names, `sqlite_code` the SQLite extended result
  code as an integer (or null), `started_at` RFC 3339 UTC. Status values: `running` (written when an
  attempt starts), `succeeded`, `busy`, `interrupted`, `shutdown`, `failed`. Stages:
  `selecting_tables`, `analyzing`, `refreshing_planner`, `done`. A report file in another shape is read
  as empty and replaced.
- **Reason:** a list is more useful than a count for diagnosis, and tolerant reading keeps a file
  written by screenpipe from blocking the job.

## 13. `optimize_on_close`

- **Question:** db-017 infers that pooled connections enable sqlx's optimize-on-close.
- **Decision:** not enabled.
- **Reason:** readers are `query_only`, so `PRAGMA optimize` would fail on every close, and on writers
  it would take the write lock at shutdown and whenever the pool retires a connection. The scheduled
  maintenance covers the same need.

## 14. What moved off the read pool

- **Question:** with `query_only=ON`, every write that used `DatabaseManager::pool` fails.
- **Decision:** writes inside `db.rs` (chunk outcomes, speaker updates, frame and chunk flags,
  `backup_to`'s `VACUUM INTO`, migrations and their repair helpers) use the write pool. Outside the
  crate, `DatabaseManager::write_pool()` serves the secrets store, the text and image redaction
  workers and retention's `PRAGMA incremental_vacuum`, and tests seed fixtures through it.
  `execute_raw_sql` stays a read API on the read pool, so `POST /raw_sql` is now read-only at the
  database level as well as in its own validation.
- **Reason:** the read pool's guarantee only holds if nothing writes through it; the accessor keeps
  direct writers explicit.

## 15. Which reads are cancellable

- **Question:** db-018 names search, timeline and activity reads.
- **Decision:** `search_ocr`, `find_video_chunks` and `execute_raw_sql` (which also serves the activity
  summary and pipes' raw SQL) run on `CancellableConnection`. Other reads can adopt it through
  `DatabaseManager::cancellable_read()`. Every read-pool connection also rolls back a transaction left
  open when it is released.
- **Reason:** these are the reads that can run for seconds or longer; the search functions belong to
  W3-02, which can move the rest when it rewrites them.

## 16. Health reporting

- **Question:** the coordinator asked for WAL problems to surface through health.
- **Decision:** `/health` is unchanged; `DatabaseManager::wal_maintenance_status()` returns the loop's
  state (backlog pages and age, WAL file size, escalations, failures, stop reason) for a later health
  WP, and the loop logs deferrals, escalations and failures.
- **Reason:** `/health`'s top-level fields and their order match the shipped build (W2-13's tests pin
  them), so new fields there need their own interop decision.
