# Freenpipe clean-room documentation

Freenpipe is an MIT-licensed fork of screenpipe. It starts from upstream commit `892199f`, the last
commit released under the MIT licence (about v2.5.27, with the `ee/` directory removed). The goal is
feature parity with screenpipe v2.7.104, reached through clean-room work. This directory holds the
specifications, the implementation plan and the owner decisions behind that work.

## Method

- **Evidence comes from the shipped product only.** The installed screenpipe v2.7.104 Windows build was
  examined statically with the REA reverse-engineering toolkit: its string table, embedded SQL and
  migrations, the bundled frontend and REA evidence records. The binary was never run.
- **No post-relicense source was consulted.** The only screenpipe source anyone read is the MIT base.
- **Behaviour is paraphrased; interop identifiers are exact.** The specs describe what the target does in
  our own words. Anything a compatible implementation must reproduce byte for byte stays verbatim:
  HTTP routes, JSON fields, SQL schema, CLI flags, environment variables, settings keys, event names,
  file names, error codes and numeric constants. A short error message that clients match on is kept
  in backticks and marked "(exact string, client-visible)". UI copy, prompts and code bodies are never
  copied.
- **Raw extracted material is never published.** String dumps, the extracted frontend and REA graph
  dumps stay in a private workspace. Evidence references in the specs (hex offsets such as `0x5a42a38`,
  REA ids such as `ev_…`, frontend chunk positions) point into that workspace. Path placeholders:
  `<re-workspace>` is the private analysis workspace, `<repo>` is a Freenpipe checkout and
  `<screenpipe-install>` is the installed target.
- **Publication is gated by an n-gram check.** Every document is compared against the extracted corpus,
  and no run of 8 or more ordinary words may appear in both. The few matches that remain are SQL
  statements, DDL, trigger error strings and identifier lists, each reviewed and kept as interop
  identifiers.

## How the documents fit together

1. **Subsystem specs** (`specs/`). Each spec covers one dimension of the product. It inventories the base
   against the target, lists numbered delta items (for example `audio-012` or `cloud-004`), records open
   questions, and ends with one or more independent verification passes.
2. **`PLAN.md`** groups the 412 live delta items into 154 work packages across waves 0 to 8. Each work
   package lists its dependencies, the files it owns and its acceptance checks. Section 10 maps every
   delta item id to its work package.
3. **`DECISIONS.md`** records the owner's answers to the plan's open questions and adds work packages
   WR-01 to WR-04. Where it conflicts with `PLAN.md`, `DECISIONS.md` wins.

`PLAN.md` is a snapshot generated by a script from internal planning data that is not published. The
regeneration notes in its last section refer to that private tooling, and a regeneration overwrites
any hand edits to the file.

## Index

| File | Contents |
|---|---|
| `DECISIONS.md` | Owner decisions that bind every work package and override `PLAN.md` |
| `PLAN.md` | Implementation plan: ground rules, acceptance harness, waves, 154 work packages, item index, risks |

| `specs/db.md` | Database schema, migrations, storage layout and hybrid Parquet storage |

| `specs/audio.md` | Audio capture, transcription and speaker identification |
| `specs/meetings_memory.md` | Meetings, memories, activity ledger, semantic layer, outputs and notifications |
| `specs/agents_pipes.md` | Pipes, AI agents, chat, MCP and LLM providers |
| `specs/connections.md` | Integrations, secrets store, browser automation and wearables |
| `specs/frontend.md` | Desktop UI: pages, settings, windows, Tauri commands and events |
| `specs/shell.md` | Tauri shell, configuration, CLI, environment variables and Windows specifics |
| `specs/cloud.md` | Vendor cloud services, telemetry and licence gates, with their local replacements |
| `specs/gap_retention-v2-engine.md` | Retention v2: lean mode, heavy-text stripping and hybrid-aware deletion |

The `gap_` specs are follow-up passes over areas the main dimension specs did not fully cover.
