# Owner decisions (binding for every work package)

Recorded 2026-10-15. These override PLAN.md wherever they conflict, and they settle PLAN.md's open questions.

## Asked and answered by the owner
1. **Drop-in compatible defaults.** Data dir stays `~/.screenpipe`, the API port stays 3030, the control server stays :11435, and the CLI binary stays named `screenpipe`. Existing pipes, skills and MCP configs must work unchanged. Handvel will not run alongside the installed screenpipe, and that is accepted. **During development, the dev-isolation rules in PLAN.md section 4 still apply** (FP_DD, port 3035, SCREENPIPE_API_KEY), because screenpipe is installed on this machine.
2. **Vendor git deps into the repo.** Every git dependency hosted under the vendor's orgs or contributors (screenpipe/whisper-rs, screenpipe/rusty-tesseract, divanshu-go/audiopipe, tauri-helper and any others found) is copied at its pinned revision into `third_party/<name>/` and consumed as a path dependency, after a licence check. Record each one's licence and source revision in `third_party/README.md`. Do not vendor anything whose pinned revision is dated after 2026-06-10 from the screenpipe org itself. (WP W0-13.)
3. **Updater wired, off by default.** The updater targets GitHub Releases of normiecore/Freenpipe and is disabled by default. The manual update-check action opens the releases page. No signing keys are generated. Keep the code path ready for a pubkey to be added later.
4. **Push to main per green wave.** The coordinator pushes; implementers never push. The owner says github.com/normiecore/Freenpipe is where everything should end up, so our own specs, PLAN.md, DECISIONS.md and dev tooling are published under docs/clean-room/ after a scrub pass. Raw extracted target material (app_strings.tsv, frontend/, REA graph dumps) is NEVER published.
5. **Fully featured: vendor-server features are restored with self-hostable or BYO replacements** (2026-10-15). Billing, paywall, trial, quota, referral, upsell, announcement and remote-control code stays removed; it gates nothing useful. Four features come back as new WPs: WR-01 pipe store on a GitHub-hosted registry in this repo; WR-02 sync and archive to BYO storage (S3/WebDAV/folder, client-side encrypted); WR-03 Handvel Hub, a self-hostable team server plus the restored team client; WR-04 Composio with a BYO key, plus workflow sharing via bundles and a GitHub gallery. Wave-0 removals of vendor wiring stand. The WR packages restore the client code from MIT base history and rewire it.
6. **Core set first, lean process** (2026-10-20). Only these 32 work packages are scheduled; every other WP is parked (not cancelled) until the owner widens the set after using the app. Core set: W1-01, W1-02, W1-03, W1-04; W2-01, W2-04, W2-05, W2-08, W2-09, W2-10, W2-11, W2-12, W2-13, W2-16, W2-17, W2-18, W2-19, W2-22, W2-23, W2-26, W2-27; W3-02, W3-06, W3-08, W3-11, W3-12, W3-13, W3-14, W3-25, W3-30; W4-02, W4-05; plus W1-05 (decision 7). They cover data compatibility with screenpipe v2.7.104, Windows capture and audio reliability, the agent runtime and pipes, meetings and audio, and search (about 19% of the remaining planned effort). Process: one combined reviewer per WP reading the diff with CI as the build gate (`wp-batch.js` `lean: true`), at most one fix round, no resolution review for a merge of main that has no code conflict, and per-WP files for spec decisions (`docs/clean-room/open-questions/<WP>.md`) and Windows smoke checks (`docs/dev/smoke/<WP>.md`).
7. **Commercial-ready builds** (2026-10-20). Every build the project ships must be usable commercially. Default builds and every `release-app.yml` feature set contain only components under permissive or weak-copyleft licences (MIT, Apache-2.0, BSD, ISC, Zlib, MPL-2.0, LGPL as a separate or dynamically linked component, CC BY for model weights with attribution). opf-rs (CC BY-NC 4.0) and tinfoil (AGPL-3.0) stay in the repository but only behind opt-in Cargo features (W1-05, added to the core set), and CI enforces this. Model weights that download at runtime need a known licence that allows commercial use before they can be a default; the PII models on screenpipe's Hugging Face account (licence unknown) and the bundled ffmpeg build are checked in a release licence audit before the first release.
8. **Evidence freeze, compatibility goal, public sourcing** (2026-10-29). This overrides PLAN.md, the earlier decisions and every other document where they conflict, including the older rule that delta features come only from REA evidence.
   - **Freeze.** Nobody analyses a screenpipe binary, installer or bundled frontend again, and the installed screenpipe is not run or updated for project work. The private analysis workspace is kept exactly as it is: not extended, not published, not deleted.
   - **Compatibility, not parity.** The goal is that Handvel reads and writes screenpipe's data, serves its API, and runs its pipes, skills and MCP configurations. Behaviour beyond that is Handvel's own design. Work packages that only mirror v2.7.104 (its UI copy, layouts or flows) are reframed or dropped when the owner widens the set.
   - **Sourcing.** The pre-freeze specs moved, unchanged, to `legacy-specs/`. `specs/` holds only re-sourced text written under [SOURCING.md](SOURCING.md): interoperability identifiers redacted from the legacy specs, and behaviour from public sources, the MIT base or Handvel's own design. Work is gated item by item: a work package is scheduled once every item it lists is in `specs/` with a source tag.
   - **Separation.** Redactor, behaviour author and implementer are different people or sessions for any item. Implementers read only `specs/` and never `legacy-specs/` or the analysis workspace. Reviewers check this against the provenance records. `.claude/settings.json` deny rules are a convenience for Claude Code sessions, not the control: the owner keeps the workspace locked down at the operating-system level.
   - **Provenance.** Every work package started from now on carries a provenance record in [provenance/](provenance/README.md). `scripts/ci/clean-room-guard.test.ts` checks the record exists and is filled in, and keeps evidence pointers out of everything but `legacy-specs/`. W4-02 and W4-05, opened before this decision, are grandfathered.
   - **Freeze record.** The freeze takes effect with the commit that adds this decision. The owner tags that commit and keeps an off-repo hash manifest of the preserved workspace.
   - **Maintenance.** Merged code may be fixed or refactored from the code itself and its `interop` items. New behaviour needs re-sourced items.
9. **Product renamed to Handvel** (2026-10-29). "Freenpipe" was too close to "screenpipe". The product name, bundle identifiers (`com.normiecore.handvel`, `.dev`, `.beta`), deep-link schemes (`handvel://`, `handvel-beta://`, with the `screenpipe://` alias kept), installer and executable names, file headers and docs now say Handvel. Kept on purpose, because changing them would break existing data, builds or the clean-room gate: settings and storage keys (`freenpipe…`), code identifiers (`FreenpipeLink`, `apply_freenpipe_ai_migrations`), `FREENPIPE_*` environment variables, the dev data directory `freenpipe-dev`, `~/.freenpipe-env.sh`, `~/.cache/freenpipe`, the `freenpipe-ci.yml` workflow, asset file names, the verbatim-gate key, and SQL migration files (their checksums are recorded in existing databases). The GitHub repository is still `normiecore/Freenpipe` until the owner renames it.
